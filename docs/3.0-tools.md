# Tools

Every script and binary that acts on the application, grouped by what it is
for, each linking to the document that explains it. The programme's tooling,
and the rule that tells the two kinds apart, are
[5.0](5.0-programme-tooling.md). What they touch (environment
variables, volumes, ports) is [4.1](4.1-configuration.md).

### Deliver

Getting a commit to every environment, and the gates on the way: preview, rehearsal and production together.

| Tool | Purpose | Explained in |
|---|---|---|
| `scripts/deploy-preview.sh` | Build and run the preview stack locally: `up`/`down`/`reset`/`at <ref>`/`at prod`/`verify`. Reports failing document checks at the end — a check, not a gate | [Testing, CI & Release](3.3-testing-ci-and-release.md#13-deploy-to-the-preview-environment) |
| `scripts/deploy-rehearsal.sh` | `deploy.sh` pointed at the rehearsal host: same script, same image, same steps, against a machine built to match production. Also `reset` — empty the database and restart, so a testing phase starts from nothing and any seeded production data is gone | [Testing, CI & Release](3.3-testing-ci-and-release.md#15-rehearse-the-release-and-run-the-technical-tests) |
| `scripts/deploy.sh` | `DEPLOY_GATES_ONLY=1` to ask whether a deploy would be allowed, without building anything. Otherwise: build images locally from a fresh checkout of a commit (`HEAD`, or any ref — that's also how you roll back) and ship them to the production VM | [How `deploy.sh` ships an image](3.3-testing-ci-and-release.md#25-how-deploysh-ships-an-image) · [Rolling back](3.3-testing-ci-and-release.md#111-roll-back-production) · **Exits `3`** when production is live and a step after the swap failed, naming each and what it needs — see [4.8](4.8-artefacts.md#what-a-scripts-exit-status-means) for what a status means |
| `scripts/rollback.sh` | Put production back to the previous images *and* the database snapshot taken with them — `deploy.sh` calls it automatically when a deploy fails, and it is the **first thing to reach for** when production is broken | [Rolling back across a migration](3.3-testing-ci-and-release.md#112-roll-back-across-a-migration) |
| `scripts/rollback-rehearsal.sh` | `rollback.sh` pointed at rehearsal, so the rollback path is rehearsed on a host you can afford to break | [Testing, CI & Release](3.3-testing-ci-and-release.md#111-roll-back-production) |
| `scripts/seed-rehearsal.sh` | Copies production's database to rehearsal, so a migration is rehearsed against real rows rather than an empty volume | [Testing, CI & Release](3.3-testing-ci-and-release.md#15-rehearse-the-release-and-run-the-technical-tests) |
| `scripts/rehearsal-access.sh` | Lets one device into rehearsal, and takes every device out. `grant` prints the unlock URL as a QR code to scan; `revoke` rotates the secret; `status` says whether the key on the host is the one the container is running. Needs `qrencode` for the code, and prints the URL without it | [Production Environment](3.4-production-environment.md) |
| `scripts/rehearsal-limits.sh` | Switches rehearsal between production's rate limits and ones a regression suite can survive (`show`/`regression`/`production`). Registration is 2 a minute with a burst of 3 and the suite registers an account per test, so under production's numbers **21 of 31 fail at the limiter**. A switch rather than a permanent relaxation, because `check-rate-limits.sh` exists to prove production's numbers hold there — relaxed, it would pass and mean nothing | [4.1](4.1-configuration.md) · #371 |
| `scripts/rehearsal-key.sh` | The rehearsal access key, from `REHEARSAL_ACCESS_KEY` or over ssh from the host's `.env`. Rehearsal is closed by the Caddyfile (#240) and answers 403 to everything but `/health`, so any tool that must reach it lets itself in with `Cookie: rehearsal=<key>`. **One place knows how** — `check-rate-limits.sh` learned it and the Rust example did not, which is #371, and a second copy is how that happens twice | [3.3](3.3-testing-ci-and-release.md) · #371 |
| `scripts/rehearsal-target.sh` | Where rehearsal lives — host, key and URL, defined once. Sourced, not run | [Production Environment & Operations](3.4-production-environment.md) |
| `scripts/ssh-preflight.sh` | Proves the deploy key works before anything expensive starts. Sourced by `deploy.sh` and `rollback.sh`, not run | [Testing, CI & Release](3.3-testing-ci-and-release.md#16-ship-it) |
| `scripts/run-log.sh` | **#328.** Sourced, not run: a machine-readable record of a script run that outlives the terminal, at `${XDG_STATE_HOME:-~/.local/state}/tile-lite-elite/`. Outside the repository so two worktrees do not produce two answers; one file per run, pruned to the last 20 per script. Adds a channel and changes nothing printed. A caller with its own EXIT trap must chain it, capturing `$?` first | [4.7](4.7-log-events.md) · #328 |
| `scripts/verify.sh` | Asserts the whole world is as it should be and exits non-zero if not, where `board-status.py` only shows it. Run after every deploy, trusting the exit status rather than the output | [Testing, CI & Release](3.3-testing-ci-and-release.md#17-verify-what-is-live) |

| Tool | Purpose | Explained in |
|---|---|---|
| `scripts/check-hosts.sh` | Reads kernel, Docker version and pending-reboot from rehearsal and production and reports where they differ — **#360 R3**, the two having drifted for weeks on facts that take a second to read. Also answers R2: a kernel installed and not running is not a fix. Read-only; rebooting a host is the owner's call | [3.4](3.4-production-environment.md) · #360 |
| `scripts/restore-backup.sh` | Restore from the offsite backups — **never runs on the production VM**, which holds a write-only credential by design. | `scripts/backup-to-oci.sh` | The nightly offsite backup: `VACUUM INTO` for a consistent copy with the server still running, `PRAGMA integrity_check` before trusting it, gzip, then upload through a **write-only** pre-authenticated request the VM cannot read back. | `scripts/check-log-hygiene.py` | Validates a stream of JSON log lines against the schema `docs/4.7` declares: no address in any field, no field the document does not declare, and no debug-only event in a production stream. **Reads; never drives** — CI feeds it the regression suite's captured output, and the nightly check on the host feeds it the day's journal | [The Change Lifecycle](5.1-change-lifecycle.md#213-the-impacted-artefacts-and-why-they-are-listed-early) |

## Examples

**`crates/*/examples/` is not registered**, and that is deliberate rather than
a backlog. An example demonstrates, measures or reproduces; it is not something
you are expected to find here and run. Three of them write a results CSV that is
committed, which is fine — what an example must never do is produce something
compiled into the binary. That is the line, and it is the same line
`.githooks/pre-commit` draws when it excludes `examples/` from the rule that an
image change takes a branch: anything generating a file the binary
`include_str!`s is a crate, not an example (see `crates/wordlist-tools`, #306).

An example gets a row here only when a document sends you to it, as the two
benchmarks do. That is a choice, not an obligation.
