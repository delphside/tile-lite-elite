# Authentication and invitation examples

Runnable `curl` calls for the account and invitation flows.

The calls come in the order a client makes them. They show the request bodies
and the values that pass from one call to the next. The rest is elsewhere:

- each call's fields, responses and refusals: [4.4.3](4.4.3-api-schema.md)
- the rules for accounts: [4.2.5](4.2.5-authentication.md)
- the rules for seats and invitations:
  [4.2.7](4.2.7-authentication-and-invitations.md)

## Before you start

1. To read the emails, join link included, in the server log
   (`.logs/server.log`), set `TILE_LITE_ELITE_LOG_EMAIL_BODIES` before the
   server starts ([4.4.1](4.4.1-configuration.md#environment-variables)).
   `./scripts/develop/services.sh` passes your shell's environment to the
   server, so an exported `RESEND_API_KEY` sends real email.

   ```bash
   export TILE_LITE_ELITE_LOG_EMAIL_BODIES=1
   ```

2. Start the server from the repository root. It listens on
   `http://127.0.0.1:3000` and runs with raised rate limits
   ([4.4.1](4.4.1-configuration.md#rate-limits)).

   ```bash
   ./scripts/develop/services.sh start
   ```

   A running server keeps the settings it started with. If one is already
   running, restart it instead:

   ```bash
   ./scripts/develop/services.sh restart-server
   ```

Conventions on this page:

- every call except registering and signing in sends
  `Authorization: Bearer <session_token>`; a call that needs a session
  answers `401` without a valid one;
- IDs and tokens are placeholders for the UUIDs the server generates;
- responses show the fields the next step uses;
- timestamps are Unix seconds.

## Alice invites Bob by name

### Alice registers

`stay_logged_in` is required, and leaves expiry as it is
([4.2.5](4.2.5-authentication.md#how-long-a-session-lasts)).

```bash
curl -X POST http://127.0.0.1:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "display_name": "Alice",
    "email": "alice@example.com",
    "password": "alice-secret-phrase-123",
    "stay_logged_in": false
  }'
```

```json
{
  "player_id": "<alice_player_id>",
  "session_token": "<alice_token>",
  "display_name": "Alice",
  "email": "alice@example.com"
}
```

### Bob registers

The same call with Bob's details returns his `player_id` and `session_token`.
Later calls write them `<bob_player_id>` and `<bob_token>`.

### Alice creates a game and names Bob

In this request:

- every human seat carries a `claim`: `creator` takes Alice's own seat, and
  `named` reserves seat 1 for Bob;
- `seed`, `variant` and `move_time_limit_seconds` default when `null`;
  `language` and `board_layout` are ignored.

```bash
curl -X POST http://127.0.0.1:3000/games \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{
    "seats": [
      { "kind": "human", "display_name": "Alice", "engine_id": null,
        "claim": { "type": "creator" } },
      { "kind": "human", "display_name": "Bob", "engine_id": null,
        "claim": { "type": "named", "display_name": "Bob" } }
    ],
    "seed": null,
    "variant": null,
    "language": null,
    "board_layout": null,
    "move_time_limit_seconds": null
  }'
```

The response is a `GameStateDto`; this excerpt keeps the fields used later.
Bob's invitation exists as soon as the game does, and is emailed to him in the
same request.

```json
{
  "id": "<game_id>",
  "status": "waiting",
  "creator_player_id": "<alice_player_id>",
  "participants": [
    { "seat_number": 0, "display_name": "Alice",
      "player_id": "<alice_player_id>", "invitation_status": null },
    { "seat_number": 1, "display_name": "Bob",
      "player_id": null, "invitation_status": "pending" }
  ]
}
```

### Bob lists his invitations

The path names the caller's own ID; any other ID answers `403`. Unless the
inviter's account has been deleted, the list holds:

- every `named` invitation addressed to Bob, whatever its status;
- every `open` or `email` invitation he has accepted.

```bash
curl http://127.0.0.1:3000/players/<bob_player_id>/invitations \
  -H "Authorization: Bearer <bob_token>"
```

```json
[
  {
    "id": "<invitation_id>",
    "game_id": "<game_id>",
    "invited_player_id": "<bob_player_id>",
    "inviting_player_id": "<alice_player_id>",
    "seat_number": 1,
    "status": "pending",
    "created_at": 1760000000,
    "responded_at": null,
    "inviting_player_display_name": "Alice"
  }
]
```

### Bob accepts

The response is the updated game: seat 1's `player_id` is Bob's.

```bash
curl -X POST http://127.0.0.1:3000/invitations/<invitation_id>/accept \
  -H "Authorization: Bearer <bob_token>"
```

### Alice starts the game

The rules for starting are in
[4.2.7](4.2.7-authentication-and-invitations.md#managing-the-roster).

```bash
curl -X POST http://127.0.0.1:3000/games/<game_id>/start \
  -H "Authorization: Bearer <alice_token>" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Alice invites a guest by email

An `email` claim needs no existing account. The server mails a join link,
`/invite?id=<carol_invitation_id>` on the web client's address, which the guest
opens to register or sign in and confirm
([4.2.7](4.2.7-authentication-and-invitations.md#joining-by-email)).

```bash
curl -X POST http://127.0.0.1:3000/games \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{
    "seats": [
      { "kind": "human", "display_name": "Alice", "engine_id": null,
        "claim": { "type": "creator" } },
      { "kind": "human", "display_name": "Carol", "engine_id": null,
        "claim": { "type": "email", "email": "carol@example.com" } }
    ],
    "seed": null,
    "variant": null,
    "language": null,
    "board_layout": null,
    "move_time_limit_seconds": null
  }'
```

The create response's `id` is `<carol_game_id>`.

A seat added with `POST /games/<carol_game_id>/seats` sends no invitation, so
Alice adds seat 2, then invites it with `POST /games/<carol_game_id>/invite`.
The request holds one of:

- `invited_display_name`, for a named player;
- `invited_email`, for an address;
- neither, for an open seat.

```bash
curl -X POST http://127.0.0.1:3000/games/<carol_game_id>/seats \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{ "kind": "human", "display_name": "Dave", "engine_id": null,
        "claim": { "type": "email", "email": "dave@example.com" } }'

curl -X POST http://127.0.0.1:3000/games/<carol_game_id>/invite \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{ "seat_number": 2, "invited_email": "dave@example.com" }'
```

## Alice signs in on a new device

Signing in returns a new token for the same `player_id`.

```bash
curl -X POST http://127.0.0.1:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "display_name": "Alice",
    "password": "alice-secret-phrase-123",
    "stay_logged_in": true
  }'
```

The response has the shape of registration's.

## Bob rejects an invitation

Alice repeats the first create call, naming Bob in a new game; Bob's
invitation list then holds a second pending invitation,
`<second_invitation_id>`.

Rejecting `<invitation_id>`, which Bob has accepted, answers `400`: it is
already answered
([4.4.3](4.4.3-api-schema.md#what-each-invitations-call-refuses-and-why)).
Rejecting the new one succeeds:

```bash
curl -X POST http://127.0.0.1:3000/invitations/<second_invitation_id>/reject \
  -H "Authorization: Bearer <bob_token>"
```

```json
{ "status": "rejected" }
```
