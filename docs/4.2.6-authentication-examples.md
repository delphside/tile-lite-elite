# Authentication and invitation examples

Runnable `curl` calls for the account and invitation flows.

The calls come in the order a client makes them.
[4.4.3](4.4.3-api-schema.md) lists each call's fields, responses and
refusals; these examples add the request bodies and the values that pass from
one call to the next. The rules behind them are in
[4.2.5](4.2.5-authentication.md) (accounts) and
[4.2.7](4.2.7-authentication-and-invitations.md) (seats and invitations).

## Before you start

1. Start the server from the repository root. It listens on
   `http://127.0.0.1:3000` and runs with raised rate limits
   ([4.4.1](4.4.1-configuration.md#rate-limits)).

   ```bash
   ./scripts/develop/services.sh start
   ```

2. Send `Authorization: Bearer <session_token>` on every call on this page
   except registering and signing in. Without it, or with an expired or unknown token,
   a call that needs a session answers `401`.

Responses show the fields the next step uses; IDs and tokens are placeholders
for the UUIDs the server generates. Timestamps are Unix seconds.

## Alice invites Bob by name

### Alice registers

`stay_logged_in` is required; it does not change expiry
([4.2.5](4.2.5-authentication.md#how-long-a-session-lasts)).

```bash
curl -X POST http://127.0.0.1:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "display_name": "Alice",
    "email": "alice@example.com",
    "password": "alice-secret-phrase-123",
    "stay_logged_in": false
  }'
```

```json
{
  "player_id": "<alice_player_id>",
  "session_token": "<alice_token>",
  "display_name": "Alice",
  "email": "alice@example.com"
}
```

### Bob registers

The same call with Bob's details returns his `player_id` and `session_token`.
Later calls write them `<bob_player_id>` and `<bob_token>`.

### Alice creates a game and names Bob

Every human seat carries a `claim`; the `creator` claim takes Alice's own seat
and `named` reserves seat 1 for Bob. A name that matches no player fails the
whole request with `404`, before anything is created. `seed`, `variant` and
`move_time_limit_seconds` default when `null`; `language` and `board_layout`
are not read.

```bash
curl -X POST http://127.0.0.1:3000/games \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{
    "seats": [
      { "kind": "human", "display_name": "Alice", "engine_id": null,
        "claim": { "type": "creator" } },
      { "kind": "human", "display_name": "Bob", "engine_id": null,
        "claim": { "type": "named", "display_name": "Bob" } }
    ],
    "seed": null,
    "variant": null,
    "language": null,
    "board_layout": null,
    "move_time_limit_seconds": null
  }'
```

The response is a `GameStateDto`; this excerpt keeps the fields used later.
Bob's invitation exists as soon as the game does, and is emailed to him in the
same request.

```json
{
  "id": "<game_id>",
  "status": "waiting",
  "creator_player_id": "<alice_player_id>",
  "participants": [
    { "seat_number": 0, "display_name": "Alice",
      "player_id": "<alice_player_id>", "invitation_status": null },
    { "seat_number": 1, "display_name": "Bob",
      "player_id": null, "invitation_status": "pending" }
  ]
}
```

### Bob lists his invitations

The path names the caller's own id; any other id answers `403`. The list holds
every invitation addressed to Bob, whatever its status: `named` ones, and open
or email ones he has accepted. An invitation whose inviter's account no longer
exists is left out.

```bash
curl http://127.0.0.1:3000/players/<bob_player_id>/invitations \
  -H "Authorization: Bearer <bob_token>"
```

```json
[
  {
    "id": "<invitation_id>",
    "game_id": "<game_id>",
    "invited_player_id": "<bob_player_id>",
    "inviting_player_id": "<alice_player_id>",
    "seat_number": 1,
    "status": "pending",
    "created_at": 1760000000,
    "responded_at": null,
    "inviting_player_display_name": "Alice"
  }
]
```

### Bob accepts

The response is the updated game: seat 1's `player_id` is Bob's.

```bash
curl -X POST http://127.0.0.1:3000/invitations/<invitation_id>/accept \
  -H "Authorization: Bearer <bob_token>"
```

### Alice starts the game

The rules for starting are in
[4.2.7](4.2.7-authentication-and-invitations.md#managing-the-roster).

```bash
curl -X POST http://127.0.0.1:3000/games/<game_id>/start \
  -H "Authorization: Bearer <alice_token>" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Alice invites a guest by email

An `email` claim needs no existing account. The server mails a join link,
`/invite?id=<invitation_id>` on the web client's address, which the guest opens
to register or sign in and confirm
([4.2.7](4.2.7-authentication-and-invitations.md#joining-by-email)).

```bash
curl -X POST http://127.0.0.1:3000/games \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{
    "seats": [
      { "kind": "human", "display_name": "Alice", "engine_id": null,
        "claim": { "type": "creator" } },
      { "kind": "human", "display_name": "Carol", "engine_id": null,
        "claim": { "type": "email", "email": "carol@example.com" } }
    ],
    "seed": null,
    "variant": null,
    "language": null,
    "board_layout": null,
    "move_time_limit_seconds": null
  }'
```

A seat with no pending invitation (added later, or declined) is invited with
`POST /games/<game_id>/invite`: `invited_display_name` for a named player,
`invited_email` for an address, neither for an open seat, never both.

```bash
curl -X POST http://127.0.0.1:3000/games/<game_id>/invite \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <alice_token>" \
  -d '{ "seat_number": 1, "invited_email": "carol@example.com" }'
```

## Alice signs in on a new device

Signing in returns a new token for the same `player_id`.

```bash
curl -X POST http://127.0.0.1:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "display_name": "Alice",
    "password": "alice-secret-phrase-123",
    "stay_logged_in": true
  }'
```

The response has the shape of registration's. A wrong name or password answers
`400` with the same message for both.

## Bob rejects an invitation

Only a pending `named` invitation addressed to the caller can be rejected.
Alice names Bob in a second game with the first create call, which gives him a
second pending invitation, `<second_invitation_id>`.

| Refusal | When |
| --- | --- |
| `404` | the caller has no invitation by that id: it is open, an email one not yet accepted, or not his |
| `400` | the invitation has already been answered, as `<invitation_id>` has |

```bash
curl -X POST http://127.0.0.1:3000/invitations/<second_invitation_id>/reject \
  -H "Authorization: Bearer <bob_token>"
```

```json
{ "status": "rejected" }
```
