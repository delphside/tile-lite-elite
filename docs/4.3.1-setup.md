# Setup

Setting up a development machine, once. Building the production host is in
[4.3.4](4.3.4-production-environment.md#building-a-host); every script is in
[4.3.0 Tools](4.3.0-tools.md).

## Development environment

The dev machine (WSL2 Ubuntu, treated as disposable) needs a Rust toolchain,
the `wasm32-unknown-unknown` target, `dioxus-cli` and `wasm-bindgen-cli` at the
versions this project uses (a mismatch fails confusingly, see
[Troubleshooting](#troubleshooting)), `sccache`, bats with its two helper
libraries, and Docker Engine with its build cache capped at 20 GB. Under WSL
Docker sizes its limit from the virtual disk rather than the Windows drive, and
without a fixed cap it kept 305 GB.

```bash
git clone https://github.com/delphside/tile-lite-elite.git
git clone https://github.com/delphside/programme.git
cd tile-lite-elite
./scripts/develop/setup-dev-environment.sh
```

The second clone is the programme repository's **live checkout**, beside this
one at `../programme` (or wherever `PROGRAMME_DIR` points). It holds the
records the scripts read and write: the activity log, the weekly digests, the
delivery log, the capacity plan and the change documents. A script that needs
it and cannot find it stops and says where it looked. The setup script also
runs `git submodule update --init`, which fetches `programme/` inside this
repository: the pinned copy of the generic documents, rules, skills and agents,
which `.claude/skills` and `.claude/agents` link into. After a `git pull` that
moves the pin, run `git submodule update --init` again.

The script is idempotent, and reads the `wasm-bindgen-cli` version from
`Cargo.lock` rather than hardcoding it. It refuses to run as root; it calls
`sudo` itself for the steps that need it.

**Two steps are manual:**

1. **Restore the deploy SSH key**, `~/.ssh/oracle_tile_lite_elite` and its
   `.pub`, from the copy kept on the Windows side outside WSL. It is a secret,
   so no script fetches it.
2. **Enable systemd in WSL** on a fresh instance, which Docker needs. It is a
   Windows-side change the distro cannot make to itself:

   ```ini
   # /etc/wsl.conf
   [boot]
   systemd=true
   ```

   then `wsl --shutdown` from PowerShell, and reopen the shell. The setup
   script warns if it is missing.

**Verify the result**:

```bash
cargo test --workspace
dx --version                 # should include 0.6.3
docker compose version
bats --version
ssh -i ~/.ssh/oracle_tile_lite_elite ubuntu@129.151.69.246 echo ok
```

## Cloud sessions

A Claude Code session on the web starts in a fresh VM that already has Rust,
Node 22, Docker and a Chromium for Playwright. The rest comes from
[`.claude/cloud-setup.sh`](../.claude/cloud-setup.sh), a SessionStart hook that
runs only where `CLAUDE_CODE_REMOTE` is `true`: the pinned toolchain and wasm
target, `dx` and `wasm-bindgen` at the versions `Cargo.lock` pins (prebuilt,
not compiled), bats, sqlite3 and `e2e/node_modules`. It takes about 20 seconds in a new
VM and under one in a resumed one. It also empties `RUSTC_WRAPPER`, because
`.cargo/config.toml` names this machine's sccache, and points Playwright at the
VM's Chromium through `PLAYWRIGHT_CHROMIUM_EXECUTABLE`, because the cloud
network refuses Playwright's own browser download. It initialises the
`programme/` submodule and switches on the git hooks (`.githooks`, the shim in front of the programme's), as the setup script does locally; the live checkout beside the repository is already
there in a cloud session, so it does not clone it. A cloud session cannot push
to `main`, so a commit there touching a programme document is refused by
`pre-commit`; when the branch is the change to the programme, commit with
`--no-verify` and say so in the message.

The hook is not cached and runs at every start. The environment's **setup
script**, set at claude.ai/code under the environment's settings, is: the VM is
snapshotted after it and reused for about seven days. So what is slow and rarely
needed goes there instead. The desktop client's libraries are the one case:

```bash
apt-get update -qq && apt-get install -y -qq --no-install-recommends \
    libwebkit2gtk-4.1-dev libgtk-3-dev libxdo-dev
```

## Troubleshooting

### sccache hangs the WASM build

sccache (configured in `.cargo/config.toml`) is incompatible with the `wasm32-unknown-unknown` target. Always set `RUSTC_WRAPPER=""` when building web targets. `scripts/develop/services.sh` handles this automatically.

### wasm-bindgen version mismatch

The `wasm-bindgen-cli` version must exactly match the `wasm-bindgen` crate version in `Cargo.lock`. Check with:

```bash
grep -A1 'name = "wasm-bindgen"' Cargo.lock | grep version
```

Then install the matching CLI version:

```bash
cargo install wasm-bindgen-cli --version <version>
```

### reference-types feature required

wasm-bindgen 0.2.103 requires the `reference-types` and `multivalue` WebAssembly proposals to be enabled at compile time. These are set in `.cargo/config.toml`:

```toml
[target.wasm32-unknown-unknown]
rustflags = ["-C", "target-feature=+reference-types,+multivalue"]
```
