# 4.9 Delivery log

One row per delivery, for somebody asking **what was delivered, and when.** Not
a runbook — a runbook holds every step for somebody doing it or undoing it, and
lives with its project. This holds the fact that it happened.

**It said *"what changed in production"* until 2026-08-25**, when #206's first
delivery created a GitHub organisation and moved the repository into it, changing
nothing in production at all. Owner, asked whether it got a row: *"yes, it gets a
row."* A delivery is *one act of putting change in front of whoever consumes it*
(§1), and the consumer is not always a player.

**A GitHub Release is not this.** Since 2026-08-27 `deploy.sh` publishes one per
`prod-X.Y.Z` tag, with notes GitHub generates from the merged pull requests. That
is the public changelog for a *release*; this is the log of *deliveries*, and the
five rows `0.7.0a` to `0.7.0e` shipped no code and so have no tag a release could
hang on. See [3.3](3.3-testing-ci-and-release.md) §3.3.1.

## What gets a row, and what does not

Owner, 2026-08-25: *"the delivery log only needs to include project deliveries,
with a label. Pre-approved changes not listed as deliveries under a project do
not get a label. Change history must be derived from git."*

| | row here? | identifier? |
| --- | --- | --- |
| a **delivery of a project** — listed under its *Deliveries* heading | **yes** | yes — a version, or the lettered form for one shipping no application code (D34) |
| a **pre-approved change** — straight to `main`, no project | **no** | **no** |

**Why the second line is not an omission.** A pre-approved change is one nothing
depends on and nobody is holding back (§2.2), and there are dozens of them: a
log recording each would be a worse copy of `git log`, kept by hand, going stale
the first time somebody forgot. **Change history is derived from git**, which
has all of it, exactly, for nothing.

**So this log answers a narrower question than "what changed":** it answers
*which planned pieces of work reached their users, when, and did they work.* A
delivery has a project behind it, a runbook, and an outcome worth recording. A
pre-approved change has a commit message.

**A worked example.** #179 — *define the change process* — closed on 2026-08-25
having produced `docs/3.6`, two issue templates, a workflow and two scripts. It
has **no row**, because it delivered through dozens of pre-approved pushes
rather than through a delivery. Its history is in `git log`, which is where it
belongs.

**It starts at #174.** Deliveries before 2026-08-22 are recoverable from the
`prod-*` tags and the closed milestones, and are not retrofitted here: a log
back-filled from memory would claim a completeness it does not have. The tags
are the record for everything earlier.

**Identifiers.** A delivery that ships application code is a release and takes
its version. A delivery that ships none — a host change, a console change, a
drill — takes the production version at the time plus a letter: `0.7.0a`, then
`0.7.0b` (D34). The letter form is not valid semver, deliberately: `deploy.sh`
reads its milestone from `Cargo.toml`, so a lettered milestone can never be
matched by a deploy and can never auto-close. These rows are closed by hand.

**Production's version, never the development one, and that is the whole point.**
Owner, 2026-09-09: *"this is why letter milestones use the production release not
the dev release, because the dev release might change."* Proven the same day —
`main` had been on `0.7.3` for a fortnight and became `0.8.0` when #301 turned
out to carry functional change. `0.7.2a` was untouched, because it is anchored to what production is
actually running. Anything named `0.7.3a` would have been silently wrong, naming
a release that never existed.

**Production only moves when a deploy moves it**, so it is the one number a
letter can be pinned to. The development version is a statement of intent and
changes whenever the intent does.

**Oldest first, newest last** — so a new row is appended and the file reads as
a history. The order drifted before this was written down: rows were being
prepended and inserted, and by 2026-08-26 the six read `0.7.0, a, e, d, c, b`.

**A letter is allocated when the delivery is recorded, not by date.** `0.7.1aa`
sits between `0.7.1a` and `0.7.1b` in the table and delivered before both — it
was written down two days late, and renumbering four milestones already cited in
closed issues and commit messages would cost more than the ordering is worth.
The date column is what says when something happened.

## What each delivery left behind that git does not show

`0.7.0a` is the first row where most of the change exists only on the host and
in the OCI console. `docs/4.8-artefacts.md` is the register of those; this log
records only that the delivery happened.

**The drill proved more than the restore path.** The two backups either side of the sweep differ by exactly one game — 27 at 18:45, 26 at 03:14 — and the journal names the cause: `terminal game auto-deleted after 7 days`, logged at 20:19:47. A backup that faithfully records a change nobody made by hand is better evidence that it is real than any assertion about it.

**Two defects were found by running it**, both fixed the same evening:

- `sqlite3` was in the server image but not on the host, and the backup's
  integrity check runs on the host. The first real run failed.
- All three marker uploads used `curl -T -`, which sends chunked encoding; OCI
  answers **501**. Since every alarm watches a marker for absence of success,
  not one could ever have been satisfied — #199.

Neither was visible from the repository. Both were found by the delivery's own
step 3, which is the argument for proving a delivery rather than declaring it.
