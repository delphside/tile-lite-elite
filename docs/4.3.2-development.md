# Development

Running the services locally, building, and resetting local state. Setup is
[4.3.1](4.3.1-setup.md); the release flow is
[4.3.3](4.3.3-testing-ci-and-release.md); every script is in
[4.3.0 Tools](4.3.0-tools.md).

## Two worktrees

```text
~/tile-lite-elite/
  main/         pinned to `main`, the primary checkout
  projectdev/   a project branch, detached at `main` when idle
```

| for | work in | because |
| --- | --- | --- |
| operating: board tooling, deploys, checks, documents, the dev services | `main` | the aliases `sadev` and `dbdev` point at the tree the setup script ran in |
| building a change | `projectdev` | the branch stays out of the operating tree |
| testing a new version of a script | `projectdev` | the one exception to operating from `main` |

- Git stops `projectdev` taking `main`: *fatal: 'main' is already used by
  worktree*. Nothing stops the `main` tree moving to another branch; the shell
  prompt shows the branch.
- Open VS Code and start Claude sessions at `~/tile-lite-elite/main`. A
  session takes its starting folder as its project, and the folder above both
  trees holds no `CLAUDE.md`, `.claude/` or git repository. `projectdev` opens
  in a second window and its session reads that tree's own `.claude/`.
- Each tree has its own `target/`, since cargo cannot share one between
  commits without invalidating both. The sccache compilation cache is shared
  across the two.
- `setup-dev-environment.sh` writes `sadev`, `sapre` and `dbdev` for the tree it
  runs in, so run it from `main`. From a linked worktree it refuses unless
  `SETUP_ALLOW_WORKTREE=1` is set.

## Quick start (scripts)

[`services.sh`](../scripts/develop/services.sh) manages the backend (`:3000`)
and the web dev client (`:8080`). Logs are in `.logs/` and process ids in
`.pid.server` and `.pid.web`, both in the tree it runs from.

| command | does |
| --- | --- |
| `./scripts/develop/services.sh start` | starts both in the background |
| `./scripts/develop/services.sh stop` | stops both |
| `./scripts/develop/services.sh restart` | stops, then starts both |
| `./scripts/develop/services.sh restart-server` | restarts the backend only |
| `./scripts/develop/services.sh restart-web` | restarts the web client only |
| `./scripts/develop/services.sh status` | shows both, and flags a service it did not start |
| `./scripts/develop/services.sh logs` | tails both logs |
| `./scripts/develop/services.sh dev` | runs both in the foreground; Ctrl+C stops them |
| `./scripts/develop/desktop.sh` | opens a desktop client in the foreground; run it again for another player |

- `start` and the `restart` commands kill whatever is listening on `:3000` or
  `:8080` first, including a process the script did not start.
- `start` and `restart-server` raise the backend's rate limits (register,
  auth, session and global) far above production's, because the e2e suite
  registers many players from one address. Set the matching
  `TILE_LITE_ELITE_LIMIT_*` variable before the command to test limiting. `dev`
  and the manual commands below leave the defaults.
- `desktop.sh` passes its argument to the client: a URL, `--server-url <url>`
  or `--env <local|preview|rehearsal|prod>`. A debug build defaults to `local`.

## Manual starts

From the workspace root unless stated.

### Manual: backend

```bash
cargo run -p server-game
```

| setting | variable | default |
| --- | --- | --- |
| bind address | `TILE_LITE_ELITE_BIND` | `127.0.0.1:3000` |
| database | `TILE_LITE_ELITE_DATABASE_URL` | `./data/tile-lite-elite.sqlite3` |

The server creates the database and applies its migrations on first run, but
not the `data/` directory: `services.sh` makes it, so a manual start in a fresh
clone needs `mkdir data` first.

### Manual: web client

From `crates/ui/`:

```bash
RUSTC_WRAPPER="" CARGO_INCREMENTAL=0 ~/.cargo/bin/dx serve --platform web --port 8080
```

`dx build --platform web` in place of `serve` compiles the WASM client without
serving it, which is how to check that it builds. `RUSTC_WRAPPER=""` is
required for both: sccache hangs a `wasm32-unknown-unknown` build.

### Manual: desktop client

```bash
cargo run -p tile-lite-elite-ui --features desktop
```

Append `-- --server-url <url>` or `-- --env <name>` to choose the server. The
client does not read `TILE_LITE_ELITE_API_BASE_URL`, which only the web build
uses.

## Resetting the database

Schema changes do not need a reset: versioned migrations apply to an existing
database at startup ([4.4.2](4.4.2-database-schema.md)). Reset to clear dev
data or after experimenting with a migration:

```bash
./scripts/develop/services.sh stop
rm -f data/tile-lite-elite.sqlite3 data/tile-lite-elite.sqlite3-wal data/tile-lite-elite.sqlite3-shm
./scripts/develop/services.sh start
```

- Stop the server first. It keeps the file open and every active game in
  memory, so deleting the file under it changes nothing until restart.
- `-wal` and `-shm` are SQLite's write-ahead-log files and may not exist.
- The server recreates the file because `persistence::connect` sets
  `create_if_missing(true)`; without it a missing file fails with
  `unable to open database file`.

## End-to-end UI tests (Playwright)

The `e2e/` suite drives the rendered client against a live server, which
`cargo test` does not. Start the services, then:

```bash
cd e2e
npm install && npx playwright install chromium   # first time only
npm test
```

- The suite registers its own players, named `T-e2e-<run>-<name>`, and
  purges them at teardown with `scripts/develop/e2e-clean.sh`.
- CI runs it as the regression pass
  ([4.3.3 §2.3](4.3.3-testing-ci-and-release.md#23-continuous-integration));
  a local run is a faster inner loop, not a release gate.
- [`e2e/README.md`](../e2e/README.md) has the options and cleanup.
