## Two worktrees

```text
~/tile-lite-elite/
  main/         the primary checkout
  projectdev/   a project branch
  programme/    the live programme checkout, a separate clone
```

`programme/` is described in
[4.3.1](4.3.1-setup.md#the-two-copies-of-the-programme).

| for | work in | because |
| --- | --- | --- |
| operating: board tooling, deploys, checks, documents, the dev services | `main` | the setup script's aliases point at this tree |
| building a change | `projectdev` | the branch stays out of the operating tree |
| testing a new version of a script | `projectdev` | `main` keeps the working version until the new one merges |

- Keep the `main` tree on `main`. Git refuses to put `projectdev` on it (*fatal:
  'main' is already used by worktree*) but lets the `main` tree move to another
  branch; `git branch --show-current` shows where it is.
- Open VS Code and start Claude sessions at `~/tile-lite-elite/main`. A
  session takes its starting folder as its project, and only the trees hold a
  `CLAUDE.md`, a `.claude/` and a git repository. Open `projectdev`
  in a second window to work on a branch; its session reads that tree's own
  `.claude/`.
- Each tree has its own `target/`; the sccache compilation cache is shared.
- `setup-dev-environment.sh` writes `sadev`, `sapre`, `dbdev` and `dbpre`
  for the tree it runs in, so run it from `main`. From a
  linked worktree it refuses unless `SETUP_ALLOW_WORKTREE=1` is set.

## Quick start (scripts)

[`services.sh`](../scripts/develop/services.sh) manages the backend and the web
dev client:

- the backend is on `:3000` and the web client on `:8080`
- logs are in `.logs/` and process ids in `.pid.server` and `.pid.web`, in the
  tree it runs from

| command | does |
| --- | --- |
| `./scripts/develop/services.sh start` | starts both in the background |
| `./scripts/develop/services.sh stop` | stops both |
| `./scripts/develop/services.sh restart` | stops, then starts both |
| `./scripts/develop/services.sh restart-server` | restarts the backend only |
| `./scripts/develop/services.sh restart-web` | restarts the web client only |
| `./scripts/develop/services.sh status` | shows both, and flags a service it did not start |
| `./scripts/develop/services.sh logs` | tails both logs |
| `./scripts/develop/services.sh dev` | runs both in the foreground (Ctrl+C stops them) |
| `./scripts/develop/desktop.sh` | opens a desktop client in the foreground |

- `start`, `restart` and `restart-server` make `data/` and raise the backend's
  rate limits far above production's; the others leave `data/` alone and run
  at production's limits. The
  [e2e suite](#end-to-end-ui-tests-playwright) registers many players from one
  address, so it needs services started with `start` or `restart`.
- To test limiting ([4.4.1](4.4.1-configuration.md#rate-limits)), set
  `TILE_LITE_ELITE_LIMIT_{REGISTER,AUTH,SESSION,GLOBAL}_{PER_MIN,BURST}`
  before the command.
- `start` and the `restart` commands kill whatever is listening on `:3000` or
  `:8080` first, including a process the script did not start.
- `desktop.sh` passes its argument to the client: a URL, `--server-url <url>`
  or `--env <local|preview|rehearsal|prod>`. A debug build defaults to `local`.
- Every desktop instance shares one `auth.json` in the user config directory
  ([4.4.6](4.4.6-client-local-storage.md#storedauth)). For several players,
  log out first and leave **Stay logged in** unticked: each launch then opens
  at the login screen.

## Manual starts

Run from the workspace root unless stated. The variables are in
[4.4.1](4.4.1-configuration.md#environment-variables).

### Manual: backend

```bash
mkdir -p data   # first time only
cargo run -p server-game
```

The server creates the database and applies its migrations on first run.

### Manual: web client

From `crates/ui/`:

```bash
RUSTC_WRAPPER="" CARGO_INCREMENTAL=0 ~/.cargo/bin/dx serve --platform web --port 8080
```

To check that the WASM client builds without serving it:

```bash
RUSTC_WRAPPER="" CARGO_INCREMENTAL=0 ~/.cargo/bin/dx build --platform web
```

`RUSTC_WRAPPER=""` is required for both: sccache hangs a
`wasm32-unknown-unknown` build.

### Manual: desktop client

```bash
cargo run -p tile-lite-elite-ui --features desktop -- --server-url <url>
```

`--env <name>` in place of `--server-url <url>` picks a named server; with
neither, a debug build connects to `local`.

## Resetting the database

Migrations apply at startup, so a schema change keeps the data
([4.4.2](4.4.2-database-schema.md#actual-current-shape)). Reset to:

- clear dev data
- start again after experimenting with a migration

```bash
./scripts/develop/services.sh stop
rm -f data/tile-lite-elite.sqlite3*
./scripts/develop/services.sh start
```

Stop the server first: it keeps the file open and every active game in memory,
so deleting the file under it changes nothing until restart. The server
recreates the file at start ([4.4.1](4.4.1-configuration.md#sqlite)).

## End-to-end UI tests (Playwright)

The `e2e/` suite drives the rendered client against a live server, beyond
what `cargo test` covers.

1. Start the services with `./scripts/develop/services.sh start` or `restart`.
2. Run the suite as [`e2e/README.md`](../e2e/README.md#running) says.

CI runs it as the regression pass
([4.3.3 §2.3](4.3.3-testing-ci-and-release.md#23-continuous-integration)); a
local run is the faster inner loop.

## When a local run fails

| symptom | cause | fix |
| --- | --- | --- |
| `unable to open database file` | `data/` is missing, as in a fresh clone | `mkdir -p data` |
