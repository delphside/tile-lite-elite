## Players and sessions

A *player* is a persistent identity: a display name, a password and an email
address. A *session* is a bearer token proving a client may act as that
player. The rules for each item:

| Item | Rule |
| --- | --- |
| display name | unique; trimmed, then NFC-normalised and lowercased before comparing (`fold_display_name`), so `José` and `JOSÉ` are one name |
| email address | shared by any number of players, so one person may run several under one address; unverified, as the `players` columns for verification are unused |
| password | hashed with Argon2, slow and salted, because people choose them; only an empty password is refused |
| session token | a random UUID v4, hashed with SHA-256, fast enough to look up on every request; the raw token exists only on its client, so a copy of the database cannot sign in |
| token transport | `Authorization: Bearer <token>` on REST calls, except `POST /auth/validate`, which takes it as `session_token` in the body; `?token=` on the WebSocket, whose handshake cannot set a header |

**Registering** creates the player and a session.

**Signing in** is by display name and password:

- a wrong name and a wrong password get the same refusal;
- a wrong name verifies the password against a fixed decoy hash, so it costs
  the same time as a wrong password;
- each sign-in starts a new session and leaves the player's others valid.

Where a client keeps its token is in
[4.4.6](4.4.6-client-local-storage.md#storedauth).

## How long a session lasts

Every session has two limits ([ACC-1](4.1.0-rules.md#accounts)):

| Limit | Value | Measured from |
| --- | --- | --- |
| idle | 48 hours (`SESSION_IDLE_WINDOW_SECS`) | `last_seen_at`, bumped on an authenticated request when it is more than 15 minutes old (`LAST_SEEN_BUMP_THROTTLE_SECS`) |
| absolute | 10 days (`SESSION_MAX_LIFETIME_SECS`) | creation; fixed |

A session ends in one of these ways:

| Event | Effect |
| --- | --- |
| expiry | the next request refused, `POST /auth/validate` included; the session's row deleted when any player next calls `GET /games` |
| signing out (`POST /auth/logout`) | this session deleted at once |
| a [password change](#changing-account-details) or [reset](#forgotten-passwords) | every session of the player deleted |
| the admin CLI's `users sign-out` or `users delete` ([4.3.4](4.3.4-production-environment.md#admin-cli)) | every session of the player deleted |

**Stay logged in** and **Remember me** are client settings that change
neither limit ([ACC-2](4.1.0-rules.md#accounts);
[4.4.6](4.4.6-client-local-storage.md#storedauth)).

## Changing account details

What each change needs, and what it does to sessions:

| Change | Needs | Afterwards |
| --- | --- | --- |
| display name or email address (`POST /auth/update-details`) | a valid session; a new display name must be unique | the session still valid |
| password (`POST /auth/change-password`) | the current password as well | every session of the player ended, this one included ([ACC-6](4.1.0-rules.md#accounts)) |

## Forgotten passwords

1. `POST /auth/forgot-password` takes an email address and answers alike
   whether or not it matches
   ([4.4.3](4.4.3-api-schema.md#what-each-auth-call-refuses-and-why)).
2. For a match, it retires the player's unused reset tokens and mails a link,
   `/reset-password?token=…` on the web client's address, carrying a
   single-use token valid for one hour. The server stores the token hashed;
   the raw token is in the link alone, and in the log only where
   [*Email*](#email) says.
3. `POST /auth/reset-password` spends the token, sets the new password and ends
   every session for the player.

Two constraints on a reset:

- the address must match the registered one exactly, case included;
- a shared address reaches one of its players, chosen arbitrarily.

## Email

The server sends five messages through Resend; the wording is in
`crates/server-game/emails/*.txt`:

| Message | To | When |
| --- | --- | --- |
| welcome | the address given | a player registers |
| invitation | the invited player's account address | a game is created with a [`named` seat](4.2.7-authentication-and-invitations.md#the-four-ways-to-claim-a-seat), or `POST /games/{id}/invite` names a player |
| join invitation | the address on the invitation | a game is created with an `email` seat, or `POST /games/{id}/invite` gives an address |
| password reset | the address given | `POST /auth/forgot-password` matches a player |
| move reminder | the account address of the player on turn | the scheduler finds a third of the move time limit left; only for limits over a day |

The server sends nothing for an `open` invitation. For every message:

- the server logs a failed send, and the request still succeeds; a failed
  reminder also counts as an error in the scheduler's health figures;
- with no `RESEND_API_KEY` configured, the server sends nothing: the log
  records the message kind, and the whole message only when
  `TILE_LITE_ELITE_LOG_EMAIL_BODIES` is enabled
  ([4.4.1](4.4.1-configuration.md#environment-variables)).

## Acting for a seat

Calls that play a seat refuse a caller who does not hold it
([4.4.3](4.4.3-api-schema.md#what-each-games-call-refuses-and-why) has the
refusals):

| Call | The caller must |
| --- | --- |
| `POST /games/{id}/actions`, `POST /games/{id}/preview` | be signed in and hold the human seat the request names, which rules out an engine's seat, an unclaimed one, another player's and a number the game lacks |
| `POST /games/{id}/suggest` | hold the seat whose turn it is, in an active game, where that seat is human |

Starting a game and managing the roster belong to the game's creator, with
the exceptions in
[4.2.7](4.2.7-authentication-and-invitations.md#managing-the-roster).

## Where authentication differs from 4.1.0

The code departs from 4.1.0's rules here:

| 4.1.0 | The code |
| --- | --- |
| ACC-4, ACC-5: sign in and ask for a reset by User ID, or by a verified address | sign-in is by display name only; a reset is by the registered email address only |
| NOTE-1, TIME-4: a third-of-time reminder by email is Never, by phone On | the server sends the reminder by email |
| NOTE-1: a changed address is told to the old one | the server sends nothing to the old address |
| NOTE-1: an address is verified by email on registering or changing it | addresses are unverified; registering sends a welcome email |
| NOTE-1: a phone notification for each event marked On | the server sends none; email is the only channel |

How unverified addresses change invitations is in
[4.2.7](4.2.7-authentication-and-invitations.md#where-seats-and-invitations-differ-from-410).
