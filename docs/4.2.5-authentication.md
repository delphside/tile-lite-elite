# Authentication and player recognition

How the server knows who a player is. The calls, with their requests,
responses and refusals, are in
[4.4.3 API Schema](4.4.3-api-schema.md#auth-endpoints). The tables are in
[4.4.2 Database Schema](4.4.2-database-schema.md#players). Seats and
invitations are in [4.2.7](4.2.7-authentication-and-invitations.md); a worked
example is in [4.2.6](4.2.6-authentication-examples.md).

## Players and sessions

A **player** is a persistent identity: a display name, a password and an
email address. A **session** is a bearer token proving a client may act as
that player. The server keeps only a hash of each token, so a copy of the
database cannot be used to sign in.

| item | rule |
| --- | --- |
| display name | unique; trimmed, then NFC-normalised and lowercased before comparing (`fold_display_name`), so `José` and `JOSÉ` are one name; login finds the player by it |
| email address | not unique: one person may run several players under one address |
| password | hashed with argon2, slow and salted, because people choose them; only an empty password is refused |
| session token | a random UUID v4, hashed with sha256, fast enough to look up on every request |
| token transport | `Authorization: Bearer <token>` on REST calls; `?token=` on the WebSocket, whose handshake cannot set a header |

**Registering** creates the player and a session. **Signing in** is by display
name and password. A wrong name and a wrong password get the same refusal, and
a wrong name costs the same time as a wrong password: the server verifies the
password against a fixed decoy hash first. Each sign-in starts a new session
and leaves the player's others valid. Where a client keeps its token is in
[4.4.6](4.4.6-client-local-storage.md).

## How long a session lasts

Two limits, the same for every session:

| limit | value | measured from |
| --- | --- | --- |
| idle | 48 hours (`SESSION_IDLE_WINDOW_SECS`) | `last_seen_at`, bumped on an authenticated request when it is more than 15 minutes old (`LAST_SEEN_BUMP_THROTTLE_SECS`) |
| absolute | 10 days (`SESSION_MAX_LIFETIME_SECS`) | creation; never extended |

An expired session is refused on its next request, including
`POST /auth/validate`. Its row is deleted when any player next calls
`GET /games`. **Logging out** deletes the session at once.

**"Stay logged in" is a client setting**: it decides whether the browser keeps
the token across a restart, and does not change either limit. **"Remember me"**
prefills the display name only.

## Changing account details

| change | needs | afterwards |
| --- | --- | --- |
| display name or email (`update-details`) | a valid session | the session stays valid; a new display name must be unique |
| password (`change-password`) | the current password as well | every session for the player is ended, including this one |

The current password is what makes a password change a deliberate act, rather
than something a stolen token could do.

## Forgotten passwords

1. `forgot-password` takes an email address and always answers `204`, whether
   or not it matched.
2. For a match, it retires the player's unused reset tokens and mails a link,
   `/reset-password?token=…` on the web client's address, carrying a
   single-use token valid for one hour.
3. `reset-password` spends the token, sets the new password and ends every
   session for the player.

The address must match the one registered exactly, case included. Because an
email address is not unique, a reset reaches one of the players sharing it,
chosen arbitrarily, never all of them.

## Email

The server sends five messages through Resend; the wording is in
`crates/server-game/emails/*.txt`:

| message | sent |
| --- | --- |
| welcome | on registering |
| invitation | to a named player's account address, when a seat names them |
| join invitation | to the address on an email seat |
| password reset | on `forgot-password` for a known address |
| move reminder | by the scheduler, once a third of the move time limit remains; only for limits over a day |

A failed send is logged and does not fail the request. With no API key
configured, nothing is sent: the log records the message kind, and the whole
message only when `TILE_LITE_ELITE_LOG_EMAIL_BODIES` is set
([4.4.1](4.4.1-configuration.md#environment-variables)).

**Email addresses are not verified.** The `players` table has columns for it,
and nothing uses them.

## Acting for a seat

Calls that play a seat refuse a caller who does not hold it. A seat nobody
holds is nobody's to act for: an engine's seat, an unclaimed human seat and a
number the game has no seat for are refused like another player's.

| call | the caller must |
| --- | --- |
| `POST /games/{id}/actions`, `POST /games/{id}/preview` | be signed in and hold the human seat named in the request; `401` without a session, `403` otherwise |
| `POST /games/{id}/suggest` | hold the seat whose turn it is; `403` otherwise |

Starting a game and the roster calls belong to the game's creator
([4.2.7](4.2.7-authentication-and-invitations.md#managing-the-roster)).

## What is stored

Only hashes of session tokens, passwords and reset tokens. A raw token exists
only on the client that holds it and in the reset email.
