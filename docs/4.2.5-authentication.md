# Authentication and player recognition

How the server knows who a player is. The calls, with their requests,
responses and refusals, are in
[4.4.3](4.4.3-api-schema.md#auth-endpoints). The tables are in
[4.4.2](4.4.2-database-schema.md#players). Seats and invitations are in
[4.2.7](4.2.7-authentication-and-invitations.md); a worked example is in
[4.2.6](4.2.6-authentication-examples.md).

## Players and sessions

A *player* is a persistent identity: a display name, a password and an email
address. A *session* is a bearer token proving a client may act as that
player. The server keeps only a hash of each token, so a copy of the database
cannot be used to sign in.

| Item | Rule |
| --- | --- |
| display name | unique; trimmed, then NFC-normalised and lowercased before comparing (`fold_display_name`), so `José` and `JOSÉ` are one name; login finds the player by it |
| email address | not unique: one person may run several players under one address |
| password | hashed with argon2, slow and salted, because people choose them; only an empty password is refused |
| session token | a random UUID v4, hashed with sha256, fast enough to look up on every request; the raw token exists only on its client |
| token transport | `Authorization: Bearer <token>` on REST calls; `?token=` on the WebSocket, whose handshake cannot set a header |

**Registering** creates the player and a session. **Signing in** is by display
name and password:

- a wrong name and a wrong password get the same refusal;
- a wrong name verifies the password against a fixed decoy hash, so it costs
  the same time as a wrong password;
- each sign-in starts a new session and leaves the player's others valid.

Where a client keeps its token is in
[4.4.6](4.4.6-client-local-storage.md#storedauth).

## How long a session lasts

Two limits ([ACC-1](4.1.0-rules.md#accounts)), the same for every session:

| Limit | Value | Measured from |
| --- | --- | --- |
| idle | 48 hours (`SESSION_IDLE_WINDOW_SECS`) | `last_seen_at`, bumped on an authenticated request when it is more than 15 minutes old (`LAST_SEEN_BUMP_THROTTLE_SECS`) |
| absolute | 10 days (`SESSION_MAX_LIFETIME_SECS`) | creation; never extended |

What happens at the end of a session:

| Event | Effect |
| --- | --- |
| expiry | the next request is refused, including `POST /auth/validate`; the row is deleted when any player next calls `GET /games` |
| logging out | the session is deleted at once |

**Stay logged in** and **Remember me** are client settings that change
neither limit ([ACC-2](4.1.0-rules.md#accounts);
[4.4.6](4.4.6-client-local-storage.md#storedauth)).

## Changing account details

| Change | Needs | Afterwards |
| --- | --- | --- |
| display name or email (`POST /auth/update-details`) | a valid session | the session stays valid; a new display name must be unique |
| password (`POST /auth/change-password`) | the current password as well | every session for the player is ended, including this one ([ACC-6](4.1.0-rules.md#accounts)) |

## Forgotten passwords

1. `POST /auth/forgot-password` takes an email address and answers `204` for
   any non-blank address, whether or not it matched; a blank one answers `400`.
2. For a match, it retires the player's unused reset tokens and mails a link,
   `/reset-password?token=…` on the web client's address, carrying a
   single-use token valid for one hour. The token is stored hashed; the raw
   token exists only in the link, which is also logged when no email provider
   is configured and the log switch below is on.
3. `POST /auth/reset-password` spends the token, sets the new password and ends
   every session for the player.

The address must match the one registered exactly, case included. Because an
email address is not unique, a reset reaches one of the players sharing it,
chosen arbitrarily.

## Email

The server sends five messages through Resend; the wording is in
`crates/server-game/emails/*.txt`:

| Message | Sent |
| --- | --- |
| welcome | on registering |
| invitation | to a named player's account address, when a named invitation is sent |
| join invitation | to the address on an email seat, when an email invitation is sent |
| password reset | on `POST /auth/forgot-password` for a known address |
| move reminder | by the scheduler, once a third of the move time limit remains; only for limits over a day |

A named or email invitation is sent when the game is created with the seat, or
on `POST /games/{id}/invite`. A failed send is logged and does not fail the
request. With no API key configured, nothing is sent: the log records the
message kind, and the whole message only when
`TILE_LITE_ELITE_LOG_EMAIL_BODIES` is `1` or `true`
([4.4.1](4.4.1-configuration.md#environment-variables)).

**Email addresses are not verified.** The `players` table has columns for it,
and nothing uses them.

## Acting for a seat

Calls that play a seat refuse a caller who does not hold it:

| Call | The caller must | Refused with |
| --- | --- | --- |
| `POST /games/{id}/actions`, `POST /games/{id}/preview` | hold the human seat named in the request | `401` without a session; `403` for any other seat: an engine's, an unclaimed one, another player's, or a number the game lacks |
| `POST /games/{id}/suggest` | hold the seat whose turn it is | `403` otherwise; `400` when the game is not active or the seat on turn is an engine's |

Starting a game and the roster calls belong to the game's creator
([4.2.7](4.2.7-authentication-and-invitations.md#managing-the-roster)).

## Where authentication differs from 4.1.0

| 4.1.0 | The code |
| --- | --- |
| ACC-4, ACC-5: sign in and ask for a reset by User ID, or by a verified address | sign-in is by display name only; a reset is by the registered email address only |
| NOTE-1, TIME-4: a third-of-time reminder by email is Never, by phone On | the reminder is sent by email |
| INV-1, INV-2: an invitation depends on whether the address is verified | addresses are not verified |
