# Log events

*Verified against the code at `617aa3f` (app 0.10.2, 2026-11-09). To see what has changed since, `git log 617aa3f..HEAD -- crates/ scripts/`; for this document's own history, `git log --follow -- <this file>`.*

Every event the server and the scripts write, and what each carries.

Two producers share two things: the envelope fields `timestamp`, `level` and
`message`, and the rule that logs carry identifiers only.

| Producer | Writes | Where |
| --- | --- | --- |
| the server | the events in [The catalogue](#the-catalogue) | stdout, JSON per line, forwarded by Docker |
| `deploy.sh` and the other scripts in [What the scripts write](#what-the-scripts-write) | `run started`, `gate passed`, `run finished` | `${XDG_STATE_HOME:-~/.local/state}/tile-lite-elite/<script>-<run>.jsonl` (`<script>` without `.sh`) |

## What the server writes

The log is JSON, one object per line. Each line carries an *envelope* —
`timestamp`, `level`, `message`, `target` — and the event's own fields
flattened alongside it. `level` is logged in capitals (`INFO`, `WARN`); the
catalogue shows it in lower case.

```json
{"timestamp":"2026-08-21T19:11:15.519240Z","level":"INFO","message":"player registered","player_id":"abc-123","target":"server_game::app::auth"}
```

**Identifiers only.** `player_id` and `game_id` are enough to diagnose. The
admin CLI resolves an ID to a person ([4.3.4](4.3.4-production-environment.md#identifiers-only)).
No display name, email address, token or password reaches the log, except in
the one `debugOnly` event ([The schema](#the-schema)). `player_id` is
pseudonymous: the database holds the table that resolves it, so the log is
still personal data under data protection.

| Check | Catches |
| --- | --- |
| `scripts/operate/check-log-hygiene.py` | an email address in any field of any event, declared or not; on a declared event, a field the schema does not declare or a declared field missing |
| `scripts/develop/check-run-log-events.py` | a script event missing from the table in [What the scripts write](#what-the-scripts-write) |

`check-log-hygiene.py` reads the CI stream and production's log;
`check-run-log-events.py` reads the scripts' source. Preview's logs are read by
neither, and neither looks for a display name.

## The field vocabulary

**The server's log uses 29 field names.** Read this table to review whether
the rule holds.

| Field | What it is | Personal? |
| --- | --- | --- |
| `player_id` | a player's UUID | **pseudonymous** — resolvable with the database |
| `creator_player_id` · `invited_player_id` | the same, in a specific role | **pseudonymous** |
| `game_id` · `invitation_id` | a game's or invitation's UUID | no |
| `seat` · `seat_number` · `seats` · `winner_seat` | positions within a game | no |
| `status` | a game's status on *game started*; the HTTP status on *email send failed*, *support intake dispatch failed* and *support mail check failed* | no |
| `kind` | which message an email was — a closed set, see `email::MessageKind` | no |
| `reason` | why a login was rejected: a category, the value supplied is not logged | no |
| `error` | a failure: the underlying library's error, or a fixed description where a response lacked a field | no |
| `move_time_limit_seconds` · `budget_ms` · `elapsed_ms` | durations | no |
| `last_completed_at` | when a scheduled job last finished a pass, epoch seconds | no |
| `job` · `join_error` | a scheduled job's name, and the panic it raised as the runtime reported it | no |
| `games_in_memory` | a count | no |
| `engine_id` | which engine played | no |
| `app_version` · `api_version` · `schema_version` · `bind` | what the process is | no |
| `database_url` | where the database is | no — a SQLite path; a Postgres URL would carry a credential |
| `to` · `subject` · `text_body` | an email in full | **yes** — written only by the `debugOnly` event ([The schema](#the-schema)) |

## What the scripts write

These scripts write a run log; every other script writes none:

- `deploy.sh` and `rollback.sh`, with their rehearsal wrappers except
  `deploy-rehearsal.sh reset`;
- `restore-backup.sh`;
- `rehearsal-limits.sh`;
- `deploy-preview.sh`, see [A preview run](#a-preview-run).

The rest of this section applies to every script but `deploy-preview.sh`.

Each line carries `timestamp`, `level` (always `INFO`), `message` and `script`,
and no `target`.

| Event | Fields | Meaning |
| --- | --- | --- |
| `run started` | `script` · `args` · `commit` | the run's own arguments and the commit the tree was on |
| `gate passed` | `script` · `gate` | one per gate, from `note_gate`, the single place `deploy.sh` records them |
| `run finished` | `script` · `status` | **the exit status**, written by a trap, because a script that fails does not reach its own last line |

`run finished` is the record of a run that fails after printing its success
lines, as 0.7.2 did.

The file is one per run, outside the repository, and the last 20 per script are
kept.

### A preview run

`deploy-preview.sh` starts a run log, then sources `deploy.sh`, whose
`run_log_start` runs before the guard that returns when
`DEPLOY_SH_FUNCTIONS_ONLY` is `1`. A preview run writes two files:

| File | `script` field | Holds |
| --- | --- | --- |
| `deploy-preview-<run>.jsonl` | `deploy-preview.sh` | `run started` only |
| `deploy-<run>.jsonl` | `deploy.sh` | its own `run started`, then `run finished` with the exit status |

The preview file never records the exit status. The `deploy.sh` file is counted
in `deploy.sh`'s 20, so preview runs evict real deploys' logs. The second start
also replaces preview's chained EXIT trap, so the worktree cleanup does not
run on exit. This is a defect in the scripts, to be fixed by #567.

## The schema

This block is machine-readable. `scripts/operate/check-log-hygiene.py`
compares log lines against it. Each event lists the fields it carries, and
`additionalProperties: false` on every object is what makes the comparison
mean anything; the checker fails if one is missing.

The block declares the events in `auth.rs`, `email.rs` and `admin.rs`, except
*admin: signed out*. Only the events it declares are schema-checked; the
address scan covers the rest. For *email send failed* the block declares the
`error` variant only, so the checker reports a line with `status` as a problem
and exits 1.

**One event is marked `debugOnly`.** *email not sent (no RESEND_API_KEY
configured)* carries the whole message — address, subject, body.

The event is written when both hold:

- no email provider is configured (`RESEND_API_KEY` is unset);
- `TILE_LITE_ELITE_LOG_EMAIL_BODIES` is `1` or `true`, or the process is a
  test build.

Only `docker-compose.preview.yml` sets the variable on a host; a developer may
export it locally ([4.2.6](4.2.6-authentication-examples.md)). The build
profile does not matter: preview builds `--release` and emits the event.

| Stream | Treatment of the `debugOnly` event |
| --- | --- |
| a test stream (CI) | exempt from the address scan |
| a production stream | fails the check |
