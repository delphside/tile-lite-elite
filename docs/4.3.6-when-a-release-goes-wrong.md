# When a release goes wrong

What to type when production must go back, when a change cannot wait for the
normal path, and when a step fails, with the diagnostic and occasional
commands. The normal path is [4.3.3](4.3.3-testing-ci-and-release.md); the
mechanisms behind both are [4.3.7](4.3.7-how-testing-and-release-work.md).

Where each section runs, in the two worktrees of
[4.3.3 *Where and who*](4.3.3-testing-ci-and-release.md#where-and-who):

| Section | Run in | Because |
| --- | --- | --- |
| §1, §2, and §4's board and production reads | `main` | `deploy.sh` asks for `production` to be typed when its tooling is not on `main` |
| §3, up to the deploy | `projectdev`, on the emergency branch | the `main` tree stays on `main` |
| §3, afterwards | `main` | git refuses to switch `projectdev` to a branch the `main` tree holds |

## 1 Roll back production

**Who**: the owner. There are two forms:

| Form | Returns production to | Discards | Gates |
| --- | --- | --- | --- |
| `deploy.sh prod-<version>` | any earlier release | nothing | all of 4.3.3 §1.6 |
| `rollback.sh <snapshot>` | the state before the last deploy | every write since the snapshot | none |

**Rolling back by deploying** is deploying an earlier commit through the same
gates, so preview and rehearsal must hold it first:

```bash
./scripts/deliver/deploy-preview.sh at prod-0.6.1
./scripts/deliver/deploy-rehearsal.sh prod-0.6.1
./scripts/deliver/deploy.sh prod-0.6.1
```

- the `ci` gate needs a green push-to-`main` run with `e2e` for that commit;
  the owner reruns a cancelled run, as [§5](#5-when-a-release-step-fails) says
- the `version` gate compares the target with the **newest** `prod-*` tag, not
  with what production runs, so a rollback to `X.Y.0` while a later patch of
  the same minor exists is judged a patch release; `check-release-version.sh`
  refuses it when the `X.Y.0` milestone carries functional change
- that check has no override and `deploy.sh` calls it unconditionally, so such
  a rollback cannot go by deploy: the owner uses the snapshot form, which
  returns only to the state before the last deploy
- `deploy.sh` writes the `prod-*` tag as for any deploy; when that version
  already has one, it appends a UTC timestamp

**Rolling back by snapshot** retags the `:previous` images and restores the
database snapshot taken before the last deploy: seconds, no build and no
gates, because it only returns production to something that already ran there.
Run it bare to list the snapshots and the `:previous` image; name a snapshot to
restore it, and the script asks again before it does:

```bash
./scripts/deliver/rollback.sh                        # lists snapshots and the :previous image; changes nothing
./scripts/deliver/rollback.sh pre-0.6.2-1c8275f-20260817T133553Z.tgz
```

A snapshot named `pre-<version>-<commit>` was taken just before that commit was
deployed, so restoring it returns to whatever was running before it
([4.3.9](4.3.9-backups-and-restores.md#automatic-pre-deploy-snapshots)).
`rollback-rehearsal.sh` runs the same against rehearsal, to practise it.

**Proved by**: exit 0, then 4.3.3 §1.7.

## 2 Roll back across a migration

**Who**: the owner. Migrations run only forward, and an older image does not
boot against a newer schema: `sqlx` validates on startup. The `schema` gate
stops a deploy of such an image. To go back past a migration, restore the
database and the images together from the snapshot taken before the deploy:

```bash
./scripts/deliver/rollback.sh <snapshot>            # database and images back, in one step
./scripts/deliver/rollback.sh --db-only <snapshot>  # database only, images untouched
```

`--db-only` is for when:

- the running images are the ones to keep, and only the data is wrong
- no `:previous` image exists, so `rollback.sh` refuses the full form

**This discards everything written since the snapshot**: every game, move and
account. It is for minutes after a release, not for recovering last week.

**Proved by**: exit 0, and `/health` reporting the old version and a schema the
image knows.

## 3 Ship an emergency change

**Who**: the owner, in `projectdev`. **Go back first, when going back can
help.** Fix forward only when it cannot:

- a bug live long enough that no good version remains
- an outage from outside the image

1. go back to what worked: list, then restore. This discards writes since the
   snapshot ([§1](#1-roll-back-production)).

   ```bash
   ./scripts/deliver/rollback.sh
   ./scripts/deliver/rollback.sh <snapshot>
   ```

2. cut a branch from the commit production runs, never from `main`, which
   carries tested but unshipped changes that would ship beside the fix
   (the `emergency-scope` gate of
   [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it) asks before it
   ships them). Production's `/health`
   reports `app_version` as `<version>+<commit>`; the highest `prod-*` tag is
   not that commit after a rollback.

   ```bash
   curl -s https://tileliteelite.com/health        # note the commit after the +
   git switch --detach <commit>
   git switch -c emergency-<what>
   ```

3. commit the one fix as `<X.Y.Z+1>`, the patch after the highest `prod-*` tag
   `X.Y.Z` (after a rollback, the patch after production's version is already
   tagged). Then push:

   ```bash
   # set `version` in Cargo.toml to <X.Y.Z+1>
   cargo check --workspace          # refreshes Cargo.lock
   git add -A
   git commit -m "app <X.Y.Z+1> api <M.N>: the fix, and why"
   git push -u origin emergency-<what>
   ```

4. open a pull request into `main`; the body follows the template:

   ```bash
   ./programme/scripts/board/create-pr.sh --base main --head emergency-<what> \
     --title "<the fix>" --body-file .github/PULL_REQUEST_TEMPLATE.md
   ```

5. take every issue out of milestone `<X.Y.Z+1>`, open or closed, which holds
   `main`'s unshipped work. Note the numbers first:

   ```bash
   gh issue list --milestone <X.Y.Z+1> --state all --limit 200 --json number --jq '.[].number' | tee ~/emergency-held.txt
   for n in $(cat ~/emergency-held.txt); do gh issue edit "$n" --remove-milestone; done
   ```

   Left in, the milestone makes the deploy:

   - list the open issues as "will be closed", flag each
     `NO COMMIT MENTIONS THIS` and ask to continue
   - refuse, through `check-release-version.sh`, when any issue of any state
     has `Type of change` `functional`; no override exists
   - close nothing, because an emergency settles no milestone

6. run preview and rehearsal as for any release, then deploy.
   `DEPLOY_EMERGENCY` skips the `preview` and `rehearsal` gates and nothing
   else ([4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it)). Leave
   preview and rehearsal out only when every minute counts, and say so in the
   retrospective:

   ```bash
   ./scripts/deliver/deploy-preview.sh
   ./scripts/deliver/deploy-rehearsal.sh
   DEPLOY_EMERGENCY="logins 500 since 14:20" ./scripts/deliver/deploy.sh emergency-<what>
   ```

   If the deploy asks to continue, because an issue is left in the milestone,
   answer `y`: nothing in it is closed.

| Rule | Because |
| --- | --- |
| gates: the emergency column of the [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it) table | `DEPLOY_SKIP_CI` means only that GitHub is unreachable; it is no part of an emergency. |
| the deploy asks for `production` to be typed | the tooling on an emergency branch is not on `main` (4.3.7 §5.6), and the `deploy.sh` that runs is the branch's, the older one from the cut. |
| the branch has a pull request, and that run is the one judged | a branch cut from a tag has no push-to-`main` run and a branch push skips `e2e`, so the `ci` gate requires the pull request's run; the owner's ticks are its review. |
| the pull request targets `main` and must merge cleanly | GitHub runs no pull-request workflow on a conflicted one. |
| step 5 takes the issues out | `<X.Y.Z+1>` is the version step 3 sets, so it names the milestone holding `main`'s work until 4.3.3 §1.2.4 renames it to a minor. |
| the tag and the version bump happen, and the milestone is not settled | [4.3.7 §5.5](4.3.7-how-testing-and-release-work.md#55-what-a-release-settles) has why; `deploy.sh` commits the bump to the emergency branch and pushes it, and Afterwards closes what shipped. |
| `deploy.sh` raises a retrospective issue | it holds the reason and a checklist separating *restore service* from *understand the cause*; `DEPLOY_EMERGENCY=1` records "(no reason given at the time)". |

**Afterwards**, in the `main` tree. The fix is not on `main`, and the
emergency branch carries `deploy.sh`'s bump
([4.3.7 §6](4.3.7-how-testing-and-release-work.md#6-how-a-change-is-merged)
has why a merge):

1. merge the fix into `main`:

   ```bash
   cd ~/tile-lite-elite/main
   git pull --ff-only
   git merge emergency-<what>      # exits 1 on the version lines
   ```

2. resolve the version lines in `Cargo.toml` and `Cargo.lock`, which conflict
   because both sides changed them: `deploy.sh`'s bump on the branch, and
   `main`'s since the cut. Keep the branch's:

   ```bash
   git diff emergency-<what>...HEAD -- Cargo.toml Cargo.lock   # main's changes since the cut: expect version lines alone
   git checkout --theirs Cargo.toml Cargo.lock                  # theirs is the emergency branch
   git add Cargo.toml Cargo.lock
   ```

   When `main` changed those files beyond the version lines, edit the conflict
   markers by hand, as 4.3.3 §1.8 says.

3. resolve `crates/api/src/lib.rs` if it conflicts, which it does only when the
   fix and `main` both changed `API_VERSION`. Keep `main`'s value:

   ```bash
   git checkout --ours crates/api/src/lib.rs               # ours is main
   git add crates/api/src/lib.rs
   ```

4. commit and push; the commit fails while any conflict is unresolved:

   ```bash
   git commit --no-edit
   git push origin main
   ```

5. when milestone `<X.Y.Z+1>` still exists, it holds `main`'s work and is now
   one version behind: rename it to the version `main` now carries,
   `<X.Y.Z+2>`, by 4.3.3 §1.2.4 step 2 with `old` set to `<X.Y.Z+1>` and `new`
   to `<X.Y.Z+2>`. Then put back the issues taken out before the deploy:

   ```bash
   for n in $(cat ~/emergency-held.txt); do gh issue edit "$n" --milestone <X.Y.Z+2>; done
   ```

6. close what shipped by hand, because the deploy settled nothing: each issue
   the fix resolved, with a comment naming the `prod-` tag:

   ```bash
   gh issue close <n> --comment "Shipped in the emergency release prod-<X.Y.Z+1>"
   ```

**Proved by**: exit 0; 4.3.3 §1.7 passing; a retrospective issue on GitHub.

## 4 Diagnostics and occasional commands

These read and change nothing, except where a row says it writes. Every script
is registered in [4.3.0](4.3.0-tools.md); the board scripts are the
programme's
([1.1](https://github.com/delphside/programme/blob/main/docs/1.1-programme-tooling.md#the-board)).

| Question | Command |
| --- | --- |
| where is every open change, and what does each environment run? | `./programme/scripts/board/board-status.py` |
| what has been said on GitHub since I last looked? | `./programme/scripts/board/board-inbox.py` |
| what is waiting on a person? | `./programme/scripts/board/board-actions.py` |
| what is in flight, and what depends on what? | `./programme/scripts/board/roadmap-diagram.py` prints it; `--write` regenerates [4.1.5](4.1.5-work-in-progress.md) |
| what is in a release? | the milestone, listed at [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it) |
| what did each delivery carry? | [3.1.1](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.1-delivery-log.md) |
| what did the server log? (the owner) | [4.3.4](4.3.4-production-environment.md#journald-not-the-container) |
| what does the admin CLI list? (the owner) | [4.3.4](4.3.4-production-environment.md#admin-cli) |

To test one crate:

```bash
cargo test -p rules-shared          # rules, scoring, validation
cargo test -p server-game           # HTTP-level integration against the real router
cargo test -p tile-lite-elite-ui    # move composer, seat presets
cargo test -p engine-core           # engine
```

**Checking a bundled asset in production** (the owner): `asset!` puts a
content-hashed name in the wasm, so find that name and check it, expecting the
asset's content type rather than `text/html`:

```bash
wasm=$(curl -s https://tileliteelite.com/ | grep -o '/assets/[^"]*\.wasm' | head -1)
curl -s "https://tileliteelite.com$wasm" | strings -a | grep -o '<name>-[0-9a-f]*\.<ext>'
```

A bare asset path answers 200 whether the asset exists or not, because
Caddy's single-page-app fallback serves `index.html`. `document::Link`
elements are injected after the wasm boots, so they are absent from the HTML
`curl` returns.

## 5 When a release step fails

| Symptom | Cause | Fix |
| --- | --- | --- |
| `deploy.sh` refuses: the run "concluded 'cancelled'" | a newer push superseded the run ([4.3.7 §3.2](4.3.7-how-testing-and-release-work.md#32-what-github-does-on-its-own)) | `gh run rerun <id>`, then deploy again |
| `deploy.sh` refuses at the `ci` gate: the run is red, or `e2e` is missing or skipped | a test failed, or the run is for an event that does not run `e2e` | fix on the branch and start again from 4.3.3 §1.1; for a missing `e2e`, name the right run ([4.3.7 §5.3](4.3.7-how-testing-and-release-work.md#53-gating-on-a-particular-run)) |
| `deploy.sh` refuses: preview runs another commit, or is not running | preview was not deployed from this commit | `deploy-preview.sh`, then 4.3.3 §1.4 |
| `deploy.sh` refuses: rehearsal runs another commit, or is unreachable | rehearsal was not deployed from this commit | `deploy-rehearsal.sh [<ref>]` |
| `deploy.sh` refuses: the production database is ahead of the build | the build predates a migration the database has applied | §2 |
| `deploy.sh` refuses: "is a patch release, but its milestone carries functional change" | the version is a patch over the newest `prod-*` tag and the milestone holds a `functional` issue. No variable overrides it. | Raise the version to a minor ([4.3.3 §1.2.4](4.3.3-testing-ci-and-release.md#124-set-the-version-for-a-functional-release), which says how once the branch is on `main`), or correct the issue's `Type of change` if it is wrong. For a rollback, see [§1](#1-roll-back-production). For an emergency, [§3](#3-ship-an-emergency-change) step 5. |
| `deploy.sh` stops at the milestone prompt | an issue has no commit claiming it, or ships under a placeholder milestone | answer at the terminal, or move the issue out of the milestone, then run again |
| `deploy.sh` refuses: "Not a terminal, so this cannot be confirmed" or "no terminal to confirm at" | a prompt (unmerged tooling, the milestone or an emergency's scope) has nobody to answer it | run it from a terminal; merge the tooling to `main` |
| `deploy-preview.sh` refuses: preview's database is ahead of the ref | the preview volume outlived a migration from another branch | `deploy-preview.sh reset`, then again |
| `git merge --ff-only` refuses | `main` moved after 4.3.3 §1.9 step 1 | the recovery in [4.3.3 §1.9](4.3.3-testing-ci-and-release.md#19-merge-a-branch-into-main) |
| the `stamp` job is red on a rebased project branch | production deployed since the branch was cut, and the rebase left each subject one version behind its tree | Repeat 4.3.3 §1.9 step 1: the `--exec` re-stamps every commit and the push follows. Then 4.3.3 §1.2's CI check and, for a release, 4.3.3 §1.9 step 2. |
| `merge-to-release.sh` refuses a pull request that changes no image file | the pull request's run skips `e2e`, which the script requires | retarget it with `gh pr edit <n> --base main` and land it at 4.3.3 §1.9; the release branch takes it with the next `git merge origin/main` (4.3.3 §1.8) |
| `deploy.sh` rolled back by itself | a migration or the smoke test failed | read the log (4.3.3 §1.6), fix and ship again |
| "THE ROLLBACK ALSO FAILED" | the automatic rollback failed too | `rollback.sh` with the snapshot the output names (§2) |
| `deploy.sh` exits `3` | production runs the new version and a recording step failed | run each remedy the output names |
| the `stamp` job is red on a Dependabot pull request | `dependabot.yml` fixes the prefix at `app 0.0.0 api 0.0`, which is not the tree's versions | reword the commit subject to the tree's stamp on the pull request's branch before merging |
| the `Docs` workflow fails: "No review heading" | the pull request body has no heading starting with *Review* | add `## Review` with the checklist, or a sentence saying none is needed |
| a red `check` job | fmt, clippy, a test, the wasm build or `check-docs.sh` failed | run the same command locally ([4.3.7 §2](4.3.7-how-testing-and-release-work.md#2-running-tests)), fix and push |
