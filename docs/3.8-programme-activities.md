# 3.8 Programme Activities

**The activities that keep the programme running, and never finish.** Every
container elsewhere in this document set is a thing that changes and then
stops: a requirement becomes a project, a project delivers, a delivery closes.
Sweeping the board, triaging, producing the capacity plan — none of these
close, and until now none had a home. Raised by the owner, 2026-09-22:

> I think we are missing a mechanism for bau programme activities... even that
> process involves sweeping the board, raising a new requirement etc which
> fall outside of implementing a requirement or a project.

The gap has a standard name. ITIL 4 groups this kind of ongoing responsibility
as **practices**, and the owner's own prior art called the same idea **element
ownership** — what owning a system costs on an ongoing basis, as against the
projects that change it. See #407.

## The register

**One row per activity.** `frequency` is how often it is owed, in days.
`last actioned` is not stored here — it is derived from
[`programme-activity-log.csv`](programme-activity-log.csv), the most recent
date logged against the activity's `id`. Keeping it out of this table is
deliberate: a frequency and a last-done date are different kinds of fact, one
about the programme and one about what happened, and this document is the
first kind. `scripts/board-practices.py` reads both and joins them.

**The log is never trimmed.** Owner, 2026-09-22: *"The question is whether we
need a history and how much."* The check only reads the latest row per
activity, so growth costs it nothing — at three activities and a row a week in
the busiest case, a year is under 200 rows regardless. What a full history
buys is the evidence a **continual improvement** review would need — whether a
cadence is actually being met, not just met on the day somebody looked — and
that is exactly what pruning would remove. `docs/4.9`'s delivery log is the
same shape for the same reason.

| id | activity | frequency (days) | owner | produces | ITIL practice |
| --- | --- | --- | --- | --- | --- |
| `capacity-plan` | Produce and review the capacity plan | 30 | Claude produces, owner reviews | a report in `docs/reports/capacity_plan/` | Capacity and performance management |
| `benchmark-run` | Run the engine timing benchmark on rehearsal and production | 30 | Claude | a row in `crates/server-game/examples/engine_timing_results.csv` per host | Capacity and performance management |
| `board-sweep` | Sweep the board and triage what needs it | 7 | Claude leads, owner joins | none — the board itself changes | Portfolio and project management |
| `weekly-digest` | Produce the weekly digest and review it: lessons, problems, initiatives and the measures themselves | 7 | Claude | a report in `docs/reports/weekly_digest/`, by `scripts/board-digest.py --write` | Continual improvement |
| `improvement-review` | Review the month's digests, the registers and the initiatives | 30 | owner, with Claude | the owner's box ticked on each of the month's reports | Continual improvement |

**`weekly-digest` is programme work, not a project's.** Owner, 2026-09-27:
*"This counts as programme bau work, reviewing the weekly report and making
improvements to the process."* It was first specified as an issue comment
on #382; it is a report file instead, under `CLAUDE.md`'s rule for reports the
programme produces on a cadence, so the series outlives the decision that
started it. Nothing schedules it: the two readers below say when it is due.

**`benchmark-run` is run by hand until #400 ships a scheduler.** Once
Capacity Planning's jobs move onto it, this row's `owner` changes and the
frequency may too — #291's design note records that as the open question.

## What has no row yet, and why that is recorded rather than hidden

Mapping the programme against ITIL's 34 practices (#407) found three with
nothing behind them at all:

| practice | state |
| --- | --- |
| **Continual improvement** | covered since 2026-09-27: the `weekly-digest` and `improvement-review` activities, the quality measures and the registers, below |
| **Service level management** | nothing — and #405 needs one to choose the peak's column |
| **Risk management** | nothing explicit |

**Not given invented cadences here.** A row in the table above is a commitment
somebody has to meet; inventing one to fill a gap would be worse than leaving
it visibly open, because it would look decided when it is not. Each is #407's
to design properly, with the owner, when it is taken up.

## Continual improvement

**The weekly digest is the measuring half of a loop, and Claude runs the
loop.** Owner, 2026-09-27: *"The purpose of these is to give an assessment of
how we are improving and creating initiatives to improve things. I want you to
be proactive there, since the point of this is to save my time."* It is
programme BAU, so no issue drives it: the `weekly-digest` activity above is its
cadence, and this section is its definition.

The loop is ITIL 4's continual improvement model: where are we (the measures),
where do we want to be, how do we get there (an initiative), did we get there
(next week's measures). When a measure moves the wrong way, Claude raises an
initiative without being asked. The owner reviews the digest.

### The quality measures

| area | measure | source | in the digest |
| --- | --- | --- | --- |
| bugs | raised, closed and open | the board | yes |
| bugs | why each happened, and the stage that caught it: review, CI, preview, rehearsal or production | a root-cause section filled in when a bug closes (ITIL problem management) | to build |
| code, application and tooling | a rule decided in more than one place | a duplication scanner over Rust, Python and bash | to build |
| code, application and tooling | complexity per function, and new lint warnings | clippy's cognitive complexity, radon, shellcheck | to build |
| code, application and tooling | how much of the code the tests exercise | cargo llvm-cov, coverage.py | to build |
| process | not following it: board-check findings, CI red on `main`, hooks bypassed, emergency deploys | board-check.py, CI and commit history | to build |
| documentation | information in the wrong place, or the same text in two documents | the placement check, and the duplication scanner over markdown | to build |
| documentation | unnecessary detail: describing what we do not do, justification the reader does not need | Claude's review of the week's changed sections, counting what was found and removed | to build |
| the owner's time | his input on `tooling` and `documentation` issues and pull requests: comments, answers, ticked boxes | the board and GitHub's comment history | to build |

**A measure is a baseline and a trend first**, and becomes a threshold only
once a normal week is known. A measure that costs the owner more time than it
saves is dropped.

### The continual improvement register

ITIL's name for the list of initiatives. An initiative is BAU or a project, as
the table after this one decides.

| id | initiative | measure it moves | state | raised |
| --- | --- | --- | --- | --- |
| `CI-1` | the tooling's tests on the standard runners, bats and unittest | tests that pass with their target broken: five found while moving | done 2026-09-27 | 2026-09-26 |
| `CI-2` | each rule decided once, in the Python model | a rule decided in more than one place: #421's analysis table | in progress, #421 R3 | 2026-09-26 |
| `CI-3` | the digest's own measures and reviews: process conformance, the owner's time, documentation placement and detail, lessons, problems and initiatives | those rows above | in progress as BAU, for the digest of 2026-10-04 | 2026-09-27 |
| `CI-4` | the measures needing new tools, and bug root causes | the remaining *to build* rows | a project, #425, at Scope | 2026-09-27 |
| `CI-5` | every check says how many things it examined, and treats none as not run rather than as a pass | `P-3`'s occurrences | a project, #426, at Scope: it changes how gates report | 2026-09-27 |

**BAU is its own triage, so it raises projects, not requirements.** Owner,
2026-09-27: *"bau can update its own documents without an issue"*, and *"I
don't think bau will typically be raising requirement issues, because it is
effectively triaging requirements itself."* An initiative is done as BAU, with
no issue, its row here as its record and its commits carrying the trailers
`Activity: weekly-digest` and `Initiative: <id>`; or it is a project, which its
row names. Which, by type of change (owner: *"suggest rules based on the type of
change. We don't really have a concept of budget, or even of effort"*):

| type of change | done as BAU | a project |
| --- | --- | --- |
| `documentation` | BAU's own documents (this one, the reports, the log); correcting misplaced, duplicated or unnecessary text in any document | none: a new or changed rule in a process document is the owner's decision, and BAU applies it once made |
| `tooling` | changing an existing script, check, test or hook | a new tool or dependency; a new or changed gate on what reaches production |
| `bug` | in the tooling | in the application: it ships in a release |
| `functional`, `cosmetic`, `non-functional` | never | always: it reaches players |

**An initiative that needs regular progress is also a reason for a project**, so
it is progressed on the board rather than only mentioned each week (owner,
2026-09-27).

### Reviewing it

| who | how often | what |
| --- | --- | --- |
| Claude | weekly, when the digest is written, and more often while an initiative is running | the week's lessons, notes and measures for new problems and initiatives, updating both registers; and whether each section and measure is still earning its place: one that led to no action in four weeks is dropped, and the digest says so |
| the owner | whenever he wants, and officially monthly, the `improvement-review` activity | the month's digests; he says when a review is done and Claude ticks his box and logs it, so no review means editing a file (owner, 2026-09-27). A report is fixed once his review has covered it, and may be regenerated until then |

**Every lesson and note ends with a conclusion**, decided at the weekly
review (owner, 2026-09-27: *"Does it lead to an initiative. Are we going to
monitor it. Have we tweaked the process. Have we decided to take no action."*).
These are the usual ones, and not the only ones (owner: *"that list may not be
comprehensive"*); any other is stated with what it rests on:

| conclusion | says |
| --- | --- |
| initiative | which `CI-` row |
| monitor | which `P-` row or measure |
| process changed | what changed, and where |
| no action | why |

The digest leaves each one to decide, and Claude's weekly review is not done
while any is.

Each report ends with a box for each review. **Notes between digests** go in the
next week's report, which starts as a draft holding only a *Notes* section as
soon as the current one is written. Either of us adds to it during the week, and
writing the report keeps the notes and fills in the rest (owner: *"a draft of
next weeks, or an addendum that remains editable for a week"*).

## Reading the register

```bash
scripts/board-practices.py          # every activity, its frequency and when it was last done
scripts/board-practices.py --json   # the same, for a workflow to consume
```

Overdue means `today − last actioned > frequency`. An activity never logged is
overdue from the day it enters this table — the log has nothing to say it was
ever done, and *never done* and *not yet due* must not read alike.

## Two readers, not one channel

Owner, 2026-09-22: *"Ideally it is something that triggers both of us... there
could be two triggers reading the same information."*

Both read this register and the log; neither delivers to the other.

| reader | fires | for |
| --- | --- | --- |
| the session-start hook | every session | Claude, who cannot be woken and does not need to be |
| a scheduled GitHub Actions workflow | weekly | the owner, during an absence — the one gap the session-start report and `board-actions.py` leave |

The workflow is [`.github/workflows/programme-activities.yml`](../.github/workflows/programme-activities.yml)
and opens or updates a standing issue by title, the same shape
`advisories.yml` already uses for dependency findings.

## Why a log and not a date derived from an artefact

An earlier design derived *due* from the age of the newest file an activity
produces. The owner rejected it:

> Deriving actions from the presence or absence of a document seems fragile to
> me. I think we need to document the activities we do and how often and have
> a record of the activities we have done, or the last date each one was done.

**The decisive reason is not fragility, it is coverage.** `board-sweep`
produces no artefact at all, so an artefact-age rule could never have covered
it while looking like a general answer. The log records the *performance*,
which every activity has whether or not it leaves a file behind.
