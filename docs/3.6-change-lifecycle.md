# The change lifecycle: from an issue raised to production

The change lifecycle is the process by which the programme implements changes.  The main vehicle of change is the 'project' which has a well defined gated process and is designed to ensure changes to the application are of high quality and low risk.  Small changes to documentation and tooling can follow a pre-approved route and be made without a project.

Typically a change starts as a requirement.  After analysis a requirement may be incorporated into a project, at which point the requirement is closed and scoping becomes the job of the project.  It is also possible to a raise project without first having a requirement, when it is clear that a project will be needed.

This document covers the process from raising a requirement to project closedown after the change is made.  It focusses on the analysis and approval steps rather than on the technical tooling and environments.

## What the process is for

To spend the owner's time on game functionality and engine logic rather than
on process, non-functional work and bugs. So a rule is judged by whether it
saves his attention or spends it.

It is carried by four mechanisms, cheapest first:

| | | |
| --- | --- | --- |
| **hooks** | `.githooks/pre-commit`, `commit-msg` | refuse at the moment of the mistake |
| **checks** | `verify.sh`, `check-docs.sh`, `board-check.py` and the rest | report, and leave the judgement to a person |
| **gates** | `deploy.sh`'s refusals | stop a change that would be costly to undo |
| **skills** | `.claude/skills/`: `triage`, `raise-project`, `change-a-document` | carry the shape of a task, so it is done the same way each time |

A rule held only in a document, for a person to remember, is the weakest form,
and the others exist to replace it. Who decides what is in
[3.7](3.7-workstreams.md#who-decides-within-a-workstream).

Its sibling, [3.3 Testing, CI & Release](3.3-testing-ci-and-release.md), holds
the machinery: the environments, CI, the deploy script, rollback and the
runbook. This document holds the rules, in three parts:

| | |
| --- | --- |
| **[1 The flow](#1-the-flow-how-a-change-reaches-production)** | the terms, the stages, and how a release is shaped |
| **[2 The rules](#2-the-rules)** | one subsection per rule |

## 1 The flow: how a change reaches production

**Key terms used in the process:**

| term | what it is | defined in |
| --- | --- | --- |
| **programme** | the application *and everything we maintain to keep it going* — production, the dev, preview and rehearsal environments, the documents, the process | here |
| **workstream** | a capability within the programme, which might be a functional or technical component of the application, or a service such as Capacity Planning | [3.7](3.7-workstreams.md) |
| **artefact** | Anything maintained by the programme, including all files in the repository as well as environments, configuration settings, etc.  Artefacts are owned by workstreams and associated with a route. | [4.8](4.8-artefacts.md#what-counts-as-an-artefact) |
| **route** | The route by which a change is delivered to its users: a Release of the application image to production, a change of files in the Repository, or Other - changing a test environment, configuring the VM infrastructure, etc. | [§2.15](#route) |
| **project** | a change delivery vehicle for a bounded piece of work with fixed scope. Projects can be a small cosmetic change, or an overhaul of the design | [§2.11](#211-what-a-project-is) |
| **work package** | A project's work is split into one or more work packages. Work packages deliver into the project and are planned as black boxes. | here |
| **delivery** | Delivering changed artefacts by a route.  A delivery can include changes from many projects, and a project can have many deliveries. | `CLAUDE.md` |
| **release** | A delivery which is a release of the application image into production, so via the Release route. Each release changes the application semver.  | `CLAUDE.md` |

**Workstreams definitions are owned by [3.7](3.7-workstreams.md)**.

**The flow, in three stages.**

**1 · The project branch is where everything happens** — code, documents,
everything the project touches, until it is live.

**2 · The release branch is made by merging, and never edited.** A defect found
while testing is fixed on the project branch and merged in again, because a fix
made in the release branch exists nowhere else. Dropping a project from a release
means recreating the branch from the others.

**3 · `main` receives a proven branch, and a release ships from `main`.** They
are two acts: a branch merges once it is proven, and a release ships whatever
has accumulated on `main`, immediately or later.

*Stage 2 applies where a release must stabilise while `main` moves on. For a
single proven delivery the project branch fast-forwards `main` directly.*

### One round of preview and rehearsal, or two?

**Two only when the merge changes the tree.** The rule underneath is *test the
artefact you will ship*, and a second round exists to catch a merge that made
something new — so when there is nothing new, it proves nothing.

| | |
| --- | --- |
| **`main` has moved**, and the merge combines work | **two rounds.** The combination has never existed before and is what ships |
| **a fast-forward** — the branch already contains `main` | **one round.** The tested commit and the shipped commit are the same object |

**Use `--ff-only` where it is available**, in place of the usual written merge
commit: a merge commit changes the sha, and the commit tested stops being the
commit shipped. The branch's own messages carry the story.

**Preview from the branch before merging is still worth it**, and is not part of
either round: it is a cheap look for whatever would otherwise reach `main`, and
it costs one command.

**The trade, stated because it is real**: a problem found in rehearsal after
merging means fixing on the branch, re-merging and re-testing. Accepted because
preview from the branch has already exercised the same tree.

### Why the questions stop being asked

**The image is built once per commit and promoted**, not rebuilt for each
environment, so *which commit was tested?* has an answer rather than a
procedure.

**Where a project delivers by more than one route**, the routes are ordered: a
step applied by hand usually assumes the release carrying it is already out.

### 1.0 The shape of a delivery

Three questions decide it:

| question | decides |
| --- | --- |
| is the old version needed while the work is in progress? | if so, the change is held on a branch, which owes a pull request, a milestone and a delivery-log row |
| does it reach the image? | `Route` ([§2.15](#route)); a Production Release always takes a branch |
| how many work packages ship together? | their shared milestone |

| shape | `Route` | milestone | branch | pull request | delivery log |
| --- | --- | --- | --- | --- | --- |
| straight to `main` | Repository Change, Other | `pre-approved`, or none | none | none | no row |
| repository change with a branch | Repository Change | production's version plus a letter | one | yes | a row |
| single-delivery release | Production Release | a semver | one | yes | a row |
| release branch | Production Release | a semver | `release/X.Y.Z`, and one per delivery | one each | a row |

**A change straight to `main` has no milestone** because it is not a point in
time; its record is the commit, citing what it serves. `pre-approved` marks
approval, not a position in the sequence.

**A release is never straight to `main`.** An unproven release commit there
blocks every other release until it is proven or removed (§2.2).

**Proven and unshipped is the normal state** (D55). A branch merges to `main`
once preview, user testing and rehearsal have passed against its tip; a release
ships whatever has accumulated on `main`, then or later.

**A release branch is for a release that must stabilise while `main` moves on**,
or for several projects proven as a set before any lands. It is made by merging
project branches and never edited, so it can be rebuilt from a different subset
to drop one. Every project branch comes off `main`.

**A release may group unrelated changes**, because they are ready. A large
change carries what it affects and nothing unrelated, so a failure has one
candidate.

**An emergency is cut from the last `prod-*` tag, never from `main`**, which
would ship every unreleased change beside the fix ([3.3 §1.13](3.3-testing-ci-and-release.md#113-ship-an-emergency-change)).

Which app version a release takes is [3.3 §2.4](3.3-testing-ci-and-release.md#24-version-numbers-which-to-bump-and-when).
The steps each shape runs are [3.3 §1](3.3-testing-ci-and-release.md#which-steps-each-shape-runs).

### 1.1 What a milestone says

A milestone says how a change reaches its users.

| milestone | what it says |
| --- | --- |
| `no-release` | provisional: the change needs no new application version |
| `patch`, `minor`, `major` | provisional: the **minimum** the version must move by |
| `pre-approved` | the change goes directly to `main`, with no delivery |
| `0.7.2`, `1.0.0` | the release that carries it |
| `0.7.1a`, `0.7.1b` | a delivery that ships no image, after that release; see below |

**Every delivery made at one point in time has a milestone and a row in
[the delivery log](4.9-delivery-log.md)**, as one act: the semver for a
release, otherwise production's current version with a letter.

**What was done decides, not what was permitted.** A project that took a branch
and a pull request has made a delivery, and takes a milestone and a row
whatever its type. A delivery need not take a branch: a change on a host is a
delivery with neither.

**Documentation and tooling projects that go straight to `main` take
`pre-approved`**: no delivery, no row, and the commits and the closed issue are
the record. A tooling change that needs a branch, because a half-finished
version on `main` would block other deliveries, takes one and is a delivery.

**A requirement carries no milestone**, except `pre-approved` when its change is
made directly without raising a project. So a requirement's milestone means
exactly that, and its absence means it is waiting, folded or closed unbuilt.

**Provisional values move**, as it becomes clear how the work reaches `main`:

| from | to | when |
| --- | --- | --- |
| `no-release`, `patch`, `minor`, `major` | a semver | it ships in a release |
| `no-release` | a letter | it delivers without an image |
| `no-release` | `pre-approved` | it goes straight to `main` |

**`no-release` is resolved before the issue closes**: a closed issue still
carrying it has lost the record of how its change reached `main`.
`board-check.py` reports one.

**`pre-approved` is closed by hand**: no deploy settles it. It covers however
many pushes the work takes, where a letter milestone names one delivery.

#### A delivery that ships no application code

A host change, a console change or a drill reaches production without changing
the build, so no version names it. It takes **production's current version
plus a letter**: `0.7.0a`, then `0.7.0b`. Production's, because the version in
`Cargo.toml` leads production by one and says what is intended, not what was
running when the delivery landed.

**`0.7.0a`, never `0.7.0-a`**: the hyphenated form is a SemVer prerelease,
which sorts *before* its release. And since `deploy.sh` reads its milestone
from `Cargo.toml`, which holds only real SemVer, a lettered milestone is never
matched or closed by a deploy. It is closed by hand.

Only a project's deliveries get an identifier; a pre-approved change straight to
`main` takes neither a letter nor a row ([4.9](4.9-delivery-log.md)).

#### A delivery can be shared across projects

Two projects ready at once may ship in one delivery, so the release's cost is
paid once. It gets one row in [4.9](4.9-delivery-log.md), naming both, and
neither project skips its own test approach or post-deployment checks.
Dropping one project from a shared delivery late means unpicking the release
branch rather than rebuilding it without that project.

#### Answering a post-deployment check

**A check says how it is done**, so anybody can run it: *"run this script and
look for this line"*, not *"the bot does not play the plural"*. It is answered
one of three ways, with a note on what happened:

| | |
| --- | --- |
| **passed** | it was done, and the benefit is there |
| **cannot be tested** | there is no way to observe it in production. Say what evidence stands instead, and where it was taken |
| **failed** | it was done, and the benefit is not there |

**Where a check cannot be run**, two earlier facts stand in: the change was
tested outside production by the project's test approach, and it was in the
build when the build was made ([4.9](4.9-delivery-log.md) and the build
manifest).

#### Milestones, deliveries, and which of them get an issue

| | is | carries |
| --- | --- | --- |
| a **delivery** | a change reaching its users. **Every change has one** | nothing of its own: it is an event, not an object |
| a **work package** | a unit of work: a `Project` whose parent is this one | a milestone, where its delivery is a point in time |
| a **milestone** | the marker on a delivery made at one moment, and its place in the sequence. Packages sharing one go live together | no issue of its own |
| the **parent** | the owner of the requirements, the design and the documents | no milestone and no `Route`: it has no delivery role |

**A parent's milestone or `Route`, if set, is ignored.** A parent may carry a
target release. `deploy.sh` skips a parent when it settles a milestone, and
`board-check.py` reports a `Route` on one. Anything else reading these fields
owes the same exception, or a parent would be told it was released.

#### Impacted artefacts: one table per delivery, three rows

A delivery is a mixture of routes, so each has a table with a row per route:

| route | in this delivery | artefacts | branch | PR |
| --- | --- | --- | --- | --- |
| **Production Release** | yes/no | | **always yes** | **always yes** |
| **Other** | yes/no | | | |
| **Repository Change** | yes/no | | | |

- **A `no` row stays**, with dashes: an absent row and an empty one read the
  same, and only one means *nothing here*.
- **The Production Release row decides the shape.** Yes forces a branch and a
  pull request for the whole delivery, because `main` is what gets deployed,
  and the other rows then ride that branch too, documentation included. Without
  it, a row takes a branch only where the old version is needed while the work
  is in progress, and a document-only change never takes one.
- **The branch and PR columns answer yes or no first**, then say which: `yes —
  rides the same branch`, `yes — rides #341`.
- **The work package has its own table, and the parent repeats each package's**
  under its list of deliveries: the package is built from, the parent is
  planned from.
- **The parent lists what it delivers**, each row naming the work packages that
  share a milestone, or saying the change went straight to `main`. A milestone
  has no issue, so this list is what makes a grouping findable.

#### The model, and the four cases that follow from it

**Every delivery is a work package**, with no exceptions. The sub-project issue
that carries a work package may be saved where nothing needs it: the test is
whether a second `Phase` is needed.

| | sub-project | why |
| --- | --- | --- |
| one delivery | **saved** | the parent's fields answer for it |
| two deliveries, one milestone between them | **needed** for each | which packages ship together is read off the milestone |
| two deliveries, one straight to `main` | **needed** for each | a delivery with no milestone still has a phase, and the parent cannot hold two |

**A work package is at most one delivery, and so one route.** A delivery may
carry several packages; a package never spans two. Work that takes two routes,
or reaches its users at two points in time, is two packages: building a tool
and running it are two.

#### Four cases, which is what follows

| | work packages | how they go live | sub-projects | the parent lists |
| --- | --- | --- | --- | --- |
| **A** | one | one delivery | **none**: the parent is the work package and carries the milestone | one delivery |
| **B** | two | together | two, **the same** milestone | one delivery, carrying both |
| **C** | two | separately | two, **different** milestones | two deliveries, one work package each |
| **D** | three, two together | mixed | three | two deliveries, one carrying two packages, one carrying one |

Case A is the common shape, and needs no sub-issue. The delivery is not the
sub-project, because in cases B and D one delivery carries two packages.

#### Naming

| | form |
| --- | --- |
| a parent | `#N MAIN PROJECT: <what it is>` |
| a work package, alone in its delivery | `#N WP A Del 1 of 2: <what it delivers>` |
| a work package sharing its delivery | `#N WP A Del 1 of 2, pt 1 of 2: <what it delivers>` |
| a work package whose deliveries are not yet decided | `#N WP A: <what it delivers>` |

| | |
| --- | --- |
| `WP A` | **which package**, lettered so it never reads as a delivery number |
| `Del 1 of 2` | **which delivery carries it**, and how many the project has |
| `pt 1 of 2` | **its share of that delivery**, only where the delivery carries more than one package |

The parent's number is repeated in each child, so a listing sorted by title
groups the family. **The counts go stale and are kept anyway**: a title saying
`Del 1 of 2` is wrong loudly, where `Del 1` is silently incomplete. They are
derivable from the packages' milestones, and nothing checks them yet.

| case | the titles |
| --- | --- |
| **A** | no sub-project |
| **B** | `WP A Del 1 of 1, pt 1 of 2` · `WP B Del 1 of 1, pt 2 of 2` |
| **C** | `WP A Del 1 of 2` · `WP B Del 2 of 2` |
| **D** | `WP A Del 1 of 2, pt 1 of 2` · `WP B Del 1 of 2, pt 2 of 2` · `WP C Del 2 of 2` |

**The delivery part waits for the design**: until deliveries are decided, a
package is titled `#N WP A:`. `board-check.py` asks for a Deliveries table only
from `Deployment` onward.

#### Why the parent carries no delivery fields

One `Phase`, `Milestone` and `Route` cannot answer for two deliveries, and
post-deployment checks are answered per delivery. So each delivery's work
package carries its own.

#### What each owns

| | parent | work package |
| --- | --- | --- |
| requirements, design, the documents | **owns** | links |
| the delivery list | **owns** | is one row of it |
| impacted artefacts, test approach | — | **its own** |
| post-deployment checks | — | **its own** |
| milestone | none | **its own** |

**One documents folder, named for the parent** (see *Which document goes
where*). A work package's design is a section of the parent's document or a
file beside it, never a folder of its own.

#### The parent's lifecycle is shorter

`Scope`, the queue, `Design and Test Approach`, **and then it stops**: oversight
is a design role, so the parent never takes the phases that describe a
delivery. It may still reach `Post-deployment`, for a requirement no single
delivery satisfies, and `Project Closedown`, to close.

**A work package may delegate its lessons learnt to the parent**, saying
`Delegated to #<parent>`, so `board-check.py` reads an answer rather than an
omission. The form is
[`docs/templates/post-deployment-review.md`](templates/post-deployment-review.md),
the After Action Review's four questions, where every finding ends as an issue
or is explicitly dropped.

**A milestone set on a parent is ignored by the tooling**: `settle_milestone`
skips a project with `Project` children, since settling a milestone closes
every open issue in it and would close a parent with deliveries still to come.

#### What counts as a delivery

**A delivery to a non-production environment is a delivery in full**: it
reaches its users and delivers a benefit, and consumes no version. The same
change delivered to rehearsal and then to production is two deliveries, each
with its own benefit and check.

**A repository change's first use against production is a check, not a
delivery.** The test is whether an artefact reaches production:

| | reaches production | so the production run is |
| --- | --- | --- |
| a change to `deploy.sh`, which runs from the development machine | nothing | a **post-deployment check**: it is live at merge |
| a change to the `Caddyfile`, which is built into the image | the file itself | a **delivery**, with its milestone and log row |

**A delivery's runbook lives in one place**: its work package where it has one,
otherwise the parent's delivery table. Never both.

**What needs a release is the artefact, not the audience.** Documents and
scripts are built into nothing and are live when they land on `main`. Client
and server code is in the image whether or not its effect is visible, and can
break production while its feature is development-only. So the question is
**"is this built into what we deploy?"**

**`no-release` denies a release, not a delivery.** A release is a new
application version; a delivery is any changed artefact reaching its users. A
`no-release` change is delivered when it reaches `origin/main`
([2.15](#215-classifying-a-change)).

#### Scheduling a release

**The placeholder milestones are queues**: `patch` for a change that can ship on
its own, `minor` for one that rides a grouped release, `major` for one that
ships alone. **Scheduling is moving an issue from its queue to a version.**
`no-release` is never scheduled: nothing it holds waits for a deploy.

- **`patch` means a change *can* go out alone, not that it must.** The default
  is to batch, so a release is looked at once, not four times. And it must be a
  change that can be done well quickly.
- **One larger change per release**, so that when something goes wrong it can
  be understood on its own.
- **A release takes the version of the highest thing in it**: add one
  `functional` change to four patches and it is not a patch.
- **A slower queue never blocks a faster one**, which is the point of having
  three.
- **Scope closes when it is set**: what is in a release is decided when the
  version is chosen.

### 1.2 Keeping a release branch current

`main` is merged into a release branch after every release and when the
release's scope closes, so the release does not revert a fix already live. The
version line conflicts each time, and the branch's version is kept. Commands:
[3.3 §1.8](3.3-testing-ci-and-release.md#18-keep-a-release-branch-current).

### 1.3 Releasing a release branch: merge first, and fast-forward

The branch tip is proven, then `main` fast-forwards to it, so the commit tested
is the commit shipped. Any merge commit is a new commit and takes its own lap of
CI, preview and rehearsal. Commands:
[3.3 §1.9](3.3-testing-ci-and-release.md#19-merge-a-branch-into-main).

### 1.4 Delete the branch once its change is live

Live means merged into whatever it ships from, not deployed. `verify.sh`
reports a branch left behind. Commands:
[3.3 §1.10](3.3-testing-ci-and-release.md#110-delete-a-branch-once-its-change-is-live).

## 2 The rules

[Part 1](#1-the-flow-how-a-change-reaches-production) is the flow. These are the
rules that govern it, one subsection each.

**A project issue carries eight headings**, each holding text or a link to a
document, never absent and never empty ([2.11](#211-what-a-project-is)):

| heading | |
| --- | --- |
| **requirements** | what must be true when this is done |
| **design** | how it works now, then how it will be done. The as-is first: a change to a script cannot be judged without it |
| **impacted artefacts** | what it touches, each marked **new**, **modified** or **reuse**, with why |
| **test approach** | environment, tools, and what is measured against what criteria — as **two task lists**, functional tests on Preview and technical tests on Rehearsal, which `verify.sh` counts |
| **non-functional design** | capacity, failure, limits and timeouts, secrets and access — four questions, each answerable *none, because…* |
| **dependencies and related work** | what it waits on, **what needs it**, what it overlaps, and what it anticipates — one line each, with the reason |
| **deliveries** | a **runbook** per delivery: the steps in order, the route each takes, and — filled in afterwards — which version carried it, and when |
| **post-deployment checks** | one check per requirement, saying **how** it is done. Answered **passed**, **cannot be tested**, or **failed** |

| | rule |
| --- | --- |
| [merging](#21-when-to-merge-and-what-to-hold-back) | Testing does not require merging. A release-route change merges into **`main`** once its user and technical testing have passed, and `main` accumulates the next release. A release branch is for a release that must stabilise while `main` moves on. |
| [branching](#22-when-to-branch-and-what-pre-approved-means) | A branch exists to hold a change back. No branch means the change goes live immediately, which is what **pre-approved** means. A project either has a branch or it does not — if it has one, *everything* it touches goes there, documentation included. |
| [living documents](#23-living-documents-and-the-standing-issue-that-carries-them) | A document that is never finished gets a **standing issue**, which closes when its *subject* concludes rather than when an edit lands. It lives wherever its issue's changes live — `main`, or the project's branch. |
| [where a document lives](#24-where-a-document-lives-about-the-work-or-a-product-of-it) | A document lives wherever its issue's changes live. Testing documents belong to the release; design and test documents to the project, in its folder. |
| [tracking](#25-tracking-a-change-to-production) | `Refs #N` in the commit — **except where the change never leaves the repository, where `Closes #N` is correct**, because nothing else will ever close it. |
| [types](#26-type-of-change) | Every **project** carries one `Type of change`, and it is a field — not a `Decision`, which ships nothing, and not a `PullRequest`, which inherits from the issue it serves. `non-functional` classifies the **objective** of optimisation and reliability work, so a functional side-benefit does not contradict it. |
| [evidence](#27-evidence-follows-what-the-change-does) | Evidence follows what the change **does**, not the label it carries. |
| [closing](#28-closing-an-issue) | Use `stateReason`, not a label. |
| [documentation](#29-documentation-is-owed-by-every-type-not-just-its-own) | Every type owes documentation; the `documentation` label means the *whole* change is documentation. |
| [splitting](#210-requirements-split-projects-gather) | Requirements split into parts; projects gather them. An issue touching both tooling and the app is two issues. |
| [gate or check](#216-a-gate-refuses-a-check-reports) | A **gate** refuses and the work stops. A **check** reports and a person decides. |
| [classifying](#215-classifying-a-change) | Three questions, three fields: **type** and **release** on the issue, **route** on the delivery. |
| [triage](#217-triage-what-happens-to-an-issue-when-it-is-raised) | Four outcomes for an issue that is not rejected: straight to `main`, a patch project, a project of its own, or folded into one. |
| [projects](#211-what-a-project-is) | Issues group into a **project**, which owns the requirements from that moment. The sources are **folded** and closed. |
| [branches](#212-a-branch-belongs-to-a-project) | **One branch per project**, and it is the only place edits happen until the project is live. |
| [runbooks](#214-the-delivery-runbook) | Each delivery has a runbook: the steps before, and which version carried them, when, afterwards. |
| [artefacts](#213-the-impacted-artefacts-and-why-they-are-listed-early) | List what a change touches as early as possible, even wrongly — it is how two projects discover they collide. |

**Preview is not a step towards production.** It is where you look at
something: `./scripts/deploy-preview.sh at <branch>` builds any ref with no
merge, so showing a change and standing up a release for user testing are
separate acts on the same environment.

### 2.1 When to merge, and what to hold back

Testing does not require merging. Merging is needed only to test changes
*together*:

| | asks |
| --- | --- |
| `deploy-preview.sh at <project-branch>` | does this one change work? |
| `deploy-preview.sh at <release-branch>` | does the release candidate hold together? |

**`main` is the accumulating next release.** A Production Release change merges
to `main` once its user and technical testing pass; the release ships whatever
has gathered there. A release branch is for a release that must stabilise
while `main` moves on: several projects landing together, or a release held
while other work continues.

**Two conditions, neither optional:**

| | |
| --- | --- |
| the checks are written **before** the merge | `### Technical tests — Rehearsal` answered, and the post-deployment checks stated |
| an emergency release is cut from the **last released tag**, not from `main` | otherwise an emergency ships every unreleased change on `main` with it; [3.3 §1.13](3.3-testing-ci-and-release.md#113-ship-an-emergency-change) |

**Changes merge when their testing has passed. Controversial ones are held
back**, where *controversial* means the change might change following review,
not that it is risky. Merging is the point of no easy return: before it,
removing a change is deleting a branch; after it, a revert.

**Merge by rebase and fast-forward, never a merge commit.** `deploy.sh` requires
preview to be running the exact commit being deployed, and a merge commit is
one preview has never run.

#### A problem found before the merge, and one found after

**Before the merge, fix it on the branch and test the branch again**, so a
defect in the implementation or in the requirement costs a commit and a retest,
and `main` never sees it.

**After the merge, either reopen the package or put the change in a later
one:**

| | what happens |
| --- | --- |
| reopen the package | a new branch off `main`, the package back to `Development`, the testing done again, merged again |
| a later package | the change goes in a package not yet merged, where it fits |

**What a merge does to the phase depends on the route.** A Production Release
package moves to `Deployment` and reaches `Post-deployment` only after the
deploy. A Repository Change package's merge is its deployment, so it moves
straight to `Post-deployment`. The post-merge hook makes both moves
(`scripts/board/merge.py`), including for a reopened package merged again.

### 2.2 When to branch, and what *pre-approved* means

**A branch exists to hold a change back**: branch only when the change cannot
go into `main` until the work is complete, because the old versions of the
documents or tooling are still needed in the meantime. Otherwise commit
straight to `main`. **A change that needs no branch is a pre-approved change**;
the two are the same test asked from opposite ends. It asks about the work, not
the change's size: a large change nothing depends on belongs on `main`, a
one-line change to a script people are running today does not.

#### A Production Release is not subject to that test

**A release always takes a branch, a pull request, a semver milestone and a
delivery-log row**, whether or not the old version is needed meanwhile.
`main` is what gets deployed, so an unproven release commit there blocks every
other release until it is proven or removed; and an image change is not cheap
to reverse, which is what pre-approval relies on.

### The standing pre-approval for process changes

**A process change agreed in discussion needs no project, no branch and no
separate review.** It goes straight to `main`, and any issue it answers is
closed by hand ([3.7](3.7-workstreams.md), under process definition).

**Pre-approved does not mean unreviewed**: the discussion before the change was
the review. That is safe exactly where a change is cheap to reverse, which is
why the only refusals in `.githooks/pre-commit` are about the image.

**It settles authorisation, not rigour.** A change to `deploy.sh` is
pre-approved and still owes a design and a test approach agreed before it is
built, and takes a branch where a half-finished version on `main` would block
every other delivery. **Size is not the test; blast radius is.**

**A view may be tweaked freely; what it reads may not.** A board view is a saved
filter. An issue type, a field, one of its values, a label or a milestone is
read by scripts matching the string literally, so renaming one is a code
change. [4.8](4.8-artefacts.md) lists which strings are read and by what.

### 2.2.1 Business-as-usual updates

**A routine update owes what its route owes, and nothing more**: dependency
bumps, base images, advisories, host packages, kernels. Size and who raised it
decide how much is written down, not what the change owes.

| update | route | what it owes |
| --- | --- | --- |
| Dependabot, GitHub Actions | `Repository Change` | its commit message |
| Dependabot, Docker base images | **`Production Release`** | its commit message; it ships with the next release |
| a crate bump, advisory or otherwise | **`Production Release`** | the same |
| host packages, the container runtime | **`Other`** | a work package, letter milestone and delivery-log row |
| a kernel, or a reboot to adopt one | **`Other`** | the same |

The `Dockerfile`, `Caddyfile` and `docker-compose.yml` reach the image, so a
change to one is a Production Release however small; `scripts/board/shipping.py`
decides the list.

**A `Production Release` update rides the next release and never justifies
one.** It lands on `main` as a pre-approved change and is proved by that
release's regression testing. **An `Other` update has no release to ride**, so
it supplies its own vehicle: a work package, a letter milestone and a row.

**Urgency is the exception**: an advisory that cannot wait is a release, and
takes a release's shape. And a host update that is a package upgrade and a
reboot is two deliveries and two work packages, since either can fail alone
and the record must say which.

### 2.3 Living documents, and the standing issue that carries them

**A document that is never finished gets a standing issue**, which closes when
its subject concludes rather than when an edit lands. A living document is
finished whenever it is accurate, so it belongs on `main`.

**A document-only change does not take a branch**: a document branch is never
urgent, so it lives long, `main` moves, the diff stops being reviewable, and
the review it existed for does not happen.

**Where a project has a branch, its technical documents go on it**, since one
change lives in one place. **Process documents do not**: they describe the
programme, not any project's code, and change on `main`, so no project and the
process depend on each other. `scripts/board/documents.py` holds the list, and
`.githooks/pre-commit` refuses one on a branch. `docs/1.6` is generated, and is
regenerated on a branch after the rebase that precedes its merge.

#### The documents live; the issues expire

**The numbered documents are the only thing kept current.** A `docs/N.N` file
answers what is true now; an issue answers what was argued and when, and once
it closes, that is all it answers.

So when something changes, change the document. Do not edit a closed issue to
agree with it, and do not cite one as the authority for a rule: a stale copy
still reads as authoritative. A single line added to a closed issue at the
moment it is superseded, pointing at what replaced it, is a record rather than
maintenance.

### 2.4 Where a document lives: about the work, or a product of it

**About the work**: a testing report, an impact assessment, a decision note. It
is true now, so it lives on `main` from the moment it exists, where it can be
read while the work it tracks is happening.

**A product of the work**: documentation the change delivers, such as a new
runbook or API reference for something being built. It is true only once the
change ships, so it lives on the branch and lands with the change.

**Which owns it:**

- **Testing documents belong to the release**, always, so there is one place to
  look.
- **Technical design documents belong to the issue that produced them**, which
  may be a parent, and then the note lives on `main` for the life of the
  workstream, visible to every work package's branch.
- **One document has one owner.** A document that seems to belong to several
  issues says those issues should have a parent that owns it.

#### Which document goes where

| document | folder |
| --- | --- |
| a project's design, impact, test approach | `docs/changes/workstreams/<workstream>/<issue>-<name>/` |
| a release's testing record | `docs/changes/<version>-user-testing.md` |
| a report the programme produces on a cadence | `docs/reports/<name>/TLE_<CODE>_<period>.md`, from [a template](templates/README.md) |

| | describes | changes when | superseded? |
| --- | --- | --- | --- |
| a numbered `docs/N.N` | the programme | the programme does | edited in place; there is one |
| a change document | one issue's design | that issue does | it expires with the issue |
| **a report** | what was true at a moment | never: a new one is written | **no**; the series is what carries the meaning |

**A report gets a folder**, because this month's does not replace last month's:
together they say whether a number is moving. It is named `TLE_<CODE>_<period>`
so the name means something once it has left the folder, and each series has a
template so its periods stay comparable. The capacity plan's is
[`docs/templates/capacity-plan.md`](templates/capacity-plan.md).

**A change folder is named for the parent project**, never for a version or a
work package, so one design is not scattered. A work package's design is a
section of the parent's document where it reads in place, or a file of its own
beside it where it is self-contained, such as a runbook or a schema. Either way
the parent links to it.

**A folder appears when its first document does**, never in anticipation.

### 2.5 Tracking a change to production

**Commits say `Refs #N`**, except where the change never leaves the repository,
where `Closes #N` is correct, because nothing else will close it.

**Examples use `#0` or `#NNN`**: GitHub links every `#N` it finds, so an
example with a real number attaches itself to that issue.

**A milestone is a shipping list, and the deploy settles everything in it.**
Move out what is not shipping before deploying. A project advances to
`Post-deployment`; anything else closes.

### 2.6 Type of change

**Every issue carries one `Type of change`.** It says what the change owes
before it can ship. The field is authoritative; this describes it.

| type | what it is | ships by |
| --- | --- | --- |
| `documentation` | documents | its route: usually Repository Change |
| `tooling` | scripts, CI, the machinery around the app | its route |
| `cosmetic` | a visual difference only: nothing behaves differently and nothing on the wire moves | Production Release, as a patch |
| `bug` | the app doing the wrong thing | Production Release, as a patch |
| `non-functional` | the app doing the same thing better: optimisation, reliability, capacity. It classifies the objective, so a functional side-benefit does not change it | Production Release |
| `functional` | the app doing something new or different | Production Release, and **not** as a patch |

**`documentation` and `tooling` do not change the app; the others do.** So a
bug fixed in `deploy.sh` is `tooling`.

**`functional` is read by `check-release-version.sh`**, which refuses a patch
release whose milestone carries one: the one place this field decides something
rather than describing it ([4.8](4.8-artefacts.md#what-the-tooling-reads-and-would-break-on)).

### 2.7 Evidence follows what the change does

**What a change owes is decided by what it can break, not what it is called.** A
tooling change that ships in the image, such as the admin CLI, takes the full
release path; a change that cannot reach production does not, whatever its
type.

### 2.7.1 A check that has to wait for a release

**Some post-deployment checks cannot be answered when the change ships**: one
comparing a release's image with the previous release's has nothing to compare
until the next.

**The `Release Check` label marks those.** `board/turn.py` shows the project as
waiting for the next release rather than as a review due, and `deploy.sh` names
every labelled issue after a production release. Answer them then, and take the
label off. It is a label, not a field, because it is temporary and binary.

### 2.8 Closing an issue

**Use `stateReason`, not a label**: `completed` for work done, `not planned` for
work that will not be. **`folded` is the one label kept**: a requirement
absorbed into a project closes as `completed` and carries it to say so.

**The triage queue is a requirement with no workstream**, not a label.

### 2.9 Documentation is owed by every type, not just its own

> A change is not done until the documentation it invalidated has been
> updated, **in the same commit**.

Never a follow-up issue: an API reference once declared a version five bumps
stale, because each change left its update for later.

A doc comment in `crates/**` rides the next release like any source edit;
anything under `docs/` ships nowhere.

### 2.10 Requirements split; projects gather

| | |
| --- | --- |
| a **requirement** | one thing, split as finely as it honestly divides |
| a **project** | as many requirements as one delivery carries well |

**A requirement becomes two** when it touches both tooling and the app, when it
will be two releases, or when it belongs to two workstreams. Two releases means
two changes even when the type is the same.

**A project may span workstreams** where that simplifies the delivery: two
requirements in one project are reviewed, branched, tested and shipped once. It
still carries **one** `Workstream`, the one where its content is defined
([3.7](3.7-workstreams.md)). A project that cannot say which is not one
project.

**Where one half generates requirements for the other, it goes first**, whether
they are one project or two.

#### Spanning two workstreams: split it, and do the end-to-end half first

| | belongs to |
| --- | --- |
| what the game does, what the server says, the DTOs that carry it | **application & game architecture** |
| how that reaches a person: which control, which screen, what a notification does | **client UI** |

**The end-to-end half goes first**: until the game decides what happens and what
it broadcasts, the UI requirement can only be guessed at. This is the common
case, since client UI is the layer over every other capability. A split is
needed only where the game's behaviour changes; UI logic alone is one
requirement.

**Deferred work is a second issue**, raised before the merge. A commit or comment
saying "left deliberately" with no issue beside it is the tell that it was not.

### 2.11 What a project is

**A project is a state an issue enters**, not a thing created up front. Issues
group into one, which owns their requirements from that moment. A project may
also be raised directly, with no requirement first, where its shape is already
clear. **One project or two** is decided by whether one design covers them.

**A requirement's issue is never rewritten into a project's**: its body is the
record of what was noticed, and a project's holds eight headings kept current.

#### The project owns the requirements, so its sources are folded

A source issue still live is a second place its requirements can change. **To
fold one**: copy its content into the project **first**, then close it as
`completed` with the `folded` label and a comment naming the project. Fold
before closing, or the requirement is lost; a folded issue can be reopened if it
turns out not to belong.

#### One project, one design

A project has one design, covering all its requirements and however many
deliveries they take.

#### Text or a link, decided per heading and driven by size

**Each heading holds its content or a link to a document, never both**, decided
per heading rather than per project. A small project holds everything as text;
a larger one links, and **keeps the body short**, because a body that links and
restates drifts from the document.

**The exception is the artefact names**, which stay in the issue even when a
design lists them: the design lives on the branch until the project is live,
and the issue is always visible ([2.13](#213-the-impacted-artefacts-and-why-they-are-listed-early)).
The per-artefact detail is not repeated.

**Headings, not paragraphs**, because an empty heading says nobody has decided
and a missing one says nobody asked, and a script can check which.

### 2.12 A branch belongs to a project

| | |
| --- | --- |
| **created** | when the project starts |
| **during** | **the only place its edits happen**: code, documents, everything |
| **merges out** | to `main` once its testing passes, or into a release branch where the release has one. More than once, if the project takes more than one delivery |
| **deleted** | when the project is **live** and closed |

**The one-place rule is about where a change is made**, not where content
exists: editing in two places produces two versions that each look current.

**A branch is deleted only when the project is live**, because a release branch
is rebuilt from project branches, and a deleted branch cannot be rebuilt from.

**Nothing is committed directly to a release branch**: a fix made there is lost
at the next rebuild. A defect found in preview goes to its project's branch.

**A project branch is kept current with `main`**, so a rebuild stays mechanical
rather than a conflict resolution nobody reviewed.

### 2.13 The impacted artefacts, and why they are listed early

A project has **deliveries**; each delivery has **artefacts**; each artefact has
a **route**, which follows from what the artefact is.

```text
project
  └── delivery            one act of putting change in front of its users
        └── artefact      what that act touches
              └── route   how it reaches them: derived, not written
```

**The list is kept per delivery**, because the runbook, a rollback and *"is it
delivered?"* each need one delivery's set, not the project's union. The union
still serves the collision test between two projects.

Every project lists what it touches, each marked **new** or **modified**: a
guess when raised, **accurate once the design is agreed**, including any test
tooling the test approach builds. **List it early even though it will be
wrong**: a wrong list naming the right file finds a collision as well as a
right one.

| an overlap between two projects means | so |
| --- | --- |
| they are the same work seen twice | one project |
| one needs the other's change first | sequence them, and say so |
| they touch different parts of one file | do it once, or accept a conflict resolved under pressure |

**An artefact is not only a file**: a project may touch a host file, a bucket,
an alarm and a GitHub label without changing any code.

**The table shows the route as a column**, though nobody decides it: a reader
should not have to derive it. A row whose route disagrees with its name is a
typo, not a decision.

#### Naming, so two lists can be compared

| kind | canonical name |
| --- | --- |
| in the repository | its path from the repository root |
| on a host | the host role, then the absolute path: `production:/etc/…` |
| a cloud resource | provider, type, and the provider's own name: `OCI bucket tile-lite-elite-backups` |
| a GitHub object | `github:label folded` · `github:ruleset main` |

A repository artefact is self-naming. Everything else is registered in
[4.8 Artefacts](4.8-artefacts.md). **Mark a provisional list provisional.**

#### A new artefact says whether it outlives the project, and what runs it

| | |
| --- | --- |
| **1 · ends with the project** | deleted when it closes |
| **2 · runs in CI** | it has a trigger already |
| **3 · runs on a schedule or a trigger** | the entry says **what fires it** |
| **4 · run by hand** | the entry says **when somebody would think to** |

**A kept script with no trigger is worse than none**: it looks like cover and is
not. Test tooling is the usual case. `scripts/` is run by people and CI;
anywhere else needs saying why.

#### What the design owes on top

The design lists **the same artefacts and what changes in each**: what each does
afterwards that it did not before, not which lines changed. The depth owed is
inverse to how well git records it: least for a repository file, whose diff is
the detail, and most for a host file or cloud resource, where the entry is the
only record and must be enough to do it again.

#### And what it reports when it goes wrong

**A design says what its failures will tell somebody**, and reviews what is
reported or logged, since the moment a failure is read is too late to add
detail to it.

**An error is part of an interface**, so it is documented where its reader
looks:

| what | documented in |
| --- | --- |
| an error the API returns | [`4.3`](4.3-api-schema.md), against the endpoint that returns it, with any behaviour no type can express: login's one message for two conditions |
| an event the server logs | [`4.7`](4.7-log-events.md) |
| what a script reports or logs | its own header and `--help`, next to the code that produces it; [`3.0`](3.0-tools.md) stays a register, and [`4.8`](4.8-artefacts.md) says what an exit status means |

### 2.14 The delivery runbook

**A delivery's steps live in one place**: its work package where it has one,
linked from the parent's delivery list; under that list for a pre-approved
delivery. Never both.

The runbook is filled in three times:

| when | what goes in |
| --- | --- |
| writing the project | the steps, in order, and the route each takes |
| before the delivery | the commands as they will actually be typed; a step that cannot be written as a command has not been thought through |
| after it | which version or build carried it, and when |

For the host and service routes it is the only record of what was typed.

#### The delivery log row is part of the delivery

**The row is written in the change that delivers**, so it cannot be forgotten.
Only project deliveries get one, appended at the end of
[`4.9`](4.9-delivery-log.md); pre-approved changes get none. The runbook says
how; the row says that it happened.

### 2.15 Classifying a change

**Every way a change is categorised is an issue field**, listed here once. The
fields are authoritative; a document describes them and never defines a
parallel set.

| field | values | what it decides |
| --- | --- | --- |
| issue type | `Requirement · Project · Decision` | what the issue is |
| Workstream | the ten in [3.7](3.7-workstreams.md); unset is the triage queue | who owns it |
| Type of change | `bug · functional · non-functional · cosmetic · documentation · tooling` | what it owes before shipping (§2.6) |
| Route | `Production Release · Repository Change · Other` | how it reaches its users, and whether it takes a semver |
| Priority | `Urgent · High · Medium · Low` | a judgement, not derived |
| Effort | `High · Medium · Low`; unset means triage could not say | a band, not an estimate |
| Stage | `Triage · Scope, Options and Dependencies · On Hold · Ready for Project · Candidate Project 1–3` | a requirement's journey (§2.23) |
| Phase | `Scope · Q3 · Q2 · Q1 · Design and Test Approach · Development · User testing · Deployment · Post-deployment · Project Closedown` | a project's journey |
| Milestone | a semver, production's version plus a letter, `no-release`, or `pre-approved` | which delivery carries it ([1.1](#11-what-a-milestone-says)) |
| Decision State | `Asked · Feedback Provided · Documented Ready for Sign-Off · Decided · Actioned` | who holds a decision; the turn alternates at each step |
| Topic | a named project or focused subject; unset is normal | which decision log a `Decision` appears in |
| Parent | an issue | what owns it; on a `Decision`, what triggered it |

**Three distinctions are not fields**, because none categorises a change: a
gate against a check (§2.16), a delivery against a release (CLAUDE.md), and an
artefact's route, which is where the `Route` field comes from (below).

Retired, and named so they are recognised rather than reinstated: `lane`, the
seven type labels, `needs-triage`, the `patch`, `minor` and `major`
milestones, and the `Workstream` and `Index` issue types.

#### Option colour says whose turn it is

On every field that carries a journey (`Stage`, `Phase`, `Decision State`, and
the board's `PR State`):

| colour | means |
| --- | --- |
| blue | Claude leads, and finds it without being asked |
| green | the owner has to act first |
| yellow | on hold, or waiting |
| red | finished |

An option is green only when the owner acts first, not when he has to agree, so
`Triage` and `Ready for Project` are blue. `Decision State` alternates blue and
green and has no red: `Actioned` waits for the owner to read and close it.
`Awaiting review` is the only green `PR State`. A new option needs its colour
chosen; nothing checks it.

#### Route

**Route is a property of the artefact**, and a delivery has one route. Work
touching artefacts with different routes is split into a delivery per route,
each its own work package, and the parent carries none. Documentation is the
exception: it rides on the delivery it accompanies. `Route` says how the change
reaches its users; the shape it takes also depends on whether the old version
must keep working meanwhile and how many packages ship together
([1.1](#11-what-a-milestone-says)).

| route | which artefacts | reaches its users | semver |
| --- | --- | --- | --- |
| Production Release | anything built into the image (`crates/**`, the word lists, `Caddyfile`, `Dockerfile`, `docker-compose.yml`), and anything deployed to the production host: files under `/opt/tile-lite-elite/`, systemd units, packages we install there | when `deploy.sh` deploys to production | always |
| Repository Change | anything else in the repository: `docs/**`, `scripts/**`, `.github/**`, `.cargo/audit.toml` | when it is pushed to `origin/main` | no |
| Other | cloud resources, GitHub objects, deploys to preview or rehearsal | when somebody applies it | no |

**A release always takes a semver**, even when only the `Caddyfile` changed:
the version is compiled in, so the new number names bytes that differ.

**A change to the production host is a release, and rides with one.** It takes
a semver milestone and joins the release being planned rather than causing its
own; the release is what records that production moved. The delivery's runbook
orders the image and host steps (§2.14). "The production host" is the Oracle
VM: its packages, its Docker daemon, and the image's packages are ours; the
hypervisor is not. A package a project names is ours; an OS update applied by
`unattended-upgrades` is the platform maintaining itself and takes no semver.

**Production cloud configuration stays Other.** A file, unit or package landing
on the host is a release; an OCI alarm, policy or dynamic group is applied by
hand. Preview and rehearsal deploys are Other whatever they carry.

**A generator whose output is committed takes the generator's route.** The test
is whether a human step stands between it and the image: `wordlist-tools` and
`scripts/mkfavicon.py` produce files that ship, but somebody runs them, reads
the result and commits it, so they are Repository Change. A generator the build
invokes is Production Release wherever it lives.

**`.cargo/audit.toml` is Repository Change and `.cargo/config.toml` would not
be.** The first configures `cargo audit` only; the second changes the bytes.

**The rule in executable form is
[`scripts/board/shipping.py`](../scripts/board/shipping.py)**, which the
pre-commit hook, `deploy.sh`, `verify.sh` and CI ask through
`scripts/board-shipping.py`. It lists the paths that do not ship, which is the
stable list. This section is the authority. A commit touching any image path is
an image change, whatever else it touches.

**A repository change is delivered when it is pushed to `origin/main`**: until
then it exists on one disk. Run an unpushed script to test it, never to use it.

### 2.16 A gate refuses; a check reports

| | it | example |
| --- | --- | --- |
| **gate** | **refuses**: the work stops and there is nothing to decide | `deploy.sh`'s gates; CI's `check` job on a protected branch |
| **check** | **reports**: a person reads it and decides | `verify.sh` after a deploy; `board-status.py`; `board-check.py` |

The difference is who acts next, not severity.

### 2.17 Triage: what happens to an issue when it is raised

| | |
| --- | --- |
| **requirement** | a request for a change, raised quickly and analysed later. Where the project is already clear, raise the project instead ([Straight to project](#straight-to-project)) |
| **triage** | the initial assessment: at least a clear short title, and `Workstream`, `Priority` and `Type of change` set |
| **scope** | functional and technical options, a check that the one recommended can be done, dependencies, and `Effort` |
| **project planning** | whether it joins an existing project, starts a new one, or waits |
| **projects** | a requirement a project takes becomes its sub-issue, labelled `folded` and closed as `completed` |

```text
requirement ──triage──▶ ──scope──▶ ──ready for project──▶ ──planning──▶ solo project · grouped project · on hold · cancelled
              enriches    enriches  └───── the backlog ─────┘   creates
```

Triaging, scoping and planning are continual work of the programme.

#### What triage asks

**Eight questions, in whatever order they answer themselves**, except that what
it touches and who owns it come before whether it joins existing work, which
depends on them. The last three are where the value is.

| | question | where the answer goes |
| --- | --- | --- |
| 1 | **Is it real, and still relevant?** | close it, or carry on. Rejecting is a legitimate outcome |
| 2 | **What kind of change is it?** | the `Type of change` field |
| 3 | **What does it touch?** | the artefact guess; its route follows |
| 4 | **Which capability owns it?** | the `Workstream` |
| 5 | **What carries it to users?** | the milestone |
| 6 | **How big is it, roughly?** | the `Effort` field: a band, not an estimate |
| 7 | **What else does it relate to?** | the comment: dependencies, overlaps, whether to plan it alone |
| 8 | **What do we know now that the raiser did not?** | the comment. Conclusions are edited into the body; discussion stays in the comments |

**The triage comment** is [`docs/templates/triage-comment.md`](templates/triage-comment.md).
It holds only what no field can: the artefacts, the context, and what triage
found. **Context and what-we-know are never left blank**, and kept short: triage
decides whether and with what, not how. The author is the GitHub account, so
comments carry no footer and no typed date.

**Impact is not asked**: it follows from route and environment. Triage states
it where it is not obvious.

#### The outcomes

| outcome | what it means |
| --- | --- |
| **straight to `main`** | meets the [pre-approval test](#22-when-to-branch-and-what-pre-approved-means): done directly, carrying `pre-approved` |
| **solo project** | its own project |
| **grouped project** | folded into a project that owns the subject, closed as `completed` with the `folded` label and a comment naming the project |
| **on hold** | `Stage` set to `On Hold`, and the body says what it waits for |
| **cancelled** | closed as `not planned`, with why |

*Not decided yet* is where most of the backlog sits, and is an honest state:
whether an issue joins other work depends on what else turns out to be ready.

#### Decisions

**A decision is an issue only while there is a choice to discuss.** An answer
already settled goes straight to its owning document and to `CLAUDE.md`, with
the argument in the commit message: no issue, nothing to close later.

**A decision is applied in the same commit that marks it decided**, or an issue
is raised and named in it, so *applied* has a signature a tool can check.

**It is raised as a `Decision` issue**, from `.github/ISSUE_TEMPLATE/decision.yml`,
with no `Stage` and no `Phase`:

| | |
| --- | --- |
| **the body** | the context, the options, each saying what it constrains, and a recommendation. Then *Agreed Decision*, written when settled |
| **the comments** | the argument |
| **`Open actions`** | what it creates, each box labelled `**owner**` or `**Claude**` |
| **`Decision State`** | who holds it, below |

| state | with | until |
| --- | --- | --- |
| `Asked` | **the owner** | he gives his view |
| `Feedback Provided` | **Claude** | Claude writes the decision down |
| `Documented Ready for Sign-Off` | **the owner** | he reads it and signs it off |
| `Decided` | **Claude** | it is applied |
| `Actioned` | **the owner** | he has read the outcome, and closes it |

**The state routes it, not a tick**: a box ticked while the discussion continues
does not move it on. **Documenting it is what ends `Feedback Provided`.**
`Actioned` means applied, and closed means read, so the owner closes it.
`board-check.py` checks the field against the body, and the body is the
authority.

**Once settled, a decision issue is never maintained**: when the answer later
changes, the document changes and the issue does not.

**A decision is not a change vehicle.** It records an answer and routes the
work:

| the action | where |
| --- | --- |
| raise a requirement | nothing yet owns the thing decided |
| add a requirement to a project | a project does |
| update a project's design, test approach or artefacts | the answer changes how it will be built |
| update the documentation | the answer is a rule rather than work |
| a small tooling change | the rule lives in a script |
| close or cancel | the answer is not to do it |

The last three are pre-approved changes, allowed only where no suitable
requirement or project exists. So a decision takes no semver and no letter
milestone, and no row in [4.9](4.9-delivery-log.md), and a deploy never settles
one unread.

**Where it belongs**: its **Parent** is the project or requirement that raised
it, its **Workstream** is who owns it, and **`Topic`** names a focused subject
where one helps, usually unset.

**D1 to D38** predate the issue type and live in the process-definition
glossary, as an archive. Decisions since are issues, and keep their `Dxx` in the
title.

### 2.18 Exceptions to the normal process, and pre-approval

The normal path is a requirement, folded into a project, developed on a branch,
merged, and deployed to preview, rehearsal and production. It is shortened
where a change is well understood, does not affect production, is small and
already agreed, or is only documentation.

#### Make tooling changes when they are first needed

**Tooling work is scheduled by the first thing that needs it**, not by being an
improvement: a change nothing waits on goes stale before it is used. It is a
scheduling rule, not a licence to defer: the requirement is still raised and
says what is wrong.

**A waiting requirement is triaged and scoped first**, so it carries a type,
priority and effort that let it be weighed when its wait ends, and a dependency
note saying what it waits for. Then it goes one of two ways:

| | when |
| --- | --- |
| **On Hold**, with the dependency noted | what it waits on is not yet a project |
| **folded into that project** | it is, because the need and the work are one piece |

#### Straight to project

A change well understood enough to need no analysis is raised directly as a
project, skipping the requirement. A requirement raised first can be converted
to a project without loss.

#### Change directly on main

A documentation or tooling change that needs no review before it is live goes
directly to `main`, and **its approval is the `pre-approved` milestone**. It
answers the branch test from the approving end: nobody needs the old version
meanwhile.

| on a | `pre-approved` says |
| --- | --- |
| **requirement** | its change was made directly, and no project was raised |
| **project** | the project needs no branch: everything it touches goes straight to `main` |
| **work package** | this delivery can be done on `main`, whatever the rest of the project does |

**Anything other than `pre-approved` means not pre-approved**, including no
milestone: only the explicit value authorises. That reading fails closed, and an
unset milestone is invisible to a board filter, so a list of things not yet
approved built from it would come back empty.

#### Changes to the repository only

A document or script is live once it reaches `origin/main`. A document-only
change never takes a branch; a script takes one only where the old version is
needed meanwhile ([2.2](#22-when-to-branch-and-what-pre-approved-means)).

#### Changes outside the repository

Invisible to git, so made by hand, recorded in [4.8](4.8-artefacts.md), and
the project's status updated by hand.

### 2.19 What planning produces: the roadmap

**The roadmap is which projects go together, and in what order**, and nothing
maintains it by hand:

| | answers |
| --- | --- |
| the **board views** | what is in each release, what is blocked by what, and the backlog: the place to work from |
| [1.5](1.5-work-in-progress.md) | the picture of what depends on and belongs to what, drawn by `scripts/roadmap-diagram.py` |

**Ordering is the `Phase` field**: `Q1` is next, then `Q2` and `Q3`; projects at
`Scope` are not yet ordered. **No dates**: a date needs an estimate, and an
estimate a commitment nothing here obliges.

#### Four relations between two projects

| | means | example |
| --- | --- | --- |
| **can** go together | nothing shared; the default | most small changes |
| **should** go together | one makes the other testable, or they share a cost worth paying once | a schema change and the code that reads it |
| **cannot** go together | one needs the other's change first, or both touch the same artefact | an overlap between two artefact lists |
| **should not** go together | allowed and unwise: a rollback takes back the whole release, so a change that must not be reverted should not ride with a risky one | a security fix; two large projects |

*Cannot* is discoverable by comparing artefact lists; *should not* is a
judgement of what a rollback would cost.

#### Where a dependency is recorded

**Under the heading *Dependencies and related work*, one line per relation**,
naming the issue and the reason, which is what survives the other issue
changing shape:

```markdown
## Dependencies and related work

- **waits on #NNN**: the seam it introduces is what this plugs into
- **is needed by #NNN**: that project builds on this one's schema
- **overlaps #NNN**: both touch `crates/server-game/src/app/games.rs`
- **anticipates #NNN**: the store is shaped for per-game eviction, which that will want
```

| | means | discovered by |
| --- | --- | --- |
| **waits on**, and its inverse **is needed by** | cannot start or ship until that one has | a person, usually while designing |
| **overlaps** | touches the same artefact | comparing artefact lists |
| **anticipates** | this design makes room for that project, which it names | impact assessment |

**A dependency is declared from both ends**, `waits on` in one body and `is
needed by` in the other, and is also a GitHub dependency link (`blocked by`),
which the board marks and tools read. `board-check.py` reports a line with no
link behind it. **The order is derived from the relations**, never written down
separately.

#### The backlog

**The backlog is the set of triaged requirements**: classified, not scheduled,
and not yet any project's. An untriaged requirement is in the queue in front
of it. A requirement's fields freeze when it folds into a project, as the
record of what triage thought, and the project's own fields take over. **Triage
gathers; planning decides**: an answer nobody can give yet is left unset.
`Priority` stays a judgement, since nothing obliges anyone to meet objectives a
score could be derived from.

**Two hierarchies meet at the project**: the terms in part 1 organise the
**work**, and requirements say what is **wanted**. A project owns requirements,
which is why a requirement is not a small project.

### 2.20 Workstreams: overlapping requirements should land together

What a workstream is, and which one owns what, is `docs/3.7`. The lifecycle
rule that follows from it:

**If two requirements touch the same artefacts and sit in different
workstreams, the workstreams are drawn wrongly**, not the requirements. Work
that collides has to be planned together; planned in two sittings, the
collision surfaces at merge. A recurring overlap across a boundary is evidence
to move the boundary, which is what makes 3.7's artefact lists a test of the
taxonomy.

### 2.21 Impact assessment writes context, not only a list

An impact assessment has three outputs:

| output | feeds |
| --- | --- |
| what it touches: the artefact list | the collision test, and the rollback list |
| how it relates to other work: depends on, overlaps, duplicates | planning, and the order |
| what that means for the design | the change itself |

The third changes what gets built: "put the seam here, because #N will want to
plug into it". Unwritten, the next reader finds a shape with no reason and
tidies it away.

#### Anticipation names its project

"Another project is coming" is also how over-engineering starts. So the design
**names the project** it is making room for. If that project is dropped, the
shape it justified is reviewable: somebody can find why the seam is there and
decide whether it still earns its place.

### 2.22 Triage and planning are separate steps

| | triage | project planning |
| --- | --- | --- |
| scope | one requirement | across all of them |
| when | when it is raised, or shortly after | when there is appetite and capacity |
| cost | seconds | a sitting |
| the artefact list | produces the guess: what would this touch? | compares the guesses: do any two overlap? |

A **triaged requirement** is an open requirement with its `Workstream` set,
not yet folded into a project. How far it has travelled since is the
`Stage` field, below.

Project planning is where the pipeline is managed: what is in flight, in what
order, what waits on what. Its tools are `board-status.py`, the board's release
and backlog views, and comparing artefact lists. When the pipeline is looked at,
and who decides the order, is not yet set.

### 2.23 The journey after triage: the `Stage` field

On requirements only:

| stage | means |
| --- | --- |
| unset | raised, nobody has looked. The inbox |
| Triage | initial assessment: keep it? priority, type of change |
| Scope, Options and Dependencies | scope, functional and technical options, overlapping issues, and feasibility: that the recommended option can be done |
| On Hold | scoped, and waiting on something named under its dependencies |
| Ready for Project | understood well enough to be planned; a queue, meant to have a length |
| Candidate Project 1, 2, 3 | grouped with the others carrying the same number: a project waiting to be raised |

Unset and `Triage` are both kept: unset means nobody has looked, `Triage` that
somebody is looking.

**A candidate has three outcomes**: join a project that already exists, combine
with others into a new one, or be a project on its own. Which is a planning
decision.

#### The numbered slots are positions, not names

`Candidate Project 1` means the next project this workstream will raise. When
it is raised, what was 2 becomes 1. Moving a requirement into a numbered column
groups it with whatever else carries that number. Three columns limit how far
ahead planning goes, not how much work a workstream may have.

#### Non-functional design is four questions

Every project answers these, and "none, because..." is a complete answer to any
of them:

| question | asks |
| --- | --- |
| capacity | what this adds to load, against which ceiling in the capacity plan |
| failure | what can go wrong, what the caller is told, what reaches the log, whether the server should act |
| limits and timeouts | any new timeout, queue depth, rate limit or concurrency bound, and where its number came from |
| secrets and access | anything touching credentials, tokens, or who can reach what |

A question nobody asked per change becomes a project later: #402 for failure
and #291 for cost.

#### A dependency is declared from both ends

`waits on #N` has an inverse, `is needed by #N`. Both go under *Dependencies
and related work*, and the same edge is set in GitHub (`blockedBy`), one link
serving both ends. The link is what the context header at the top of every
project shows, and `board-check.py` reports a line in that section with no link
behind it. A dependency written anywhere else in the body is not read.

A project with many `is needed by` lines is a shared mechanism, whether or not
anybody has called it one; see the exception below.

#### Related change belongs in the same project

**The design decides the boundary, not the delivery.** Work that has to be
designed together goes in one project, which splits into as many work packages
as it has deliveries. A different route is a reason to split a delivery, not a
project: #329's script refusals went to `main` as a Repository Change and its
caller-facing errors took a release, two packages in one project.

Two projects are right where deciding one does not constrain the other: the
same file, week or workstream is not enough. Then a link under *Dependencies
and related work* is enough. A requirement still folds into the project that
owns its area rather than becoming a new number.

##### The exception: a shared mechanism is owned once and designed to

A mechanism several functions need is owned by one workstream (`docs/3.7` says
which) and gets a delivery project of its own. That project treats every use
case as a customer feeding requirements for the generic mechanism; each
workstream then builds its own functionality on top, in its own project.

**The test is whether it would exist for only one caller.** If it would, it
belongs to that caller's project.

**It ships with its first customers**, so its interface is tested against a
real requirement rather than only its own tests. Scoped and designed
independently, scheduled jointly: its milestone is the one its first callers
carry.

#### The industry's names for these stages

| here | elsewhere |
| --- | --- |
| raising a requirement | demand intake |
| triage | demand qualification |
| scope, options and dependencies | solution shaping |
| project planning | portfolio or pipeline management |
| a project | delivery |

Raising an issue stays a five-second act. Nothing downstream assumes the person
raising it knew more than what they noticed.

#### A recurrence is a date in an issue body

Something a person has to do again gets a line in the issue that owns it:

```text
**Next capacity review due:** 2026-12-21 — **Claude**
```

`board-actions.py` surfaces it on the day it falls due and every day after,
labelled like a checkbox. **Doing the thing moves the date on**; the date is the
only state. A date is not gated by the phase, as checkboxes are by `DUE_AT`: a
review falling due while its project is at `Design and Test Approach` is due
then.

A job a machine runs with nobody involved belongs to the scheduler (#400)
instead.

#### Look it up before naming it

Where a practice this programme needs exists in ITIL (incident and problem
management, event classification, change types, release against deployment),
its terms and structure are used, and the document says which practice an
answer came from. The vocabulary and shape are taken; ceremony that needs
separate teams is left. Where ours differs, the mapping tables above say how.

## 3 Notes on release scope and version numbers

### 3.1 What closing a release's scope does not freeze

Closing scope stops **new issues and new functionality** entering a release. It
does not freeze the issues already in it: user testing checks the requirement
as well as the build, so a requirement may be refined under testing, and
preview is rebuilt after each round rather than tested once.

The test for whether something has left the scope: **does it add an issue, or a
piece of functionality, that was not there when scope closed?** Size is not the
measure.

### 3.2 Version numbers

The app version, the API version and the build id are defined in
[4.1 Versioning](4.1-configuration.md#versioning); which app version a release
takes is [3.3 §2.4](3.3-testing-ci-and-release.md#24-version-numbers-which-to-bump-and-when). They move independently.
The next structural release takes the major slot: `1.0.0`. It says breaking
changes get a major bump, not that there will be none.

### 3.3 Priority

`Priority` is an issue field, a judgement rather than a derived value. It
informs what enters a release; ordering within a release is decided when the
release is planned. The milestone does not express priority: it says how a
change ships, not when.

### 3.4 What tests the tooling

Documentation and tooling are in use as soon as they reach `main`: no deploy,
preview, rehearsal or user testing stands in front of them. So **a gate that
can fail open gets a test in `scripts/tests/`, and CI runs it.** A tool that
shows something is wrong visibly; one that permits something is wrong
silently, because a gate that has stopped checking looks exactly like one
everything passed.

Where CI cannot reach, the tool's own use is the test, before the merge: a
change to `deploy.sh` is tried by deploying to rehearsal. Tooling is the one
kind of change whose author is its only user, on the machine where it already
works, so it is tried somewhere else first. A test that passes locally and
fails in CI is found this way: one hid `gh` by trimming `PATH` to `/usr/bin`,
which on a runner is exactly where `gh` lives.

### 3.5 Why `deploy.sh` needs no approval step of its own

Rehearsal and production run the same `deploy.sh`. A production release of a
commit refuses unless rehearsal already runs that commit, so a change to
`deploy.sh` cannot reach production without having deployed rehearsal
successfully first.

The chain does not close for a rollback, which runs the current tooling
against an older commit, or with `DEPLOY_SKIP_PREVIEW` or `DEPLOY_SKIP_BUMP`,
which step around parts of it by design.

### 3.6 Pull requests, and what they are for here

**They trigger and track human review, and nothing else** — not merges, not CI.

**A review, not a comment.** A comment can approve something nobody looked at; a
review is against a commit, and GitHub records who approved what. The owner
approves; Claude merges.

**Approved is not merged.** A pull request can be approved and stay open.
Claude merges it locally, by rebasing and fast-forwarding, so the commit that
ships is the commit that was tested ([3.3 §1.9](3.3-testing-ci-and-release.md)).

**It runs what a branch push does not.** CI's `check` job runs on every push;
`e2e` runs on pull requests and on `main`. Opening one is how a branch gets the
full suite.

**Open it as a draft** when the branch is created, and mark it ready when it is.
It is then a running view of the release: every commit, and what CI made of them.

**Never squash**: every commit carries a version stamp that CI checks, and a
squash writes a new subject that does not.

**`Closes #N` belongs in the pull request, not the commits** — and only on a
project's last delivery, since an earlier one closing the project would close it
before the rest shipped.

**Request a reviewer when opening one** (`gh pr create --reviewer …`). Without
one it appears in nobody's queue.
