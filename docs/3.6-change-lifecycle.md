# The change lifecycle: from an issue raised to production

The change lifecycle is the process by which the programme implements changes.  The main vehicle of change is the 'project' which has a well defined gated process and is designed to ensure changes to the application are of high quality and low risk.  Small changes to documentation and tooling can follow a pre-approved route and be made without a project.

Typically a change starts as a requirement.  After analysis a requirement may be incorporated into a project, at which point the requirement is closed and scoping becomes the job of the project.  It is also possible to a raise project without first having a requirement, when it is clear that a project will be needed.

This document covers the process from raising a requirement to project closedown after the change is made.  It focusses on the analysis and approval steps rather than on the technical tooling and environments.

## What the process is for

To spend the owner's time on game functionality and engine logic rather than
on process, non-functional work and bugs. So a rule is judged by whether it
saves his attention or spends it.

It is carried by four mechanisms, cheapest first:

| | | |
| --- | --- | --- |
| **hooks** | `.githooks/pre-commit`, `commit-msg` | refuse at the moment of the mistake |
| **checks** | `verify.sh`, `check-docs.sh`, `board-check.py` and the rest | report, and leave the judgement to a person |
| **gates** | `deploy.sh`'s refusals | stop a change that would be costly to undo |
| **skills** | `.claude/skills/`: `triage`, `raise-project`, `change-a-document` | carry the shape of a task, so it is done the same way each time |

A rule held only in a document, for a person to remember, is the weakest form,
and the others exist to replace it. Who decides what is in
[3.7](3.7-workstreams.md#who-decides-within-a-workstream).

Its sibling, [3.3 Testing, CI & Release](3.3-testing-ci-and-release.md), holds
the machinery: the environments, CI, the deploy script, rollback and the
runbook. This document holds the rules, in three parts:

| | |
| --- | --- |
| **[1 The flow](#1-the-flow-how-a-change-reaches-production)** | the terms, the stages, and how a release is shaped |
| **[2 The rules](#2-the-rules)** | one subsection per rule |
| **[3 Notes](#3-notes-on-release-scope-and-version-numbers)** | release scope and version numbers |

## 1 The flow: how a change reaches production

**Key terms used in the process:**

| term | what it is | defined in |
| --- | --- | --- |
| **programme** | the application *and everything we maintain to keep it going* — production, the dev, preview and rehearsal environments, the documents, the process | here |
| **workstream** | a capability within the programme, which might be a functional or technical component of the application, or a service such as Capacity Planning | [3.7](3.7-workstreams.md) |
| **artefact** | Anything maintained by the programme, including all files in the repository as well as environments, configuration settings, etc.  Artefacts are owned by workstreams and associated with a route. | [4.8](4.8-artefacts.md#what-counts-as-an-artefact) |
| **route** | The route by which a change is delivered to its users: a Release of the application image to production, a change of files in the Repository, or Other - changing a test environment, configuring the VM infrastructure, etc. | [4.8](4.8-artefacts.md#the-route-an-artefact-takes) |
| **project** | a change delivery vehicle for a bounded piece of work with fixed scope. Projects can be a small cosmetic change, or an overhaul of the design | [§2.11](#211-what-a-project-is) |
| **work package** | A project's work is split into one or more work packages. Work packages deliver into the project and are planned as black boxes. | here |
| **delivery** | Delivering changed artefacts by a route.  A delivery can include changes from many projects, and a project can have many deliveries. | `CLAUDE.md` |
| **release** | A delivery which is a release of the application image into production, so via the Release route. Each release changes the application semver.  | `CLAUDE.md` |

**Workstreams definitions are owned by [3.7](3.7-workstreams.md)**.

**The flow, in three stages.**

**1 · The project branch is where everything happens** — code, documents,
everything the project touches, until it is live.

**2 · The release branch is made by merging, and never edited.** A defect found
while testing is fixed on the project branch and merged in again, because a fix
made in the release branch exists nowhere else. Dropping a project from a release
means recreating the branch from the others.

**3 · `main` receives a proven branch, and a release ships from `main`.** They
are two acts: a branch merges once it is proven, and a release ships whatever
has accumulated on `main`, immediately or later.

*Stage 2 applies where a release must stabilise while `main` moves on. For a
single proven delivery the project branch fast-forwards `main` directly.*

### One round of preview and rehearsal, or two?

**Two only when the merge changes the tree.** The rule underneath is *test the
artefact you will ship*, and a second round exists to catch a merge that made
something new — so when there is nothing new, it proves nothing.

| | |
| --- | --- |
| **`main` has moved**, and the merge combines work | **two rounds.** The combination has never existed before and is what ships |
| **a fast-forward** — the branch already contains `main` | **one round.** The tested commit and the shipped commit are the same object |

**Use `--ff-only` where it is available**, in place of the usual written merge
commit: a merge commit changes the sha, and the commit tested stops being the
commit shipped. The branch's own messages carry the story.

**Preview from the branch before merging is still worth it**, and is not part of
either round: it is a cheap look for whatever would otherwise reach `main`, and
it costs one command.

**The trade, stated because it is real**: a problem found in rehearsal after
merging means fixing on the branch, re-merging and re-testing. Accepted because
preview from the branch has already exercised the same tree.

### Why the questions stop being asked

**The image is built once per commit and promoted**, not rebuilt for each
environment, so *which commit was tested?* has an answer rather than a
procedure.

**Where a project delivers by more than one route**, the routes are ordered: a
step applied by hand usually assumes the release carrying it is already out.

### 1.0 The shape of a release

Three queues, named for the version slot each releases into, so the answer and a
version number are the same word. Which queue a change is in is the first thing
to settle about it.

| | **patch** | **minor** | **major** |
| --- | --- | --- | --- |
| what | a change that can go live quickly without being grouped: an urgent defect fix, or something small like a cosmetic change | minor functional changes, normally released as a group | a major functional or architectural change with a large impact |
| chosen because | **either** it is low risk **or** it is urgent | it is ready, and worth releasing alongside whatever else is | its impact is large enough that it wants its own release |
| lives on | `main` | `main`, which accumulates the next release — a release branch only where it must stabilise while `main` moves on | usually a release branch of its own, because a major is what most often needs to stabilise |
| released as | a patch, if it goes alone — otherwise the version of whatever it rides with | a minor | a major |
| released with | nothing, if it is urgent; otherwise the next release going | whatever else is in the group | the changes it affects, and nothing else |
| owes | user testing | user testing per change, then again for the whole group | a design note in `docs/2.x` **first**, then all of the above |
| pull request | yes, for an image change: every Production Release takes one | yes, opened with its branch | yes, opened with its branch |

**`main` is where a release accumulates.** Development and testing happen on a
branch; a change merges to `main` once its testing has passed, and the release
ships whatever has gathered there. A release branch is still right where a release must
stabilise while `main` moves on, or where dependencies mean several changes
have to be merged together — that is the *reason* the row above asks for. The
shapes this leaves are tabulated in
`docs/changes/workstreams/delivery-tooling/383-one-board-model/flows.md`.

**Low risk *or* urgent, not both.** A production fire is often not low risk and
goes out today anyway, because waiting is worse. Demanding both would push the
changes that most need speed into the slowest queue.

**A group need not be connected.** Three unrelated small changes can share a
release because all three are ready; grouping is about the cost of releasing.
Where a group is connected, that is a reason to test it together rather than a
condition of forming one.

**A major release carries what it affects, and nothing else.** Not "ships
alone": work the change drags with it belongs in the same release, because it
exists to keep up. What must not ride along is anything unrelated — a large
change has a blast radius that is hard to predict, and if something breaks there
should be one candidate rather than several.

### 1.1 What a milestone says

A milestone says how a change reaches its users.

| milestone | what it says |
| --- | --- |
| `no-release` | provisional: the change needs no new application version |
| `patch`, `minor`, `major` | provisional: the **minimum** the version must move by |
| `pre-approved` | the change goes directly to `main`, with no delivery |
| `0.7.2`, `1.0.0` | the release that carries it |
| `0.7.1a`, `0.7.1b` | a delivery that ships no image, after that release; see below |

**Every delivery made at one point in time has a milestone and a row in
[the delivery log](4.9-delivery-log.md)**, as one act: the semver for a
release, otherwise production's current version with a letter.

**What was done decides, not what was permitted.** A project that took a branch
and a pull request has made a delivery, and takes a milestone and a row
whatever its type. A delivery need not take a branch: a change on a host is a
delivery with neither.

**Documentation and tooling projects that go straight to `main` take
`pre-approved`**: no delivery, no row, and the commits and the closed issue are
the record. A tooling change that needs a branch, because a half-finished
version on `main` would block other deliveries, takes one and is a delivery.

**A requirement carries no milestone**, except `pre-approved` when its change is
made directly without raising a project. So a requirement's milestone means
exactly that, and its absence means it is waiting, folded or closed unbuilt.

**Provisional values move**, as it becomes clear how the work reaches `main`:

| from | to | when |
| --- | --- | --- |
| `no-release`, `patch`, `minor`, `major` | a semver | it ships in a release |
| `no-release` | a letter | it delivers without an image |
| `no-release` | `pre-approved` | it goes straight to `main` |

**`no-release` is resolved before the issue closes**: a closed issue still
carrying it has lost the record of how its change reached `main`.
`board-check.py` reports one.

**`pre-approved` is closed by hand**: no deploy settles it. It covers however
many pushes the work takes, where a letter milestone names one delivery.

#### A delivery that ships no application code

A host change, a console change or a drill reaches production without changing
the build, so no version names it. It takes **production's current version
plus a letter**: `0.7.0a`, then `0.7.0b`. Production's, because the version in
`Cargo.toml` leads production by one and says what is intended, not what was
running when the delivery landed.

**`0.7.0a`, never `0.7.0-a`**: the hyphenated form is a SemVer prerelease,
which sorts *before* its release. And since `deploy.sh` reads its milestone
from `Cargo.toml`, which holds only real SemVer, a lettered milestone is never
matched or closed by a deploy. It is closed by hand.

Only a project's deliveries get an identifier; a pre-approved change straight to
`main` takes neither a letter nor a row ([4.9](4.9-delivery-log.md)).

#### A delivery can be shared across projects

Two projects ready at once may ship in one delivery, so the release's cost is
paid once. It gets one row in [4.9](4.9-delivery-log.md), naming both, and
neither project skips its own test approach or post-deployment checks.
Dropping one project from a shared delivery late means unpicking the release
branch rather than rebuilding it without that project.

#### Answering a post-deployment check

**A check says how it is done**, so anybody can run it: *"run this script and
look for this line"*, not *"the bot does not play the plural"*. It is answered
one of three ways, with a note on what happened:

| | |
| --- | --- |
| **passed** | it was done, and the benefit is there |
| **cannot be tested** | there is no way to observe it in production. Say what evidence stands instead, and where it was taken |
| **failed** | it was done, and the benefit is not there |

**Where a check cannot be run**, two earlier facts stand in: the change was
tested outside production by the project's test approach, and it was in the
build when the build was made ([4.9](4.9-delivery-log.md) and the build
manifest).

#### Milestones, deliveries, and which of them get an issue

| | is | carries |
| --- | --- | --- |
| a **delivery** | a change reaching its users. **Every change has one** | nothing of its own: it is an event, not an object |
| a **work package** | a unit of work: a `Project` whose parent is this one | a milestone, where its delivery is a point in time |
| a **milestone** | the marker on a delivery made at one moment, and its place in the sequence. Packages sharing one go live together | no issue of its own |
| the **parent** | the owner of the requirements, the design and the documents | no milestone and no `Route`: it has no delivery role |

**A parent's milestone or `Route`, if set, is ignored.** A parent may carry a
target release. `deploy.sh` skips a parent when it settles a milestone, and
`board-check.py` reports a `Route` on one. Anything else reading these fields
owes the same exception, or a parent would be told it was released.

#### Impacted artefacts: one table per delivery, three rows

A delivery is a mixture of routes, so each has a table with a row per route:

| route | in this delivery | artefacts | branch | PR |
| --- | --- | --- | --- | --- |
| **Production Release** | yes/no | | **always yes** | **always yes** |
| **Other** | yes/no | | | |
| **Repository Change** | yes/no | | | |

- **A `no` row stays**, with dashes: an absent row and an empty one read the
  same, and only one means *nothing here*.
- **The Production Release row decides the shape.** Yes forces a branch and a
  pull request for the whole delivery, because `main` is what gets deployed,
  and the other rows then ride that branch too, documentation included. Without
  it, a row takes a branch only where the old version is needed while the work
  is in progress, and a document-only change never takes one.
- **The branch and PR columns answer yes or no first**, then say which: `yes —
  rides the same branch`, `yes — rides #341`.
- **The work package has its own table, and the parent repeats each package's**
  under its list of deliveries: the package is built from, the parent is
  planned from.
- **The parent lists what it delivers**, each row naming the work packages that
  share a milestone, or saying the change went straight to `main`. A milestone
  has no issue, so this list is what makes a grouping findable.

#### The model, and the four cases that follow from it

**Every delivery is a work package**, with no exceptions. The sub-project issue
that carries a work package may be saved where nothing needs it: the test is
whether a second `Phase` is needed.

| | sub-project | why |
| --- | --- | --- |
| one delivery | **saved** | the parent's fields answer for it |
| two deliveries, one milestone between them | **needed** for each | which packages ship together is read off the milestone |
| two deliveries, one straight to `main` | **needed** for each | a delivery with no milestone still has a phase, and the parent cannot hold two |

**A work package is at most one delivery, and so one route.** A delivery may
carry several packages; a package never spans two. Work that takes two routes,
or reaches its users at two points in time, is two packages: building a tool
and running it are two.

#### Four cases, which is what follows

| | work packages | how they go live | sub-projects | the parent lists |
| --- | --- | --- | --- | --- |
| **A** | one | one delivery | **none**: the parent is the work package and carries the milestone | one delivery |
| **B** | two | together | two, **the same** milestone | one delivery, carrying both |
| **C** | two | separately | two, **different** milestones | two deliveries, one work package each |
| **D** | three, two together | mixed | three | two deliveries, one carrying two packages, one carrying one |

Case A is the common shape, and needs no sub-issue. The delivery is not the
sub-project, because in cases B and D one delivery carries two packages.

#### Naming

| | form |
| --- | --- |
| a parent | `#N MAIN PROJECT: <what it is>` |
| a work package, alone in its delivery | `#N WP A Del 1 of 2: <what it delivers>` |
| a work package sharing its delivery | `#N WP A Del 1 of 2, pt 1 of 2: <what it delivers>` |
| a work package whose deliveries are not yet decided | `#N WP A: <what it delivers>` |

| | |
| --- | --- |
| `WP A` | **which package**, lettered so it never reads as a delivery number |
| `Del 1 of 2` | **which delivery carries it**, and how many the project has |
| `pt 1 of 2` | **its share of that delivery**, only where the delivery carries more than one package |

The parent's number is repeated in each child, so a listing sorted by title
groups the family. **The counts go stale and are kept anyway**: a title saying
`Del 1 of 2` is wrong loudly, where `Del 1` is silently incomplete. They are
derivable from the packages' milestones, and nothing checks them yet.

| case | the titles |
| --- | --- |
| **A** | no sub-project |
| **B** | `WP A Del 1 of 1, pt 1 of 2` · `WP B Del 1 of 1, pt 2 of 2` |
| **C** | `WP A Del 1 of 2` · `WP B Del 2 of 2` |
| **D** | `WP A Del 1 of 2, pt 1 of 2` · `WP B Del 1 of 2, pt 2 of 2` · `WP C Del 2 of 2` |

**The delivery part waits for the design**: until deliveries are decided, a
package is titled `#N WP A:`. `board-check.py` asks for a Deliveries table only
from `Deployment` onward.

#### Why the parent carries no delivery fields

One `Phase`, `Milestone` and `Route` cannot answer for two deliveries, and
post-deployment checks are answered per delivery. So each delivery's work
package carries its own.

#### What each owns

| | parent | work package |
| --- | --- | --- |
| requirements, design, the documents | **owns** | links |
| the delivery list | **owns** | is one row of it |
| impacted artefacts, test approach | — | **its own** |
| post-deployment checks | — | **its own** |
| milestone | none | **its own** |

**One documents folder, named for the parent** (see *Which document goes
where*). A work package's design is a section of the parent's document or a
file beside it, never a folder of its own.

#### The parent's lifecycle is shorter

`Scope`, the queue, `Design and Test Approach`, **and then it stops**: oversight
is a design role, so the parent never takes the phases that describe a
delivery. It may still reach `Post-deployment`, for a requirement no single
delivery satisfies, and `Project Closedown`, to close.

**A work package may delegate its lessons learnt to the parent**, saying
`Delegated to #<parent>`, so `board-check.py` reads an answer rather than an
omission. The form is
[`docs/templates/post-deployment-review.md`](templates/post-deployment-review.md),
the After Action Review's four questions, where every finding ends as an issue
or is explicitly dropped.

**A milestone set on a parent is ignored by the tooling**: `settle_milestone`
skips a project with `Project` children, since settling a milestone closes
every open issue in it and would close a parent with deliveries still to come.

#### What counts as a delivery

**A delivery to a non-production environment is a delivery in full**: it
reaches its users and delivers a benefit, and consumes no version. The same
change delivered to rehearsal and then to production is two deliveries, each
with its own benefit and check.

**A repository change's first use against production is a check, not a
delivery.** The test is whether an artefact reaches production:

| | reaches production | so the production run is |
| --- | --- | --- |
| a change to `deploy.sh`, which runs from the development machine | nothing | a **post-deployment check**: it is live at merge |
| a change to the `Caddyfile`, which is built into the image | the file itself | a **delivery**, with its milestone and log row |

**A delivery's runbook lives in one place**: its work package where it has one,
otherwise the parent's delivery table. Never both.

**What needs a release is the artefact, not the audience.** Documents and
scripts are built into nothing and are live when they land on `main`. Client
and server code is in the image whether or not its effect is visible, and can
break production while its feature is development-only. So the question is
**"is this built into what we deploy?"**

**`no-release` denies a release, not a delivery.** A release is a new
application version; a delivery is any changed artefact reaching its users. A
`no-release` change is delivered when it reaches `origin/main`
([2.15](#215-classifying-a-change)).

#### Scheduling a release

**The placeholder milestones are queues**: `patch` for a change that can ship on
its own, `minor` for one that rides a grouped release, `major` for one that
ships alone. **Scheduling is moving an issue from its queue to a version.**
`no-release` is never scheduled: nothing it holds waits for a deploy.

- **`patch` means a change *can* go out alone, not that it must.** The default
  is to batch, so a release is looked at once, not four times. And it must be a
  change that can be done well quickly.
- **One larger change per release**, so that when something goes wrong it can
  be understood on its own.
- **A release takes the version of the highest thing in it**: add one
  `functional` change to four patches and it is not a patch.
- **A slower queue never blocks a faster one**, which is the point of having
  three.
- **Scope closes when it is set**: what is in a release is decided when the
  version is chosen.

### 1.2 Keeping a release branch current

**Merges flow one way: from the faster queue into the slower ones, after every
release.** `main` releases a patch, so `main` goes into `0.5.0`. `0.5.0`
releases and merges to `main`, so `main` — now carrying it — goes into the
structural branch. Never the other way: a slower queue's work reaching `main`
early is exactly what the three queues exist to prevent.

**And once more when the release's scope closes**, as the first step of
preparing it. Merge every change the release is taking, then merge `main`,
then rebuild preview from the result — so what is tested is what ships.

Not continuously: that means resolving the version-line conflict below at
every merge, where once at scope-close is one resolution against final content.

Skip it and the slower release quietly reverts a fix that is already live, and
the person who reported the bug is the one who finds out.

```text
main ──patch──▶ 0.5.0 ──▶ 1.0.0        after every release, forward only
```

```bash
git checkout 0.5.0
git merge main
git push
```

**That merge conflicts on the version line every single time**, because `main`
says `0.4.27` and the branch says `0.5.0`. The answer is always the branch's:

```text
<<<<<<< HEAD
version = "0.5.0"
=======
version = "0.4.27"
>>>>>>> main
```

Keep `0.5.0`. Taking `main`'s would silently turn the release you are building
into a patch, and the first thing to notice would be
`check-release-version.sh` refusing to ship it.

Nothing else fights: `check-commit-stamp.sh` reads each commit's version from
*its own* tree, so `0.4.27` commits sitting in a `0.5.0` branch are all correct
about themselves, and merge commits are skipped entirely.

### 1.3 Releasing a release branch: merge first, and fast-forward

**The merge comes before the deploy.** `main` is what is live, so merging into
it is the act of releasing. A production deploy run from tooling that is not on
`main`, or has uncommitted changes under `scripts/`, warns and asks before going
on — a confirmation with a terminal, a refusal without one, so nothing scripted
slips past. The check is on the tooling being run, not on the commit being
shipped; that is always a clean worktree checkout.

**Fast-forward if you can, and you usually can.**

```bash
git checkout main
git merge --ff-only 0.5.0
```

A release branch kept current has `main` as an ancestor, so the merge can be a
fast-forward, and then the commit that was tested is the commit that is
released, byte for byte.

**Any merge commit costs a full lap.** `--no-ff` here, or the forward-merge
needed when `main` has moved, creates a commit that nothing has previewed,
rehearsed or tested — so it needs its own CI run, preview and rehearsal, and the
gates correctly refuse it until it has them. The release is not "already tested"
once such a commit lands, because what was tested is no longer what is shipping.

Repository-route work continues on `main` throughout a release, so `main` moving
is the normal case, and keeping the release branch current is what avoids the
lap.

### 1.4 Delete the branch once its change is live

**Live means merged into whatever it ships from, not deployed.** A branch whose
work is in the release branch is done, whatever the release does next.

**A branch merged through a pull request cleans up its remote**; a release branch
does not, because it never becomes one. Both need the local branch deleting by
hand — nothing server-side reaches your working copy.

**`verify.sh` reports what was missed**, as a note rather than a failure: a
lingering branch is untidy, not dangerous.

## 2 The rules

[Part 1](#1-the-flow-how-a-change-reaches-production) is the flow. These are the
rules that govern it, one subsection each.

**A project issue carries eight headings**, each holding text or a link to a
document, never absent and never empty ([2.11](#211-what-a-project-is)):

| heading | |
| --- | --- |
| **requirements** | what must be true when this is done |
| **design** | how it works now, then how it will be done. The as-is first: a change to a script cannot be judged without it |
| **impacted artefacts** | what it touches, each marked **new**, **modified** or **reuse**, with why |
| **test approach** | environment, tools, and what is measured against what criteria — as **two task lists**, functional tests on Preview and technical tests on Rehearsal, which `verify.sh` counts |
| **non-functional design** | capacity, failure, limits and timeouts, secrets and access — four questions, each answerable *none, because…* |
| **dependencies and related work** | what it waits on, **what needs it**, what it overlaps, and what it anticipates — one line each, with the reason |
| **deliveries** | a **runbook** per delivery: the steps in order, the route each takes, and — filled in afterwards — which version carried it, and when |
| **post-deployment checks** | one check per requirement, saying **how** it is done. Answered **passed**, **cannot be tested**, or **failed** |

| | rule |
| --- | --- |
| [merging](#21-when-to-merge-and-what-to-hold-back) | Testing does not require merging. A release-route change merges into **`main`** once its user and technical testing have passed, and `main` accumulates the next release. A release branch is for a release that must stabilise while `main` moves on. |
| [branching](#22-when-to-branch-and-what-pre-approved-means) | A branch exists to hold a change back. No branch means the change goes live immediately, which is what **pre-approved** means. A project either has a branch or it does not — if it has one, *everything* it touches goes there, documentation included. |
| [living documents](#23-living-documents-and-the-standing-issue-that-carries-them) | A document that is never finished gets a **standing issue**, which closes when its *subject* concludes rather than when an edit lands. It lives wherever its issue's changes live — `main`, or the project's branch. |
| [where a document lives](#24-where-a-document-lives-about-the-work-or-a-product-of-it) | A document lives wherever its issue's changes live. Testing documents belong to the release; design and test documents to the project, in its folder. |
| [tracking](#25-tracking-a-change-to-production) | `Refs #N` in the commit — **except where the change never leaves the repository, where `Closes #N` is correct**, because nothing else will ever close it. |
| [types](#26-type-of-change) | Every **project** carries one `Type of change`, and it is a field — not a `Decision`, which ships nothing, and not a `PullRequest`, which inherits from the issue it serves. `non-functional` classifies the **objective** of optimisation and reliability work, so a functional side-benefit does not contradict it. |
| [evidence](#27-evidence-follows-what-the-change-does) | Evidence follows what the change **does**, not the label it carries. |
| [closing](#28-closing-an-issue) | Use `stateReason`, not a label. |
| [documentation](#29-documentation-is-owed-by-every-type-not-just-its-own) | Every type owes documentation; the `documentation` label means the *whole* change is documentation. |
| [splitting](#210-requirements-split-projects-gather) | Requirements split into parts; projects gather them. An issue touching both tooling and the app is two issues. |
| [gate or check](#216-a-gate-refuses-a-check-reports) | A **gate** refuses and the work stops. A **check** reports and a person decides. |
| [classifying](#215-classifying-a-change) | Three questions, three fields: **type** and **release** on the issue, **route** on the delivery. |
| [triage](#217-triage-what-happens-to-an-issue-when-it-is-raised) | Four outcomes for an issue that is not rejected: straight to `main`, a patch project, a project of its own, or folded into one. |
| [projects](#211-what-a-project-is) | Issues group into a **project**, which owns the requirements from that moment. The sources are **folded** and closed. |
| [branches](#212-a-branch-belongs-to-a-project) | **One branch per project**, and it is the only place edits happen until the project is live. |
| [runbooks](#214-the-delivery-runbook) | Each delivery has a runbook: the steps before, and which version carried them, when, afterwards. |
| [artefacts](#213-the-impacted-artefacts-and-why-they-are-listed-early) | List what a change touches as early as possible, even wrongly — it is how two projects discover they collide. |

**Preview is not a step towards production.** It is where you look at
something: `./scripts/deploy-preview.sh at <branch>` builds any ref with no
merge, so showing a change and standing up a release for user testing are
separate acts on the same environment.

### 2.1 When to merge, and what to hold back

Testing does not require merging. Merging is needed only to test changes
*together*:

| | asks |
| --- | --- |
| `deploy-preview.sh at <project-branch>` | does this one change work? |
| `deploy-preview.sh at <release-branch>` | does the release candidate hold together? |

**`main` is the accumulating next release.** A Production Release change merges
to `main` once its user and technical testing pass; the release ships whatever
has gathered there. A release branch is for a release that must stabilise
while `main` moves on: several projects landing together, or a release held
while other work continues.

**Two conditions, neither optional:**

| | |
| --- | --- |
| the checks are written **before** the merge | `### Technical tests — Rehearsal` answered, and the post-deployment checks stated |
| an emergency release is cut from the **last released tag**, not from `main` | otherwise an emergency ships every unreleased change on `main` with it; see "Rollbacks and Emergency Changes" in [3.3](3.3-testing-ci-and-release.md) |

**Changes merge when their testing has passed. Controversial ones are held
back**, where *controversial* means the change might change following review,
not that it is risky. Merging is the point of no easy return: before it,
removing a change is deleting a branch; after it, a revert.

**Merge by rebase and fast-forward, never a merge commit.** `deploy.sh` requires
preview to be running the exact commit being deployed, and a merge commit is
one preview has never run.

#### A problem found before the merge, and one found after

**Before the merge, fix it on the branch and test the branch again**, so a
defect in the implementation or in the requirement costs a commit and a retest,
and `main` never sees it.

**After the merge, either reopen the package or put the change in a later
one:**

| | what happens |
| --- | --- |
| reopen the package | a new branch off `main`, the package back to `Development`, the testing done again, merged again |
| a later package | the change goes in a package not yet merged, where it fits |

**What a merge does to the phase depends on the route.** A Production Release
package moves to `Deployment` and reaches `Post-deployment` only after the
deploy. A Repository Change package's merge is its deployment, so it moves
straight to `Post-deployment`. The post-merge hook makes both moves
(`scripts/board/merge.py`), including for a reopened package merged again.

### 2.2 When to branch, and what *pre-approved* means

**A branch exists to hold a change back**: branch only when the change cannot
go into `main` until the work is complete, because the old versions of the
documents or tooling are still needed in the meantime. Otherwise commit
straight to `main`. **A change that needs no branch is a pre-approved change**;
the two are the same test asked from opposite ends. It asks about the work, not
the change's size: a large change nothing depends on belongs on `main`, a
one-line change to a script people are running today does not.

#### A Production Release is not subject to that test

**A release always takes a branch, a pull request, a semver milestone and a
delivery-log row**, whether or not the old version is needed meanwhile.
`main` is what gets deployed, so an unproven release commit there blocks every
other release until it is proven or removed; and an image change is not cheap
to reverse, which is what pre-approval relies on.

### The standing pre-approval for process changes

**A process change agreed in discussion needs no project, no branch and no
separate review.** It goes straight to `main`, and any issue it answers is
closed by hand ([3.7](3.7-workstreams.md), under process definition).

**Pre-approved does not mean unreviewed**: the discussion before the change was
the review. That is safe exactly where a change is cheap to reverse, which is
why the only refusals in `.githooks/pre-commit` are about the image.

**It settles authorisation, not rigour.** A change to `deploy.sh` is
pre-approved and still owes a design and a test approach agreed before it is
built, and takes a branch where a half-finished version on `main` would block
every other delivery. **Size is not the test; blast radius is.**

**A view may be tweaked freely; what it reads may not.** A board view is a saved
filter. An issue type, a field, one of its values, a label or a milestone is
read by scripts matching the string literally, so renaming one is a code
change. [4.8](4.8-artefacts.md) lists which strings are read and by what.

### 2.2.1 Business-as-usual updates

**One definition for every routine update**, whoever or whatever raises it:
dependency bumps, base images, advisories, host packages, kernels. Owner,
2026-09-19: *"I don't want to introduce ceremony for bau updates, especially
when they are driven by tooling."*

**The route already decides this**, and a BAU update needs no new vocabulary.
Not its size, and not who raised it — those decide how much gets written down,
not what the change owes.

| update | route | what it owes |
| --- | --- | --- |
| Dependabot, GitHub Actions | `Repository Change` | its commit message |
| Dependabot, Docker base images | **`Production Release`** | its commit message; it ships with the next release |
| a crate bump, advisory or otherwise | **`Production Release`** | the same |
| host packages, the container runtime | **`Other`** | a work package, letter milestone and delivery-log row |
| a kernel, or a reboot to adopt one | **`Other`** | the same |

Owner, 2026-09-19: *"Dockerfile is Release, host change is Other."* The
`Dockerfile`, `Caddyfile` and `docker-compose.yml` are ours and reach the image,
so changing one is a Production Release however small the diff and whoever
raised it — `scripts/board/shipping.py` is where that list is decided, for the pre-commit
hook and the build manifest as well as for this.

**A `Production Release` BAU update rides the next release and never justifies
one.**
Owner: *"Changes to the dockerfile image would only reach production as part of
a release, and we wouldn't do a release just for dependabot wanting to update
the base image. So it would be a semver release with the normal regression
testing."* It lands on `main` as a pre-approved change, accumulates there — which
is what D55 made `main` for — and is proved by the regression testing the
release already does. No project, no milestone of its own, no row.

**An `Other` update has no release to ride, and that is the whole asymmetry.**
Nothing carries it, nothing tests it on the way, and no tag records it
afterwards. So it supplies its own vehicle: the work package is what makes it a
point in time, the letter milestone places it in the sequence, and the row says
it happened. The kernel and package work of 2026-09-19 went out that way, as
`0.8.0a` and `0.8.0b`.

**The exception in both columns is urgency.** An advisory that cannot wait for
the next release is not a BAU update any more; it is a release, and takes the
shape a release takes. Nothing here overrides that — it decides what a *routine*
update owes, and routine is the claim being made when this table is applied.

**Split deliveries split work packages.** Owner, 2026-09-19: *"split delivery
means multiple wps unless route is pre-approved."* Where a host update is a
package upgrade and a reboot, those are two deliveries and two work packages,
because either can fail on its own and the record has to say which did.

### 2.3 Living documents, and the standing issue that carries them

**A document that is never finished gets a standing issue**, which closes when
its *subject* concludes rather than when an edit lands. A workstream's design
note is one: it describes a state the code reaches only when the last work
package does, so it belongs to no single branch.

**Finished means accurate, not complete.** A living document is finished whenever
it correctly describes what it reports on, so *nothing unfinished on `main`* does
not keep it off `main`.

**A document-only change does not take a branch.** Owner, 2026-09-03: *"I am now
against having branches for documents, it keeps going wrong."* And it did —
`issue-71-detailed-design` sat five days while `main` moved 57 commits ahead and
its pull request was abandoned rather than merged, and two document commits
landed on branches they did not belong to.

**The failure is structural.** A document branch is never urgent, so it lives a
long time, `main` moves, the diff stops being reviewable, and the review the
branch existed to provide does not happen.

**Where a project has a branch, its technical documents go on it** — the
one-place rule outranks this, and no issue has changes in `main` and changes in
a branch. **Process documents do not**, whatever project prompts the change.
Owner, 2026-09-25: a technical document describes the application and changes
with its code; a process document describes the programme and how it operates,
is unrelated to any particular project, and changes on `main`, which avoids
dependencies between projects and the process. `scripts/board/documents.py` holds the
list, and `.githooks/pre-commit` asks it before committing one on a branch.
`docs/1.6` is generated, so it is neither: it is regenerated on the branch after
the rebase that precedes a merge.

#### The documents live; the issues expire

Owner, 2026-09-21: *"The project documents are living documents, the issues are
only relevant while they are open."*

**So the numbered documents are the only thing kept current.** A `docs/N.N` file
answers *what is true now*, and it is edited whenever that changes. An issue
answers *what was argued, and when* — and once it closes, that is all it answers
and all it is asked to answer.

**Which settles what to do when something changes.** Change the document. Do not
go back and edit a closed issue to agree with it, and do not cite one as the
authority for a rule: the citation goes to the owning document, which is *one
fact, one home* in its ordinary form. Two copies of a rule is a cost; two copies
where only one is kept current is worse, because the stale one still reads as
authoritative and carries a date that makes it look checked.

**Saying so once is a record, not maintenance.** A line added to a closed issue
at the moment it is superseded — #343 points at D55, which narrowed D50 on
2026-09-16 — stops a reader being misled and is then never touched again. What
is forbidden is editing a closed issue to keep it true.

**The cost this avoids is real and was being paid.** Reading an old issue to
answer *what do we do today* is how a retired script gets recommended: `docs/3.6`
and two skills named `check-transitions.sh` and `actions.py` for days after both
were retired, and the fix each time was to the document rather than to the issues
that had argued for them.

### 2.4 Where a document lives: about the work, or a product of it

Two kinds of document attach to a release or an issue, and they belong in
different places.

**About the work** — a testing report, an impact assessment, a decision note.
It has the same lifetime as the release or issue it describes, and it lives on
`main` from the moment it exists. A testing report kept on a branch is one
nobody can read while the testing it tracks is happening, which is the whole
point of it.

**A product of the work** — documentation the change itself delivers: a new
runbook, an updated section of this file, API reference for something being
built. It lives on the branch and lands with the change, because it describes
behaviour that is not true yet.

The test is the same one that decides whether something is finished: **is this
true now, or true only once the change ships?** A document saying "here is what
we are testing and how far it has got" is true now. A document saying "the
server accepts this new field" is not true until the server does.

So a release's own folder of notes is on `main` throughout, while the
documentation that release delivers arrives with it.

**Which owns it: the release, or an issue?**

- **Testing documents belong to the release. Always.** A test report, a testing
  status, an assessment of whether a release did what was wanted — release
  level, with no exceptions, so there is never a question where to look. A rule
  with a case-by-case judgement in it produces documents filed in two places and
  found in neither.
- **Technical design documents belong to the issue** that produced them — which
  may be a **parent issue**, and then the note lives on `main` for the life of
  the workstream. A note for a single change outlives no release; a workstream's
  note outlives several by design, because its work packages are separate
  branches and a note on one of them is invisible to the others.
- **One document has exactly one owner.** Where a document appears to belong to
  several issues, that is the signal those issues should be one issue: several
  issues collaborating on one product get a **parent issue** that owns the
  product and its documents, and the others become its sub-issues.

#### Which document goes where

| document | folder |
| --- | --- |
| a project's design, impact, test approach | `docs/changes/workstreams/<workstream>/<issue>-<name>/` |
| a release's testing record | `docs/changes/<version>-user-testing.md` |
| **a report the programme produces on a cadence** | `docs/reports/<name>/TLE_<CODE>_<period>.md`, from [a template](templates/README.md) |

**A report is a third kind, and it was missing.** Owner, 2026-09-22: *"The
Capacity Plan needs a folder containing each month's plan. It is a report that is
a product of the programme produced regularly. The numbered docs describe the
programme and would be static if the programme didn't change."*

| | describes | changes when | superseded? |
| --- | --- | --- | --- |
| a numbered `docs/N.N` | the programme | the programme does | it is edited in place; there is one |
| a change document | one issue's design | that issue does | it expires with the issue |
| **a report** | what was true at a moment | never — a new one is written | **no.** The series is the thing |

**Which is why it gets a folder and not a file.** Last month's capacity plan is
not wrong, and this month's does not replace it: the two together say whether a
number is moving, which is the only question a single measurement cannot answer.
Overwriting one would destroy the information.

**And why it is not a numbered document.** A `docs/N.N` answers *what is true
now* and is kept current — the living-documents rule. A report is deliberately
not kept current: it is a record of a measurement, dated, and left alone.

**A report is named so the name means something off the path.** Owner,
2026-09-22: *"Capacity plans should be named `TLE_CP_yyyy_mm.md` so the name is
meaningful without the path."* So `TLE_<CODE>_<period>` — the programme, what
kind of report, and when. A report is the one document here that gets mailed,
pasted into a message or dropped on a desktop, and `2026-09.md` says nothing
once it has left the folder it was filed in.

**Each report has a template**, and it earns its place for a reason a
one-off document's does not: the risk is not forgetting a part, it is the shape
drifting between periods, which destroys the only property that makes a series
worth keeping — that the rows are comparable. The capacity plan's is
[`docs/templates/capacity-plan.md`](templates/capacity-plan.md).

**The folder is named for the project, not for a version**, because a project may
deliver into several.

**And named for the *parent*, never for a work package.** Owner, 2026-09-08:
*"All the documents will be in the same changes folder, named after the parent.
It would be messy to have folders for sub-projects."* The parent owns the design
and the documents; a work package links to them. A folder per package would
scatter one design across several, which is the arrangement the folder exists to
prevent.

**So a work package's design has two homes to choose between**, and both are in
that one folder: a section of the parent's document, or a document of its own
beside it. Owner, same day.

**The test is whether it reads in place.** A package whose design is part of the
argument — this is how *this* piece works, given the whole — belongs in the
parent's document, where the reader already has the context. A package carrying
something self-contained — a runbook, a schema, a table somebody will look up
without reading the rest — earns its own file, because a reader wanting it
should not have to find it inside a longer argument.

**Either way the parent links to it**, so the design is reachable from one place
whichever shape it took.

**A folder appears when its first document does** — never by anticipation. Where
a release or workstream does not exist yet, the document waits with its issue
rather than creating an empty home.

### 2.5 Tracking a change to production

**Commits say `Refs #N`** — except where the change never leaves the repository,
where `Closes #N` is correct, because nothing else will ever close it.

**A reference in a commit message is never only an illustration.** GitHub links
every `#N` it finds, so an example in a document or a commit body attaches
itself to a real issue. Examples use `#0` or `#NNN`, which cannot exist.

**A milestone is a shipping list, and the deploy settles everything in it.** Move
out what is not shipping before deploying. What settlement means depends on the
issue: a project advances to `Post-deployment`, anything else closes.

**Removing a change that fails**: before merge, delete the branch and `main`
never saw it. After merge it is a revert — history keeps both, which is correct
and permanent. That asymmetry is why the bar for merging is *confident this
ships*, not *want to look at it*.

### 2.6 Type of change

**Every issue carries one `Type of change`.** It is descriptive — a change
classifies itself rather than having a test applied to it — and it says what the
change owes before it can ship. The field is authoritative; this describes it.

| type | what it is | ships by |
| --- | --- | --- |
| `documentation` | documents | its route: usually Repository Change |
| `tooling` | scripts, CI, the machinery around the app | its route |
| `cosmetic` | only a visual difference — nothing behaves differently and nothing on the wire moves | Production Release, as a patch |
| `bug` | the app doing the wrong thing | Production Release, as a patch |
| `functional` | the app doing something new or different | Production Release, and **not** as a patch |

**`documentation` and `tooling` do not change the app; the other three do.** That
settles the awkward cases: fixing a bug in `deploy.sh` is `tooling`, because the
app is untouched.

**`cosmetic` exists because a version number describes what the software does.** A
purely visual change is in the image and a person has to look at it, so it takes
the full release path — but nothing it does has changed, so it is a patch. It was
added after the last-move highlight was typed as functional, which made the
release gate refuse a patch: correct for the label, wrong for the change.

**`functional` is read by `check-release-version.sh`**, which refuses a patch
release whose milestone carries one. That is the single place this field decides
something rather than describing it — see [4.8](4.8-artefacts.md).

### 2.7 Evidence follows what the change does

**What a change owes is decided by what it does, not by what it is called.**

**Ask what the change can break.** A tooling change that ships in the image —
`admin-cli` is the example — takes the full release path, because it is in what
production runs whatever its type says. A change that cannot reach production
does not, whatever its type says.

**`enhancement` is deliberately absent** from the field's options: it occupies
the same slot as `functional` and adds nothing.

### 2.7.1 A check that has to wait for a release

**Some post-deployment checks cannot be answered when the change ships.** #214
compares a release's image digest against the previous one, and until a second
release there is nothing to compare against.

**The `Release Check` label marks those**, and two tools read it: `board/turn.py`
shows the project as *waiting for the next release* rather than as a review that
is due, and `deploy.sh` names every labelled issue after a production release —
the moment they stop waiting. Answer them there, then take the label off.

**It is a label rather than a field** because it is temporary and binary: it is
true from deployment until the next release and then never again. A field would
need a value meaning *no longer waiting*, which is the same as not being there.

### 2.8 Closing an issue

**Use `stateReason`, not a label.** `completed` for work that was done,
`not planned` for work that will not be.

**`folded` is the one label that survives**, because no reason fits: a
requirement absorbed into a project was neither completed nor abandoned. It
closes as `completed` and carries the label to say which.

**The triage queue is a requirement with no workstream**, not a label. A label
had to be added and removed by hand; an unset field is the state itself.

### 2.9 Documentation is owed by every type, not just its own

The `documentation` label means *the whole change is documentation*. It is
not how documentation normally gets written.

> A change is not done until the documentation it invalidated has been
> updated, **in the same commit**.

Never a follow-up issue. `docs/4.3-api-schema.md` sat declaring API 2.4 for
five bumps because each change left its own doc update for later, and later
never came for any of them.

Documentation-typed changes come in two shapes with the same process and
different delivery: anything under `docs/` ships nowhere, while a doc comment
in `crates/**` rides the next release and moves the build id like any other
source edit.

### 2.10 Requirements split; projects gather

**The two levels pull in opposite directions, and that is deliberate.** Owner,
2026-08-28: *"requirements should be broken into separate parts. Project should
bring requirements together where it simplifies the delivery, even if it spans
workstreams."*

| | |
| --- | --- |
| a **requirement** | one thing, split as finely as it honestly divides |
| a **project** | as many requirements as one delivery carries well |

**A requirement becomes two** when it **touches both tooling and the app**, when
it **will be two releases**, or when it **belongs to two workstreams**. The second
is the one that gets missed: two releases means two changes even when the type is
identical.

**#160 is the worked example.** It held five GitHub features on one shortlist and
never felt ready to plan, because it was three types at once — a `bug`
(#234, nothing reports a vulnerable dependency), `tooling` (#235, no ruleset
on `main`) and `tooling` (#236, actions never updated). Split on
2026-08-28, each part became obvious on its own.

**A project may span workstreams**, and the test is whether it **simplifies the
delivery** — not whether the boundary is crossed. This reverses what this section
said until 2026-08-28, which read the splitting rule as governing both levels and
would have forbidden a project that gathers work naturally delivered together.

**Splitting a requirement costs nothing; splitting a delivery costs a release.**
Two requirements in one project are reviewed once, branched once, tested once and
shipped once. The same two as separate projects pay all of that twice, and the
second one waits.

**What a cross-workstream project still owes.** It carries **one** `Workstream`
value, because the field is single-select and one owner is the point. It takes
the workstream where the **content** is defined — the same rule that puts the
shared messaging mechanism with the game rather than with everything that uses
it ([3.7](3.7-workstreams.md)). A project that cannot say which workstream
defines it is not one project.

**And the sequencing rule survives the reversal**: where one half generates
requirements for the other, the generating half still goes first, whether they
are one project or two.

#### Spanning two workstreams: split it, and do the end-to-end half first

| | belongs to |
| --- | --- |
| what the game does, what the server says, the DTOs that carry it | **application & game architecture** |
| how that reaches a person: which control, which screen, what a notification does | **client UI** |

**The end-to-end half goes first, and generates the other.** Until the game
decides what happens and what it broadcasts, the UI requirement can only be
guessed at, and the design would be of the presentation of behaviour nobody has
agreed to yet.

**This is the common case, not the exception.** Client UI is a layer on top of the
game logic providing access to every other capability, so most user-visible
requirements have a half in it. That is what the layer is, and §2.11's overlap
test does not apply to it.

**The test for whether a split is needed** is whether the game's behaviour
changes at all. #88, out-of-turn staging, is UI logic alone if staging is purely
client-side, and a split if it changes what the server accepts.

**Deferred work is a second release, so it is a second issue**, raised before
the merge rather than after the release has closed the first. The tell is a
commit or comment saying "left deliberately" with no issue number beside it:
issue #35 shipped that way, its diagram render deferred, the automation closed the
issue, and the published picture disagreed with the prose beside it until #46
finished the job.

Issues #9 and #10 are the worked example. Moving the DTO conversions to where a
client can reach them is `functional` and ships alone; the bot harness that then
becomes possible is `tooling`. One issue each, with the dependency recorded.

### 2.11 What a project is

**A project is a state an issue enters**, not a thing created up front. Issues
group into one, which owns their requirements from that moment; the sources are
folded and closed.

**Never by rewriting a requirement's issue into a project's.** A requirement's
body holds what was noticed and its conclusions; a project's holds seven headings
kept current. Overwriting one with the other destroys the record.

**A project may be raised directly**, with no requirement first, where the shape
is already clear — a record not needed rather than a formality skipped. That is
not a licence to skip triage: it is the same judgement triage would have made,
made once.

**One project or two** is not decided by how many issues went in, but by whether
one design covers them. Two designs mean two projects, however related.

#### The project owns the requirements, so its sources are folded

Once a project owns them, a source issue that is still live is a second place
requirements can change, and two sources drift silently.

**Folding an issue**: copy its content into the project **first**, then close it
with the `folded` label and a comment naming the project. Two rules keep the
freeze from becoming a trap — **fold before you freeze**, because closing an
issue whose requirement was never copied loses it; and **a frozen issue can be
thawed** if it turns out not to belong.

`folded` is a label rather than a close reason because GitHub offers only
*completed*, *not planned* and *duplicate*. The close reason is **not planned**,
which carries the one bit that matters: it was not delivered as itself. This is
the exception to [2.9.8](#28-closing-an-issue) — the
reason is used *and* a label, because no native reason means "its requirement
moved".

#### One project, one design

A project does not accumulate a design per issue it absorbed. It has *a* design,
covering however many requirements it carries and however many deliveries it
takes to satisfy them. That is the fold seen from the other end: folding puts the
requirements in one place, and one design puts the answer there too.

#### Text or a link, decided per heading and driven by size

Owner, 2026-08-22: *"the project issue should either contain the content or point
to a project document. Although this is not a rule that each project will do one
or the other consistently. A small single issue project will have its
documentation within the project issue body, a larger project will have separate
documents and link to them. In the second case the project body should be kept
short to avoid duplicating the documents."*

**Per heading, not per project.** A project may hold its requirements as text and
link to a design; nothing has to be consistent across the five, because the five
are different sizes for different projects.

| | |
| --- | --- |
| **a small, single-issue project** | all six headings are text in the issue. There is nothing to link to, and creating documents for three lines each is the ceremony this process keeps refusing |
| **a larger project** | separate documents, and the heading is a link — **and the body is kept short** |

**The second half of that is the operative one.** A body that links *and*
restates is worse than either, because the two copies drift and the reader cannot
tell which is current. So a linked heading says what the document is and where it
is, and stops.

**The exception is the artefact names**, and it is deliberate rather than an
oversight. They stay in the issue even when a design document lists them again,
because a design lives on the project's branch until the project is live and the
issue is the part that is always visible — see
[2.13](#213-the-impacted-artefacts-and-why-they-are-listed-early). What must
*not* be repeated is the per-artefact detail: the names are an index, the
summaries are the content.

#### Why headings and not paragraphs

**An empty heading and a missing heading look identical in prose and mean
completely different things** — one says *nobody has decided*, the other says
*nobody thought to ask*. Headings make the difference visible, and a script can
check they are present.

A heading with three lines under it is a complete answer. The size of a project
changes how long each one is, never whether it exists.

### 2.12 A branch belongs to a project

| | |
| --- | --- |
| **created** | when the project starts |
| **during** | **the only place edits happen** — code, documents, everything |
| **merges out** | into a release branch, and to `main` as part of testing and deploying. More than once, if the project takes more than one release |
| **deleted** | when the project is **live** and closed |

**The one-place rule is about where a change can be made, not where content
exists.** A project's content reaches `main` every time it delivers while the
branch runs on; what is forbidden is editing in two places, which is what
produces a file whose two versions each look current.

**Deleting the branch only when the project is live is required, not tidy.** A
release branch is always rebuildable from the project branches — cut from `main`,
merge the projects named in the release, stamp the version — and **you cannot
rebuild from a branch that has been deleted**. Keeping it is what lets a project
be dropped from a release right up to the last release it needs.

**Nothing is ever committed directly to a release branch.** A fix made there is
lost at the next rebuild, silently, and the release then ships without a change
everybody watched being made. A defect found in preview goes to **its project's
branch**.

**A project branch is kept current with `main`.** A branch that has not seen
`main` for three weeks makes the rebuild a conflict resolution rather than a
mechanical step, and a conflict resolution is a change nobody reviewed.

### 2.13 The impacted artefacts, and why they are listed early

**The shape, first.** A project has **deliveries**; each delivery has
**artefacts**; each artefact has a **route**, which is a property of the artefact
and never stated. So the project's artefact list is the union of its deliveries'.

```text
project
  └── delivery            one act of putting change in front of its consumer
        └── artefact      what that act touches
              └── route   how it reaches its consumer — derived, not written
```

**The list carries a delivery column**, and that is not tidiness: three things
need the per-delivery set and cannot use the union. The **runbook** is written
per delivery and has to know which artefacts *this* act touches, in what order.
**Rollback** — *"what does undoing this delivery touch?"* — gets the wrong answer
from the union, which names artefacts a different delivery put there. And *"is it
delivered?"* has no answer at all for a project that is half-delivered, which is
every project with two deliveries for as long as it takes.

The union still does what the list was invented for: the collision test between
two projects works on the whole table.

Every project lists what it touches, each marked **new** or **modified**. The
list is a guess when the issue is raised, argued through design, and **accurate
once the design is agreed** — and once the test approach is agreed too, if the
testing builds anything, because **test tooling is an artefact** and the one most
often forgotten.

**Attempt it early even though it will be wrong**, because a wrong list naming
the right file finds a collision just as well as a right one. Three things an
overlap between two projects can mean:

| | |
| --- | --- |
| they are the same work seen twice | one project |
| one needs the other's change first | sequence them, and say so — a dependency found at merge time is found too late |
| they touch different parts of one file | do it once, or accept a conflict somebody resolves under pressure |

**An artefact is not only a file.** A change reaches production five different
ways, and a list that quietly means *files changed* describes only one of them. A
project may touch a host file, a bucket, an alarm and a GitHub label without
changing a line of code.

#### Derived does not mean hidden — show the route

Owner, 2026-08-22: *"in the artefact tables I think we should include the routes
as a column. They are derived from the artefact registry, but it is useful to see
them rather than having to look them up."*

**So the artefact table carries a route column**, and the distinction worth
keeping is between *stored* and *shown*:

| | |
| --- | --- |
| **not stored** | nobody decides a route, and nobody maintains it as an independent fact. It follows from what the artefact **is** |
| **shown** | because a reader asking *"what does delivering this involve?"* should not have to hold the convention in their head and translate each row |

Same shape as `board-status.py` and `board-actions.py`, which display things nothing stores —
where a change is, what a release would ship. **Deriving a value is a reason not
to ask for it, never a reason to withhold it.**

**And the naming convention makes the column checkable.** A repository path, a
`production:` prefix, `OCI`, `github:` — the name already says which kind the
artefact is, so a row whose route disagrees with its name is a **typo, not a
decision**, and a script could say so. Not built; worth knowing it could be.

#### Naming, so two lists can be compared

| kind | canonical name |
| --- | --- |
| in the repository | its path from the repository root |
| on a host | the host role, then the absolute path — `production:/etc/…` |
| a cloud resource | provider, type, and the provider's own name — `OCI bucket tile-lite-elite-backups` |
| a GitHub object | `github:label folded` · `github:ruleset main` |

**A repository artefact is self-naming** — the path is the name and the file
either exists or it does not. Everything else is registered in
[4.8 Artefacts](4.8-artefacts.md), which holds exactly what git does not, and is
therefore also the answer to *"what else was on that box?"*

**Mark a provisional list provisional.** A guess that looks settled is worse than
no list, for the same reason a missing heading differs from an empty one.

#### A new artefact says whether it outlives the project, and what runs it

**Test tooling is the case this exists for**, because it is the only kind
routinely written to be thrown away and then kept by accident.

| | |
| --- | --- |
| **1 · ends with the project** | deleted when it closes |
| **2 · runs in CI** | it has a trigger already |
| **3 · runs on a schedule or a trigger** | the entry says **what fires it** |
| **4 · run by hand** | the entry says **when somebody would think to** |

**The line between 3 and 4 is the one that matters**, and it is not importance:
it is whether anything will run the thing without being asked. **A kept script
with no trigger is worse than no script** — it looks like cover and is not.

**Where it lives is part of the answer.** `scripts/` is run by people and CI;
anywhere else needs saying why.

#### What the design owes on top

The design lists **the same artefacts and what changes in each** — the names are
deliberately in both places and nothing else is, because the issue is the part
that stays visible while the design sits on a branch.

The summary is **what the artefact does afterwards that it did not before**, not
what lines changed. *"Modified: added a function"* is what the table looks like
when it has died.

**And the depth owed is inverse to how well git records it**: least for a
repository file, where the diff is the detail and the summary is the intent above
it; most for a host file or a cloud resource, where there is no diff anywhere, so
that entry **is** the record and must be enough to do it again.

#### And what it reports when it goes wrong

**A design says what its failures will tell somebody.** Owner, 2026-09-06:
*"either way it should report sufficient information on errors so that we can
diagnose the problem. Maybe it already does, but reviewing what is reported or
logged should be part of the design."*

Not a new artefact and usually not new work — most changes already report
something. What is new is that the design **looks at it** rather than assuming
it, because the moment a failure is read is the moment nobody can go back and
add detail to it.

0.7.2 is the worked example, on #319: it exited `1` with every success line
already printed, saying *the deploy failed* while production was live and
correct. Nothing was missing from the code — only anyone having asked what
that exit would mean to a reader.

Where the change runs in the server container, this is
[`4.7`](4.7-log-events.md)'s job and the design points at it. Where it is a
script, the question is what reaches stdout and stderr, and whether that is
enough to diagnose from afterwards.

**And what it reports is documented, not only decided.** Owner, 2026-09-06:
*"APIs should include errors they return as part of their documentation.
Scripts should also document what errors they return or log."*

An error is part of an interface. A caller writes code against *"Current
password is incorrect"* as surely as against the shape of the response that
carries it, and a person reading a script's failure needs to know whether it is
one the script means or one it did not expect.

**The two are documented differently because their readers differ.** An API is a
published contract read by somebody who cannot see the source, so its errors are
written down. A script is run by somebody who has the source in front of them,
so it can be self-documenting (owner, 2026-09-06) — the detail goes in its
header and its `--help`, where it cannot drift from the code that produces it. **An undocumented error is an
undeclared part of the contract**, which is why it belongs with the schema
rather than only in the design that produced it.

**And it goes with the behaviour, not with the fields** (owner, 2026-09-06).
`/auth/login` returns one message for two different conditions, deliberately,
so a caller cannot enumerate display names — which no request type, response
type or status code can express. #329 carries the case.

| what | documented in |
| --- | --- |
| an error the API returns | [`4.3`](4.3-api-schema.md), **against the endpoint that returns it** — part of describing what that call does, not a list of its own |
| an event the server logs | [`4.7`](4.7-log-events.md), which already declares forty-eight |
| what a script reports or logs | its own header and `--help` — it is run by somebody with the source in front of them, so the detail lives next to the code that produces it. [`3.0`](3.0-tools.md) stays a register, and [`4.8`](4.8-artefacts.md) says what an exit status means |

### 2.14 The delivery runbook

**A delivery's steps live in one place.** A delivery with a sub-project keeps
its runbook there, and the parent's delivery list links to it. A pre-approved
delivery has no issue, so its runbook sits under that list. Never both: a
runbook written twice is two places to update, and the one nobody is looking at
is the one that goes stale.

A project's *deliveries* heading holds **one runbook per delivery** — written
before as a procedure, completed afterwards as a record.

| written before | filled in after |
| --- | --- |
| the steps, in order, and the route each takes | which app version or build carried it, and **when** |

#### The delivery log row is part of the delivery

**Write it in the change that delivers**, not afterwards. Owner, 2026-08-26,
reviewing a delivery whose row was missing: *"as it is project delivery it
should have an entry on the delivery log."*

Three deliveries were recorded in three days and **two of the three rows were
added after the fact** — noticed each time, and each time by someone happening
to look. A row written afterwards depends on somebody remembering; a row written
in the same branch cannot be forgotten, because the delivery does not merge
without it.

**This is D36 one level up.** That rule says a decision is applied in the same
commit that records it, or an issue is raised. The same argument holds for a
delivery and its row: recording and doing are one act, or the gap has an owner.

**Only project deliveries get a row**, and pre-approved changes get none — see
[`4.9`](4.9-delivery-log.md), whose order is **oldest first, newest last**, so a
new row is appended.

#### The runbook is filled in three times

| when | what goes in |
| --- | --- |
| writing the project | the steps, in order, and the route each takes |
| before the delivery | the commands as they will actually be typed |
| after it | which version carried it, and when |

**Writing the commands in advance is a design check.** A step that cannot be
written as a command is a step nobody has thought through.

**For the host and service routes it is the only record that will exist** —
nothing else captures what was typed on a machine.

**It is not a second copy of the delivery log**, which holds one row per delivery
saying that it happened. This holds how.

### 2.15 Classifying a change

**Three questions, three answers**, each recorded on the issue in its own field.
[4.8](4.8-artefacts.md) lists every scheme in one place; these are the three that
classify a change rather than describing where it lives.

| question | field |
| --- | --- |
| what kind of change is this? | `Type of change` — §2.6 |
| how does it reach its users? | `Route` |
| which delivery carries it? | `Milestone` |

**None of them says who owns it.** That is the `Workstream`, and it is a
different question: a change to rehearsal's exposure is Operations work even
though rehearsal is not production.

#### Route

| route | reaches its users | takes a semver |
| --- | --- | --- |
| **Production Release** | when `deploy.sh` deploys to production | **yes, always** |
| **Repository Change** | when it is pushed to `origin/main` | no |
| **Other** | when somebody applies it — a host, a console, a deploy to preview or rehearsal | no |

**A release always takes a semver**, even when only the `Caddyfile` changed. The
version is compiled in, so bumping it rebuilds the binary: the new number names
bytes that genuinely differ.

**An artefact has a route and a delivery takes the heaviest of them**, in the
order above. `docs/4.8` records each artefact's route, which is where the field's
value comes from.

**The repository route has one delivery moment: the push to `origin/main`.**
Documents are read from `origin/main` and scripts are run from the local `main`
in dev, so until it is pushed a change exists on one disk. The test is what would
survive a rebuild elsewhere.

**Run an unpushed script to test it, never to use it.** Exercising one to find
out whether it works is how it gets built; using one to do a job depends on a
state that exists nowhere else and cannot be reproduced by whoever looks next.

### 2.16 A gate refuses; a check reports

Two words for two different things, used strictly from 2026-08-21. They had been
interchangeable, and #137's audit found `docs/3.3` describing one as the other —
which is what a word doing two jobs eventually does to a reader.

| | it | example |
| --- | --- | --- |
| **gate** | **refuses.** The work stops and there is nothing to decide | `deploy.sh`'s nine gates; CI's `check` job on a protected branch; the review checklist while a box is unticked |
| **check** | **reports.** A person reads it and decides | `verify.sh` after a deploy; `status.sh`; the warning when tooling lands on `main` |

The distinction is not about severity but about **who acts next**. A gate has
already decided; a check has handed you something to decide with.

### 2.17 Triage: what happens to an issue when it is raised

|||
| --- | --- |
| **requirement**  | A request for a change.  Can be raised quickly and analysed in more detail later.  **Unless the project is already clear** — then raise the project and skip this, see [Straight to project](#straight-to-project). |
| **triage**  | Initial assessment.  Add any useful info but the minimum is ensure a clear short description and set workstream, priority and type of change.  |
| **scope** | Functional options to meet the requirement.  Technical options.  **Feasibility** — check that the option recommended can actually be done, rather than assuming it.  Identify dependencies.  Make recommendations and set effort accordingly.  |
| **project planning**  | Should this requirement be in an existing project?  Should it be grouped into a new project?  Is it urgent and need to be released in it's own project?  |
| **projects**  | When a project is raised the requirement is made a sub-issue, labelled as 'folded' and closed.  Projects have their own lifecycle to deliver the required change. |

#### The Requirement Lifecycle

```text
requirement ──triage──▶ ──scope──▶ ──ready for project──▶ ──planninng──▶ candidate solo project/ candidate grouped project/ on hold/ cancelled
              enriches    enriches  └──── the backlog ────┘   creates
```

The work involved in triaging, scoping and planning requirements is a continual process which is a function of the programme.

#### Applying Decisions — D36

Owner, 2026-08-26: *"either the answer is applied in the same commit as the
decision is marked decided, or an issue is raised."*

**Recording a decision and applying it were two acts, and only the first had a
home.** *"I will apply it later"* is the state this abolishes: later has no
owner, no date and no record, and four times out of four it did not happen —
D34 over D6, D7 left unapplied and going stale, seven decisions living in issue
comments, and D5 reaching the documents but not the issues that assumed
otherwise.

> A decision marked **answered** is applied to the numbered documents **in the
> same commit** that marks it answered — or an **issue is raised** and named in
> the decision.

**An issue is the honest answer** when the decision needs design, or is blocked
on work that has not happened. D7 was exactly that. The failure was not the
deferral; it was that the deferral lived nowhere a tool could see.

**It gives *applied* a signature**, which is what makes checking it possible: a
citation in a numbered document, or an issue number. Both are queryable, and a
good intention is not.

#### A decision is an issue — D39

**Only where there is a choice to discuss.** Owner, 2026-09-21: *"Decisions are
only useful when there is a choice to be discussed. A settled decision lives in
the permanent documents and claude files."* So the issue is the place the
argument happens, not the place the answer is kept. Where the answer is already
settled — the owner says it, or it follows from what is written — it goes
straight to its owning document and to `CLAUDE.md`, with the argument in the
commit message. No issue, no `D` number, nothing to close later.

**The test is whether anybody still has to be convinced.** Options that need
weighing, a trade nobody has priced, a rule two people read differently: that is
a decision. *"Production access is mine"* is not, and raising an issue for it
would have produced a second home for a rule that already has one — one fact,
one home, failing in the place it is written down.

**And a decision issue closes once it is applied**, for the same reason: what is
settled lives in the document. One stays open deliberately — #382, D54, whose
threshold is still being measured — and that is an open question wearing a
decided answer, not a decided one being kept.

**A settled decision issue is never maintained**, which is the general rule in
[The documents live; the issues expire](#the-documents-live-the-issues-expire)
applied here rather than a second rule. Owner, 2026-09-21: *"we don't want to
maintain a settled decision issue if things change, only the documentation
carrying the decision."* When the answer later changes, the document changes and
the issue does not.

**A decision is raised as an issue of type `Decision`**, from
`.github/ISSUE_TEMPLATE/decision.yml`. It has no `Stage` and no `Phase`.

| | |
| --- | --- |
| **the body** | the context, the options and a recommendation. Then *Agreed Decision*, written when it is settled |
| **the comments** | the argument, as everywhere else — discussion in the comments, conclusions in the body |
| **`Open actions`** | what the decision creates, `(Steve)` or `(Claude)` prefixed so `board-actions.py` shows it. The shapes it may take are below |
| **`Decision State`** | `Asked · Feedback Provided · Documented Ready for Sign-Off · Decided · Actioned`, the columns of the Decisions board. It says who is holding it |

##### A decision is not a change vehicle

**It records an answer and routes the work.** Owner, 2026-09-08. So a decision
never carries a delivery of its own, and an action on one is a routing act
rather than the work itself:

| the action | |
| --- | --- |
| **raise a requirement** | where nothing yet owns the thing decided |
| **add a requirement to a project** | where a project does |
| **update a project** — its design, test approach, artefacts | where the answer changes how that project will be built |
| **update the documentation** | where the answer is a rule rather than work |
| **a small tooling change** | the same, where the rule lives in a script |
| **close or cancel** | where the answer is *not to do it* |

**The last three are pre-approved changes**, and they are allowed *only where no
suitable requirement or project already exists*. Where one does, the change
belongs to it: routing it there is the action, and doing it there is the work.

**So a decision takes no semver and no letter milestone.** `pre-approved` is the
only one it can carry, and only when it made such a change. It makes no
delivery, so it gets no row in [4.9](4.9-delivery-log.md).

**Which is why `deploy.sh` cannot meet one.** `settle_issue` closes a
non-`Project` in a release milestone under *"no review to wait for"* — true of a
requirement and false of a decision, which closes only when the owner has read
the outcome (D44). A decision in a release milestone would be closed unread.
The rule above makes that unreachable rather than guarding against it in code.

##### Who holds it, and how it changes hands

**The state says whose turn it is** — D45, and that is its main job. The
`(Steve)` / `(Claude)` prefixes on the actions say *what* to do; the state says
*who holds it*. #321 is why: it was answered in a comment and its `(Steve)
choose` action ticked, which took it off the owner's list and put it on nobody's.
A tick means a task is done and should not decide routing.

| state | with | until |
| --- | --- | --- |
| `Asked` | **the owner** | he gives his view. Claude raised it with options and a recommendation |
| `Feedback Provided` | **Claude** | he has commented; Claude responds and **writes the decision down** |
| `Documented Ready for Sign-Off` | **the owner** | it is documented; he reads it, ticks the box and moves it on |
| `Decided` | **Claude** | signed off. This is when applying falls due, and not before |
| `Actioned` | **the owner** | applied; he reads the outcome and closes it |

**A tick means a task is done, not that a state has moved on.** The two came
apart on #321: the owner ticked *choose* while commenting, then the discussion
continued for another round. Since routing is by state, a premature tick costs
nothing — `actions.py` falls back to naming the state's own act when the body
has no unticked items left, so a decision cannot disappear from both lists the
way #321 did before D45.

**Documenting it is what ends `Feedback Provided`** — not Claude agreeing. That puts
the *Agreed Decision* section on the critical path rather than beside it, and
gives the owner something to sign off against.

##### Why there are five states and not three

**`Documented Ready for Sign-Off` is not redundant with `Decided`.** I argued it was, and
was wrong: `Decided` means *signed off*, and what was missing is the state
before it — written down, waiting to be read. Conflating them leaves no way to
say *the decision is documented and needs your reading* as distinct from *your
reading is done*.

**The names were argued over, and the rejected ones are on #325** with the
constraint that ruled them all out: no name may mean *settled* before the
settling happens.

**`Decided` is the state worth having.** It is *agreed but not yet applied* —
the gap D36 exists because of, and the one the glossary's decision index could
not express, since a `Dxx` was either answered or not. A decision sitting in
`Decided` is visibly owing something.

##### When a decision closes

**`Actioned` means applied; closed means read** — D44, and the two are
different moments. `Actioned` is set when the work is done: an agreed decision
with every action ticked. **The owner closes it**, once he has read the outcome.

The rule it replaces said the two coincide. #323 is why: it was agreed, applied
and closed inside one exchange, so its outcome — what was tested and why nothing
was built — never reached anybody. A decision that vanishes on being applied has
not been communicated, only finished.

So a closed decision is still `Actioned` and that is checked; an **open** one
that is `Actioned` is the normal state of a decision waiting to be read, and
`actions.py` shows it as *applied — read the agreed decision and close it*.

**Nothing enforces the closing**, and that is deliberate. Owner, 2026-09-05:
*"I am aware there is a risk I just leave Decisions in Actioned, but my desire
to tidy up will make me want to clear the column."* The mechanism rests on a
habit rather than a gate, knowingly — a reading step is a poor thing to refuse
work over.

**The field and the body are two records of one fact**, so
`board-check.py` checks they still agree — in both directions, because a
board column is dragged in a browser and a body is edited in an editor, and
either can move without the other. **The body is the authority and the field is
the index**: only one of them can be read by somebody deciding what to do next,
and it is not the column.

**Closed meaning applied is the whole of D36 made mechanical.** That rule gave
*applied* a signature so it could be checked; this makes the signature the
issue's own state, so *"I will apply it later"* is a queue entry rather than a
good intention.

**Where a decision belongs** (owner, 2026-09-05):

| field | |
| --- | --- |
| **Parent** | the project or requirement that triggered it, as a sub-issue |
| **Workstream** | who owns it |
| **`Topic`** | a **named** project or focused subject, `One Game Model` say. **Unset is normal** — the level a decision sits at is already said by Parent and Workstream, and saying it twice is how the two come to disagree |

##### The earlier decisions are an archive

**D1–D38 are not issues.** They were settled before this existed and live in the
process-definition glossary, with the argument for each embedded in the section
it belongs to. That is an archive, and the boundary is stated there rather than
migrated: all 38 are answered, 43 citations of `Dxx` point into them, and
extracting the arguments would gut a document that is also a glossary. New
decisions number from **D39** and keep the `Dxx` in the title, so a citation
reads the same either side of the line.

#### What triage asks

**Eight questions, in no fixed order** — D35: you cannot prescribe which
categorisation gets made when. Some answer themselves; the last three are where
the value is.

| | question | where the answer goes |
| --- | --- | --- |
| 1 | **Is it real, and still relevant?** | close it, or carry on. *Reject* is a legitimate outcome, not a failure |
| 2 | **What kind of change is it?** | the **Type of change** field |
| 3 | **What does it touch?** | the artefact guess. Route is derived from it, so route is never asked |
| 4 | **Which capability owns it?** | the workstream — made a sub-issue of it |
| 5 | **What carries it to users?** | the release attribute — a milestone |
| 6 | **How big is it, roughly?** | the **Effort** field. A band, not an estimate |
| 7 | **What else does it relate to?** | the comment: dependencies, overlaps, and whether it should be planned on its own at all |
| 8 | **What do we know now that the raiser did not?** | the comment. **Conclusions are edited into the body; discussion stays in the comments** |

````markdown
on its own at all.*

### What we know now that the raiser did not

*The point of the exercise. If there is nothing here, triage found nothing.*
````

**No footer.** Comments used to end `Typed by Claude` or `Typed by Steve`, from
when both of us posted as one GitHub user and a marker in the text was the only
thing to go on. Since #206 delivery 2 there are two accounts — owner,
2026-09-21: *"We no longer use the footer in comments, we rely on the different
GitHub accounts."* The author is a fact GitHub records; the marker was a
convention nothing enforced, and a check of the thirty most recent comments on
2026-09-03 found it on none of them.

**It holds only what no field can hold** — the artefacts, the context, and what
triage found that the raiser did not know. `Workstream`, `Type of change`,
`Effort` and `Priority` are set in the sidebar, and asking again here would
record the same fact where nothing reads it.

**No date**: GitHub timestamps every comment, and a saved reply cannot fill in
today's, so a typed one eventually goes stale.

**Question 1 has no row.** If the requirement is not real or no longer relevant
the issue is closed, not annotated — *reject* is an outcome of triage rather
than a value in it.

**Leave nothing blank in the last two.** Context and what-we-know are where
triage earns its place; a comment with both empty has classified an issue rather
than assessed one. Keep them short: triage decides **whether and with what**,
not **how**, and a comment that argues the design has done the project's work
before the project exists.

#### The order the questions are asked, and why

| | question | why here |
| --- | --- | --- |
| 1 | **do we want it at all?** | otherwise it closes as *not planned*, with the reason in a comment. Everything below costs effort that a rejected issue should not spend |
| 2 | **what kind of change is it?** — the **type** label | it is the cheapest question, it is answerable from the issue alone, and the release attribute and the process both follow from it |
| 3 | **what would it touch?** — the first guess at the **impacted artefacts** | wrong at this stage and worth writing anyway: **this is the step that discovers the issue overlaps work already in flight**, which changes the answer to question 5 |
| 4 | **which capability?** — the **workstream** | every issue has one. An issue without a workstream is an issue not yet filed — **and see the test below, because this question is doing more work than it looks** |
| 5 | **does it belong to work that already exists, or start its own?** | answerable only after 3 and 4, which is why they come first |

**Impact is not asked**, because it is derived: *care scales with who a defect
reaches, and how soon*, and that follows from route and environment. A change in
the artifact reaches users when it goes live; one applied on a rehearsal host
reaches developers next time somebody uses it. Triage **states** the impact where
it is not obvious; it does not collect it as a field.

#### The four outcomes

Question 5 has four answers, and every issue that is not rejected reaches one of
them:

| outcome | what it means | release |
| --- | --- | --- |
| **pre-approved** | meets the [standard-change criteria](#22-when-to-branch-and-what-pre-approved-means). Implemented **directly on `main`**: no branch, no project, no review | **nothing**, or a patch it rides along with |
| **a patch project** | small or urgent, and its own project with one requirement | **patch alone** |
| **a project of its own** | large enough to owe a design, a test approach and an artefact list | **minor** or **major** |
| **folded into another project** | its requirement moves into a project that already owns the subject. Closed as *not planned*, labelled `folded`, with a comment naming the project | none of its own — it ships inside the project's |

**And a fifth state, which is where most of the backlog sits**: *not decided
yet*. It is a real answer and not a failure to answer — question 5 is the one it
is honest to defer, because it depends on what else turns out to be ready.

#### What the four have in common, which is the point

**None of them is new machinery.** Each is a combination of things already
recorded: the `Type of change` field, the milestone, and whether the issue owns
a project or joins one. Triage is not a fifth axis — it is the moment those
attributes get their first answers.

**Two of the four end with the issue closed** and its work still to come, which
is why `folded` exists and why *closed* has to stay answerable in two ways:
**delivered**, or **its requirement moved**.

### 2.18 Exceptions to the normal process, and pre-approval

The normal process for making a change involves a requirement, which is folded into a project, which is developed on a branch, which is merged into a release, which is deployed to Preview, Rehearsal and, finally, Production.

However there are exceptions to this process.  These can apply in the following situations:

- the change is well understood and does not need further analysis
- the change does not affect the production service
- the change is small and already agreed
- the change is only to documentation for a particular project

In particular a change can be 'pre-approved' meaning it is allowed to bypass parts of the normal process.

#### Make tooling changes when they are first needed

Owner, 2026-09-02. Tooling work is scheduled by the first thing that needs it,
not by the fact that it would be an improvement. A change nothing is waiting on
is paid for now and used later, and *later* is where it goes stale before it is
used at all.

**#279 is the worked example.** The desktop client compiles a vulnerable
`webbrowser` and unmaintained GTK3 bindings, and neither can be fixed without a
dioxus upgrade. That upgrade is real work, and no desktop build is distributed
to anybody — so it waits for #38, the decision about a download site, and
happens as part of it.

**It is a scheduling rule, not a licence to defer.** The requirement is still
raised and still says what is wrong; what waits is the doing. The thing that
would make it wrong is silence — a defect nobody wrote down, waiting on nothing.

**On Hold comes after triage and scoping, not instead of them.** Owner,
2026-09-02: *"it should go through Triage and Scoping on the way, which sets some
more fields."* A requirement parked before it is scoped is parked without a
priority, an effort or a type — so nothing can weigh it against anything else
when the thing it waits for arrives. Scoping is also what produces the
dependency note that says why it is waiting.

**So a waiting requirement goes one of two ways**, owner 2026-09-02:

| | |
| --- | --- |
| **On Hold**, with a note under **dependencies** saying what it waits for | when the thing it waits on is not yet a project |
| **folded into that project** | when it is, because the need and the work are one piece |

Issue #279 took the first: #38 is a requirement, not a project, so there was nothing to
fold into. If #38 becomes a project, #279 folds into it — the dioxus upgrade and
the vulnerabilities it clears are the same work.

#### Straight to project

If the change is well understood and does not need further analysis there is no reason to raise a requirement.  A project can be raised directly.

**It has to be said where the requirement rule is stated, not only here.** Owner,
2026-09-02: *"there is an earlier rule 'where there is a gap raise a requirement',
so that tends to happen before we consider 'straight to project'."* A rule stated
first is the one followed, so the caveat belongs beside it — which is why the
requirement row above carries it.

**A requirement can also be converted to a project**, and nothing is lost by
having raised one. The point is not that converting is difficult; it is to avoid
spending time raising a requirement when the project's shape is already known.
Issue #288 was raised as a requirement and converted the same hour, which is the step
this rule exists to skip.

#### Change directly on main

Changes can be made directly on main without going through a branch and pull request if they are straightforward documentation or tooling changes which do not need a review before they are 'live'.

**The approval is recorded on the issue, as the `pre-approved` milestone.**
Owner, 2026-09-02, on first recording it at all: *"It's a way for me to do it
with a record, rather than just saying in chat."* It was a separate
`Pre-approved` field until 2026-09-04, when it became a milestone value and the
field was deleted — two fields were carrying one answer between them, and an
issue could disagree with itself.

**The question it answers, in the owner's words:** *"there is no risk doing this
directly on main without further review."* That is the branch test asked from the
approving end — [2.2](#22-when-to-branch-and-what-pre-approved-means) asks whether
the old version is still needed in the interim, and this says nobody needs it.

**It is set on a project or on a project delivery, and not on a requirement.**
Milestones go with deliveries; a requirement is not a thing that ships. For a
requirement the answer is the triage outcome instead: choosing *straight to
`main`* rather than *make it a project* says the same thing.

| on a | `pre-approved` says |
| --- | --- |
| **Project** (parent) | the project needs no branch — everything it touches goes straight to `main` |
| **Project** (work package) | this delivery specifically can be done on `main`, whatever the parent does |

The second row is why a delivery may carry its own milestone: a project heading
for a release can still have one delivery — a documentation update, say —
approved to go directly.

**Anything other than `pre-approved` means not pre-approved**, including no
milestone at all. Owner, 2026-09-02, when it was a field: *"we must take that as
meaning 'not pre-approved', or it will catch us out in the future."* Only the
explicit value authorises; a semver, a letter, `no-release` or nothing means the
change takes a branch and a review.

**That is deliberately the fail-closed reading**, and the same choice as
`REHEARSAL_ACCESS_KEY`'s sentinel: a missing value means locked, not open. It
also survives the thing that would otherwise catch us — an unset milestone is
invisible to a board filter, so a list of *things not yet approved* built that
way comes back empty and looks reassuring.

#### Changes to repo only

Changes to documentation or scripts are 'live' as soon as they are merged into main and pushed to origin.  They only require a branch and a pull request review.

#### Changes to configuration outside of the repository

Such changes are not visible to the repo.  They are made manually and the project status is updated manually.

### 2.19 What planning produces: the roadmap

**The roadmap is which projects go together, and in what order.** Two things
answer it, from the same issues, and neither is maintained by hand:

| | answers |
| --- | --- |
| the **board views** | what is in each release, what is blocked by what, and the backlog — live, filtered and grouped, and the place to work from |
| [1.5](1.5-work-in-progress.md) | the picture: what depends on what and what belongs to what, drawn by `scripts/roadmap-diagram.py` and regenerated |

The board is the answer where the question is *what is the state of things now*;
`docs/1.5` is the answer where it is *show me the shape*, and it is the half
that survives in the repository. `scripts/roadmap.sh` was the third answer until
2026-08-28, when #229 retired it in favour of the views.

**Ordering is the `Phase` field**: `Q1` is next off the blocks, then `Q2` and
`Q3`. Projects at `Scope` are not yet ordered.

**It carries no dates, deliberately.** A date needs an estimate, an estimate
needs a commitment, and nothing here obliges anybody to meet one. `Q1`–`Q3` say
what is next without inventing a day it will happen.

#### Four relations between two projects

| | means | example |
| --- | --- | --- |
| **can** go together | nothing shared. The default | most small changes |
| **should** go together | one makes the other testable, or they share a cost worth paying once | a schema change and the code that reads it |
| **cannot** go together | one needs the other's change to exist first, or both touch the same artefact | an overlap between two artefact lists says so |
| **should not** go together | allowed and unwise. A rollback takes back the whole release, so a change that must not be reverted should not ride with a risky one | a security fix; two large projects |

**The last row is a judgement and the third is a fact**, which is why they are
different words. *Cannot* is discoverable — compare the artefact lists. *Should
not* has to be decided by somebody weighing what a rollback would cost.

#### Where a dependency is recorded

**On the project that waits, under its own heading** — the sixth, added
2026-08-22 when writing the templates showed that nothing held it:

```markdown
## Dependencies and related work

- **waits on #71** — the seam it introduces is what this plugs into
- **overlaps #165** — both touch `crates/server-game/src/app/games.rs`
- **anticipates #29** — the store is shaped for per-game eviction, which #29
  will want. If #29 is dropped, this shape is reviewable
```

**One line per relation, naming the issue and the reason.** The reason is the
part that survives: *"waits on #71"* without it becomes unfalsifiable the moment
that issue changes shape.

**Three kinds, and they are not interchangeable:**

| | means | discovered by |
| --- | --- | --- |
| **waits on** | cannot start, or cannot ship, until that one has | a person, usually while designing |
| **overlaps** | touches the same artefact | **comparing artefact lists** — mechanical |
| **anticipates** | this design makes room for that project | impact assessment, and it must **name** the project, or it is speculation |

**It is written on the project that waits**, not on both, so there is one place to
change when it resolves — and since 2026-08-28 it is written as a **GitHub
dependency**, `blocked by`, rather than as prose somebody has to read. A blocked
issue carries a **Blocked** marker on the board and in the issue list, and the
relation is readable by tools: `Issue.blockedBy`, `Issue.blocking`, and
`gh issue list --json blockedBy`.

#### Store the dependency, derive the order

The roadmap is not written down and maintained. **What is recorded is the
relation** — *this project waits on that one* — on the projects themselves, and
the order follows from it.

That is the fifth time this shape has come out: route, the process category, the
milestone's contents, the release branch, and now the sequence. **We store what
somebody decided and derive what follows.**

**One naming point to settle.** `docs/1.4-roadmap.md` is a *product* roadmap —
where the project came from and where it is going. That is a different thing from
the delivery order. Either 1.4 is renamed to say so, or both are qualified —
*product roadmap* and *delivery roadmap* — wherever the two could be confused.
Four references to 1.4, so the rename is cheap if it is wanted.

**A requirement does not become a different kind of thing when it is triaged.**
It is the same issue in a later state, which is exactly why the state needs no
machinery to hold it: a workstream as its parent, and not yet folded.
*Triaged requirements* is not a fourth noun; it is an adjective doing honest
work.

**The second transition does create a new thing**, and that asymmetry is the
point of [D33](#211-what-a-project-is): triage edits
labels, planning raises a project issue and folds the requirement into it.

#### The backlog is the standard word for the middle state

Adopted rather than coined, on the same rule as everything else here: a reader
who knows the term maps straight on to it. **The backlog is the set of triaged
requirements** — classified, not scheduled, and not yet anybody's project.

Which also makes *"the backlog"* mean something precise here rather than "all the
open issues". An untriaged requirement is **not** in the backlog; it is in the
queue in front of it.

#### These attributes stop at the fold

**The backlog's job ends when a requirement folds into a project.** Its fields
freeze at that moment — they are the record of what triage thought, not a status
anybody maintains afterwards. The project's own fields take over.

**What the backlog records afterwards is only that it was done**: the requirement
closes with `folded`, the sub-issue link says which project took it, and
[4.9](4.9-delivery-log.md) says when that project delivered.

**Triage gathers; planning decides.** An answer nobody can give yet is left
unset, which is what an empty field already means. Triage may recommend a
sequence; it does not set one.

**`Priority` is a judgement and will stay one.** It could be derived — score each
requirement against fixed objectives and total them — but that only works where
somebody is obliged to meet the objectives. Nothing obliges anything here, so a
scoring model would be a longer way of writing the same judgement.

#### Two hierarchies, meeting at the project

Worth stating because it explains why *requirement* is absent from
[the terms](#1-the-flow-how-a-change-reaches-production):

| | |
| --- | --- |
| **the terms** — programme, workstream, project, work package, delivery, release | how **work** is organised |
| **requirements** | what is **wanted** |

They are different hierarchies and they meet at exactly one place: **a project
owns requirements**, which is D18's first heading. That is why a requirement is
not a small project and a project is not a large requirement.

### 2.20 Workstreams: overlapping requirements should land together

**What a workstream is, and which one owns what, is `docs/3.7`.** This section is
only the lifecycle rule that follows from it.

> **If two requirements touch the same artefacts and sit in different
> workstreams, the workstreams are drawn wrongly** — not the requirements.

**Because work that collides has to be planned together.** Two requirements
about the same file in two different workstreams are planned in two different
sittings, and the collision surfaces at merge instead of in the plan. A
recurring overlap across a boundary is evidence to move the boundary.

**So the artefact lists in 3.7 test the taxonomy**, not only each other. That is
what makes the workstream list falsifiable: *a capability we maintain* is true of
any list, and this is something it can be wrong about.

### 2.21 Impact assessment writes context, not only a list

Owner, 2026-08-22: *"when I wrote an impact assessment for a new request I
would always add context — how does this relate to other projects. It would help
us with planning and also the design: we will change it this way for this project
because we know another project is coming which will want this feature."*

**Three outputs, and the third is the one usually left out:**

| | feeds |
| --- | --- |
| **what it touches** — the artefact list | the collision test, and the rollback list |
| **how it relates to other work** — depends on, overlaps, duplicates | planning, and the order |
| **what that means for the design** | **the change itself** |

**The third changes what gets built, not only when.** *"Put the seam here rather
than there, because #71 will want to plug into it"* is a decision made on
information living entirely outside the issue being designed. Unwritten, the next
reader finds a shape with no reason and tidies it away.

#### The guard it needs, because this is how over-engineering starts

*"Another project is coming"* is also the oldest excuse for building what nobody
asked for. The difference between anticipation and speculation is whether the
anticipated thing is **named**:

- **name the project** the design is making room for, so the claim is checkable
- **if that project is dropped, the shape it justified becomes reviewable** —
  somebody can find why the seam is there and decide whether it still earns its
  place

Unnamed, *"we might need this later"* is untestable and permanent. Named, it is a
bet with something to settle it.

### 2.22 Triage and planning are separate steps

**Triage and planning ask different questions of different scopes**, which is why
they happen at different times.

| | triage | project planning |
| --- | --- | --- |
| **scope** | one requirement | across all of them |
| **when** | the moment it is raised, or shortly after | when there is appetite and capacity |
| **cost** | seconds | a sitting |
| **the artefact list** | **produces the guess** — what would this touch? | **compares the guesses** — do any two overlap? |

That last row is the one that had been muddled. The guess is per requirement and
belongs to triage; **the comparison is across requirements and belongs to
planning**, which is where two projects discover they collide.

#### The state needs no new machinery

A **triaged requirement** is an open issue whose parent is a workstream, and
which has not yet folded into a project. Both are already true and queryable, so
the state is visible without inventing anything to hold it — and how far it has
travelled since is the `Stage` field, below.

#### And it gives the missing capability a home

*Pipeline management* — what is in flight, in what order, what waits on what —
has been the thin one since it was named. **It is project planning**, and it was
homeless because the model had no stage for it: triage was doing per-item work
and projects were already committed.

The tools for it exist — `status.sh`, the board's release and backlog views, and
an overlap between two artefact lists. What is still missing is the **rule**: when the pipeline is
looked at, who decides the order, and where a dependency is recorded once found.
Naming the stage does not close that, but it says where the answer will go.

### 2.23 The journey after triage: the `Stage` field

**On requirements only**, added 2026-08-28 (#229). `Scope, Options and
Dependencies` includes **feasibility** — checking the recommended option can
actually be done, rather than assuming it:

| | |
| --- | --- |
| *unset* | raised, nobody has looked. The inbox |
| **Triage** | initial assessment — keep it? priority, type of change |
| **Scope, Options and Dependencies** | define scope, functional and technical options, and overlapping issues |
| **On Hold** | scoped, and waiting on something named under its dependencies |
| **Ready for Project** | understood well enough to be planned |
| **Candidate Project 1 · 2 · 3** | grouped with the others carrying the same number — a project waiting to be raised |

**The candidate stage is three outcomes, not one**, and that is deliberate: a
candidate may join a project that already exists, combine with others into a new
one, or be a project on its own. Which of the three it turns out to be is a
planning decision, and planning is where it belongs — triage gathers, planning
decides.

#### The numbered slots are positions, not names

**`Candidate Project 1` means *the next project this workstream will raise*.** It
is a position in a queue, so it is reused: when 1 is raised, what was 2 becomes
the next 1.

**Dragging a requirement into a numbered column is the act of grouping it** with
whatever else carries that number. Three columns means three candidate projects
per workstream, each holding as many requirements as belong in it — a limit on
how far ahead planning goes, not on how much work a workstream may have.

**So `Ready for Project` is a queue and is meant to have a length.** A
requirement sitting there is understood and unscheduled, which is a resting
state rather than a backlog failure.

#### Non-functional design is a heading, not a habit

Owner, 2026-09-22, after reading a 2010s integration domain's design process:
every design presentation there answered **capacity; error handling and retry;
volumetrics, queue depth and timeouts; encryption and tokens** — as standing
sections, for every change, however small.

**The argument for adopting it is two of our own projects.** #402 exists because
nothing asked what a change does when it fails; #291 exists because nothing asked
what a change costs. Both accumulated into projects, and a project is the
expensive way to answer a question that was cheap at the time it should have been
asked.

**So four questions, and *none, because…* is a complete answer to any of them.**
Most changes add no load and no timeout. What the heading stops is nobody having
asked — and a section that cannot be answered *none* becomes a ritual, which is
worse than no section.

| | |
| --- | --- |
| **capacity** | what this adds to load, against which ceiling in the capacity plan |
| **failure** | what can go wrong, what the caller is told, what reaches the log, whether the server should act |
| **limits and timeouts** | any new timeout, queue depth, rate limit or concurrency bound, **and where its number came from** |
| **secrets and access** | anything touching credentials, tokens, or who can reach what |

**The third one carries #291 R9's rule down to every change.** A limit whose
number came from nowhere is the defect that requirement names; asking here is how
it stops being created in the first place.

#### A dependency is declared from both ends

**`waits on` has an inverse and it was missing.** `is needed by` is the same edge
written from the other side, so a relation exists in both bodies rather than in
whichever was written second.

**#400 is why.** Its eight customers were found by somebody going looking through
`docs/3.7` and three issue bodies, rather than by each customer having said so.
Had the edge been declared from both ends, the scheduler's existence as a shared
mechanism would have been visible from any one of them.

**It is not bookkeeping for its own sake.** A project with many `is needed by`
lines is a shared mechanism whether or not anybody has called it one — which is
the test [the shared-mechanism exception](#the-exception-a-shared-mechanism-is-owned-once-and-designed-to)
asks, answerable by reading rather than by judgement.

**The edge itself is a GitHub dependency link; the lines are its reasons.** A
`waits on #N` or `is needed by #N` goes under *Dependencies and related work*,
and the same edge is set in GitHub (`blockedBy`), one link serving both ends.
The link is what the context header at the top of every project shows, by
number and name, and `board-check.py` reports a line in that section with no
link behind it. A dependency written anywhere else in the body is not read.

#### Related change belongs in the same project

Owner, 2026-09-21: *"I am keen we keep related changes in the same project so
they can be designed together. I want to minimise having to coordinate design
across projects."*

**The design, not the delivery, is what decides the boundary.** Work that has to
be designed together goes in one project, and the project then splits into as
many work packages as it has routes and moments. Splitting it into two projects
instead buys nothing and costs a coordination: two bodies to keep consistent, two
designs that can drift, and a change to one that has to be noticed by whoever
holds the other.

**A different route is not a reason to split a project.** It is a reason to split
a *delivery*, which is what a work package already is. #329 is the worked
example: the errors, the gate and the scripts' refusals went straight to `main`
as a `Repository Change`, and changing what a caller is told when the database
fails takes the image and a semver. Two routes, two work packages, one project,
because both answer the same question — what a caller is told when a call fails.

**What does justify two projects** is subjects that happen to touch: the same
file, the same week, the same workstream. The test is whether deciding one
constrains the other. Where it does, one project; where it does not, the link in
*Dependencies and related work* is enough.

**This narrows nothing about issues.** A requirement still folds into the project
that owns its area rather than becoming a new number, which is the same
principle one level down.

##### The exception: a shared mechanism is owned once and designed to

Owner, 2026-09-21: *"where there is a shared mechanism it is owned by one
workstream, so other workstreams design to it. That is an exception to the
principle."*

**So a mechanism several functions need does not get designed inside whichever
project reaches it first.** It is owned by one workstream — `docs/3.7` says
which, and the rule there is that ownership follows where most of its content is
defined — and it gets a delivery project of its own.

**That project treats every use case as a customer.** Each one feeds requirements
for the generic mechanism; the project's job is to satisfy those generic
requirements and nothing more. Each workstream then builds its own functionality
on top of what is delivered, in its own project, against an interface that
already exists.

**Why this does not contradict the principle above.** Designing related change
together is cheap when the work is one subject. A shared mechanism is not one
subject: it is one *substrate* under several. Folding it into the first caller's
project makes every later caller a change to that project, which is the
coordination cost the principle exists to avoid, pointed the other way.

**The test is whether the thing would exist for only one caller.** If it would,
it belongs to that caller's project. If it would not, it is a mechanism and owed
its own delivery.

**And that delivery ships with its first customers.** Owner, 2026-09-21: *"The
scheduler should be in the same release as its first customers, so it can be
tested against a real requirement."* A mechanism released alone has nothing to
prove it against: its tests are its own, written by whoever built it, against the
interface they designed. The first real caller is what says whether the interface
was the right shape, and finding that out a release later means changing a
mechanism that is already live.

**So a mechanism project is scoped and designed independently and scheduled
jointly.** It owns its requirements and its own phase, and its milestone is the
one its first callers carry. That is the same shape as any other work packages
sharing a milestone — which is how a delivery says *these go together* without an
issue of its own.

**Unset and `Triage` are different states, and both are kept.** Unset means
nobody has looked; `Triage` means somebody is looking. Unlike the retired
`needs-triage` label, neither has to be added or removed by hand — the field is
set when the work is done.

#### The industry's names for these stages

Kept because the process is meant to be portable: someone arriving from another
programme should recognise what this is, and someone leaving should be able to
name it.

| here | elsewhere |
| --- | --- |
| raising a requirement | demand intake |
| triage | demand qualification |
| scope, options and dependencies | solution shaping |
| project planning | portfolio or pipeline management |
| a project | delivery |

**Raising an issue stays a five-second act**, whatever it is called. Nothing
downstream assumes the person raising it knew anything beyond what they noticed.

#### A recurrence is a date in an issue body

**Something that has to happen again gets a line, not a reminder.** #291 R2
asked for the capacity plan to be reviewed on a recurrence rather than when
somebody remembers, and the form is:

```text
**Next capacity review due:** 2026-12-21 — **Claude**
```

`board-actions.py` surfaces it on the day it falls due and every day after,
labelled like a checkbox so a reader sees whose move it is. **Doing the thing
moves the date on**, which is what makes it recur — and that date is the only
state there is. No store, no last-run file, nothing to reconcile after a
restart, which is #166's reasoning applied one level up: rederive rather than
record.

**It is not gated by the phase, and checkboxes are.** A box written at design
describes work a later step will do, so `DUE_AT` holds it back. A date describes
nothing — it is the statement that this comes round again — so a review falling
due while its project sits at `Design and Test Approach` is due then.

**This is not the mechanism for a job a machine runs.** Owner, 2026-09-21:
*"Reviewing the capacity plan requires Claude to update and Steve to review, so
an issue date makes more sense."* A benchmark run needs nobody and belongs to
the scheduler (#400); a review has to reach a person and wait for them. The two
look alike only because *recurrence* is one word for both.

#### Look it up before naming it

Owner, 2026-09-21: *"Refer to ITIL, none of this is new to us. We should be
reusing the industry standard terminology and process."*

**So the table above is the pattern, not a curiosity.** When a practice this
programme needs already exists in ITIL — incident and problem management, event
classification, change types, release against deployment — the terms and the
structure are taken from there, and the document records which practice an answer
came from. Inventing a parallel vocabulary costs twice: once writing it, and
again every time somebody has to learn that our word means the standard one.

**It is a reason to read before designing, not a reason to adopt wholesale.**
ITIL is written for organisations with separate teams and change advisory boards.
What is taken is the vocabulary and the shape of the practice; what is left is
ceremony that needs more people than this has.

**Where ours already differs, the difference is stated rather than hidden** — see
the mapping tables above, which say what our word answers and which axis it sits
on. A reader who knows ITIL should be able to find their footing in a page.

## 3 Notes on release scope and version numbers

### 3.1 What closing a release's scope does not freeze

Closing scope stops **new issues and new functionality** entering a release. It
does not freeze the issues already in it: user testing checks the requirement
as well as the build, so a requirement may be refined under testing, and
preview is rebuilt after each round rather than tested once.

The test for whether something has left the scope: **does it add an issue, or a
piece of functionality, that was not there when scope closed?** Size is not the
measure.

### 3.2 Version numbers

The app version, the API version and the build id are defined in
[4.1 Versioning](4.1-configuration.md#versioning); which app version a release
takes is [3.3 §2.7](3.3-testing-ci-and-release.md). They move independently.
The next structural release takes the major slot: `1.0.0`. It says breaking
changes get a major bump, not that there will be none.

### 3.3 Priority

`Priority` is an issue field, a judgement rather than a derived value. It
informs what enters a release; ordering within a release is decided when the
release is planned. The milestone does not express priority: it says how a
change ships, not when.

### 3.4 What tests the tooling

Documentation and tooling are in use as soon as they reach `main`: no deploy,
preview, rehearsal or user testing stands in front of them. So **a gate that
can fail open gets a test in `scripts/tests/`, and CI runs it.** A tool that
shows something is wrong visibly; one that permits something is wrong
silently, because a gate that has stopped checking looks exactly like one
everything passed.

Where CI cannot reach, the tool's own use is the test, before the merge: a
change to `deploy.sh` is tried by deploying to rehearsal. Tooling is the one
kind of change whose author is its only user, on the machine where it already
works, so it is tried somewhere else first. A test that passes locally and
fails in CI is found this way: one hid `gh` by trimming `PATH` to `/usr/bin`,
which on a runner is exactly where `gh` lives.

### 3.5 Why `deploy.sh` needs no approval step of its own

Rehearsal and production run the same `deploy.sh`. A production release of a
commit refuses unless rehearsal already runs that commit, so a change to
`deploy.sh` cannot reach production without having deployed rehearsal
successfully first.

The chain does not close for a rollback, which runs the current tooling
against an older commit, or with `DEPLOY_SKIP_PREVIEW` or `DEPLOY_SKIP_BUMP`,
which step around parts of it by design.

### 3.7 Pull requests, and what they are for here

**They trigger and track human review, and nothing else** — not merges, not CI.

**A review, not a comment.** A comment can approve something nobody looked at; a
review is against a commit, and GitHub records who approved what. The owner
approves; Claude merges.

**Approved is not merged.** A pull request can be approved and stay open.
Claude merges it locally, by rebasing and fast-forwarding, so the commit that
ships is the commit that was tested ([3.3 §1.9](3.3-testing-ci-and-release.md)).

**It runs what a branch push does not.** CI's `check` job runs on every push;
`e2e` runs on pull requests and on `main`. Opening one is how a branch gets the
full suite.

**Open it as a draft** when the branch is created, and mark it ready when it is.
It is then a running view of the release: every commit, and what CI made of them.

**Never squash**: every commit carries a version stamp that CI checks, and a
squash writes a new subject that does not.

**`Closes #N` belongs in the pull request, not the commits** — and only on a
project's last delivery, since an earlier one closing the project would close it
before the rest shipped.

**Request a reviewer when opening one** (`gh pr create --reviewer …`). Without
one it appears in nobody's queue, which is how the first natively reviewed pull
request was nearly missed.

GitHub's own review states do all of this. A `/approve`, `/prov`, `/rework` and
`/ready` parser in `docs.yml` stood in for them until 2026-08-26, because every
pull request was authored by the owner's token and GitHub refuses self-approval.
Project #206's second delivery gave Claude its own account, so the parser and its three
labels were deleted rather than fixed. The one capability lost is `/prov`:
request changes, then approve when told they are done, which costs a lap and
buys a look at the change before it merges.
