# How testing and release work

The mechanisms behind the steps in [4.3.3](4.3.3-testing-ci-and-release.md)
and [4.3.6](4.3.6-when-a-release-goes-wrong.md): the environments, the tests,
CI, the version numbers, how `deploy.sh` ships an image, how a change is
merged and what `verify.sh` checks.

## 1 The environments

| Environment | Runs | Asks | Reached by |
| --- | --- | --- | --- |
| dev | `cargo run` and `dx serve` on the laptop | does the code I am writing work? | `./scripts/develop/services.sh` |
| preview | the real images in Docker, on the laptop | does the change do what was wanted? | `./scripts/deliver/deploy-preview.sh` |
| rehearsal | the real images on an Oracle VM matching production | does deploying work, and does it behave on production's hardware? | `./scripts/deliver/deploy-rehearsal.sh` |
| production | the same, on the live VM | none: it serves users | `./scripts/deliver/deploy.sh` |
| CI | GitHub's runners, and the preview stack for `e2e` | does anything that used to work still work? | every push and pull request ([3](#3-continuous-integration)) |

The questions differ, so each answer settles only its own: a green CI run is
one deploy gate of several, and rehearsal is the only place a claim about
production's hardware is tested.

### 1.1 Deployments build a commit, never the working tree

Every deploy builds a clean `git worktree` at the target commit, once, and every
environment loads the same artefact
([5.1](#51-one-build-per-commit-shared-by-every-environment)). Rolling
forward and rolling back by deploy both name a commit and deploy it.

## 2 Running tests

```bash
cargo test --workspace                              # every crate, the old-crates prototypes included
bats scripts/tests                                  # the shell tooling
python3 -m unittest discover -s scripts -t scripts  # this repository's Python checks
```

| Tests | Runner |
| --- | --- |
| shell scripts | [bats-core](https://bats-core.readthedocs.io/) with bats-support and bats-assert, installed by the setup script ([4.3.1](4.3.1-setup.md#development-environment)) |
| this repository's Python checks, `scripts/tests/test_*.py` | `unittest` |
| the board model, programme scripts, hooks and documents gate | the programme repository's CI, from that repository alone; a change reaches this one by moving the `programme/` pin |

`cargo test` runs against the host target, never `wasm32-unknown-unknown`;
[4.3.2](4.3.2-development.md#manual-web-client) has how to check that a wasm
build compiles. One crate at a time is in
[4.3.6 §4](4.3.6-when-a-release-goes-wrong.md#4-diagnostics-and-occasional-commands).

### 2.1 How the tests are shaped

The standards every test is held to, the test design specification and the
unit-test checklist are the programme's
[1.9](https://github.com/delphside/programme/blob/main/docs/1.9-testing-standards.md).

**Tests build their own world.** Each creates a throwaway SQLite file and
constructs the Axum router in-process, so CI runs them on a bare runner and no
test's state reaches another.

- **In-process**: hand a `Request` to the router with `tower`'s `oneshot` and
  read the `Response`. Routing, extractors, handlers and status codes all run.
- **Over a socket**: bind `127.0.0.1:0` and serve, for what a function call
  cannot reach. `require_loopback` reads `ConnectInfo`, which only a real
  connection populates, so in-process tests inject `loopback_peer()`.
- **A binary**: `cargo test` supplies each of the package's binaries as
  `CARGO_BIN_EXE_<name>` to that package's `tests/` directory.
  `crates/admin-cli/tests/user_deletion.rs` hosts a server on a loopback port
  and spawns the real admin binary against it.

`crates/server-game/src/app/tests_account_lifecycle.rs` is the example of
[1.9](https://github.com/delphside/programme/blob/main/docs/1.9-testing-standards.md)'s
refusal followed by a success.

## 3 Continuous integration

`.github/workflows/ci.yml` has four jobs and `.github/workflows/docs.yml` one:

| Job | Runs on | Does |
| --- | --- | --- |
| `check` · *fmt · clippy · test · wasm · docs* | every push, every pull request and on demand | `check-docs.sh`, `cargo fmt --check`, the Python and bats tests, `clippy -D warnings`, `cargo test --workspace`, the log-hygiene suite against [4.4.7](4.4.7-log-events.md), and the wasm build |
| `stamp` · *commit stamp (app/api versions)* | the same | refuses a commit whose subject lacks either version, or whose versions differ from its own tree's |
| `touches-image` · *does this pull request reach the image?* | pull requests only | says whether the diff reaches the image, by `shipping-paths.sh` |
| `e2e` · *Playwright · preview stack* | after `check`: on demand; pull requests that reach the image; every push to `main` and `release/*` | Builds the preview stack in Docker and runs the Playwright suite. The push runs give `main` and `release/*` a real verdict: `merge-to-release.sh` and the deploy read it with `--require e2e`. |
| `review-checklist` (`docs.yml`) | pull requests that are not drafts, on every file set | fails while any box under a review heading in the body is unticked, and when the body has no review heading |

- `e2e` waits for `check`, so a lint failure never costs a Docker build.
- the workflow sets `RUSTC_WRAPPER=""`: the runner has no sccache, and wasm
  cannot use it ([4.3.2](4.3.2-development.md#manual-web-client)).

**CI is a deploy gate.** `deploy.sh` asks `scripts/deliver/ci-status.sh`, the
same code used by hand.

### 3.1 The advisory check, and why it denies warnings

`.github/workflows/advisories.yml` runs `cargo audit --deny warnings` daily and
on demand. It only reports: a failing run opens one `Requirement` issue
titled "Dependency advisories need review", or updates the open one.

**It fails a run on reachability, not severity.** `Cargo.lock` lists every
crate any feature combination could pull in, so most findings are against
crates in no build graph, and severity does not predict which. So
`--deny warnings` fails a run on a warning as on a vulnerability, and only the
ignore list in `.cargo/audit.toml` quiets one. Its single criterion is that the
crate cannot reach the build; every entry carries the reason and how it was
established.

`.github/dependabot.yml` watches the pinned actions and the `Dockerfile`'s base
images weekly; the crates are left to the advisory check, so newness and
advisories are kept apart.

### 3.2 What GitHub does on its own

| Workflow | Fires on |
| --- | --- |
| `ci.yml` | `push` (any branch), `pull_request`, `workflow_dispatch` |
| `ci.yml` concurrency | group `ci-<ref>`: a newer push cancels the running run, except on `main` and `release/*`, where GitHub keeps one pending run per group, so a third push cancels the second's run before it starts |
| `docs.yml` | `pull_request`: opened, edited, synchronize, reopened, ready_for_review |
| `advisories.yml` | `schedule` at 06:15 UTC, and `workflow_dispatch` |

Ticking a box is an `edited` event, so the checklist goes green without a
re-run. The board workflows (`context.yml`, `pr-state.yml`,
`requirement-stage.yml`, `programme-activities.yml`) are the programme's:
[1.1](https://github.com/delphside/programme/blob/main/docs/1.1-programme-tooling.md#the-board).

GitHub behaviours the process works around:

| Behaviour | So |
| --- | --- |
| a `skipped` job still concludes the run `success` | a gate names a run and requires a job: `ci-status.sh --run push:main --require e2e` |
| `Closes #N` closes an issue when the commit reaches the default branch, before it ships or is checked | commits say `Refs #N` ([1.2 §2.5](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#25-tracking-a-change-to-production)) |

**The `main` ruleset**
([3.1.2](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.2-artefacts.md#github))
is why a push of the version bump to `main` reports "Bypassed rule
violations".

## 4 Version numbers: which to bump, and when

The two versions and the build ID are defined in
[4.4.1](4.4.1-configuration.md#versioning). **The versions in `main`'s tree are
provisional**: they are the next release's version and API version as far as is
known, and fixed only when `turpin release` makes the release (owner,
2026-11-16). The tree's current values:

```bash
grep -m1 '^version' Cargo.toml                             # app
./scripts/deliver/read-api-version.sh < crates/api/src/lib.rs   # api
```

### 4.1 Check the commit subject carries both versions

Every subject starts `app <X.Y.Z> api <M.N>:`, the numbers `GET /health`
reports. Both come from that commit's own tree, which leads production: the app
version is what the next release will be, until a change moves it.
`check-commit-stamp.sh` checks them; CI runs it as the `stamp` job.

### 4.2 Decide whether the app version moves

`turpin release` bumps `main` to the next patch when it makes a release, so no
commit is built carrying a version that has been released. The `bump` hook then
brings `Cargo.lock` after it. The app version moves again with later changes,
which may raise it from the patch the bump set. A version is spent once
it is released, even if it never ships, and a later release takes the next.

**The default is a patch, and a functional release is at least a minor.** When
any package in the release's milestone has `Type of change` `functional`, the
owner raises the version to the next minor on the branch that is
fast-forwarded into `main`, as
[4.3.3 §1.2.4](4.3.3-testing-ci-and-release.md#124-set-the-version-for-a-functional-release)
says.

When [4.3.3 §1.8](4.3.3-testing-ci-and-release.md#18-keep-a-release-branch-current)
merges `main` into a release branch, the version lines in `Cargo.toml` and
`Cargo.lock` conflict only when both sides changed them since the cut:

| Branch | `main` | Result |
| --- | --- | --- |
| ran 4.3.3 §1.2.4 | released since the cut, so `turpin release` bumped it | Conflict: keep the branch's, because `main`'s would ship, and settle the milestone of, the wrong version. |
| did not run 4.3.3 §1.2.4 | released since the cut | Clean: the branch takes `main`'s bump, but the release has already taken the milestone it was gathered under. This case needs the owner. |

`check-release-version.sh` refuses a patch release whose milestone carries
functional change. A version is a patch release when its major and minor equal
the newest `prod-*` tag's, whatever production runs. The check passes whenever it cannot judge (no milestone, no `gh`, no
network); `turpin release` runs it as the `release-check` hook, and
`turpin release --check` shows it early.

### 4.3 Decide whether the API version moves

The API version describes the wire contract alone
([4.4](#44-how-a-client-learns-there-is-a-new-build) has what announces a new
build). It moves only if the wire contract changed, in the same commit as the
change. A change to `crates/ui` alone moves nothing.

| Change | Bump |
| --- | --- |
| breaking: an old client cannot continue | major |
| additive: old clients still work without the new thing | minor |
| a newly accepted value, such as a new edition | minor |
| a status changed on a path that already existed | minor |
| anything a client cannot observe on the wire | none |

A changed status is minor, not major, because an old client still receives a
status it understands. **Bump per wire change, even when production skips
versions**: each environment can run any committed version, so each change
keeps its own increment and a comparison of `api_version` means what it says.
**Where both sides of a merge moved it, the merge takes the higher value and
applies the other side's bumps to it**, as when an emergency is merged into
`main`. Each side's bumps are counted from the value at the common commit:
from `2.16`, `2.17` against `2.18` gives `2.19`, and `3.0` against `2.17`
gives `3.1`.

The reasoning for each bump goes in the comment block above `API_VERSION`.

### 4.4 How a client learns there is a new build

A client learns of a new build by the build ID: every deploy moves it, and a
tab reloads when the web container serves a build other than its own
([4.4.1](4.4.1-configuration.md#how-a-tab-learns-there-is-a-new-build)).

## 5 How `deploy.sh` ships an image

**This section describes `deploy.sh`, the fallback until 0.10.3.** Turpin's
build, record and deploy are [4.3.3 §2](4.3.3-testing-ci-and-release.md#2-what-a-build-a-payload-and-a-record-hold)
and [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it).

The gates are in
[4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it);
`DEPLOY_GATES_ONLY=1` runs them and stops before anything changes. Everything
destructive happens after everything that can refuse:

1. builds the artefact, or reuses the one for this commit
2. checks its digest, transfers it, retags the live images `:previous` and
   loads the new ones
3. stops the server and snapshots the database
4. runs migrations as their own step, so a failure there is not an outage
5. starts the new version
6. smoke-tests the public URL for the exact `app_version`, not merely a 200
7. tags the commit, publishes the GitHub Release, bumps the dev version
   ([4.2](#42-decide-whether-the-app-version-moves)) and settles the
   milestone

| Fails at | `deploy.sh` | Exits |
| --- | --- | --- |
| step 1, or step 2's digest check or transfer | stops before anything is loaded | `1`, or the failing command's own status |
| step 2's retag or load, or step 3 | points `:latest` back at the images that were live and starts the stopped server again; nothing was migrated | `1` |
| step 4, 5 or 6 | calls `scripts/deliver/rollback.sh --yes` with the snapshot from step 3, the same code run by hand | `1` |
| that rollback | says so and names the snapshot | `1` |
| step 7, except the Release | reports the failure and carries on | `3` ([4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it)) |
| step 7's GitHub Release | warns and carries on ([5.4](#54-the-github-release)) | `0` |

### 5.1 One build per commit, shared by every environment

| Item | Detail |
| --- | --- |
| where | `artifacts/<sha>.tar.gz` in the working copy, git-ignored, with a `.sha256` and a `.manifest` beside it |
| when it builds | Only when that file is absent. Preview or rehearsal builds it; production loads the same bytes. |
| what proves sameness | the digest, printed on every deploy as `sha256:` after the size |
| retention | the newest `ARTIFACT_KEEP`, pruned after a successful deploy ([4.4.1](4.4.1-configuration.md#environment-variables)) |
| if one is lost | It rebuilds from the commit; it is a cache, not a record. |

**The digest is the check, not the version.** A rebuild of a commit stamps the
same version but can differ in bytes, because base images and mirrors move. The
digest is re-checked before every transfer, so a truncated file fails the
deploy.

### 5.2 What is in a build, said by the build

`artifacts/<sha>.manifest` is written from git alone, so it exists when GitHub
is unreachable:

| Line | Says |
| --- | --- |
| `digest` | the bytes it describes |
| `since` | the newest `prod-` tag that is an ancestor of this commit |
| the commits | each in that range, with `*` against those reaching the image (`ships.non_shipping` in `app-profile.toml`, read through `board-shipping.py`) |
| the issues | those claimed by a `Refs` or `Closes` trailer in that range, and whether any of their commits reach the image |

After a successful deploy, `deploy.sh` runs a check, not a gate: it reports an
issue whose commits reach the image and which carries no milestone, leaving
out requirements and parents.

### 5.3 Gating on a particular run

One commit has many runs, and they run different jobs, so a gate names the run
it judges. `ci-status.sh` takes:

| Option | Meaning |
| --- | --- |
| `--run <event>[:<branch>]` | required: the newest run of that event, and branch where given, for the exact commit |
| `--require <job-prefix>` | a job that must be present and green in that run; repeatable |
| `--wait` | polls every 10 seconds, up to 20 minutes, until the run finishes |

The runs production and an emergency judge are the `ci` and `pull-request`
gates of [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it). A rehearsal
judges the newest `push` run for the commit, on any branch, since it has not
reached `main` yet.

### 5.4 The GitHub Release

`deploy.sh` runs `gh release create` on the tag it pushed, with
`--generate-notes --verify-tag --title <version>` and, where a predecessor
exists, `--notes-start-tag` set to the newest other `prod-X.Y.Z` tag. Only a
tag named `prod-<version>` gets a Release: a redeploy's timestamped tag gets
none. A failure prints the command to run by hand, and the deploy still exits
`0`.

A Release hangs off a tag, so only a delivery that ships code has one;
[3.1.1](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.1-delivery-log.md)
stays the record of every delivery.

### 5.5 What a release settles

| Deploy | Settles |
| --- | --- |
| production | Each open issue in the milestone: a parent is skipped; any other gets a "Released in" comment, then a project moves to Post-deployment and stays open, and anything else is closed. Then the milestone closes and the next opens. |
| rehearsal or preview | Nothing: it has not reached users, and writes no `prod-*` tag and no version bump. |
| emergency | Nothing, deliberately: closing the milestone would say the normal process completed, which it did not. The tag and bump still happen, because they record what runs, and the retrospective issue is the record. |

`scripts/tests/deploy-milestone.bats` covers all three.

### 5.6 Where a gate meets a limit

How the gates of [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it)
behave at a limit:

| Gate | When | Does |
| --- | --- | --- |
| `pull-request` | no pull-request run for the commit | says so, and passes |
| `schema` | `/health` unreachable, or reporting no `schema_version` | skips, with a note |
| `milestone` | no open issues | lists nothing, asks nothing and skips the placeholder check |
| `milestone` | no `gh` | prints that the milestone was not checked, and passes |
| `milestone` | `gh` present, the query failing | prints that the milestone could not be read, and passes |
| `milestone` | an issue that is not a project | warns without asking |
| `milestone` | `DEPLOY_GATES_ONLY=1`, where the gate would ask | passes without asking |
| `milestone` and `emergency-scope` | no terminal, where the gate would ask | refuses |
| `emergency-scope` | production's `/health` not answering, or naming a commit this checkout lacks | passes without asking |

When the `milestone` gate warns that an issue is not a project, the deploy goes
on, so the owner decides before it, from the milestone list or the gates-only
run of [4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it), to do one of
these:

- fold it into a work package
- move it out of the milestone
- ship it in the milestone, where the deploy settles it
  ([5.5](#55-what-a-release-settles))

A production deploy from tooling that is not on `main`, or has uncommitted
changes under `scripts/`:

- warns and asks for `production` to be typed
- refuses without a terminal
- passes without asking under `DEPLOY_GATES_ONLY=1`

So a gates-only run, `verify.sh`'s included, can pass where the deploy itself
stops at a prompt.

`deploy.sh` compares the gates that ran with its *checklist*, and refuses on a
missing one as its own fault:

- a release or an emergency: every gate its 4.3.3 §1.6 column expects, except
  `emergency-scope`
- a rehearsal: `on-remote`, `ci`, `schema` and `version`

The variables that skip or change a gate (`DEPLOY_SKIP_PREVIEW`,
`DEPLOY_SKIP_CI`, `DEPLOY_SKIP_BUMP`, `DEPLOY_EMERGENCY`, `DEPLOY_GATES_ONLY`)
are in [4.4.1](4.4.1-configuration.md#environment-variables).

## 6 How a change is merged

A commit's version stamp is read from its own tree, and the commit CI tested
must be the commit that lands.

| Change | Method | Why |
| --- | --- | --- |
| a project into a release branch ([4.3.3 §1.8.1](4.3.3-testing-ci-and-release.md#181-merge-a-project-into-a-release-branch)) | `--merge --delete-branch` | Each commit lands as CI proved it, with a stamp that matches its tree. `--ff-only` at 4.3.3 §1.9 takes the merge commit with the branch. |
| a project branch onto `main` ([4.3.3 §1.9](4.3.3-testing-ci-and-release.md#19-merge-a-branch-into-main) step 1) | rebase and re-stamp, before 4.3.3 §1.3 to 1.5 | The rebase comes first, so preview and rehearsal judge the commit that lands; the re-stamp corrects the subject, which the rebase leaves one version behind its tree once a deploy has bumped `main`. |
| a release branch into `main` ([4.3.3 §1.9](4.3.3-testing-ci-and-release.md#19-merge-a-branch-into-main)) | fast-forward | It adds no commit, so `main` gets the commit already proven. |
| an emergency fix into `main` ([4.3.6 §3](4.3.6-when-a-release-goes-wrong.md#3-ship-an-emergency-change)) | merge | `main` keeps every commit an `artifacts/<sha>.tar.gz` was built from, and production's commit becomes an ancestor of `main`, as `verify.sh` expects. |

## 7 What `verify.sh` checks

`verify.sh`
([4.3.3 §1.7](4.3.3-testing-ci-and-release.md#17-verify-what-is-live))
fails on:

- an unclean working tree, or a branch whose tip differs from its `origin`
  counterpart
- no `origin/main` to compare branches against
- CI not green for the current branch's push run, or no `gh`
- failing tooling tests, or no `bats`
- production, rehearsal or preview not answering
- rehearsal's access gate open to everybody, refusing every device (no key
  configured), not answering or answering unexpectedly
- a release of `HEAD` that `turpin release --check` would refuse, or whose
  gate check runs past 120 seconds, unless nothing on `main` ships beyond
  production
- rehearsal or production running other than what its record says, or host
  files that differ from the payload's (`turpin status ENV`), or no current
  Turpin deploy
- the GitHub token advertising an expiry under 7 days away
- the board's `PR State` check unable to run or to reach the board

It notes, without failing:

- image changes waiting on `main`, or production not answering or reporting a
  commit this checkout lacks
- hosts that owe an upgrade, a reboot or a repair, differ, or could not be
  read (`check-hosts.sh`)
- a local branch merged into `origin/main`, once its remote branch is gone
- a token expiring in 7 to 29 days
- what `board-check.py` reports, or that it could not run
- the corrections it made to the board's `PR State`, to match GitHub
