# 5.5 GitHub Project Board

The GitHub objects the programme is run on: the issue types and fields, the
project board, labels, accounts and rules, and the strings the tooling reads
from them. Like [4.8](4.8-artefacts.md), it is the only record of artefacts
that leave no trace in git, named as 4.8 names them; each artefact's route is
in [5.1 §2.15](5.1-change-lifecycle.md#route).

## What is held in GitHub

| artefact | route | what it is |
| --- | --- | --- |
| `github:labels` | Other | **two**. `folded` says a closed requirement was absorbed into a project rather than rejected. `Release Check` says a deployed change owes a post-deployment check that cannot be answered until the *next* release — `board-actions.py` shows those as waiting rather than due, and `deploy.sh` names them after a production release. Everything else that would be a label is a field |
| `github:issue bodies` | Other | GitHub Flavoured Markdown, where **a single newline is a line break**. So a paragraph is written as one line however long, unlike `docs/**`, where markdownlint requires wrapping. The two are the same format and not the same dialect |
| `github:issue types` | Other | `Requirement`, `Project`, `Decision`, org-level, set when an issue is raised. `Workstream` and `Index` are disabled; a disabled type reads as null through the API, so ten closed issues report no type |
| `github:issue fields` | Other | **issues only in practice.** GraphQL refuses a `PR_` node id for `setIssueFieldValue`, and REST accepts one but offers no way to clear it again — so a field set on a pull request is stuck until the UI removes it. A pull-request lifecycle therefore lives on the board. Ours: `Workstream`, `Type of change`, `Route`, `Phase`, `Stage`, `Decision State`, `Topic`. GitHub's built-ins used: `Priority`, `Effort`, `Start date`, `Target date` |
| `github:project` | Other | `Tile Lite Elite Programme`, org-owned and linked to the repository. Its **views** are pre-approved to change; the fields they read are not |
| `github:project auto-add filter` | Other | **`is:issue,pr`** — one qualifier with two values. `is:issue is:pr` is two qualifiers and adds neither, while previewing a count that includes both. Set in the project's settings; there is no API for it (`updateProjectV2Workflow` does not exist), so it is read and changed by hand |
| `github:project field PR State` | Other | a **Projects v2** single-select on the board, not an issue field: `Drafting · Awaiting review · Changes requested · Approved · Merged · Closed`. **Derived from GitHub's own state, never typed** — `isDraft`, `reviewDecision` and whether a review is requested, the same ladder `board/sources.py` reads. Written by `scripts/sync-pr-state.sh`, which also adds any pull request the board is missing |
| `github:releases` | Other | one per `prod-X.Y.Z` tag, published by `deploy.sh` with auto-generated notes. Public, and the natural home for desktop build attachments |
| `github:ruleset main` | Other | Requires CI's `check` job on `main`; the owner's account and the bot bypass it, which is what lets `deploy.sh` push the version bump |
| `github:owner account` | Other | **`SteveStyle`**. Not `stephenmor`, which is the email prefix and is what `--reviewer` silently accepts: `gh` reports an unknown login on stderr and creates the pull request anyway, requesting nobody. `scripts/create-pr.sh` defaults to it, and `sync-pr-state.sh` reports a pull request that requests nobody |
| `github:machine account` | Other | `SteveStyle-typed-by-Claude`, created 2026-08-25 (#206). Claude's identity, so the owner can approve what Claude opens. Permitted by GitHub's Terms B.3 (one machine account beside a personal one, set up by a human, with a valid email, used only for automated tasks, the human responsible); it must not be used as a second personal account. Must carry 2FA from 17 October 2026 (#308) |

## Which level carries which field

A field is pinned to types (org settings, Planning, Issue fields, the field,
*Pin to types*); an unpinned field is absent from the sidebar and the creation
form. Pinning does not restrict: any field can be added to any issue, so the
rule is this table and `board-check.py`.

| field | Requirement | Project (parent) | Project (work package or standalone) |
| --- | --- | --- | --- |
| Workstream | set at triage | yes | yes |
| Type of change | set at triage | yes | yes |
| Priority | set at triage | yes, past Scope | yes, past Scope |
| Effort | set at Scope, Options and Dependencies | yes, past Scope | yes, past Scope |
| Route | known by Candidate Project | never | yes |
| Stage | yes; unset is read as `Triage` | — | — |
| Phase | — | yes | yes |
| Milestone | `pre-approved` only | none needed; ignored if set | yes |
| Parent | none | none | its parent project, for a work package |

A project whose sub-issues include projects is a parent; a project with a
parent is a work package; any other project is standalone (`board/model.py`).
Values of each field are in [5.1 §2.15](5.1-change-lifecycle.md#215-classifying-a-change).

## What the tooling reads, and would break on

Every row is a string matched literally, so renaming one is a change with
consequences ([5.1](5.1-change-lifecycle.md) §2.2).

| what | read by | breaks how |
| --- | --- | --- |
| `Type of change` = `functional` | [`check-release-version.sh`](../scripts/check-release-version.sh), [`board/programme.py`](../scripts/board/programme.py) | silently: the release gate stops finding functional work, so every patch release passes |
| the `Route` option names, and `Repository Change` as a prefix | [`board/model.py`](../scripts/board/model.py) (`delivered_by_merge`) | quietly: a merged tooling package is not moved to Post-deployment, and looks blocked on a release |
| the field name `Type of change` | `check-release-version.sh`, [`board/digest.py`](../scripts/board/digest.py), [`board/obligations.py`](../scripts/board/obligations.py) | the gate finds no functional work; the digest and triage checks read every issue as unset |
| issue type names `Requirement`, `Project`, `Decision` | [`board/model.py`](../scripts/board/model.py), the board's `type:` view filters | the tree flattens; views empty |
| the `Phase` field name | [`board/model.py`](../scripts/board/model.py), [`deploy.sh`](../scripts/deploy.sh), [`verify.sh`](../scripts/verify.sh) | a project shows as not started; a shipped project is never advanced |
| the option `Post-deployment`, and its id | `deploy.sh` sets it by id after a release; `board/turn.py` and `verify.sh` match it by name | a release stops advancing what it ships, or the review reminder never fires |
| `IssueFieldChangedEvent` in an issue's timeline | [`board/sources.py`](../scripts/board/sources.py) `step_ages`, `verify.sh` | the time at a phase is unknown, and the review reminder says nothing |
| milestone titles that are versions | `deploy.sh`, `check-release-version.sh` | a release closes nothing, or the gate cannot find its scope |
| milestones `no-release`, `patch`, `minor`, `major` | `deploy.sh` `placeholder_shipping` | an issue shipping under a placeholder is not reported |
| the parent link | [`board/model.py`](../scripts/board/model.py) `classify` | work packages read as standalone projects, and parents as nothing special |
| `Stage` and its values | the board's backlog view, [`board/obligations.py`](../scripts/board/obligations.py) | a requirement's journey stops being visible or checked |
| label `folded` | search, and the project form's instructions | a folded requirement cannot be told from a rejected one |
| the field slug `type-of-change` | the board's Needs triage filter | the view renders empty, which reads as nothing to triage |

Workflows live in `.github/workflows/` and are repository artefacts, so they are
not listed here.
