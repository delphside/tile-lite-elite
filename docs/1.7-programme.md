# Programme

How the work on Tile Lite Elite is organised, in a page. The **programme** is
the organisation that owns, operates, maintains and enhances the application;
the **application** is the thing itself, its code and its environments
([5.2](5.2-workstreams.md#programme-and-application)). Roles are
[5.7](5.7-roles-and-responsibilities.md). The detail is in [5.1](5.1-change-lifecycle.md) (how a change reaches
production), [5.2](5.2-workstreams.md) (who owns what) and
[5.3](5.3-programme-activities.md) (the recurring work); the rules on one page
are [`CLAUDE.md`](../CLAUDE.md).

## Who does what

The owner decides; Claude does the work and brings anything needing a
decision to him. Claude alone decides in Process Definition, Programme Tooling
and Delivery Tooling, and for tooling and documentation changes anywhere. The
owner decides anything reaching production, the product and game rules, and
anything irreversible outside git ([5.7](5.7-roles-and-responsibilities.md#who-decides)).

## Workstreams

Eleven workstreams each own a part of what the programme maintains and a named set of artefacts,
and never finish:

| | workstreams |
| --- | --- |
| the application | Application & Game Architecture, Game Rules, Engine Player, Client UI, Client Management, Authentication & Authorisation |
| running it | Capacity Planning, Operations & Infrastructure |
| delivering it | Delivery Tooling |
| the programme itself | Process Definition, Programme Tooling |

Section 2 designs the application's functional areas; section 3 details how
the programme is organised and run.

## How a change is made

A **requirement** says what should be true. Triage places it in a workstream;
a **project** gathers related requirements so they are designed together, and
delivers them in **work packages**, one delivery each, by one **route**: a
release of the application, a change to the repository, or something applied
by hand. A release is tested on preview and rehearsal before it ships. The
steps, rules and commands are [5.1](5.1-change-lifecycle.md) and
[3.3](3.3-testing-ci-and-release.md).

Everything is tracked in GitHub: issues typed Requirement, Project or
Decision, their fields, and the project board. The daily state is read with
`scripts/programme/board/board-status.py`,
`scripts/programme/board/board-inbox.py` and
`scripts/programme/board/board-actions.py`.

## Recurring work and improvement

Work that never closes is **programme BAU**: sweeping the board, the capacity
plan, the benchmark run, and the weekly digest, each with a frequency in
[5.3](5.3-programme-activities.md). The weekly digest measures where the owner's
time goes and tracks lessons, recurring problems and improvement initiatives;
Claude reviews it weekly and the owner monthly.
