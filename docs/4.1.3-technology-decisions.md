# Technology decisions

The technology the system is built on, and why.

The constraint is that it stays free or nearly free to host.

## The stack

| Area | Choice | Pros | Cons |
|---|---|---|---|
| Core language | Rust | Safe, fast, one language for server, clients and rules | Slower to iterate than scripting languages |
| Client framework | Dioxus | One Rust stack for web and desktop | Smaller ecosystem than mainstream web UI stacks |
| Server framework | Axum | Async-first, a good fit for typed APIs | More infrastructure assembled by hand |
| API style | HTTP plus WebSocket | Requests for actions, a socket for live game updates | More design work than a single protocol |
| Persistence | SQLite, with versioned migrations | Simple, low operational burden, free to run | One writer at a time, on one host |
| Engine boundary (computer players) | A Rust trait (`GameEngine`) compiled into the server and run in its process; one engine, Greedy, is registered | Type-safe, no IPC, the same validation as a player's move | Engines run with the server's privileges, so an untrusted engine needs sandboxing first; a search that overruns 5 s per turn costs the seat a pass ([4.2.3](4.2.3-engine-interface.md#how-the-server-runs-an-engine)) |
| Shared rules | A pure shared Rust crate, `rules-shared` | The same legality and scoring everywhere | Needs strict dependency discipline |
| Word lists | Embedded per edition in the server and the desktop client; fetched by the web client | Fast and deterministic; the web bundle stays small | Larger server and desktop binaries; a list change is a release ([4.3.5](4.3.5-word-lists-and-dictionaries.md)) |
| Message format | Typed Rust DTOs in `crates/api`, versioned | Strong contracts | Whoever releases moves the version by hand ([4.3.3 §2.4](4.3.3-testing-ci-and-release.md#24-version-numbers-which-to-bump-and-when)) |
| Testing | Unit and in-process integration tests, Playwright end to end | Rules and API regressions caught in CI | Setup cost |
| Auth | Bearer-token sessions, argon2 passwords ([4.2.5](4.2.5-authentication.md)) | Simple, and enough for accounts and ratings | No email verification |
| Hosting | One Oracle Always Free VM: the server and Caddy in Docker ([4.3.4](4.3.4-production-environment.md)) | Free; Caddy terminates TLS and serves the static bundle from the API's origin, so the browser makes no cross-origin request ([4.3.4](4.3.4-production-environment.md#container-topology)) | One machine, no redundancy |
| Mobile | Deferred ([4.1.1](4.1.1-architecture.md#clients)) | Keeps scope manageable | No native mobile client yet |

## Why this stack fits the project

The project is a hobby project, so the stack minimises cost and operational
overhead. The separation of the rules and the engine is in
[4.1.1](4.1.1-architecture.md#guiding-principles).
