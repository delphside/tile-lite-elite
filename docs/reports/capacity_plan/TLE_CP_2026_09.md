**Measured on production, 2026-09-21.** The first of these.

**Every figure below is a single sample, not a month's average or peak**, taken
from a service nobody was using at the time. That is a real limitation and not a
caveat: capacity is sized against a peak, and nothing here samples often enough

what is consumed, against what ceiling, and what would have to change before the

## Which number moves first

**The games table, and it is the only unbounded thing here.** `AppState::new`
loads every game into a map at boot — `persistence.rs:448`,
`select id from games order by created_at desc`, no `where` clause — so boot
time and resident memory scale with the row count.

| status | swept by | bounded |
| --- | --- | --- |
| `finished`, `aborted` | `expire_old_terminal_games`, a week after `ended_at` | **yes** |
| `active` | `expire_overdue_turns` retires a seat past its move limit | **yes, eventually** |
| **`waiting`** | **nothing today** | **no** |

**Seven of the fifteen games are `waiting`, idle 46 to 62 days.** A waiting game
has no current seat, so the move-timeout sweep never looks at it, and it is not
terminal, so the terminal sweep never looks at it either. Each is loaded at every
boot for the life of the service.

**RET-3 is the answer and it is not built.** *A game that never started runs a
thirty-day countdown from its last activity; seven days in, its creator is asked
what to do with it.* The build is #68, closed into #270. Until it lands, this row
grows with every abandoned game — which is the common case, because abandoning
costs nothing.

## History, and where it is heading

**One column, because this is the first.** The table below is the shape the next
one fills in, and it is the reason each report carries a window rather than only
its own figures.

| --- | --- |

| journal | 51 MB |

| — of them `waiting` | 7 |
| accounts | 6 |

**CPU dropped out of every section after the first table until now** — a plain
omission, not a judgement that it was too low to bother with. It never made it
into `measurements.csv`, and everything below the first table is generated from
that file, so it disappeared silently rather than by decision.

**And the ceiling here is an approximation, worth stating plainly.** Load average
is not the same unit as vCPU count — it is the mean length of the run queue, not
a percentage of CPU consumed — but a load average below the core count is the
standard rule of thumb for *not saturated*, so `2` stands in for the ceiling
until something more precise is worth building.

**A resting monthly reading of this metric may never move.** Load average at
idle tracks nothing this service does under normal use; what would make it move
is concurrent engine searches, which #91's stress test is what actually
measures. It stays in the table for completeness and to catch a change in
baseline — a creeping increase with no game being played would itself be a
finding — but the real answer to *does CPU have headroom* is #91's, not this
row's.

**And the ceiling itself is soft, because production is a VM on somebody
else's hardware.** Owner, 2026-09-22: *"CPU headroom might depend on the
hypervisor, and be difficult to know."* Right, and already measured rather
than hypothetical: `engine_timing_results.csv`'s `steal_pct_of_capacity`
column records the share of the whole machine OCI's hypervisor took during a
benchmark run, and production has read **2.6%** on its one recorded run,
rehearsal 2.6% to 4.4% across several. That is time the guest never sees at
all — `docs/2.3`'s own account of it: *"the kernel does not record who lost
the time."*

**So `2` in the ceiling column is the nominal core count, not a guarantee of
two full cores.** The true ceiling is `2 × (1 − steal)`, and steal is
machine-wide, per-run, and not something this service controls or can predict
— it depends on what else OCI is running on the same host. Stated as an
approximation rather than corrected for, because a single figure would claim a
precision the measurement does not have: steal varies run to run, and the
production figure is one sample.

## What is not known, and is the next thing worth measuring

**Where the service breaks.** #91 asks for it and nothing has measured it. Every
number above is a *resting* figure taken from a service nobody was using at the
time, so none of them says what happens under load. The plan is worth more once
there is a row saying *registrations fail at N per minute* beside the ceiling
that N is forty times away from.

**Account growth has no ceiling set.** Six accounts, and nothing says what number
would be a problem or at what rate. #291 R3 owes that rate.

## How this was measured

Memory, disk, journal and load: read on the production host. Games by status and
account count: the admin CLI over loopback, run by the owner —
`sa games list`, `sa users list`. Container figures: `docker stats`.

**Nothing here was posted by the application.** D49: the application holds no OCI
credential, and a capacity figure is read by a person or by the host, never
reached out for by the service.
