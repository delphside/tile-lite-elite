# Persistence

Where the server keeps game and account state, and how long it keeps games.

## SQLite file layout

Each environment has one SQLite database in write-ahead-logging mode
(`persistence::connect`): the main file, plus `-wal` and `-shm` sidecar files
that SQLite creates beside it as needed. The path is
`TILE_LITE_ELITE_DATABASE_URL`
([4.4.1](4.4.1-configuration.md#environment-variables)):

| Environment | Main file |
| --- | --- |
| local development | `data/tile-lite-elite.sqlite3` in the checkout |
| preview, rehearsal and production | `/data/tile-lite-elite.sqlite3` in the server container, on a named volume |

## What is persisted

The tables are [4.4.2](4.4.2-database-schema.md):

- games, each with its authoritative state as a `snapshot_json` text column and
  queryable columns projected from it, plus its seats, moves, chat messages
  and invitations;
- players, sessions and password-reset tokens;
- engine profiles, written at startup and never read back;
- ratings and their history, kept apart from games so they outlive them
  (ACC-3, RET-2);
- a daily record of the database's size;
- the applied migrations, which `sqlx` runs at startup.

## What stays in memory

Every retained game is also held in memory: `AppState::new` loads them all at
boot, and requests read and change the in-memory copy, which is saved after
each change, so a game survives a restart. Previews and the clients' state
live in the clients; engine search state lasts only as long as the search.

## Persistence model

- the server is authoritative and the only writer;
- clients use the shared rules library for previews;
- the schema evolves by migration; a change that cannot be migrated may
  [discard games](#games-may-be-discarded-for-a-breaking-schema-change)
  instead;
- backups are [4.3.4](4.3.4-production-environment.md#backups).

## Games may be discarded for a breaking schema change

A change to the database schema or to `snapshot_json`'s shape may delete the
games rather than migrate them, provided no game is active. Finished games are
deleted after RET-1's period ([4.1.0](4.1.0-rules.md#retention)), so migrating
them is not worth its cost.

- the owner checks each environment for active games first
  ([4.3.4](4.3.4-production-environment.md#admin-cli));
- whether waiting games also block is the owner's decision;
- `player_ratings` and `rating_history` are kept: they belong to the player
  rather than the game (ACC-3).

## Retention: how long a game is kept

The rules are RET-1 to RET-4 in [4.1.0](4.1.0-rules.md#retention); this section
is how they are met.

### The problem

Resident memory and startup time grow with the games kept, not the games
active, and without deletion they grow forever. Memory is the constraint, on
the 954 MB host ([4.4.1](4.4.1-configuration.md#tuning-a-host)).

### What is deleted, and when

Three situations, two of which need a clock:

| Status | Rule | Built |
| --- | --- | --- |
| `Finished` / `Aborted` | deleted a fixed time after it ended (RET-1) | yes |
| `Waiting` | countdown from last activity, with the creator asked part-way (RET-3) | no |
| `Active` | none of its own: it resolves itself | not needed |

A finished game is final, so its clock starts when it ends.

A game that never started may yet go somewhere, and only its creator can say.
Planned, not built: the countdown runs from RET-3's *last activity*, which no
stored field carries. The games list's `last_activity_at` is the latest move or
the creation time (`persistence::last_activity_by_game`), which a roster change
does not move.

An active game needs no rule. `apply_move_timeout` retires a seat that
overruns `move_time_limit_seconds`, and the game finishes once at most one
seat is still playing. Every game carries a limit of at most 40 days
(`MAX_MOVE_TIME_LIMIT_SECONDS`), so an abandoned game finishes within
(seats − 1) × 40 days and the RET-1 rule takes it from there. A player who
moves once per limit keeps it active.

#### Why a game that never started gets a question rather than a deadline

A waiting game's seats each carry a
`SeatInvitationStatus`, and the combination says who is waiting for whom:

| Situation | What it means | Who loses if it is deleted |
| --- | --- | --- |
| every human seat `NotSent` | the creator built a roster and asked nobody | only the creator, who forgot about it |
| any seat `Pending` | someone has been asked and has not replied | an invitee who may still act on it |
| any seat `Rejected` | someone declined; the roster needs attention | the creator, who may not have noticed |
| every seat claimed | everyone accepted; waiting on **Start** | everyone who accepted |

The last is not an invitation state at all — `invitation_status` is `None`
once a seat is claimed — but it is the case where deletion throws away the
most: several people agreed to play and the creator did not press the button.

#### Where the question appears

Not built. When built, the question goes in the games list, as its own
section alongside invitations: it is addressed to this player and waits on
their answer, so it belongs where they already look for such things. Its three
answers are RET-3's; **delete** lets a creator clear a dead game in one
action.

### Where the sweep runs

Lazily, from a signed-in `GET /games` (`expire_old_terminal_games`,
`crates/server-game/src/app/sweeps_capacity.rs`). Turn expiry runs on the
scheduler.

**Growth requires use, and use triggers the sweep.** A server nobody plays
accumulates nothing; one being played is swept whenever a player lists their
games. The sweep takes finished and aborted games only, so waiting games stay
until RET-3 is built.

### What survives

Ratings and their history outlive the games they came from
([what is persisted](#what-is-persisted)).
