# Persistence

## SQLite file layout

Each environment has one SQLite database in write-ahead-logging mode
(`persistence::connect`): the main file, plus `-wal` and `-shm` sidecar files
that SQLite creates beside it as needed. The path is
`TILE_LITE_ELITE_DATABASE_URL`
([4.4.1](4.4.1-configuration.md#environment-variables)):

| environment | main file |
| --- | --- |
| local development | `data/tile-lite-elite.sqlite3` in the checkout |
| preview and production | `/data/tile-lite-elite.sqlite3` in the server container, on a named volume |

## What is persisted

One SQLite database per environment holds the durable state; the tables are
[4.4.2](4.4.2-database-schema.md):

- games, each with its authoritative state as a `snapshot_json` blob and
  queryable columns projected from it, plus its seats, moves, chat messages
  and invitations;
- players, sessions and password-reset tokens;
- engine profiles, written at startup and never read back;
- ratings and their history, kept apart from games so they outlive them;
- a daily record of the database's size;
- the applied migrations, which `sqlx` runs at startup.

## What stays in memory

Every retained game is also held in memory: `AppState::new` loads them all at
boot, and requests read and change the in-memory copy, which is saved after
each change. So a game survives a restart, and resident memory grows with the
games kept (see *Retention* below). Engine search state, move previews and the
clients' state are never persisted.

## Persistence model

The server is authoritative and the only writer. Clients use the shared rules
library for previews and own no persisted state. The schema evolves by
migration; a change that cannot be migrated may discard games instead
([below](#games-may-be-discarded-for-a-breaking-schema-change)). Backups are
[4.3.4](4.3.4-production-environment.md#backups).

## Games may be discarded for a breaking schema change

A change to the database schema or to `snapshot_json`'s shape may delete the
games rather than migrate them, provided nobody else is mid-game.

Writing a data migration for game state is the expensive half of a change like
the seat model or the event log, and games are short-lived by design: every one
is deleted seven days after it ends (RET-1).

The condition is checked first:

```bash
./scripts/develop/admin.sh games list --status active
```

This lists every game in play with its seats and their players. Waiting games
matter less, since nobody is mid-move; `--status waiting` lists them.

`player_ratings` and `rating_history` are not discardable: they belong to the
player rather than the game (ACC-3), which is what makes deleting games
acceptable.

## Retention: how long a game is kept

The rules are RET-1 to RET-4 in [4.1.0](4.1.0-rules.md#retention). This section
is how they are met, and why the shape is what it is.

### The problem

Every retained game is in the database and in memory: `AppState::new` loads
all of them at boot. So resident memory and startup time grow with the games
kept, not the games active, and without deletion they grow forever. Bounding
the set is preferred to lazy loading or eviction, because memory, startup time
and disk all follow from it. Memory is the constraint, on the 954 MB host
([4.4.1](4.4.1-configuration.md#tuning-a-host)).

### What is deleted, and when

Three situations, of which only two need a clock:

| status | rule | built |
| --- | --- | --- |
| `Finished` / `Aborted` | deleted seven days after it ended | yes |
| `Waiting` | thirty-day countdown from last activity, with the creator asked at seven days | no |
| `Active` | none of its own — it resolves itself | n/a |

A completed game is finished with. Nothing more will happen to it, so the only
question is how long anyone wants to look back at it, and the clock can start
the moment it ends.

A game that never started may yet go somewhere, and the only way to find out
is to ask its creator. The countdown needs a "last activity" that moves
whenever anyone joins, declines or changes the roster, so it runs only on a
roster nobody has touched, and a creator answering *keep* restarts the same
clock. No stored field carries it: the games list's `last_activity_at` is the
latest move or the creation time (`persistence::last_activity_by_game`), which
a roster change does not move.

An active game needs no rule. `apply_move_timeout` retires a seat that
overruns `move_time_limit_seconds`, and the game finishes once at most one
seat is still playing. Every game carries a limit, capped at forty days, so an
active game becomes a completed one within weeks and the seven-day rule takes
it from there. A countdown of its own would also fight that cap: a thirty-day
countdown would reach zero ten days before a forty-day limit.

#### Why a game that never started gets a question rather than a deadline

The question is not built. A waiting game's seats each carry a
`SeatInvitationStatus`, and the combination says who is waiting for whom:

| situation | what it means | who loses if it is deleted |
| --- | --- | --- |
| every human seat `NotSent` | the creator built a roster and asked nobody | only the creator, who forgot about it |
| any seat `Pending` | someone has been asked and has not replied | an invitee who may still act on it |
| any seat `Rejected` | someone declined; the roster needs attention | the creator, who may not have noticed |
| every seat claimed | everyone accepted; waiting on **Start** | everyone who accepted |

The last is not an invitation state at all — `invitation_status` is `None`
once a seat is claimed — but it is the case where deletion throws away the
most: several people agreed to play and the creator did not press the button.

A period alone cannot tell the four apart. The last row matters most: the
creator is the only person who can act and the only one who has forgotten.
Asking costs a prompt; guessing costs everyone who accepted their game.

#### Where the question appears

In the games list, as its own section alongside invitations: it is addressed to
this player and waits on their answer, so it belongs where they already look
for such things rather than in a notification that passes. Its three answers
are RET-3's; **delete** lets a creator clear a dead game in one action.

### Where the sweep runs

Lazily, from `GET /games` (`expire_old_terminal_games`,
`crates/server-game/src/app/sweeps_capacity.rs`); no scheduler job runs it.
Turn expiry does run on the scheduler.

**Growth requires use, and use triggers the sweep.** A server nobody plays
accumulates nothing; one being played cleans itself on every request.

### What survives

`player_ratings` and `rating_history` are separate tables, so a player's
rating and its history outlive the games they came from (RET-2).
