# Persistence

Where the server keeps game and account state, and how long it keeps games.

## SQLite file layout

Each environment has one SQLite database in write-ahead-logging mode
(`persistence::connect`), at the path `TILE_LITE_ELITE_DATABASE_URL` gives.
4.4.1 has each environment's
[path and volume](4.4.1-configuration.md#environment-specific-values), and the
[pragmas](4.4.1-configuration.md#sqlite) and the `-wal` and `-shm` files
beside the database.

## What is persisted

The tables are [4.4.2](4.4.2-database-schema.md):

- games, each with its authoritative state as a `snapshot_json` text column and
  queryable columns projected from it, plus its seats, moves, chat messages
  and invitations;
- players, sessions and password-reset tokens;
- engine profiles, written at startup and never read back;
- ratings and their history, kept apart from games so they outlive them
  ([ACC-3](4.1.0-rules.md#accounts), [RET-2](4.1.0-rules.md#retention));
- a daily record of the database's size;
- the applied migrations, which `sqlx` runs at startup.

## What stays in memory

What is held in memory, and for how long:

- every retained game: `AppState::new` loads them all at boot, requests read
  and change the in-memory copy, and each change is saved, so a game survives
  a restart;
- each client's own state, held by the client;
- engine search state, for as long as the search runs.

## Persistence model

The model:

- the server is authoritative and the only writer;
- clients use the shared rules library for previews;
- the schema evolves by migration, or a breaking change may
  [discard games](#games-may-be-discarded-for-a-breaking-schema-change);
- backups are [4.3.9](4.3.9-backups-and-restores.md).

## Games may be discarded for a breaking schema change

**A breaking change to the schema or to `snapshot_json`'s shape may delete the
games in place of migrating them**, on these conditions:

- only when no game is active: the owner checks each environment first
  ([4.3.4](4.3.4-production-environment.md#admin-cli));
- whether waiting games also block a discard is the owner's decision;
- `player_ratings` and `rating_history` are kept: they belong to the player
  (ACC-3).

Finished games are deleted after RET-1's period
([4.1.0](4.1.0-rules.md#retention)), so migrating them is not worth its cost.

## Retention: how long a game is kept

The rules are RET-1 to RET-4 in [4.1.0](4.1.0-rules.md#retention); this section
is how they are met.

### What is deleted, and when

The rule for each status:

| Status | Rule | Built |
| --- | --- | --- |
| `Finished` / `Aborted` | deleted a fixed time after it ends (RET-1) | yes |
| `Waiting` | countdown from last activity, with the creator asked part-way (RET-3) | no: #270 builds it |
| `Active` | none of its own: it resolves itself | not needed |

Games are deleted because resident memory and startup time grow with every
game kept, active or not, and without deletion they grow forever. Memory is
the constraint, on the 1 GB host
([6.3.4](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#the-hosts)).

RET-3's countdown runs from *last activity*, which no stored field carries.
For a waiting game, the games list's `last_activity_at`
(`persistence::last_activity_by_game`;
[4.4.3](4.4.3-api-schema.md#core-game-domain-dtos)) is its creation time,
which a roster change does not move, so it cannot serve as RET-3's last
activity.

An active game ends this way:

1. `apply_move_timeout` retires a seat that overruns
   `move_time_limit_seconds`.
2. The game finishes once at most one seat is still playing.
3. RET-1 then deletes it.

A game is created with a limit of at most 40 days
(`MAX_MOVE_TIME_LIMIT_SECONDS`), so an abandoned game finishes within
(seats − 1) × 40 days. A player who moves once per limit keeps it active.

#### Why a waiting game's creator is asked

A waiting game's unclaimed human seats each carry a `SeatInvitationStatus`,
and a claimed seat carries none. The combination says who is waiting for whom:

| Situation | What it means | Who loses if it is deleted |
| --- | --- | --- |
| every unclaimed human seat `NotSent` | the creator built a roster and asked nobody | only the creator, who forgot about it |
| any seat `Pending` | someone has been asked and has not replied | an invitee who may still act on it |
| any seat `Rejected` | someone declined or withdrew; the roster needs attention | the creator, who may not have noticed |
| every human seat claimed | everyone accepted; waiting on **Start** | everyone who accepted |

Only the creator can tell whether a game in any of these situations is still
wanted. A roster with both `Pending` and `Rejected` seats is in both.

#### Where the question appears

When #270 builds it, the question goes in the games list, as its own section
beside invitations, the other requests that wait on the player. The creator
answers RET-3's **delete** or **keep**, and not answering lets the countdown
run; **delete** lets a creator clear a dead game in one action.

### Where the sweeps run

| Sweep | What it does | Runs from |
| --- | --- | --- |
| `expire_old_terminal_games` (`crates/server-game/src/app/sweeps_capacity.rs`) | deletes finished and aborted games past RET-1's period | a signed-in `GET /games`, lazily |
| `expire_overdue_turns` (`crates/server-game/src/app/sweeps_game.rs`) | calls `apply_move_timeout` on every game | the scheduler |

**The deletion sweep is lazy, as RET-4 allows.** A server nobody plays
accumulates nothing; one being played is swept whenever a player lists their
games.
