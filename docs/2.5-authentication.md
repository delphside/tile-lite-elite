# Authentication And Player Recognition

How the server knows who a player is. The calls themselves, with their
requests, responses and refusals, are in [4.3 API Schema](4.3-api-schema.md#auth-endpoints);
the tables in [4.2 Database Schema](4.2-database-schema.md); worked examples in
[2.6](2.6-authentication-examples.md); seats and invitations in
[2.7](2.7-authentication-and-invitations.md).

## Players and sessions

A **player** is a persistent identity: a display name, a password and an
email address. A **session** is a bearer token (`Authorization: Bearer
<token>`) proving a client may act as that player. The server keeps only a
hash of each token, so a copy of the database cannot be used to sign in.

A **display name is unique**, compared case-insensitively and after Unicode
folding, because login finds the player by it. An **email address is not
unique**: one person may run several players under one address.

**Passwords** are hashed with argon2, slow and salted, because people choose
them. **Tokens** are random and are hashed with sha256, fast enough to look up
on every request. There is no password length or strength rule.

**Signing in** is by display name and password. A wrong name and a wrong
password get the same refusal, so the refusal does not reveal which names
exist. Each sign-in starts a new session and leaves the player's others valid.
Where a client keeps its token is in [4.6](4.6-client-local-storage.md).

## How long a session lasts

Two limits, the same for every session:

| limit | value | measured from |
| --- | --- | --- |
| idle | 48 hours (`SESSION_IDLE_WINDOW_SECS`) | `last_seen_at`, bumped on authenticated requests, throttled |
| absolute | 10 days (`SESSION_MAX_LIFETIME_SECS`) | creation; never extended |

An expired session is refused, and the row is deleted when `GET /games` next
runs. **Logging out** deletes the session at once.

**"Stay logged in" is a client setting**: it decides whether the browser keeps
the token across a restart, and does not change either limit. **"Remember me"**
prefills the display name only.

## Changing account details

| change | needs | afterwards |
| --- | --- | --- |
| display name or email (`update-details`) | a valid session | the session stays valid; a new display name must be unique |
| password (`change-password`) | the current password as well | every session for the player is ended, including this one |

The current password is what makes a password change a deliberate act, rather
than something a stolen token could do.

## Forgotten passwords

`forgot-password` takes an email address, always answers `204` whether or not
it matched, and mails a link carrying a single-use token valid for an hour; a
new request retires any earlier token. `reset-password` spends the token, sets
the new password and ends every session for the player. The link opens
`/reset-password?token=…` in the web client.

Because an email address is not unique, a reset reaches one of the players
sharing it, never all of them.

## Email

The server sends four messages through Resend: a welcome on registering, a
named invitation, a join invitation for an email seat, and the password-reset
link. The wording is in `crates/server-game/emails/*.txt`. With no API key
configured, each message is logged instead of sent
([4.1](4.1-configuration.md#environment-variables)).

**Email addresses are not verified.** The schema has columns for it, and
nothing uses them.

## Acting for a seat

Every call that acts in a game refuses a seat the caller does not own, and
refuses everyone for a seat nobody has claimed yet: moves, starting, previews,
suggestions, reordering and the roster calls.

## What is stored

Only hashes of session tokens, passwords and reset tokens. A raw token exists
only on the client that holds it and in the reset email.
