# 3.7 Workstreams

The programme delivers change through workstreams. Each owns a part of the
service and a named set of artefacts. A workstream is unbounded, with no end
date and no scope to complete; the projects under it end. It is defined by this
document and the `Workstream` issue field, and by nothing else.

| Workstream | owns |
| --- | --- |
| Application & Game Architecture | a game's life, the message flows, and the interfaces to clients: `crates/server-game/src/app/` (`games.rs`, `roster.rs`, `events.rs`, `ratings.rs`) and `crates/api` |
| Game Rules | the mechanics of a move, the editions and the word lists: `crates/rules-shared` |
| Engine Player | the bot as a participant: `crates/engine-core` |
| Client UI | what a player sees and touches: `crates/ui` |
| Client Management | getting a client to a player and keeping it current: the desktop build, `/version.txt` and the build id |
| Authentication & Authorisation | accounts and people: `crates/server-game/src/app/` (`auth.rs`, `admin.rs`, `invitations.rs`) and `crates/admin-cli` |
| Capacity Planning | whether the service will outgrow its infrastructure: `sweeps_capacity.rs`, `throttle.rs` |
| Operations & Infrastructure | the live service, run, watched and recovered: the host, the `Caddyfile`, `docker-compose.yml`, certificates |
| Delivery Tooling | the machinery from a commit to a running environment: `scripts/`, CI, the build model |
| Process Definition | how we work, and the documents that state it: `docs/3.x` |

`crates/rules-shared` and `crates/api` are compiled into both the server and the
web client: they are the shared code.

A requirement can be raised by anyone. The owning workstream triages it, and
if accepted it folds into a project that workstream runs
([3.6](3.6-change-lifecycle.md)). Older issues cite workstreams by issue
number; the [glossary](changes/workstreams/process-definition/glossary.md#workstreams-the-capabilities-we-maintain)
maps them.

## What makes something a workstream

**A workstream is a self-contained subsystem with mechanisms of its own**:
Authentication & Authorisation has tokens, sessions and hashing; Client
Management has bundles, versions and update signals. Something with no
mechanisms of its own is a project. Application & Game Architecture is the
exception: it is what remains when the self-contained subsystems are carved
out, the application's architecture and its central function together.

**The list grows when a subsystem develops mechanisms of its own**, not because
the centre has grown large.

**The boundaries are tested by the artefact lists.** If two requirements touch
the same artefacts and sit in different workstreams, the workstreams are drawn
wrongly, not the requirements ([3.6 §2.20](3.6-change-lifecycle.md#220-workstreams-overlapping-requirements-should-land-together)).
An issue belongs to the workstream whose artefacts it changes.

**A shared mechanism goes where its content is defined**, not where its
plumbing runs, and is designed to by the other workstreams
([3.6 §2.23](3.6-change-lifecycle.md#the-exception-a-shared-mechanism-is-owned-once-and-designed-to)).

**The test is what a change is for, not how it shipped.** #174's logging
shipped as a release and is Operations & Infrastructure's, because it changes
how the running service is watched. `Type of change` says what a change owes;
`Workstream` says who owns it.

**Where a requirement needs two workstreams' artefacts**, it is one project
carrying both, not a dispute about ownership.

## How the names are written

A workstream's name is a proper noun and is capitalised: "this project belongs
to Capacity Planning". Every other title is sentence case. `&` is used rather
than `and`, because the names are field values in column headers.

## Application & Game Architecture

A game's life on the server (creating it, filling seats, playing, finishing,
and what happens to it afterwards), and the client-server architecture that
carries it. They are one capability because the hard part of a game's life is
that two sides must agree about it while neither waits: a move made in one
place has to reach the other, out of order, after a disconnection, or to a
client that was closed.

| it owns | which means |
| --- | --- |
| the data models | what a game is: the snapshot, the DTOs, the schema the two sides agree on |
| the message flows | what is said, when, to whom, and what happens if it arrives late or twice |
| the interfaces to clients | `crates/api` and the version pair that says whether the two sides still agree |

### The artefacts Application & Game Architecture owns

| artefact | |
| --- | --- |
| `crates/server-game/src/app/`: `games.rs`, `roster.rs`, `events.rs`, `ratings.rs` | a game's life on the server |
| `sweeps_game.rs` (`expire_overdue_turns`, `expire_overdue_turn`, `send_move_time_reminders`), `scheduler.rs`, `scheduler_jobs.rs` | sweeps that apply game rules, and the scheduler that runs every sweep |
| `crates/server-game/src/app.rs`, `game_state.rs`, and `app/events.rs` | the WebSocket transport, broadcasts, and reconnection |
| `crates/api`, `docs/4.3-api-schema.md` | the shapes the two sides exchange, and the version pair |
| `docs/2.3`, `docs/4.4-snapshot-json-schema.md` | the engine interface, and what a game's state is |

### Networking: layer 7 here, layers 1 to 6 in operations

| | | owner |
| --- | --- | --- |
| layer 7 | what is said over the connection: WebSocket message flows, broadcasts, reconnection and re-fetch, the DTOs | here, for game state |
| layers 1 to 6 | that a connection exists and is private: TLS, certificates, the reverse proxy, ports, DNS | Operations & Infrastructure |

The layer separates application from infrastructure; it does not say which
application concern. Authentication's layer-7 flows are Authentication &
Authorisation's.

### The general messaging mechanism is owned here, and shared

| | owner |
| --- | --- |
| the mechanism: the socket, framing, broadcast, reconnection, ordering, the version pair | here, shared |
| the messages each function sends through it | that function: an authentication flow's are Authentication & Authorisation's, a client-update signal's are Client Management's |

A change to the shape of what is delivered (a common header field, how messages
are dispatched, a DTO convention) is here, whoever it is for. A change to what
is said is the workstream saying it. Whether the connection exists at all is
operations. The mechanism is here because the game defines most of what flows
through it.

### Sweeps: the mechanism here, each sweep with its owner

A sweep applies a rule on a schedule, and is owned by the workstream whose rule
it applies: turn expiry and move-time reminders here, retention and the daily
size measurement Capacity Planning's. The scheduler (#400) is here, because
this workstream's sweeps change game state and broadcast it, and need more
control of it than a retention delete does. Turn expiry runs every five
seconds and reminders hourly; a job is added in `scheduler_jobs.rs`. Retention
and the size measurement still run lazily from `GET /games`.

### Invitations: the state here, accepting one in authentication

Who has been invited, whether they accepted or declined, and what that does to
the roster is a game's life, and is here. Following an emailed invitation means
registering or signing in first, and is Authentication & Authorisation's.
`invitations.rs` and `docs/2.7` have two owners by design.

## Game Rules

The mechanics of playing a move: is this placement legal, is this a word, what
does it score. It also owns the editions and word lists those mechanics use.
Who moves, passes or resigns is game play, and is Application & Game
Architecture's.

### The artefacts Game Rules owns

All of `crates/rules-shared`:

| artefact | |
| --- | --- |
| `board.rs`, `model.rs`, `validate.rs`, `score.rs`, `format.rs` | is this legal, and what does it score |
| `generate.rs` | enumerating every legal move; see the open question below |
| `dictionary.rs`, `tiered.rs`, `cache.rs` | structures derived from static data |
| `src/wordlists/`, `docs/3.5` | which words exist, which are refused, and where each list came from |
| the editions: alphabets, tile economies, board layouts | what a game is played with |
| `docs/2.1`, `docs/2.2` | the rules engine and its implementation |

### A component with three consumers

`crates/rules-shared` is a leaf: the client, the game manager and the engine
depend on it, and it depends on none of them. It validates and scores
candidate words and prefixes quickly enough for a search. The client uses it to
score a staged move, the game manager for the official validation and score,
and the engine to search. That interface is what the boundary is drawn around.

A dictionary structure belongs here, not with the engine: a trie built from a
word list is a faster way of answering "is this a word", which is validation.

### Open: does enumerating every legal move belong here?

`generate.rs` enumerates all legal moves and the engine consumes the list, so
today the rules decide how the search is walked. If iterating every move is one
strategy's way of using the rules, it belongs to Engine Player. #71 separates
the engine from the rules and will settle it.

## Engine Player

The bot as a participant: how it chooses a move, how strong and how fast it is,
and how it is driven. The standing goal is stronger bots. A change that makes a
bot play differently is a new bot with a new name, not a change to Greedy Bot.

### The artefacts Engine Player owns

| artefact | |
| --- | --- |
| `crates/engine-core` | `choose_action`: the player, as distinct from the rules |
| `crates/server-game/src/app.rs`: `run_engine_turns` | how and when the engine is asked to move |
| `crates/server-game/examples/engine_timing_bench.rs` and its CSV | how strength and speed are measured over time |

It consumes Game Rules' validation, scoring and dictionary structures; what is
here is the algorithm on top: which legal move to play, how the search is
ordered and pruned, and how long it takes.

### This boundary anticipates the architecture

| | now | where it is going |
| --- | --- | --- |
| client | split out, asynchronous | |
| game manager | the server | |
| engine player | tightly bound: `run_engine_turns` computes replies inside the request that triggered them | a client like any other |

So the workstream is drawn where the seam will be. Until #71 (the engine as a
client) and #10 (the bot client harness over the public API) land, some
requirements belong to both this and Application & Game Architecture. If #71 is
dropped, this shape is reviewable.

## Client UI

What a player sees and touches: the board, the rack, the controls, the lists.

### The artefacts Client UI owns

| artefact | |
| --- | --- |
| `crates/ui` | the whole client |
| `docs/4.6-client-local-storage.md` | what the client keeps |
| `docs/4.3-api-schema.md`'s client-facing shapes | what the UI renders |

### A layer over every other capability

A requirement here usually touches another workstream too, and that is not a
boundary failure: everything has to be shown, and showing it is one capability
with one set of conventions. The test is which half of the pair a change is. A
move is legal or not: Game Rules; how it is displayed: here. A client is out of
date: Client Management; where that is said on screen: here.

## Client Management

Getting a client into a player's hands and keeping it current: builds,
distribution, versions, and how a running client learns a newer one exists. It
is separate from Client UI because they fail differently: a UI defect is
visible, a distribution defect means somebody is running last month's client
and nothing says so.

### The artefacts Client Management owns

| artefact | |
| --- | --- |
| the desktop build and its distribution | how a client reaches a player at all |
| version skew handling in `crates/ui` | what a client does when the server has moved on |
| `/version.txt` and the build id | how a running client notices a new one |
| `docs/4.3-api-schema.md`'s version pair | what "too old" means |

Delivery Tooling gets a build to an environment; this gets it to a person. The
code often shares a crate with Client UI; the test is what the change is for.

## Authentication & Authorisation

Accounts and people: who someone is, what they may do, and how they stop being

### The artefacts Authentication & Authorisation owns

| artefact | |
| --- | --- |
| `crates/server-game/src/app/`: `auth.rs`, `admin.rs`, `invitations.rs` | registering, signing in, sessions, accepting an emailed invitation, administrative action on an account |
| `crates/admin-cli` | what an operator can do to an account |

## Capacity Planning

Tracks when the service is expected to outgrow its infrastructure. The capacity
plan (`docs/reports/capacity_plan/`) is updated regularly: historic data,
extrapolation, and hard and soft thresholds with the dates they are expected to
be crossed. A hard threshold is a risk to the production service; a soft one
says headroom should be increased. It tracks memory, CPU, storage, server
startup time, and counts such as registrations and games. It owns the tooling
that captures this, and the functionality that protects the application from
high demand.

**It identifies; the owner of the artefact fixes.** A capacity problem becomes a
requirement for whichever workstream owns what must change: infrastructure to
Operations & Infrastructure, in-memory caching to Application & Game
Architecture, rate limits here.

**The regular work needs no requirement or project**: it is programme BAU
([3.8](3.8-programme-activities.md)). Improvements to its own process and
tooling are projects.

### The artefacts Capacity Planning owns

| artefact | |
| --- | --- |
| `docs/2.4-persistence.md` | what is stored and how much of it |
| `sweeps_capacity.rs`: `expire_old_terminal_games`, `record_database_size` | what is removed and when, and the daily size series |
| `throttle.rs` | rate limiting |
| the in-memory game model's growth | startup time and resident size |
| the 1 GB VM's headroom, and the 20 GB Always Free allowance | the ceiling everything is measured against |

### The boundary with Operations & Infrastructure

| | asks |
| --- | --- |
| Operations & Infrastructure | is it healthy now? An alarm fires and someone acts today: disk full, service down, backup missing |
| Capacity Planning | is the trend acceptable? Across every metric, application and technical, does what is coming still fit? |

An alarm on the disk filling is operations; a design that stops it filling, or
noticing registrations growing unexpectedly, is here. Stress testing is here
too: its question is how big the data can get and where the service breaks.

## Operations & Infrastructure

The live service, run, watched and recovered: the host, monitoring, alerting,
logging, backups and disaster recovery, and the infrastructure it runs on, in
all three environments. Preview and rehearsal are run and watched here as well,
because splitting their ownership from production's would let them drift.
Infrastructure and operations are one workstream until infrastructure projects
start waiting on operations ones.

| the preview and rehearsal environments, and their exposure | `scripts/rehearsal-access.sh` gates rehearsal |
| the host's own packages and users | `sqlite3`, `systemd-journal` membership |

| `scripts/check-log-hygiene.py`, `scripts/check-log-hygiene-nightly.sh` | logging, and what must never appear in it |
| `scripts/services.sh`, `scripts/board-status.py` | what is running, and what state it is in |

| `docs/3.4-production-environment.md`, `docs/4.7-log-events.md` | the documents that state all of it |

## Process Definition

How we work: how a change is raised, classified, agreed, built, tested,
delivered and reviewed, the documents that state it, and the tooling that
manages the process. `docs/3.x` is meant to be portable to another project, so
each rule is kept separable from this project's answer to it.

### The artefacts Process Definition owns

| artefact | |
| --- | --- |
| `CLAUDE.md`, `AGENTS.md` | the one-page rules, and the guide for outside agents |
| `docs/3.6`, `docs/3.7`, `docs/3.8`, `docs/3.9` | the lifecycle, who owns what, the programme's activities, how documents are written |
| `docs/4.8-artefacts.md`, `docs/4.9-delivery-log.md` | the artefact register, and what shipped when |
| `docs/changes/workstreams/process-definition/glossary.md` | D1 to D38; history, not added to |
| `docs/templates/`, `.github/ISSUE_TEMPLATE/`, the issue types, fields and option values | the forms, and the strings tooling matches |
| `.github/workflows/docs.yml` | the review workflow |
| `scripts/board-*.py`, `scripts/board/`, `scripts/issue-mentions.sh` | the board model: what needs doing, what changed, what refers to what |
| `scripts/check-docs.sh`, `scripts/check-doc-links.py`, `scripts/document-map.py` | the documentation gates and the map |

Process documents change on `main`, never on a project branch
([3.6 §2.2](3.6-change-lifecycle.md#22-when-to-branch-and-what-pre-approved-means)).
Pre-approval settles authorisation, not rigour: a change to process tooling may
still need a design and a test approach agreed before it is built.

## The line between process, tooling and operations

| | owns | ends at |
| --- | --- | --- |
| Process Definition | the rules and the documents that state them, and the tooling that manages the process | it says what should happen |
| Delivery Tooling | the machinery that makes a change happen: deploy, build, CI, release gates, test tooling | the release |
| Operations & Infrastructure | the service once it is live | never; it is a running concern |

A deploy is the release, so deployment tooling is Delivery Tooling's, not
operations'. Process and tooling are separate workstreams because they are
agreed, tested and delivered differently: a document is discussed and merged;
`deploy.sh` earns a design, a test approach and a rehearsal.

## Who decides, within a workstream

(D54.) Everything is reported, and everything lands in the repository.

| | decides |
| --- | --- |
| Claude alone | Delivery Tooling and Process Definition, and any issue of type `tooling` or `documentation` in any workstream: triage, decide, build, land, close, and delete |
| the owner | anything reaching production; the product and game rules; anything irreversible outside git; a rule in `CLAUDE.md` that changes how he works; and anything Claude judges he would want to see |

Deleting a check, script, section or rule that is not earning its keep is in
scope, and needs no more permission than adding one.

**The brake**, which either of us can apply in one sentence:

1. **Fewer programme-overhead issues, and less of the owner's time.** Every
   `Type of change` is counted, raised and closed per week, and read in the
   owner's words:

   | `Type of change` | use of Steve's time | should |
   | --- | --- | --- |
   | `functional` | constructive | be where the time goes |
   | `cosmetic` | constructive: counted separately, credited as functional | be where the time goes |
   | `non-functional` | constructive if an enhancement | |
   | `bug` | poor quality overhead | fall; #71's refactor exists to reduce them |
   | `tooling`, `documentation` | programme overhead, what the brake is for | fall |
   | unset | not categorised | not persist |

   Less of his time is read from what the board reports as waiting on him.
   `scripts/board-digest.py` reports both weekly, as the `weekly-digest`
   activity ([3.8](3.8-programme-activities.md)). The series is comparable from
   2026-09-07; before that many issues had no type. The tooling share is an
   observation, not a target, until the board model has replaced the tooling
   it replaces (#383).
2. **A check that only ever finds defects in other checks is deleted, not
   fixed.**
3. **No new check without a named past failure it would have caught**, with its
   issue number.

The reasoning is on #382.
