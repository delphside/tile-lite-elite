# 3.7 Workstreams

The Tile Lite Elite Programme delivers change through Workstreams.  Each Workstream owns a part of the service.  A Workstream owns a named set of artefacts, for example documents or source code.  

These are the current Workstreams, and the code or configuration each owns. Each section below gives the full list.

| Workstream | owns |
| --- | --- |
| Application & Game Architecture | `crates/server-game/src/app/` — `games.rs`, `roster.rs`, `events.rs`, `ratings.rs` — and `crates/api` |
| Game Rules | `crates/rules-shared` |
| Engine Player | `crates/engine-core` |
| Client UI | `crates/ui` |
| Client Management | the desktop build and its distribution, `/version.txt` and the bundle hash |
| Authentication & Authorisation | `crates/server-game/src/app/` — `auth.rs`, `admin.rs`, `invitations.rs` — and `crates/admin-cli` |
| Capacity Planning | `crates/server-game/src/app/` — `sweeps_capacity.rs`, `throttle.rs` |
| Operations & Infrastructure | the `Caddyfile`, `docker-compose.yml`, the host and its certificates |
| Delivery Tooling | `scripts/`, the CI workflows, the build model |
| Process Definition | `docs/3.x` — the rules and the documents that state them |

`crates/rules-shared` and `crates/api` are compiled into both the server executable and the web client WASM application. They are the shared code: the rules the two sides must agree on, and the shapes they exchange.

Workstreams operate using 'Requirements' and 'Projects'.  A requirement can be raised by anyone.  It is evaluated by the relevant Workstream and, if accepted, is assigned to a Project.  The Workstream runs the project and delivers the requirement.

Requirements and Projects are tracked in GitHub.  Each is an Issue Type.  Fields are defined for both Requirements and Projects.  Workstream is a field on both.

## What makes something a workstream

Two tests, and they answer different questions.

**Is the boundary in the right place?** If two requirements touch the same
artefacts and sit in different workstreams, the workstreams are drawn wrongly —
not the requirements. That is why each section below lists the artefacts it
owns: the lists test the taxonomy, not only each other.

**Should there be a boundary at all?** A workstream is a **self-contained
subsystem with technical mechanisms of its own** — Authentication &
Authorisation has tokens, sessions and hashing; Client Management has bundles,
versions and update signals. Something with no mechanisms of its own is a
project, not a workstream.

**Application & Game Architecture is the exception, deliberately.** Owner,
2026-08-28: *"it is two things together, the overall application architecture
and the central part of the functionality."* It is what remains when the
self-contained subsystems have been carved out, which is why it alone is named
by two nouns rather than one.

**A shared mechanism goes where its content is defined**, not where the plumbing
runs. The general messaging mechanism could be a workstream by the test above —
it is self-contained and everything uses it — and is not one, because the game
defines most of what flows through it. Self-containment makes a workstream
*possible*; being the place its content is defined makes one *right*.

**The list grows when a subsystem develops mechanisms of its own.** It does not
grow because the centre has become large: splitting that by size would put the
architecture in one workstream and the functionality it carries in another.

## How the names are written

**A workstream's name is a proper noun and is capitalised** — *"in a sentence I
want to say 'This project belongs to Capacity Planning'."* Every other title in
this repository is sentence case, because a requirement or project title is a
sentence. These are the names of permanent categories, and the capitals say
which kind of thing is being named before it has been read.

**`&` rather than `and`**, consistently, because these are field values in
column headers and swimlane labels where four characters matter.

**Quotations keep whatever they said at the time**, including the older names:
this workstream list began as three areas, and Application & Game Architecture
was *game lifecycle and client-server architecture* until 2026-08-28.

## Application & Game Architecture

Renamed 2026-08-28 from *game lifecycle and client-server architecture*, which described the two things it started as rather than the one thing it is. Owner: *"then it naturally owns the data models, message flows, and interfaces to clients."*

| it owns | which here means |
| --- | --- |
| **the data models** | what a game *is* — the snapshot, the DTOs, the schema the two sides agree on |
| **the message flows** | what is said, when, to whom, and what happens if it arrives late or twice |
| **the interfaces to clients** | `crates/api` and the version pair that says whether the two sides still agree |

**The game lifecycle capability** is what those exist for: creating a game, adding players, playing it, and finishing it — and everything that happens to a game after that.

**And the client-server architecture that carries it.** Owner, 2026-08-24: *"game lifecycle should go with client-server architecture — asynchronous interactions between client and server."* The two are one capability because the hard part of a game's life is that **two sides have to agree about it while neither is waiting**: a move made in one place has to reach the other, out of order, after a disconnection, or to a client that was closed at the time. Splitting them would put the state in one workstream and the means of agreeing about it in another.

A **workstream** is unbounded: no end date, no scope to complete. Projects under it do end.

Created 2026-08-24, when triaging the backlog found that the three existing workstreams — Process Definition, Delivery Tooling and Operations & Infrastructure — covered the supporting capabilities and not the product.

### The artefacts Application & Game Architecture owns

Owner, 2026-08-24: *"it also helps if they map to artefacts."* That is what makes allocation checkable rather than a matter of taste — an issue belongs here if it changes one of these.

| artefact | |
| --- | --- |
| `crates/server-game/src/app/` — `games.rs`, `roster.rs`, `events.rs`, `ratings.rs` | a game's life on the server |
| `sweeps_game.rs` — `expire_overdue_turns`, `expire_overdue_turn`, `send_move_time_reminders` — and the **mechanism** that runs every sweep | sweeps that apply game rules, and the thing that runs them |
| `docs/2.3` | the engine interface — how the manager asks an engine for a move |
| `docs/4.4-snapshot-json-schema.md` | what a game's state is |
| `crates/server-game/src/app/events.rs`, `game_state.rs`, `app.rs` | the WebSocket transport, broadcasts, and reconnection |
| `crates/api` and `docs/4.3-api-schema.md` | the shapes the two sides exchange, and the version pair that says whether they still agree |

#### Networking: layer 7 here, layers 1–6 in operations

Owner, 2026-08-24: *"the actual message flows (layer 7) is part of the functionality of the application and belongs with game lifecycle (mainly). But there is a technical side to do with the network configuration, layers 1–6."*

| | | owner |
| --- | --- | --- |
| **layer 7** | what is said, when, to whom, and what happens if it arrives late or twice — the WebSocket message flows, broadcasts, reconnection and re-fetch, the DTOs | **here** |
| **layers 1–6** | that a connection exists and is private — TLS, certificates, the reverse proxy, ports, DNS. `Caddyfile`, `caddy-data` / `caddy-config`, `docs/3.4` | **Operations & Infrastructure** |

That is a sharper test than "which crate is it in", because both sides touch the same running system. **The WebSocket is here because it carries game state; the transport it runs over is not.** A change to what a `GameUpdate` contains is this workstream. A change to how the certificate is obtained is not, and neither is a port mapping.

*"Mainly"* is doing real work in that sentence: authentication also has layer-7 message flows, and they belong to authentication & authorisation. The layer is what separates application from infrastructure — it does not, on its own, say **which** application concern.

##### The general messaging mechanism is owned here, and shared

Owner, 2026-08-28: *"we need a workstream to own the general messaging mechanism, which is shared between the functions. Game defines most of the actual messages and data types, so it best fits there."*

| | owner |
| --- | --- |
| **the mechanism** — the socket, framing, broadcast, reconnection, ordering, the version pair that says whether two sides still agree | **here**, and it is shared |
| **the messages** each function sends through it | **that function** — an authentication flow's messages are authentication & authorisation's, a client-update signal's are client management's |

**Ownership follows where the content is defined, not where the plumbing runs.** By the test above the mechanism *could* be a workstream of its own: it is self-contained and has mechanisms of its own. It is not one, because the game defines most of what flows through it — and separating the mechanism from the messages that dominate it would put the DTOs in one workstream and the thing that carries them in another. That is the same objection that joined game lifecycle to client-server architecture in the first place.

**What that means in practice**: a change to the *shape* of what is delivered — a new common header field, a change to how messages are dispatched, a DTO convention — is this workstream, whoever it is delivered for. A change to *what* is said is the workstream of whatever is saying it. A change to *whether the connection exists at all* is operations.

#### Sweeps: the mechanism here, each sweep with its owner

A sweep applies some rule on a schedule. **The individual sweeps are owned by the workstream whose rule they apply.** Turn expiry and move-time reminders apply game rules, so they are here. Retention and the daily size measurement are Capacity Planning's.

**The mechanism is here**, including the scheduler when it is built. Owner, 2026-09-01: the sweeps that belong here are tied to other functionality in this workstream in a way that Capacity Planning's are not, so they need more control of the mechanism. Turn expiry changes whose turn it is and broadcasts the result; retention deletes a row.

That follows the same rule as the messaging mechanism above: it goes where most of its content is defined.

Until it is built there is no scheduler. Sweeps run lazily from `GET /games`, which #166 records as the defect it is.

#### Game Rules and Engine Player: what this workstream does not own

**Validation, scoring and the structures derived from static data moved to Game Rules** on 2026-08-31, and choosing a move was always Engine Player's. What is left here is a game's *life*: whose turn it is, passing and resigning and timing out, what the two sides exchange, and the transport that carries it.

The earlier wording is kept because it was right when written and explains the shape:

> Owner, 2026-08-24: *"everything up to validation and scoring is owned by #208. This includes data derived from static data which can be used by an engine, such as the trie dictionary structure. #213 builds a search algorithm on top."*

At the time there was no Game Rules workstream, so *"up to validation and scoring"* meant *here*. It now means Game Rules, and the sentence is otherwise unchanged: the line between rules and search has not moved, only the name of what sits on the rules side of it.

#### The Authentication & Authorisation: invitation state versus accepting one

Owner, 2026-08-24: *"the invitation state is owned by the game, some mechanics about accepting an email invitation belongs to #210, since it involves registering or authenticating."*

**The state is here.** Who has been invited to a game, whether they accepted, declined, or were re-invited, and what that means for the game's roster — that is a game's life.

**Accepting an emailed invitation is Authentication & Authorisation's**, because following the link means registering or authenticating first. The identity has to exist before the seat can be filled.

`invitations.rs` and `docs/2.7` therefore have two owners by design rather than by accident.

## Game Rules

**The game rules capability**: the mechanics of playing a move. Is this placement legal? Is this a word? What does it score? It also owns the editions and word lists those mechanics use.

The distinction from Application & Game Architecture is game play against the mechanics of playing a move. Who moves, passes or resigns is game play. Validating and scoring the move is mechanics.

### A component with three consumers

Four components cover game logic: client, game manager, game rules, game engine. The crate mapping is in the introduction.

`crates/rules-shared` is a leaf: the client, the manager and the engine all depend on it, and it depends on none of them. It is compiled into both the server executable and the web client WASM application, along with `crates/api`. Those two are the shared code.

The engine is a client logically but not structurally. `server-game` links it in today. #71 changes that, and this boundary anticipates it, as Engine Player's does.

### The artefacts Game Rules owns

**The whole of `crates/rules-shared`.** The files below say what is in it, not which parts are in scope.

| artefact | |
| --- | --- |
| `board.rs`, `model.rs`, `validate.rs`, `score.rs`, `format.rs` | is this legal, and what does it score |
| `generate.rs` | enumerating every legal move — here today, and see below |
| `dictionary.rs`, `tiered.rs`, `cache.rs` | structures derived from static data |
| `src/wordlists/`, `docs/3.5` | which words exist, which are refused, and where each list came from |
| the editions — alphabets, tile economies, board layouts | what a game is played with |
| `docs/2.1`, `2.2` | the rules engine and its implementation |

The dictionary structure belongs here rather than with the engine. A trie built from a word list is a faster way of answering "is this a word", which is validation. The engine consumes it, and so does the client.

Content and mechanism stay together. The dictionary structure's content is the word lists, owned by this Workstream.

### What the three consumers use it for

Game Rules validates and scores both candidate words and candidate prefixes: do these letters start a valid word? It is very fast, and optimised for a computer player searching all possibilities.

As such it is used by the client to validate and score a player's staged move, before they decide to play it. It is used by the Game Manager to do the official validation and scoring of moves when they are played. And it is used by the Game Engine when it is searching for high scoring moves.

That interface is the part to keep. It is what all three consumers need, and it is what the boundary is drawn around.

### Open: does enumerating every legal move belong here?

`generate.rs` enumerates all legal moves, and the engine consumes the list. So today the rules decide how the search is walked, not the engine.

The question is whether iterating over every move is a core feature of the rules, or one strategy's way of using them. If it is a strategy, it belongs to Engine Player, and the engine should decide what to check and in what order.

Unresolved. #71 separates the engine from the rules and is where it will be settled.

## Engine Player

**The engine player capability**: the bot as a participant — how it chooses a move, how strong it is, how fast, and how it is driven.

A **workstream** is unbounded: no end date, no scope to complete. Projects under it do end.

Created 2026-08-24.

### The artefacts Engine Player owns

| artefact | |
| --- | --- |
| `crates/engine-core` | `choose_action` — the player, as distinct from the rules |
| `crates/rules-shared/src/generate.rs` | move generation — the search itself |
| `crates/server-game/src/app.rs` — `run_engine_turns` | how and when the engine is asked to move |
| `crates/server-game/examples/engine_timing_bench.rs` and its CSV | how strength and speed are measured over time |

### The boundary with Application & Game Architecture

Owner, 2026-08-24: *"everything up to validation and scoring is owned by #208… #213 builds a search algorithm on top."*

**Everything up to and including validation and scoring is Application & Game Architecture** — is this a word, is this placement legal, what does it score. **And so are the structures derived from static data**: the tiered/trie dictionary and the cross-check caches. A trie built from a word list is a faster way of answering *is this a word*; it is validation, not search. This workstream is a **consumer** of it, and so is the client.

**What is here is the algorithm on top**: which of the legal moves to play, how the search is ordered and pruned, how long it takes, and how good the result is.

**The standing goal is stronger bots**, which is why the timing benchmark exists and is kept: a change that makes the engine faster is only interesting because it buys search. A change that makes it *play differently* is a new bot with a new name, not a change to Greedy Bot — the owner's boundary, 2026-07-30.

### This boundary anticipates the architecture, and does not describe it yet

Owner, 2026-08-24: *"when I wrote the original version, in `old-crates/first-try`, it was a single application with client, game management and engine player all tightly bound together in a single executable, all actions triggered synchronously by actions on the client. In the current version we have split the client out and created an asynchronous interaction with the game manager. But the engine player is still tightly bound. So the distinction today is not as clear as it will be."*

| | then — `first-try` | now | where it is going |
| --- | --- | --- | --- |
| **client** | in the executable, synchronous | **split out**, asynchronous | — |
| **game manager** | in the executable | the server | — |
| **engine player** | in the executable | **still tightly bound** — `run_engine_turns` computes replies inside the request that triggered them | a client like any other |

**So this workstream is drawn where the seam will be, not where it is.** An engine change today lands in the same code as a game-manager change, and some requirements will honestly belong to both this and application & game architecture until the seam exists.

**The work that makes it real** is #71 — *one game model: version, seats, DTOs and **the engine as a client*** — and #10, the bot client harness that runs an engine over the public API rather than in-process. Once those land, the boundary stops being a statement of intent and starts being a fact about the code.

**Recording it because the alternative is worse.** Drawing the workstream only when the code allows it would leave every engine requirement homeless in the meantime, and would lose the reason the separation is wanted at all. See §2.11: *where the shape was chosen because of other work, say which work* — so that if #71 is dropped, this shape becomes reviewable rather than mysterious.

#### This workstream overlaps everything, and that is what it is

Owner, 2026-08-24: *"there will be some overlap between #209 and other functionality since #209 is a layer providing access to other functionality."*

**The client UI is a layer over every other capability**, so a requirement here almost always touches one of them too. A client is out of date — client management; where that is said on screen — here. Owner: *"#211 tells the client the version, #209 tells the client where to display it."*

**The Client Management**: the code often sits in the same crate, so the test is what the change is *for*. A control that reads better, a list that shows the right thing, a board that clears when it should — UI. A client that notices a newer version exists and reloads — management. They fail differently: a UI defect is visible, a distribution defect means somebody is looking at last month's client and nothing says so.

## Capacity Planning

**The capacity planning capability**: tracks when the service is expected to outgrow the infrastructure.  A Capacity Planning report is updated regularly.  It shows historic data and extrapolates future data.  Hard and soft thresholds are given with dates if they are expected to be crossed.  A hard threshold indicates a risk to the production service.  A soft threshold indicates that action should be taken to increase the headroom.  Data tracked includes memory usage, cpu utilisation, storage utilisation, server startup time, application counts such as registrations and games.  

Capacity planning owns tooling to capture this data, and functionality to protect the application from high demand.

### Analysis vs fix

Capacity Planning's primary job is to identify capacity related problems in good time and raise requirements to address them.  These requirements are owned by which ever workstream owns the impacted artefacts.  For example an infratructure change would go to Operations and Infrastructure.  Changes to how games are cached in memory would go to Application and Game Architecture.  Changes to rate limits would be raised on Capacity Planning, since they own that code.

### Continual Process vs Improvement Projects

Capacity Planning is an ongoing process with regular outputs in the form of updates to the Capacity Planning Report and associated requirements.  This regular work does not require requirements, projects or pull requests.  It is part of operating the programme.  

In addition Capacity Planning can raise and run improvement projects to improve it's own processes and tooling.

### The artefacts Capacity Planning owns

| artefact | |
| --- | --- |
| `docs/2.4-persistence.md` | what is stored and how much of it |
| `sweeps_capacity.rs` — `expire_old_terminal_games`, `record_database_size` | what is removed, and when, and the daily size series |
| the in-memory game model's growth | startup time and resident size |
| the 1 GB VM's headroom, and the 20 GB Always Free allowance | the ceiling everything is measured against |

**The Operations & Infrastructure**: operations *notices* — alarms, monitoring, disk. Capacity planning *changes what is consumed*, or decides what is acceptable. An alarm on the disk filling is operations; a design that stops it filling is here.

#### Why it is separate from operations, when it could be part of it

Owner, 2026-08-24: *"#212 could be a function of #189. It is a well defined function and it needs its own process."*

**It could sit inside operations and infrastructure**, and nothing about the artefacts forbids it. It is separate because it is a **well-defined function with a process of its own**: measure what is consumed, compare it against the ceiling, decide whether the trend is acceptable, and act before it is not. That recurs on its own schedule and produces its own kind of answer.

Folded into operations & infrastructure it would be one concern among monitoring, backups, TLS and the host — and the first thing to be dropped, because nothing is broken today.

**It is also never finished.** Growth is continuous, and *does this still fit* changes without anybody changing the code, which is the definition of a workstream rather than a project.

**The boundary with operations & infrastructure, sharpened 2026-08-24.** Owner, allocating *notice unusual growth in registrations* (#89) here rather than to operations: *"capacity planning — which looks across all application and technical metrics."*

| | |
| --- | --- |
| **Operations & Infrastructure** | is it healthy **now**? An alarm fires, someone acts today. Disk full, service down, backup missing |
| **capacity planning (here)** | is the **trend** acceptable? Looking across every metric there is — application and technical alike — and deciding whether what is coming still fits |

So an alarm on the disk filling is operations; noticing that registrations are growing in a way nobody expected is here, even though both are *noticing*. The difference is whether the answer is *act now* or *decide whether this is sustainable*.

**And it explains the two that look like test tooling.** Stress testing (#91) is here rather than with delivery tooling, because its question is *how big can the data get and where does the service break* — a capacity question that happens to need a harness. Owner: *"independent of other test tooling so no conflict."*

## Operations & Infrastructure

**The production operations capability**, and the workstream of every project that
changes how the live service is run, watched and recovered — the host,
monitoring, alerting, logging, backups and disaster recovery.

### The boundary with Process Definition

*Owner, 2026-08-24: "The clear division would be up to release, and then
production operations after release."*

| | |
| --- | --- |
| **process definition** | the rules, and the documents that state them |
| **delivery tooling** | the machinery that carries a change to a running environment — `deploy.sh`, `deploy-preview.sh`, the build model, CI, the release gates |
| **operations & infrastructure** (this one) | everything after the release — the service is live, and this is keeping it running, watched and recoverable |

### Infrastructure is here too, until it earns its own workstream

Owner, 2026-08-24: *"the infrastructure may cross over with operations. But it needs to be covered."*

**The classical split is real**: infrastructure is *what exists* — the instance, the network, the storage, the environments — and operations is *keeping it healthy*. They are kept together here because separating them now would create a boundary with almost nothing on one side, and the cost of that is issues falling between two owners rather than sitting in one.

So this workstream owns both, and the artefacts are listed below so nothing is
homeless.

what makes them reviewable at all.

**When to split it**: when infrastructure projects start waiting on operations ones, or a project needs both and cannot say which it is. Not before — a boundary drawn early is a boundary defended rather than used.

**Networking, layers 1–6.** TLS and certificates, the reverse proxy, ports, DNS

**All three environments, not just production.** Owner, 2026-08-24: *"Delivery

## Delivery Tooling

**The delivery tooling capability**, and the workstream of every project that changes the machinery carrying a change from a commit to a running environment — building, testing, gating and deploying.

A **workstream** is unbounded: no end date, no scope to complete. Projects under it do end.

Created 2026-08-24. Owner: *"We now have three areas: process definition, delivery tooling, operations."*

### The artefacts Delivery Tooling owns

| artefact | |
| --- | --- |
| `scripts/deploy.sh`, `deploy-preview.sh`, `deploy-rehearsal.sh` | building a commit and putting it in an environment |
| `scripts/rollback.sh`, `rollback-rehearsal.sh` | putting the previous one back |
| `scripts/verify.sh`, `ci-status.sh`, `rehearsal-target.sh`, `ssh-preflight.sh` | the checks a deploy makes, and the ones it makes about itself |
| `scripts/check-commit-stamp.sh`, `check-release-version.sh` | the release gates, which match option strings literally — see `docs/4.8` |
| `.github/workflows/ci.yml` | CI: fmt, clippy, test, wasm, docs, commit stamp, e2e |
| `Dockerfile`, and the build model | how a commit becomes an image |
| `scripts/tests/` | the tests for everything above |
| `e2e/`, `scripts/e2e-clean.sh`, `scripts/clean-test-accounts.sh`, `scripts/seed-rehearsal.sh` | test tooling and its data |
| `docs/3.3-testing-ci-and-release.md` | the document that states how a release runs |

### The three areas, and where the lines fall

| | owns | ends at |
| --- | --- | --- |
| **process definition** | the rules, and the documents that state them — how a change is raised, classified, agreed, reviewed | it says what should happen |
| **this one · delivery tooling** | the machinery that makes it happen — `deploy.sh`, `deploy-preview.sh`, the build model, CI, the release gates, test tooling | the release |
| **production operations** | the service once it is live — the host, monitoring, alerting, logging, backups, disaster recovery | never; it is a running concern |

**Two cuts produced this.** *"The clear division would be up to release, and then production operations after release"* separates operations from the rest. *"Separating the process from the tooling also works"* separates the first two. A deploy **is** the release, so deployment sits on this side of the operations line, not operations & infrastructure's — which is why that workstream no longer claims "deploys".

#### Both cover production and non-production

Owner, 2026-08-24: *"Delivery tooling and operations should cover prod and non-prod, as we want to keep these similar."*

Neither of the last two areas is a production-only concern. Delivery tooling deploys to **preview, rehearsal and production**; operations runs and watches all three. The environments are deliberately kept alike, and splitting their ownership would be the first thing to make them drift — which is exactly how `deploy.sh` and `deploy-preview.sh` came to be two implementations of one principle (#134).

So #40 (rehearsal holding production user data on a public IP) is operations, despite being a non-production environment. It is about how a running environment is exposed.

**The test is what a change is *for*, not how it shipped.** #174's logging shipped as a release and is operations work, because what it changes is how the running service is watched.

### Why this is its own workstream rather than a project under Process Definition

The process documents and the tooling that implements them are agreed, tested and delivered differently. A document is discussed and merged; `deploy.sh` earns a design, a test approach, and a rehearsal. Keeping them apart stops the heavier obligation being applied to a paragraph, or the lighter one to a release gate.

It also matches how they fail. A wrong sentence is read and corrected. A wrong gate ships something untested, or refuses to ship something that is fine — which is #194, live today.

**There is a general pre-approval** to make ad-hoc changes to the process

**Projects are still possible here**, where significant changes need design and
testing documentation.

**A branch is only needed if the changes cannot be put into `main` until the
work is completed** — which would be if the old versions of the documents and
tooling are required in the interim.

#### Risk does not change the route, it changes what is owed

*Owner, 2026-08-24: "I think it covers prod and non-prod tooling. There is
clearly different risk for changes to `deploy.sh`, so it is more likely to
require a project."*

The pre-approval settles **authorisation** — no separate review. It says nothing
about **rigour**. A change to `deploy.sh` is pre-approved and still likely to
need a design and a test approach agreed before it is built, because a defect
there breaks a deploy rather than a sentence.

The two obligations are independent, and conflating them is what made the old
`lane` idea unusable.

A **workstream** is unbounded — it has no end date and no scope to complete.
Projects under it do. This one exists because process is something we maintain
rather than something we finish, and because `docs/3.x` is meant to be portable
to a second project, which means the rule and this project's answer to it have to
stay separable.

Created 2026-08-21, splitting what #179 had been doing under one number: #179 has
a fixed scope and an end, which by our own definition of the terms makes it a
**project**. This is the level above it.

#### The boundary with operations & infrastructure, and the cut inside this one

*Owner, 2026-08-24: "The clear division would be up to release, and then
