# 3.10 Benchmarking

How the engine's performance is measured, and how to read a measurement.
Benchmarking is Capacity Planning's ([5.2](5.2-workstreams.md#capacity-planning)).
It runs at every release ([3.3 §1.5.2](3.3-testing-ci-and-release.md#152-does-it-behave-correctly-on-production-like-hardware))
and monthly as the `benchmark-run` activity ([5.3](5.3-programme-activities.md)).
What the figures say about the engine's design is [2.8](2.8-engine-performance.md).

## Reading an engine timing run

`cargo run --release --example engine_timing_bench [games] [edition]` plays
engine-vs-engine games through the same `maybe_run_engine_turn` the server uses,
and appends a row to `engine_timing_results.csv`.

**Compare CPU against wall before anything else.** Each move is timed twice: wall
clock, and CPU time from `CLOCK_PROCESS_CPUTIME_ID`. If `cpu_p99_ms` is far below
`p99_ms` the move was waiting. The converse does **not** hold on a virtual
machine.

**On the deployment VMs, `cpu_ms` cannot be trusted in the tail.** A guest kernel
attributes time to a process that the hypervisor did not actually give it, so a
stolen move can report CPU time equal to its wall time and read as hard work.
What settles it is comparing the *same move* on two machines, which the
benchmark makes possible because the games are seeded and deterministic:

| | |
| --- | --- |
| ordinary moves, VM against laptop | **1.8x** — the honest machine difference |
| tail moves that report `cpu ≈ wall` | **26x** median, 319x at worst, for identical work |

A 26x spread on the same deterministic move, between machines that differ by
1.8x everywhere else, is not a property of the search.

**The frequency chart the run prints is the other half of the argument.** One
hundred buckets spanning zero to the slowest move, 1% of the range each. Genuine
search cost falls away smoothly from zero, and on the laptop that is the whole
picture — a decay to about 16 ms and nothing beyond it. The VM decays the same
way to about 9 ms and then has a second, separate population: of 27 moves over
20 ms, **18 fall between 51 and 62 ms, and nothing at all falls between 32 and
51**. A 19 ms gap with a clump on the far side of it is not a slower kind of
move. It is the hypervisor descheduling the vCPU.

**Which statistic to read, and it is not the p99.** The outliers are few — 27
of 1229 — so everything above about p97.8 is inside them and everything below is
not. Between the same two machines on 4 September:

| | median | p95 | p99 |
| --- | --- | --- | --- |
| VM against laptop | **1.6x** | **2.4x** | 12.9x |

Median and p95 track the hardware. The p99 tracks who else is on the host. So
compare median and p95 between runs, and treat a p99 from a VM as saying nothing
about this code.

**The run says so itself.** `slow_moves` counts moves over 20 ms and
`slow_cpu_starved` the subset that used almost no CPU while they waited. The
threshold is not tuned: on a machine nobody else is sharing nothing reaches it —
the slowest of 1229 laptop moves was 16 ms — while descheduling gaps cluster at
50-60 ms. A non-zero count prints a warning naming which statistics survive it.
`slow_cpu_starved` is the provable subset only; the rest cannot be told from
work by the process itself, which is why both numbers are kept.

**Excluding whole moves biases the answer, so it is not how to quote a number.**
A genuinely slow move lasts longer and so is
likelier to overlap a descheduling event, which means the exclusion removes the
expensive positions preferentially. Measured over five runs, the moves a single
run drops cost **1.20 ms** elsewhere against **0.40 ms** for all moves — three
times typical.

**The unbiased form is several runs, reduced per move.** Each position becomes
the mean of its own timings, discarding any above three times that position's
**minimum** across the runs, and the statistics are taken over those per-move
means. Nothing is selected out, because no position is dropped.

| VM against laptop | median | p95 | p99 |
| --- | --- | --- | --- |
| one run, whole moves excluded | 1.509x | 1.552x | 1.502x |
| five runs, per-move means | **1.590x** | **1.711x** | **1.748x** |

The single-run form understates by 5% at the median and 26% at the p99, and its
flatness was an artefact of its own bias. The honest picture is a factor that
**grows with the percentile**, which is what a memory-bound workload on a
smaller cache should do.

**The baseline is the minimum, not the median**, and this is not a detail. With
two runs the median is their mean, so a stall drags the baseline up with it and
escapes rejection. Splitting five runs of the same engine two against three gave
**0.390x** at the p95 under a median baseline, where a correct rule must give
1.0; the minimum gives 1.077 on that split and 1.017 the other way. A stall only
ever adds time, so the fastest observation is the best estimate of what a
position costs uninterrupted. The test suite compares runs of the same input and
requires 1.000x.

**The single-run comparison is kept** because it needs no repetition and its
shape is still the argument: Pair the runs
on `(game, turn)` and the per-move ratio has a sharp break: p97 is 2.7x and p98
is 10.4x, so the cut is a natural one rather than a chosen threshold — anything
between 3x and 8x isolates the same 32 moves of 1229, 2.6%.

| | median | p95 | p99 |
| --- | --- | --- | --- |
| laptop | 0.25 ms | 1.39 ms | 5.54 ms |
| VM, all moves | 0.42 ms | 3.28 ms | **56.14 ms** |
| VM, 32 outliers removed | 0.41 ms | 2.21 ms | **8.10 ms** |
| **VM against laptop, cleaned** | **1.6x** | **1.6x** | **1.5x** |

The 12.9x the p99 showed before is the hypervisor. What is left after it is a
real machine difference, and the per-move means above are the way to size it.

**And the excluded moves are ordinary positions**, which is the other half of it.
They cost a median of 0.41 ms on the laptop — unremarkable — and only 6 of the
32 held a blank, about the 5% base rate, so they were not selected for
difficulty. Eight used under a fifth of their wall time as CPU.

**The blank effect survives the cleaning**: 8.3x the median on the laptop, 7.7x
on the cleaned VM. Algorithmic cost travels between machines; the tail does not.

One caveat: the cut is on the ratio, so a genuinely slow position that was also
descheduled can sit under it. The cleaned `max` still holds one such move. The
median, p95 and p99 are unaffected.

### It is a different thirty every time

It is the cleanest test of the whole argument: if the outliers were properties of the positions, every run
would flag the same ones. Four rehearsal runs against the same laptop reference:

| | |
| --- | --- |
| flagged per run | 24 to 32, about 29 |
| distinct moves flagged at least once | **102** |
| expected if each run drew at random | **111** |
| flagged in all four runs | 1 |

Pairwise overlap runs from 1.8% to 12.3%. The flagged set behaves like an
independent random draw, which is what a scheduling artefact is and what a slow
position is not.

**The small repeated remainder is the physics, not a counter-example.** Sorting
the 102 by how often they were flagged:

| flagged | moves | median cost on the laptop | with a blank |
| --- | --- | --- | --- |
| once | 93 | 0.37 ms | 10 |
| twice | 6 | 3.89 ms | 5 of 6 |
| three times | 2 | 9.06 ms | both |
| four times | 1 | 9.89 ms | yes |

Against a laptop median of 0.25 ms the repeat offenders are the *longest* moves,
and a longer move is more likely to overlap a descheduling event for the same
reason a longer journey is more likely to meet a red light. They are the
blank-rack moves. So the two findings are one: blanks make a move long, and
length is what exposes it to the hypervisor.

### What the machine difference actually is

**The two CPUs are the same speed on the cheapest moves and differ by more than
two to one on the dearest.** Five runs a side, each position reduced to its
minimum so nothing is left of the hypervisor:

| fastest single move | laptop 0.093 ms | VM **0.080 ms** |
| --- | --- | --- |

| laptop cost of the position | moves | VM against laptop |
| --- | --- | --- |
| 0 – 0.15 ms | 221 | 1.34x |
| 0.15 – 0.25 ms | 515 | 1.64x |
| 0.25 – 0.5 ms | 328 | 1.84x |
| 0.5 – 1 ms | 99 | 2.08x |
| 1 – 3 ms | 47 | 2.19x |
| 3 – 10 ms | 13 | 2.15x |

**A clock difference is flat at every size, and this is not flat.** It is nearly
1.0 where the work is smallest — the VM is marginally *faster* on the single
cheapest move — and climbs to a plateau above 2x as the search grows. That is
the signature of the memory hierarchy rather than the core: a small search stays
in cache on both machines, and a large one does not, on a two-vCPU slice of a
shared Zen 1 part against a Zen 4 laptop.

**An equation fits it, and it is a straight line.** Take one position and time
it on both machines, each as the minimum of five runs, in milliseconds:

| | |
| --- | --- |
| `laptop_ms` | what that position costs on the development machine |
| `vm_ms` | what the same position costs on rehearsal |
| `ratio` | `vm_ms / laptop_ms` — how many times longer the VM takes, so above 1 is the VM being slower |

> **vm_ms = 2.210 × laptop_ms − 0.110**
>
> equivalently **ratio = 2.210 − 0.110 / laptop_ms**

Median relative error **3.3%**, and fitted on half the positions it holds out at
3.5% on the other half, so it is not curve-fitting. Every band above is within
2.8% of it. Valid for `laptop_ms` between 0.09 and 16, which is what was
measured.

**The constant is where the two machines meet.** The extra time the VM takes is
`vm_ms − laptop_ms = 1.210 × laptop_ms − 0.110`, which is zero at **0.091 ms**
— and the fastest move measured is 0.093 ms, at which the two machines are
equal. So below about
0.09 ms of work there is no penalty, and above it the VM pays about 2.21 on the
excess. The rising ratio is that constant being outgrown, not a changing
multiplier.

**Two models that do not work, recorded so they are not tried again.** A
three-parameter saturating curve fits to 3.5% and is degenerate: nothing in the
data lies near `l → 0`, so it returns a floor of −21x and a scale of 5 µs, which
are not measurements of anything. Constraining that floor to 1.0 — the machines
equal on cache-resident work — is refuted at 6.7% error with a systematic shape,
over-predicting the smallest band by 16% and under-predicting the middle by 12%.
The smallest band really is 1.34x and not 1.0; the single fastest move being
equal is one point, not a plateau.

**Two causes produce the VM's figures.** The 55 ms stalls are the hypervisor;
the systematic 1.3x-to-2.2x gradient underneath them is cache.

**So the algorithmic tail is only readable on a machine you own.** On the laptop,
every move over 20 ms has a blank in the rack, and moves with a blank run at
6.3x the median — one blank multiplies the search by the letters it could stand
for. That is the real shape of the distribution, and it is invisible under the
VM's scheduling noise.

**Steal is machine-wide and per-run**, not per-move: the kernel does not record
who lost the time. `steal_pct_of_capacity` is against wall time times cores, so
it is the share of the whole machine the hypervisor took, and 100% would mean
every core all run.

**The host is the hostname**, never typed. What the machine is comes from the
`cpu_model` and `cores` columns. An earlier `BENCH_HOST` override produced three
labels for two machines, which read as three until somebody checked.

## Benchmarking a performance change

**A performance change or a new engine is benchmarked on rehearsal by this
method, and the method is `scripts/bench-rehearsal.sh`**. It
takes a reference run on the development machine and the rehearsal run *from the
same binary*, then pairs them with `scripts/bench-compare.py`.

**Building once and running both is what makes the comparison honest.** Pairing
a rehearsal run against a laptop run from a different commit mixes a machine
difference with a code change and attributes the sum to whichever you were
looking for.

**The exclusion is on the ratio, never on an absolute time.** A position that is
slow on both machines is a slow position and must stay in; an ordinary position
that took 55 ms on one side only was descheduled and must come out. An
absolute-time cut gets both backwards, which is what the test suite pins.

**Laptop benchmarks need none of this.** Nothing else is competing for the
cores, no move crosses the outlier threshold, and the numbers can be read as
they stand.

## The raw measurements

The summary CSV has one row per run. Beside it, `examples/moves/` has **one file
per run with one row per move** — `<run>-<host>.csv`, where `<run>` is the
summary row's `timestamp_unix_seconds`, so the two join.

| column | |
| --- | --- |
| `game`, `turn` | **the case marker.** The games are seeded, so this pair is the same position on every machine and in every run |
| `seat`, `blanks`, `rack_tiles` | the rack the engine was given. `blanks` is the one that matters: a blank multiplies the search by the letters it could stand for |
| `wall_ms`, `cpu_ms` | elapsed and CPU for that move |

**The case marker is what makes two runs comparable move for move** rather than
distribution to distribution, and that is what settled where the VM's tail comes
from: the same `(game, turn)` costing 0.4 ms on one machine and 55 ms on another
is not a property of the position. Verified rather than assumed — two runs of
1229 moves produced identical keys and identical racks at every one.

A file per run, because 1229 rows an entry makes a single growing CSV unopenable
within a dozen runs. Each is about 44 KB.

**Running on a deployment VM**: neither VM has a Rust toolchain and both run the
same glibc as the development machine, so build here and copy the binary rather
than installing one there.

```bash
cargo build --release --example engine_timing_bench -p server-game
scp target/release/examples/engine_timing_bench tile-lite-elite:/tmp/
ssh tile-lite-elite '/tmp/engine_timing_bench 30 official'
ssh tile-lite-elite 'rm -f /tmp/engine_timing_bench'
```

It peaks at 24 MB resident and uses one of the two cores for a few seconds. The
run prints its CSV row to stdout, because on the VM there is no
`CARGO_MANIFEST_DIR` to append to and no `git` to say what was built: paste the
row into the CSV here and replace its `unknown` commit with the one the binary
was built from.
