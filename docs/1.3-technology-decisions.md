# Technology Decisions

The technology the system is built on, and why, under the constraint that it
stays free or nearly free to host.

## The Stack

| Area | Choice | Pros | Cons |
|---|---|---|---|
| Core language | Rust | Safe, fast, one language for server, clients and rules | Slower to iterate than scripting languages |
| Client framework | Dioxus | One Rust stack for web and desktop | Smaller ecosystem than mainstream web UI stacks |
| Server framework | Axum | Async-first, a good fit for typed APIs | More infrastructure assembled by hand |
| API style | HTTP plus WebSocket | Requests for actions, a socket for live game updates | More design work than a single protocol |
| Persistence | SQLite, with versioned migrations | Simple, low operational burden, free to run | Less scalable than PostgreSQL |
| Engine boundary | In-process trait (`GameEngine`), compiled in | Type-safe, no IPC, engine moves pass the same validation as a player's; async-wrapped with a timeout so a slow engine cannot stall the server | Engines are not sandboxed from the server; revisit if untrusted engines are ever supported. #71 moves the engine towards being a client |
| Shared rules | A pure shared Rust crate, `rules-shared` | The same legality and scoring everywhere | Needs strict dependency discipline |
| Word lists | Embedded per edition | Fast, deterministic, offline | Larger binaries; a list change is a release |
| Message format | Typed Rust DTOs in `crates/api`, versioned | Strong contracts | The version must be moved by hand ([3.3 §2.4](3.3-testing-ci-and-release.md#24-version-numbers-which-to-bump-and-when)) |
| Testing | Unit and in-process integration tests, Playwright end to end | Rules and API regressions caught in CI | Setup cost |
| Auth | Bearer-token sessions, argon2 passwords ([2.5](2.5-authentication.md)) | Simple, and enough for accounts and ratings | No email verification |
| Hosting | One Oracle Always Free VM: the server and Caddy in Docker ([3.4](3.4-production-environment.md)) | Free; Caddy handles TLS and serves the static bundle | One machine, no redundancy |
| Mobile | Deferred; the mobile client project is #423 | Keeps scope manageable | No native mobile client yet |

## Why This Stack Fits The Project

The project is a hobby project, so the stack minimises cost and operational
overhead: Rust, SQLite and a single-server deployment. Dioxus keeps the web and
desktop clients in the same language as the server, which lets both use the
shared rules crate directly.

Axum serves the API and WebSocket. Caddy, in front of it, terminates TLS and
serves the web client's static files from the same origin, so there is no CORS
([3.4](3.4-production-environment.md#container-topology)).

The engine is kept separate from the shared rules crate, so clients can preview
legality and score without engine search state entering the canonical rules
model.
