# Persistence

## SQLite File Layout

Each environment has one SQLite database consisting of the main .sqlite3 file and sidecar files, .sqlite3-wal and .sqlite3-shm, created as needed by the database when write-ahead logging is enabled.

Main file:

- local development: `./data/tile-lite-elite.sqlite3`
- self-hosted instance: `/var/lib/tile-lite-elite/tile-lite-elite.sqlite3`

Sidecar files in the same directories:

- `tile-lite-elite.sqlite3-wal`
- `tile-lite-elite.sqlite3-shm`

## What Is Persisted

One SQLite database per environment holds the durable state; the tables are
[4.2](4.2-database-schema.md):

- games, each with its authoritative state as a `snapshot_json` blob and
  queryable columns projected from it, plus its seats, moves, chat messages
  and invitations;
- players, sessions and password-reset tokens;
- ratings and their history, kept apart from games so they outlive them;
- a daily record of the database's size;
- the applied migrations, which `sqlx` runs at startup.

## What Stays In Memory

Every retained game is also held in memory: `AppState::new` loads them all at
boot, and requests read and change the in-memory copy, which is saved after
each change. So a game survives a restart, and resident memory grows with the
games kept (see *Retention* below). Engine search state, move previews and the
clients' state are never persisted.

## Persistence Model

The server is authoritative and the only writer. Clients use the shared rules
library for previews and own no persisted state. The schema evolves by
migration; a change that cannot be migrated may discard games instead (below).
Backups are [3.4](3.4-production-environment.md#backups).

## Games may be discarded for a breaking schema change

A change to the database schema or to `snapshot_json`'s shape may delete the
games rather than migrate them, provided nobody else is mid-game.

That is a deliberate licence, not an oversight. Writing a data migration for
game state is the expensive half of a change like the seat model or the event
log, and games are short-lived by design — every one is deleted within a week
of ending anyway (RET-1).

**The check first**, because "nobody else is mid-game" is the whole condition:

    ./scripts/application/develop/admin.sh games list --status active

It shows every game still in play with its seats and their players, so the
owner can see at a glance whether any belong to somebody else. Waiting games
matter less — nobody is mid-move — but they are visible the same way.

What is *not* discardable: `player_ratings` and `rating_history`, which belong
to the player rather than the game (ACC-3) and are what make deleting games
acceptable at all.

## Retention: how long a game is kept

The rules are RET-1 to RET-4 in [1.0 Rules](1.0-rules.md). This note is how
they are met, and why the shape is what it is.

### The problem

Every retained game is in the database and in memory: `AppState::new` loads
all of them at boot. So resident memory and startup time grow with the games
kept, not the games active, and without deletion they grow forever. Bounding
the set is preferred to lazy loading or eviction (#29), because memory,
startup time and disk all follow from it; eviction is worth doing only if the
retained set is itself too large.

Measured 2026-08-03: 37 games in production, ~46 KB each. Disk is not the
constraint — that is on the order of a million games before it matters.
Memory is, on a 954 MB box.

### What is deleted, and when

Three situations, of which only two need a clock.

| status | rule | built |
| --- | --- | --- |
| `Finished` / `Aborted` | deleted seven days after it ended | yes |
| `Waiting` | thirty-day countdown from last activity, with the creator asked at seven days | no |
| `Active` | none of its own — it resolves itself | n/a |

A completed game is finished with. Nothing more will happen to it, so the only
question is how long anyone wants to look back at it, and the clock can start
the moment it ends.

A game that never started may yet go somewhere, and the only way to find out
is to ask its creator. `updated_at` carries "last activity" for it — the field
moves whenever anyone joins, declines or changes the roster, so the countdown
only runs on a roster nobody has touched at all, and a creator answering
*keep* restarts the same clock rather than needing one of its own.

An active game needs no rule. `apply_move_timeout` retires a seat that
overruns `move_time_limit_seconds`, and the game finishes once at most one
seat is still playing. Every game carries a limit, capped at forty days, so an
active game becomes a completed one within weeks and the seven-day rule takes
it from there. Giving it a countdown of its own would also fight that cap: a
player on turn with a forty-day limit would be nine days short of it when a
thirty-day countdown reached zero.

#### Why a game that never started gets a question rather than a deadline

A waiting game's seats each carry a `SeatInvitationStatus`, and the
combination says something different about who is waiting for whom:

| situation | what it means | who loses if it is deleted |
| --- | --- | --- |
| every human seat `NotSent` | the creator built a roster and asked nobody | only the creator, who forgot about it |
| any seat `Pending` | someone has been asked and has not replied | an invitee who may still act on it |
| any seat `Rejected` | someone declined; the roster needs attention | the creator, who may not have noticed |
| every seat claimed | everyone accepted; waiting on **Start** | everyone who accepted |

The last is not an invitation state at all — `invitation_status` is `None`
once a seat is claimed — but it is the case where deletion throws away the
most: several people agreed to play and the creator did not press the button.

That row is what the question exists for. A period alone cannot tell the four
apart, and the one that matters most is the one where the creator is the only
person who can act and the only person who has forgotten. Asking costs a
prompt; guessing costs four people their game.

#### Where the question appears

In the games list, as its own section alongside invitations. It is the same
kind of thing: something addressed to this player that is waiting on an answer
from them, and that belongs where they already look for such things rather
than in a notification that passes.

Its three answers are RET-3's. **Delete** is worth having for its own sake —
a creator who knows a game is dead clears it in one action instead of waiting
out the countdown.

### Where the sweep runs

Lazily, from `GET /games`. Retention moves onto the scheduler (#400) when
Capacity Planning's own schedules are ready.

That gives a useful property while it lasts: **growth requires use, and use
triggers the sweep.** A server nobody plays accumulates nothing; one being
played cleans itself on every request.

### What survives

`player_ratings` and `rating_history` are separate tables, so a player's
rating and its history outlive the games they came from. That is what makes
deleting games acceptable at all.

The waiting-game countdown is not built yet; it, and what it leaves to decide,
are #409.
