# Building and maintaining a host

How the owner builds this application's stack on a host and keeps it current.
The host is production or rehearsal; the host itself, its network and its
packages are Infrastructure's
([6.3.4](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md)).
Operating what runs on it is [4.3.4](4.3.4-production-environment.md). A host
step that changes the host is the owner's to run, and Claude may make the reads
(the programme's
[CLAUDE.md](https://github.com/delphside/programme/blob/main/CLAUDE.md)); host
commands name the host by its `ssh` alias, listed in
[6.3.4](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#the-hosts).

## Building a host

A host is built first, as Infrastructure's
[Building a host](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#building-a-host)
says, journald drop-ins included. What follows builds this application's
stack on it, and the owner runs it:

1. **Write the `.env`**
   ([Host configuration](4.3.4-production-environment.md#host-configuration-env)),
   with `SITE_ADDRESS` as [HTTPS](#https) says.
2. **On production only, install the backup and log-check jobs.** On
   rehearsal, the write pre-authenticated request (PAR) would refresh
   `marker-backup-ok`, the object that shows the last backup succeeded, from a
   rehearsal database.
   - `sudo apt-get install -y sqlite3 python3`, which the nightly jobs run;
   - `sudo usermod -aG systemd-journal ubuntu`, so the log check can read the
     journal;
   - `/opt/tile-lite-elite/` and the systemd units, copied from the repository
     by hand, with the timers enabled. The four files and the unit names are in
     [3.1.2](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.2-artefacts.md#the-production-host).
     From the repository root:

     ```bash
     scp scripts/operate/backup-to-oci.sh \
         scripts/operate/check-log-hygiene-nightly.sh \
         scripts/operate/check-log-hygiene.py \
         docs/4.4.7-log-events.md tile-lite-elite:/tmp/
     scp scripts/operate/systemd/* tile-lite-elite:/tmp/
     ssh tile-lite-elite 'sudo mkdir -p /opt/tile-lite-elite \
       && sudo install -m 755 -t /opt/tile-lite-elite \
            /tmp/backup-to-oci.sh /tmp/check-log-hygiene-nightly.sh \
            /tmp/check-log-hygiene.py \
       && sudo install -m 644 -t /opt/tile-lite-elite /tmp/4.4.7-log-events.md \
       && sudo install -m 644 -t /etc/systemd/system /tmp/tile-lite-elite-*.service \
            /tmp/tile-lite-elite-*.timer \
       && sudo systemctl daemon-reload \
       && sudo systemctl enable --now tile-lite-elite-backup.timer \
            tile-lite-elite-log-check.timer'
     ```

   - the write PAR in `~/.tile-lite-elite-backup-par`, mode `0600`
     ([Renewing the write PAR](4.3.9-backups-and-restores.md#renewing-the-write-par)).
3. **Point the rest of the tooling at the address** where it is new:
   - the repository holds the old address in several files, which
     `grep -rn <old address>` finds. Claude edits them as a Production
     Release ([4.3.3](4.3.3-testing-ci-and-release.md#1-what-to-type));
   - until the `Caddyfile` matches a rebuilt rehearsal's new `<ip>.sslip.io`,
     rehearsal is served without its access gate, open to anyone;
   - the owner points the DNS records for the host's names at it, as
     Infrastructure's
     [Making a host change](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#making-a-host-change)
     describes, because they are not in the repository.
4. **Deploy once**, which copies the images and the compose file into
   `~/tile-lite-elite` and starts the stack:
   - rehearsal: `deploy-rehearsal.sh`
     ([4.3.3](4.3.3-testing-ci-and-release.md#16-ship-it));
   - production: the `prod-*` tag that was running, `deploy.sh prod-<version>`
     ([4.3.6](4.3.6-when-a-release-goes-wrong.md#1-roll-back-production)),
     never a bare `deploy.sh`, which ships `HEAD`. Then
     [Restoring production](4.3.9-backups-and-restores.md#restoring-production),
     because the volume starts empty.

### HTTPS

Caddy handles HTTPS: it obtains and renews a Let's Encrypt certificate for the
hostname it serves and redirects `http://` itself. It serves `SITE_ADDRESS` from
`.env`, or the default in `docker-compose.yml`
([4.4.1](4.4.1-configuration.md#environment-variables)). Two cases:

- a host with a DNS name: add the name to `SITE_ADDRESS` only once its record
  resolves, because certificate issuance fails before that, and repeated
  failures risk a Let's Encrypt rate limit;
- a host with none: `SITE_ADDRESS=<ip>.sslip.io`, because Let's Encrypt does
  not certify a bare IP address and sslip.io resolves to the IP with nothing to
  register.

## Keeping the application current

The host's layers (OS packages, Docker, the kernel and libc) and what the host
read checks are Infrastructure's:
[Keeping the hosts current](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#keeping-the-hosts-current).
This application keeps its own:

| Layer | Updated by | Who acts | Cadence |
| --- | --- | --- | --- |
| GitHub Actions, Docker base images | Dependabot | Claude, on Dependabot's pull request | weekly |
| Rust crates | `cargo audit` | Claude | advisories daily, bumps as needed |
| the application | a release | Claude prepares, the owner deploys ([4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it)) | per release |

`scripts/operate/check-hosts.sh` calls the programme's `board-hosts.py` on both
hosts, and runs inside `verify.sh` as a note, leaving `verify.sh`'s exit
status unchanged. After a host change, `verify.sh` is the application's own
verification
([How an application verifies itself](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#how-an-application-verifies-itself)).
