# Building and maintaining a host

How the owner builds a production or rehearsal host, and keeps it patched.
Operating what runs on it is [4.3.4](4.3.4-production-environment.md). Every
host step is the owner's to run ([CLAUDE.md](../CLAUDE.md)); host commands name
the host by its `ssh` alias, listed in [4.3.4](4.3.4-production-environment.md).

## Building a host

Production and rehearsal are Oracle Cloud VMs on the Always Free tier. The
owner builds one in the Oracle Cloud Infrastructure (OCI) console:

1. **Sign up** at `cloud.oracle.com`. Phone and card verification is an
   identity check; nothing is charged.
2. **Upgrade to Pay-As-You-Go before creating the instance.** Oracle reclaims
   idle Free-tier instances (CPU use at the 95th percentile and network use
   both under 20% over seven days), which a quiet game server is. Staying
   within the Always Free limits costs nothing. The owner rechecks Oracle's
   policy at each build.
3. **Create the instance**:
   - image: Ubuntu 24.04 LTS;
   - shape: `VM.Standard.E2.1.Micro` (1 GB of memory; x86_64, so images
     built on an x86_64 machine run unchanged);
   - a public IPv4 address;
   - the public half of the host's deploy key, pasted in at creation:
     `oracle_tile_lite_elite` for production,
     `oracle_tile_lite_elite_rehearsal` for rehearsal. The private halves stay
     in `~/.ssh` ([4.3.1](4.3.1-setup.md#development-environment)).
4. **Point the `ssh` alias at the new address**: set `HostName` in the host's
   entry in `~/.ssh/config`. `setup-dev-environment.sh` leaves an existing
   entry as it is.
5. **Open the network.** Failures show only as timeouts:
   - the subnet needs a route to an internet gateway;
   - the rules go in the security list attached to the subnet (*Subnet →
     Security*), not the security group the *Networking* tab creates, which has
     no inbound rules;
   - ingress: TCP 22, 80 and 443, and UDP 443;
   - egress: all. A TCP-only rule blocks DNS, and with it `apt-get` and image
     pulls.
6. **Install Docker and add a swapfile**, over `ssh <alias>`:
   - Docker Engine and the Compose plugin from Docker's apt repository, as
     [Docker's Ubuntu guide](https://docs.docker.com/engine/install/ubuntu/)
     gives it;
   - `sudo usermod -aG docker ubuntu`, because the deploy scripts run `docker`
     without `sudo`;
   - a swapfile for headroom on 1 GB, persisted in `/etc/fstab`
     (`swapon --show` on the other host gives its size):

     ```bash
     sudo fallocate -l <size> /swapfile && sudo chmod 600 /swapfile
     sudo mkswap /swapfile && sudo swapon /swapfile
     echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
     ```

7. **Install what every host needs**:
   - `sudo apt-get install -y jq`, for the log commands in
     [4.3.4](4.3.4-production-environment.md#journald-not-the-container);
   - `sudo apt-get install -y unattended-upgrades`, a no-op where the image
     already has it ([Keeping the hosts current](#keeping-the-hosts-current));
   - the `.env`
     ([Host configuration](4.3.4-production-environment.md#host-configuration-env)),
     with `SITE_ADDRESS` as [HTTPS](#https) says.
8. **On production only, install the backup and log-check jobs.** On
   rehearsal, the write pre-authenticated request (PAR) would refresh
   `marker-backup-ok`, the object that shows the last backup succeeded, from a
   rehearsal database.
   - `sudo apt-get install -y sqlite3 python3`, which the nightly jobs run;
   - `sudo usermod -aG systemd-journal ubuntu`, so the log check can read the
     journal;
   - the journald drop-ins
     ([4.3.4](4.3.4-production-environment.md#journald-not-the-container));
   - `/opt/tile-lite-elite/` and the systemd units, copied from the repository
     by hand, with the timers enabled. The four files and the unit names are in
     [3.1.2](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.2-artefacts.md#the-production-host).
     From the repository root:

     ```bash
     scp scripts/operate/backup-to-oci.sh \
         scripts/operate/check-log-hygiene-nightly.sh \
         scripts/operate/check-log-hygiene.py \
         docs/4.4.7-log-events.md tile-lite-elite:/tmp/
     scp scripts/operate/systemd/* tile-lite-elite:/tmp/
     ssh tile-lite-elite 'sudo mkdir -p /opt/tile-lite-elite \
       && sudo install -m 755 -t /opt/tile-lite-elite \
            /tmp/backup-to-oci.sh /tmp/check-log-hygiene-nightly.sh \
            /tmp/check-log-hygiene.py \
       && sudo install -m 644 -t /opt/tile-lite-elite /tmp/4.4.7-log-events.md \
       && sudo install -m 644 -t /etc/systemd/system /tmp/tile-lite-elite-*.service \
            /tmp/tile-lite-elite-*.timer \
       && sudo systemctl daemon-reload \
       && sudo systemctl enable --now tile-lite-elite-backup.timer \
            tile-lite-elite-log-check.timer'
     ```

   - the write PAR in `~/.tile-lite-elite-backup-par`, mode `0600`
     ([Renewing the write PAR](4.3.9-backups-and-restores.md#renewing-the-write-par)).
9. **Point the rest of the tooling at the address** where it is new:
   - the repository holds the old address in several files, which
     `grep -rn <old address>` finds. Claude edits them as a Production
     Release ([4.3.3](4.3.3-testing-ci-and-release.md#1-what-to-type));
   - until the `Caddyfile` matches a rebuilt rehearsal's new `<ip>.sslip.io`,
     rehearsal is served without its access gate, open to anyone;
   - the owner points the DNS records for the host's names at it, as
     [Changing production configuration](4.3.4-production-environment.md#changing-production-configuration)
     describes, because they are not in the repository.
10. **Deploy once**, which copies the images and the compose file into
    `~/tile-lite-elite` and starts the stack:
    - rehearsal: `deploy-rehearsal.sh`
      ([4.3.3](4.3.3-testing-ci-and-release.md#16-ship-it));
    - production: the `prod-*` tag that was running, `deploy.sh prod-<version>`
      ([4.3.6](4.3.6-when-a-release-goes-wrong.md#1-roll-back-production)),
      never a bare `deploy.sh`, which ships `HEAD`. Then
      [Restoring production](4.3.9-backups-and-restores.md#restoring-production),
      because the volume starts empty.

### HTTPS

Caddy handles HTTPS: it obtains and renews a Let's Encrypt certificate for the
hostname it serves and redirects `http://` itself. It serves `SITE_ADDRESS` from
`.env`, or the default in `docker-compose.yml`
([4.4.1](4.4.1-configuration.md#environment-variables)). Two cases:

- a host with a DNS name: add the name to `SITE_ADDRESS` only once its record
  resolves, because certificate issuance fails before that, and repeated
  failures risk a Let's Encrypt rate limit;
- a host with none: `SITE_ADDRESS=<ip>.sslip.io`, because Let's Encrypt does
  not certify a bare IP address and sslip.io resolves to the IP with nothing to
  register.

## Keeping the hosts current

| Layer | Updated by | Who acts | Cadence |
| --- | --- | --- | --- |
| security updates to OS packages | `unattended-upgrades` | nobody (automatic) | daily (`apt-daily-upgrade.timer`) |
| other OS packages, Docker included | `apt`, as [host maintenance](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#221-business-as-usual-updates) | the owner | when needed |
| the running kernel and libc | a reboot, as host maintenance | the owner | when `/var/run/reboot-required` appears |
| GitHub Actions, Docker base images | Dependabot | Claude, on Dependabot's pull request | weekly |
| Rust crates | `cargo audit` | Claude | advisories daily, bumps as needed |
| the application | a release | Claude prepares, the owner deploys ([4.3.3 §1.6](4.3.3-testing-ci-and-release.md#16-ship-it)) | per release |

**`unattended-upgrades` installs without rebooting**, so a kernel or libc fix
goes live at the next reboot. `scripts/operate/check-hosts.sh`, a caller of the
programme's `board-hosts.py`:

- reads, on both hosts, the running and the newest installed kernel, the
  reboot flag, the packages waiting, the Docker version and how long since
  automatic updates last succeeded;
- reports a reboot pending, a newer kernel not running, packages waiting that
  automatic updates do not install (security ones install themselves),
  automatic updates that have stopped, and a kernel or Docker version that
  differs between the two;
- counts packages from the host's last daily `apt update`; a phased package
  such as `netplan.io` (which Ubuntu releases gradually) counts once this host
  is in its phase;
- runs inside `verify.sh` as a note, leaving `verify.sh`'s exit status
  unchanged.

The same read runs weekly as the programme's `host-currency` activity
([1.4](https://github.com/delphside/programme/blob/main/docs/1.4-programme-activities.md#the-register)).

A package upgrade and a reboot are each a separate delivery of host
maintenance, which is the infrastructure application's. The owner makes each as
[Changing production configuration](4.3.4-production-environment.md#changing-production-configuration)
says, rehearsal first. A reboot is an outage; the containers restart with the
host (`restart: unless-stopped`).

The upgrade:

```bash
sudo apt-get update && sudo apt-get dist-upgrade
```

The reboot:

```bash
sudo reboot
```
