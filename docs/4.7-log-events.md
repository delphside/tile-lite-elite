# Log events

**Two producers, one set of rules.** The server writes most of what follows. Since
2026-09-21 the scripts that *change* something write a record too — #328 — and
they share this document because they share the rule that matters: the envelope,
and identifiers only. Two documents would be two places for that rule to drift
apart.

| | writes | where |
| --- | --- | --- |
| the server | the events tabled below | stdout, JSON per line, forwarded by Docker |
| `deploy.sh` and the other changing scripts | `run started`, `gate passed`, `run finished` | `${XDG_STATE_HOME:-~/.local/state}/tile-lite-elite/<script>-<run>.jsonl` |

## What the scripts write

**Only scripts that change something**: the deploys, `rollback.sh`,
`restore-backup.sh`, `rehearsal-limits.sh`. A report can simply be run again; a
deploy cannot, and by then the terminal is closed. `verify.sh` and the `board-*`
reports write nothing.

| event | fields | |
| --- | --- | --- |
| `run started` | `script`, `args`, `commit` | the run's own arguments and the commit the tree was on |
| `gate passed` | `script`, `gate` | one per gate, from `note_gate` — the single place `deploy.sh` records them |
| `run finished` | `script`, `status` | **the exit status**, written by a trap, because a script that fails does not reach its own last line |

**`run finished` is the whole point.** 0.7.2 exited 1 having printed every
success line; the milestone settling and the release announcement never ran, and
both facts were in the terminal and nowhere else. The milestone was repaired from
what the owner happened to have pasted into a conversation.

**Outside the repository**, so two worktrees do not produce two answers, and one
file per run pruned to the last 20 per script — the question is *what did it say
the last time it went wrong*, which is a whole run.

Every event the server writes, what it means, and what it carries. Written for
two readers: a person working out what a line means, and a parser that needs to
know which fields exist.

**The log is JSON, one object per line** (#174). Each line carries an envelope —
`timestamp`, `level`, `message`, `target` — and the event's own fields flattened
alongside it:

```json
{"timestamp":"2026-08-21T19:11:15.519240Z","level":"INFO","message":"player registered","player_id":"abc-123","target":"server_game::app::auth"}
```

**Identifiers only.** `player_id` and `game_id` are enough to diagnose;
`scripts/admin.sh` resolves an id to a person on the rare occasion a human needs
to know who it was. No display name, no email address, no token, no password —
and the rule is checked rather than trusted, in two places:

| | what it catches |
| --- | --- |
| `tests/log_schema.rs` | a declared event gaining a field this document does not declare |
| `scripts/check-log-hygiene.sh` | an address or a display name reaching the log by **any** path, declared or not |

**`player_id` is pseudonymous, not anonymous** — we hold the table that resolves
it. That makes a leaked log worth much less; it does not put the log outside data
protection.

## The field vocabulary

**The whole log uses twenty-five field names.** This table is the one to read
when reviewing whether the rule still holds — twenty-five lines answer *"could
any of this identify somebody?"*, where forty-eight event definitions do not.

| field | what it is | personal? |
| --- | --- | --- |
| `player_id` | a player's uuid | **pseudonymous** — resolvable with the database |
| `creator_player_id` · `invited_player_id` | the same, in a specific role | **pseudonymous** |
| `game_id` · `invitation_id` | a game's or invitation's uuid | no |
| `seat` · `seat_number` · `seats` · `winner_seat` | positions within a game | no |
| `status` | a game's status | no |
| `kind` | which message an email was — a closed set, see `email::MessageKind` | no |
| `reason` | why a login was rejected | no — a category, never the value supplied |
| `error` · `status` | a failure, as the underlying library reported it | no |
| `move_time_limit_seconds` · `budget_ms` · `elapsed_ms` | durations | no |
| `engine_id` | which engine played | no |
| `app_version` · `api_version` · `schema_version` · `bind` | what the process is | no |
| `database_url` | where the database is | no **today** — a SQLite path. It would be a credential the day this becomes Postgres, and that is the day to remove it |
| `to` · `subject` · `text_body` | an email in full | **yes — and it is written only on a debug build**, guarded in `email::send`. Production takes the other branch |

**Two rows are the ones to watch.** The last carries everything, and is
unreachable in a release build. The `database_url` row is fine now and is a note
to whoever changes the database.

## The schema

**Machine-readable, and compared against what the code emits** by
`tests/log_schema.rs`. Each event lists the fields it may carry, and
`additionalProperties: false` is what makes the comparison mean anything — the
test asserts that property is present on every object as well as validating with
it, because JSON Schema is permissive by default and one omission would be a
silent hole.

**One event is marked `debugOnly`.** *email not sent (no RESEND_API_KEY
configured)* carries the whole message — address, subject, body — and needs
**two** things to be true: no provider configured, **and**
`TILE_LITE_ELITE_LOG_EMAIL_BODIES` set. Only `docker-compose.preview.yml` sets
it, so preview can read an invitation link out of the log and production cannot
emit the event at all.

*It was guarded on `debug_assertions` until 2026-08-22, when preview showed the
proxy was wrong: preview builds `--release`, so a build-profile guard switched it
off in exactly the place it is most useful.* The
checker uses the marker both ways: it **exempts** that event from the
address scan when reading a test stream, and it **fails** if the event appears in
a production stream at all. A release build cannot emit it, so seeing it there
would mean production is running a debug binary.

**It covers the events that carry player identifiers** — everything in `auth.rs`,
`email.rs` and `admin.rs`. The rest carry game ids, seats and errors, and are
documented above but not schema-checked. That is a deliberate line, and
`check-log-hygiene.sh` is what covers the other side of it: the schema test is
precise about the events most likely to leak, the hygiene script is exhaustive
about the paths a person actually walks.
