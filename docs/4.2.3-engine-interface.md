# Engine interface

How a computer player plugs into the server. An engine chooses a move; the
server validates and applies it exactly as it would a player's. What the
engine's search costs is [4.2.8](4.2.8-engine-performance.md), and how that is
measured [4.3.10](4.3.10-benchmarking.md#reading-an-engine-timing-run).

## The trait

`crates/engine-core` defines `GameEngine`:

```rust
pub trait GameEngine: Send + Sync {
    fn metadata(&self) -> &EngineMetadata;
    fn choose_action(&self, request: EngineRequest<'_>) -> EngineResponse;
}
```

`choose_action` is synchronous and pure: given a request, it returns an action.
It owns no game state and no rules; it asks `rules-shared` for candidate moves
and their scores, like any other client of the rules.

The types:

| Type | Carries |
| --- | --- |
| `EngineRequest` | the board (`GameState`), the seat, its rack, the game's `VariantRules` and an optional time budget in milliseconds |
| `EngineResponse` | an `EngineAction` and `EngineDiagnostics` |
| `EngineAction` | `Place(MoveCandidate)`, `Pass`, `Exchange(tiles)` or `Resign` |
| `EngineDiagnostics` | an optional explanation, how many candidates were considered and the chosen score |
| `EngineMetadata` | id, name, version, author, description, the editions it supports (`supported_variants`) and capability flags |

**The request carries the game's rules**, and an engine must score and generate
under them, because rules of its own would misplay every edition but one.

**The capability flags** (`supports_timed_play`, `supports_analysis`,
`supports_ranking`) are published by `GET /engines`, and nothing reads them.

## How the server runs an engine

A seat of kind `Engine` names an engine by id. When it is that seat's turn,
`GameSession::maybe_run_engine_turn` (`crates/server-game/src/game_state.rs`)
takes these steps:

1. finds the engine in the `EngineRegistry`, and returns an error if its
   metadata does not list the game's edition;
2. runs `choose_action` on a blocking thread, under a **5-second** limit
   (`ENGINE_TURN_TIMEOUT`, passed in as the request's time budget);
3. auto-passes the seat if the limit is reached (the search itself runs on to
   completion), and returns an error if the engine panicked;
4. applies the action through the same `apply_place_move`, `apply_pass`,
   `apply_exchange` or `apply_resign` a player's action goes through, so an
   illegal move is refused by the same validation;
5. records the engine's measured compute time on the move, the auto-pass
   included.

`run_engine_turns` (`crates/server-game/src/app/games.rs`) repeats this while
the current seat is an engine:

- stops after `MAX_ENGINE_TURNS_PER_TRIGGER` (400) turns per request;
- broadcasts after each turn, then pauses `ENGINE_TURN_BROADCAST_DELAY`
  (120 ms) so the moves can be seen;
- takes the games map's write lock per turn: one engine search at a time
  across all games, except that a timed-out search runs on outside the lock;
  every other game request waits.

`TILE_LITE_ELITE_ENGINE_CONCURRENCY`
([4.4.1](4.4.1-configuration.md#environment-variables)) is read into a
semaphore that nothing acquires, so it bounds nothing.

The engine runs in-process and unsandboxed, and calls the server's game code
directly ([4.1.3](4.1.3-technology-decisions.md#the-stack)); it is not a
client of the public API.

## The engines

`GET /engines` lists the registered engines' metadata as `EngineProfileDto`
([4.4.3](4.4.3-api-schema.md#meta-endpoints)), which carries no editions.
One engine is registered, **Greedy** (`greedy-v1`):

- plays the highest-scoring move among those the move generator returns, the
  first generated on a tie, and passes when there is none; the generator
  returns a subset of the legal moves
  ([4.2.1](4.2.1-rules-engine.md#move-enumeration));
- places or passes only;
- declines a move forming a main or cross word on the greylist or the denylist
  ([4.3.5](4.3.5-word-lists-and-dictionaries.md#stage-6-using-the-lists-at-run-time)),
  checking only a move about to become its best so far;
- lists every edition, retired ones included, so an engine seated in an old game
  can always move.

## Versioning an engine

An engine carries a version in its metadata, and an id that names it. The
interface has no version of its own: the trait is compiled into the server
with every engine, so the two cannot disagree.

**A change that makes an engine play differently is a new engine with a new
id**, not a change to Greedy.

- exception: shipping the greylist (app 0.6.0) changed what `greedy-v1` plays
  without changing its id.

## Testing

Three sets of tests cover engines:

- `crates/engine-core`'s tests hold the engine's choices against injected word
  lists: a move forming an avoided main or cross word is declined, and the next
  best is played instead; they also play against the real greylist and under
  the request's rules, not `VariantRules::official()`;
- the server's tests (`crates/server-game/src/app/tests.rs`) drive engines
  through the API: an engine replying to a player's move, and engine games
  against each other running to completion;
- the timing benchmark plays whole games through the same path
  ([4.3.10](4.3.10-benchmarking.md)).
