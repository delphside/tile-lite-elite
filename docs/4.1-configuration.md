## Environments

Three genuinely different places this project runs, easy to conflate since some of the same commands (`docker compose ...`) work in all three:

### Local dev machine

Where you write code, run tests, and build the images that get deployed. Has the full source tree; nothing here is what's actually serving live traffic.

**Components**: Rust toolchain + workspace crates, Docker Engine (used here only to *build* images and optionally run the stack or the preview environment for local testing — not to serve real traffic), the git clone itself (pushed to/pulled from GitHub).

**Directory structure** (repo root, `~/tile-lite-elite` in this WSL setup):

```text
tile-lite-elite/
├── crates/                  # the six workspace crates
│   ├── api/                 # shared request/response DTOs
│   ├── rules-shared/        # pure rules/scoring/move-generation
│   ├── engine-core/         # GameEngine trait + GreedyEngine
│   ├── server-game/         # Axum backend
│   ├── ui/                  # Dioxus web/desktop client
│   └── admin-cli/           # tile-lite-elite-admin operator CLI
├── old-crates/              # early prototypes, kept for design precedent only
├── docs/                    # this file and other design docs
├── scripts/                 # admin.sh, deploy.sh, deploy-preview.sh, services.sh, setup-dev-environment.sh, desktop.sh
├── data/                    # local dev SQLite file (TILE_LITE_ELITE_DATABASE_URL's default)
├── target/                  # cargo build output (gitignored)
├── .cargo/config.toml       # sccache + wasm rustflags (see 3.1-setup.md's Troubleshooting)
├── Dockerfile, docker-compose.yml, docker-compose.preview.yml, Caddyfile, Caddyfile.preview, .dockerignore
└── Cargo.toml                # workspace manifest
```

### Preview (local)

A second, disposable deployment target that runs *on the dev machine* — not a separate physical environment, but different enough in shape (its own containers, port, volume) to treat as a peer of the other two rather than a footnote. Exists purely to test a deployment (especially a schema migration) before it reaches production. See [Testing, CI & Release](3.3-testing-ci-and-release.md#13-deploy-to-the-preview-environment) for the full workflow.

**Components**: same two containers as production (`server`, `web`/Caddy), built from the identical `Dockerfile`, run via the separate `docker-compose.preview.yml` + `Caddyfile.preview` (plain HTTP, no domain, no TLS — see [Building a host](3.4-production-environment.md#building-a-host) for why production needs a real hostname and preview doesn't).

**Directory structure**: none — it's ephemeral, built from whichever git ref you point it at (`HEAD` by default, or a specific commit via `at <ref>`/`at prod`) and torn down with `down`/`reset`. Always a fresh checkout of that commit, never the working tree — see [Deployments build a commit, never the working tree](3.3-testing-ci-and-release.md#211-deployments-build-a-commit-never-the-working-tree). The only persistent thing is its data volume:

```text
tile-lite-elite-preview-server-1, tile-lite-elite-preview-web-1   # containers
tile-lite-elite-preview-data                                       # volume — /data in the server container
```

### Oracle Cloud VM (production)

Where the live deployment actually runs. **Does not have the source tree at all** — no git clone, no `crates/`, nothing to build. Just the compose file and whatever Docker itself stores (images, volumes) — `scripts/deploy.sh` builds everything locally and ships only the finished images plus `docker-compose.yml` over.

**Components**: Docker Engine only. Two running containers (`tile-lite-elite-server-1`, `tile-lite-elite-web-1`) and three named volumes (`tile-lite-elite-data`, `tile-lite-elite-caddy-data`, `tile-lite-elite-caddy-config`) — see [Container Topology](3.4-production-environment.md#container-topology) for what each holds.

**Directory structure** (`~/tile-lite-elite` on the VM — same path as local, different machine, don't let that imply it's the same *kind* of directory):

```text
~/tile-lite-elite/
└── docker-compose.yml       # the only file that lives here
```

That's genuinely everything on disk outside of Docker's own storage. What's *inside* the containers (via `docker compose exec <service> ls ...`):

```text
server container:
├── /usr/local/bin/
│   ├── server-game          # the release binary actually running
│   └── tile-lite-elite-admin       # copied in but not running — invoked on demand via `docker compose exec`
└── /data/                   # the tile-lite-elite-data volume
    └── tile-lite-elite.sqlite3

web container:
├── /srv/                    # the built web client (index.html, assets/, wasm/) — served as static files
├── /etc/caddy/Caddyfile     # baked into the image at build time, not a volume
├── /data/caddy/             # the caddy-data volume — obtained TLS certificates live here
└── /config/caddy/           # the caddy-config volume — Caddy's own runtime state
```

Preview's server container has the same `/usr/local/bin`/`/data` shape; its web container has no `/data/caddy`/`/config/caddy` (no TLS to persist).

## Rate Limits

How often a caller may ask, as distinct from how much heavy work runs at once
(`TILE_LITE_ELITE_HASH_CONCURRENCY`, `TILE_LITE_ELITE_ENGINE_CONCURRENCY`).
Set on the server; each is requests per minute, with a burst on top so an
ordinary caller never meets it.

**How the two numbers work.** Each limit carries an *allowance*: the number of
requests that would be accepted right now, before a refusal. `BURST` is the
allowance's maximum — the most that can ever be accepted at once. The allowance
starts at that maximum. `PER_MIN` is the rate it refreshes at: one unit every
`60 / PER_MIN` seconds, and that interval is the **period**. Accepted requests
spend the allowance, refresh restores it, and it never rises above the maximum.

**Refresh is spread, not granted at the top of a minute.** One unit returns one
period after the request that spent it, whenever that was; there is no window
and no reset instant. LIMIT-5 requires this — a caller over the limit is slowed
rather than shut out until a boundary passes.

A caller asking faster than the refresh rate drains the allowance to zero and
is then served at exactly the refresh rate, everything beyond it refused. The
traffic itself does not slow down; the excess is turned away. A caller asking
more slowly never meets any of this, which is what the burst is for.

Registration at `2/min, burst 3` is three registrations back to back from idle,
then one every thirty seconds — its period. `Retry-After` is built from the wait
until the next unit of allowance arrives, rounded up and given a small random
margin; [4.3](4.3-api-schema.md) has the derivation and why it is not a fixed
property of the limit.

| variable | default | applies to |
| --- | --- | --- |
| `TILE_LITE_ELITE_LIMIT_REGISTER_PER_MIN` | 2 | `/auth/register`, keyed by client address |
| `TILE_LITE_ELITE_LIMIT_REGISTER_BURST` | 3 | |
| `TILE_LITE_ELITE_LIMIT_AUTH_PER_MIN` | 10 | login and the password-reset pair, keyed by client address |
| `TILE_LITE_ELITE_LIMIT_AUTH_BURST` | 10 | |
| `TILE_LITE_ELITE_LIMIT_SESSION_PER_MIN` | 240 | everything a signed-in caller does, keyed by session |
| `TILE_LITE_ELITE_LIMIT_SESSION_BURST` | 60 | |
| `TILE_LITE_ELITE_LIMIT_GLOBAL_PER_MIN` | 1200 | the whole service, unkeyed |
| `TILE_LITE_ELITE_LIMIT_GLOBAL_BURST` | 200 | |

**Preview and dev raise all of them** — `docker-compose.preview.yml` and
`scripts/services.sh` respectively. The whole
Playwright suite comes from one address and every test registers a player, so
three tests exhaust a burst of 3 and the rest are told to wait — longer than
the suite waits for anything.

**Rehearsal keeps the defaults**, and is the only environment besides
production that does. It is where `check-rate-limits.sh` measures them and
where load testing runs, so production-shaped numbers belong there. The other
two exist to let you look at a change, and limits sized for a 2 vCPU VM only
get in the way of that. Setting any of these in the environment
still overrides preview's numbers, which is how limiting is exercised there on
purpose.

**What is limited, and what deliberately is not.** The same four tiers as a
grid of *what is counted* against *who it is counted for*. A blank is a
combination not limited at all:

| | per IP | per session | per account | global |
| --- | --- | --- | --- | --- |
| **registrations** | 2/min, burst 3 | | | |
| **logins and password resets** | 10/min, burst 10 | | | |
| **authenticated requests** | | 240/min, burst 60 | | |
| **any request** | | | | 1200/min, burst 200 |

**The account column is empty by design.** Authenticated limits key on the
session token, not the account: resolving a token to an account needs the
database, and the key is chosen before any handler runs. Session coincides with
account for a caller reusing one — a bot harness — and diverges for a person
with three devices, who gets three allowances.

**Authenticated traffic has no per-IP limit**, so several sessions from one
address get several allowances between them, bounded only by the global floor.
Collecting the sessions is itself limited, but one lasts up to ten days
(`ACC-1`).

**The client address is Caddy's, not the caller's.** With no `trusted_proxies`
configured, Caddy replaces `X-Forwarded-For` with the address the connection
came from, so a caller cannot forge one, spread across imaginary addresses, or
lock out somebody else by claiming to be them. **This holds only while nothing
can reach the server except through Caddy** — which `docker-compose.yml`
enforces by giving the `server` service no `ports:`. Adding one would let a
caller supply the header and be believed.

A consequence for anybody testing: every request from one machine is one
caller, so per-caller separation cannot be observed from outside. It is covered
in-process by `one_callers_allowance_is_not_anothers`.

The burst is what decides whether an ordinary caller ever meets a limit: the
rate refills one permit at a time, and the burst is how many can be spent at
once before that matters. Tune it alongside the rate rather than instead of it.

### Tuning a host

The limits are read when the router is built, so a change needs a container
restart and not a new image:

```bash
# on the host, beside the secrets Compose already reads
echo 'TILE_LITE_ELITE_LIMIT_REGISTER_PER_MIN=5' >> .env
docker compose up -d server
./scripts/check-rate-limits.sh https://<host>
```

`.env` is created by hand and `deploy.sh` never touches it, so a host keeps
its tuned numbers across every redeploy. An empty value means the default,
which is what an unset one in Compose becomes.

**A regression suite cannot run under these numbers**, and that is not a fault
in either. Registration is 2 a minute with a burst of 3; the e2e suite registers
an account per test, so the fourth test onwards is refused. Measured 2026-09-19
on the same code and host, the limits being the only difference:

| | failed | passed |
| --- | --- | --- |
| relaxed limits | 0 | 31 |
| production's limits | 21 | 10 |

A refused registration looks exactly like broken sign-up, which is the same
confusion the access gate one layer out produced in #286.

`scripts/rehearsal-limits.sh regression` relaxes a host for a run and
`… production` restores it. **A switch rather than leaving rehearsal relaxed**:
`check-rate-limits.sh` exists to prove production's numbers hold there, and
against 6000 registrations a minute it would pass and mean nothing. Restore it
when the run is done — `… show` says which is in force.

`/health` and the loopback-only `/admin/*` routes carry no limit at all.

The client address comes from `X-Forwarded-For`, trusted **only because the
server publishes no ports and Caddy is the sole ingress**. That precondition
sits beside the code depending on it; if anything else can reach the server,
the header is attacker-controlled.

The defaults are a first guess for a 2 vCPU, 954 MB box.
`./scripts/check-rate-limits.sh` asserts the shape holds against a running
server, and is meant for the rehearsal host — numbers checked on a development
machine say nothing about the one they protect.

## Infrastructure Configuration

The actual runtime settings of the two pieces of infrastructure this project depends on, verified against the live config/code rather than assumed — worth checking here before assuming a default.

### SQLite

`persistence::connect` (`crates/server-game/src/persistence.rs`) does exactly this and nothing else:

```rust
SqliteConnectOptions::from_str(database_url)?.create_if_missing(true)
```

`persistence::connect` sets `journal_mode` explicitly (`0.3.0`, see below); synchronous and foreign-key pragmas are left at SQLite's own defaults. Verified directly against a live database (`sqlite3 <file> "PRAGMA journal_mode; PRAGMA synchronous; PRAGMA foreign_keys;"`):

| Pragma | Actual value | Means |
|---|---|---|
| `journal_mode` | `wal` (since `0.3.0`; was `delete` before) | Readers no longer block behind a writer's transaction — matters once more than a handful of players are concurrently active. Sets `-wal`/`-shm` sidecar files alongside the main database file (`3.2-development.md`'s "Resetting the Database" step already correctly hedges on this — "may not exist depending on journal mode" — now they do). Volume backups (`3.4-production-environment.md#backups`) already tar the whole directory, so this needed no backup-procedure change. |
| `synchronous` | `2` (`FULL`) | Unchanged by the `journal_mode` switch (verified — sqlx doesn't adjust it automatically the way the `sqlite3` CLI's shorthand modes sometimes imply). Every commit still `fsync`s before returning. `NORMAL` (`1`) is commonly paired with WAL for a latency win, since WAL's own durability model needs less aggressive fsyncing — not changed here since it wasn't part of this release's scope, but worth a deliberate look if write latency ever becomes a real concern. |
| `foreign_keys` | `0` (off) | **The `foreign key to X.id` relationships documented throughout [4.2 Database Schema](4.2-database-schema.md) are not actually enforced by SQLite** — they're honored by application logic only (verified: `delete_player`/`delete_game` in `persistence.rs` already delete child rows before parent rows inside a transaction, in the right order). Turning this pragma on wouldn't currently change that, though: `crates/server-game/migrations/0001_baseline.sql` has no `foreign key ... references ...` clauses at all — the schema doc's "foreign key to X" language describes the *logical* relationship, not a declared SQL constraint. Real enforcement needs both the pragma **and** adding actual `references` clauses, and SQLite can't `alter table` a constraint onto an existing table — it means recreating each table. That's schema-migration-sized work, not a config change; not undertaken as part of this pass. |

Connection pool: `SqlitePoolOptions::new().max_connections(5)` — one shared pool per process, same in every environment (dev/preview/production all run a single `server-game` process each; there's no multi-process fan-out that would make 5 a bottleneck).

### Caddy

Version pinned via `caddy:2-alpine` (`Dockerfile`'s `runtime-web` stage) — floats on Caddy's `2.x` line, not pinned to an exact patch version.

- **Compression**: `encode zstd gzip` — zstd preferred, gzip fallback, for every response Caddy serves (static assets and proxied API alike).
- **Routing**: an explicit `route { }` block, not Caddy's default directive ordering — needed because Caddy's automatic ordering runs `try_files`/`file_server` *before* `reverse_proxy`, which would rewrite every API path to `/index.html` before the `@api` matcher ever saw it. The `@api` matcher lists exact paths/prefixes (`/health /engines /auth/* /games /games/* /players/* /invitations/* /dictionaries/*`) — a new route added to the server's API needs a matching entry here too, or it'll silently fall through to the SPA fallback instead of reaching `server-game`. (`Caddyfile.preview` duplicates this same matcher list — see [3.3 Testing, CI & Release](3.3-testing-ci-and-release.md#13-deploy-to-the-preview-environment) — so a new route needs updating in both files.)
- **Caching**: `/assets/*` gets `Cache-Control: public, max-age=31536000, immutable` (content-hashed filenames, safe to cache forever); `index.html` itself is deliberately left with no caching directive, since it's what points at the current asset hashes.
- **TLS**: fully automatic via Let's Encrypt — see [Building a host](3.4-production-environment.md#building-a-host) for the sslip.io and real-domain mechanics. No manual certificate handling anywhere.
- **Admin API**: Caddy's own runtime admin endpoint (`localhost:2019`, visible in its startup log) is **not** exposed via `docker-compose.yml`'s `ports:` — reachable only from inside the container, not the host or internet.
- **No explicit resource limits**: neither `docker-compose.yml` nor `docker-compose.preview.yml` sets `mem_limit`/`cpus`/`deploy.resources` on any service — both containers share whatever the VM (1GB RAM + swap, see [Building a host](3.4-production-environment.md#building-a-host)) or dev machine has available, uncapped.

### Docker

Multi-stage `Dockerfile`, one shared `builder` stage (`rust:1-bookworm`) feeding two final images — see [3.4 Production Environment & Operations](3.4-production-environment.md#container-topology) for the request-flow/volume picture; this is the build side.

| Stage | Base image | Produces |
|---|---|---|
| `builder` | `rust:1-bookworm` | Compiles `server-game`/`admin-cli` (release) and the web client (`dx build --release`) — not shipped itself, just feeds the two below |
| `runtime-server` | `debian:bookworm-slim` + `ca-certificates` | `server-game` + `tile-lite-elite-admin` binaries only |
| `runtime-web` | `caddy:2-alpine` | The built wasm/static bundle + `Caddyfile` |

Built images (local, `docker compose build`, `TILE_LITE_ELITE_BUILD_ID` set): `tile-lite-elite-server` ≈199MB, `tile-lite-elite-web` ≈92MB — small enough that `scripts/deploy.sh`'s `docker save | gzip` / `scp` round trip (see [How `deploy.sh` ships an image](3.3-testing-ci-and-release.md#25-how-deploysh-ships-an-image)) stays fast even over a modest connection. `.dockerignore` excludes `target`, `.git`, `data`, `.dioxus`, log/pid files, and `node_modules` from the build context, so none of those slow down the context upload to the Docker daemon or accidentally end up in an image layer.

Both runtime images define a `HEALTHCHECK`. `runtime-server` curls its own `/health`; `runtime-web` queries Caddy's admin API at `127.0.0.1:2019/config/` with busybox `wget`, not the public `/health`, because in production Caddy's HTTP-to-HTTPS redirect catches a loopback probe and the TLS handshake then fails for want of a certificate for that name. Use `127.0.0.1`, not `localhost`: busybox resolves `localhost` to IPv6 first and the admin listener is IPv4 only. Neither compose file overrides the `Dockerfile`'s intervals. The status shows in `docker compose ps`, or `docker inspect --format='{{.State.Health.Status}}' <container>`.

## Versioning

Three numbers travel with a build, and they answer different questions. The
first two are chosen by a person; the third is derived and cannot be wrong.
When to move each is [3.3 §2.4](3.3-testing-ci-and-release.md#24-version-numbers-which-to-bump-and-when).

| | **API contract version** | **App version** | **Build id** |
| --- | --- | --- | --- |
| answers | can we talk to each other? | which release is this? | which commit is this? |
| form | `Major.Minor`, e.g. `2.10` | `Major.Minor.Patch`, e.g. `0.6.0` | a short commit id, e.g. `b717733` |
| lives in | `api::API_VERSION` | root `Cargo.toml`'s `[workspace.package]`, inherited by every crate | `TILE_LITE_ELITE_BUILD_ID`, set at image build |
| changes when | a route or DTO changes, or a new value becomes acceptable | every release | every commit that gets built |
| chosen by | whoever makes the wire change, as they make it | `deploy.sh`'s patch bump, or a minor for a functional release | nobody: it is the commit |
| published as | `/health`'s `api_version` | `/health`'s `app_version`, before the `+` | `x-build-id` on every server response; `/version.txt` from the web container; after the `+` in `app_version` |
| checked by | the client, on connect | nothing automatic | the client, on every response |
| a mismatch means | major: stop, the contract is broken. Minor: carry on, say so | nothing on its own | see the comparison below |

The lifecycles are independent. A release always moves the app version and the
build id, and the API version only if the wire contract changed. A client one
build behind can talk to the server, which is the normal case during a deploy;
a client one major API version behind cannot.

### The API contract version

`api::API_VERSION` lives once in the shared `api` crate, so the server and each
client embed whatever it was at their own build. The desktop client checks it
against `/health` on first connecting (`check_api_version` and
`compare_api_version` in `crates/ui/src/app.rs`): a major mismatch blocks use
with an "update the app" message, a minor one shows a non-blocking notice. It
has no patch component, because nothing below a minor changes the wire. The
reasoning for each bump is kept in the comment block above `API_VERSION`.

### The app version and the build id

`Major.Minor.Patch` is workspace-inherited, so a bump is one line in the root
`Cargo.toml`; read the current value there. A `+<build>` suffix (SemVer build
metadata) is appended when `TILE_LITE_ELITE_BUILD_ID` is set at compile time:

```bash
# Internal/test build with a build id
TILE_LITE_ELITE_BUILD_ID=$(git rev-parse --short HEAD) cargo build -p server-game --release

# No build id set: shows "0.4.6", not "0.4.6+..."
cargo build -p server-game --release
```

`deploy.sh` and `deploy-preview.sh` set it from the short SHA of the commit
they build, through `build.args` into the `Dockerfile`. Both build a fresh
checkout of that commit ([3.3](3.3-testing-ci-and-release.md#211-deployments-build-a-commit-never-the-working-tree)),
so the suffix is exactly true of the image.

`server-game` logs both versions at startup and serves the app version as
`app_version` in `GET /health` (`api::HealthDto`); `deploy-preview.sh at prod`
and `verify` read it to find what is live. The desktop client shows its app
version in the window title.

### How a tab learns there is a new build

The build id is compiled into the server and into the wasm, and written into
the web image as `/version.txt` (`Cache-Control: no-store`). A running tab
knows three:

| it knows | from |
| --- | --- |
| its own build | compiled in |
| the web container's build | `GET /version.txt`, the one request that does not go to the server |
| the server's build | `x-build-id`, on every response ([4.3](4.3-api-schema.md#x-build-id)) |

| observation | the tab |
| --- | --- |
| web ≠ server | a deploy is in flight: waits |
| client = web | is up to date |
| otherwise | new code is being served: reloads |

The header is the trigger, on traffic already happening; `/version.txt`
confirms, because only the web container knows what bundle is being served.
Reloading on the header alone would, mid-deploy, fetch the old bundle, see the
header again, and loop. The id is validated as hex, because Caddy's SPA
fallback answers a missing `/version.txt` with `index.html` and a 200.

**A dev build sets no build id**, writes no `version.txt` and sends no header,
so every comparison answers "cannot tell" and the client does not reload. That
is the behaviour to keep: a working tree has no commit that describes it, and
not knowing must never be a reason to act.

Desktop has no bundle to re-fetch; the API version drives its update prompts.
