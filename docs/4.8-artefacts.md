# Artefacts outside the repository

Everything under change control that **leaves no trace in git**: files on the
production host, resources in Oracle Cloud, objects in GitHub, and records held
by services we do not run.

**Why only those.** A repository artefact is self-naming — its path *is* its
name, it either exists or it does not, and `git log` says what happened to it.
None of that is true here. A firewall rule, a bucket or a systemd timer is
invisible to every tool this project has, so **this file is the only record there
will ever be**, which is also why the entries carry enough detail to recreate
them.

That gives this document a second job: it is the answer to *"what else was on
that box?"* after the box is gone.

## Every way a change is categorised

**One list, so nothing invents a second scheme.** The issue fields are
authoritative — a document describes them and never defines a parallel set. Only
these appear in `docs/3.x`.

| scheme | values | what it decides |
| --- | --- | --- |
| **issue type** | `Requirement · Project · Decision` | what the issue is |
| **Workstream** | the ten in [3.7](3.7-workstreams.md); unset is the triage queue | who owns it |
| **Type of change** | `bug · functional · cosmetic · documentation · tooling` | what it owes before shipping. `functional` is read by the release gate |
| **Route** | `Production Release · Repository Change · Other` | how it reaches its users, and whether it takes a semver |
| **Priority** | `Urgent · High · Medium · Low` | a judgement, deliberately not derived |
| **Effort** | `High · Medium · Low`; unset means triage could not say | a band, not an estimate |
| **Stage** | `Triage · Scope, Options and Dependencies · On Hold · Ready for Project · Candidate Project 1–3` | a requirement's journey |
| **Phase** | `Scope · Q3 · Q2 · Q1 · Design and Test Approach · Development · User testing · Deployment · Post-deployment · Project Closedown` | a project's journey |
| **Milestone** | a semver, the previous semver plus a letter, `no-release`, or `pre-approved` | how the change reaches its users, including *directly, because it was pre-approved* |
| **Decision State** | `Asked · Feedback Provided · Documented Ready for Sign-Off · Decided · Actioned` | who is holding it, alternating each transition. `Feedback Provided` is with Claude to respond and document; `Documented Ready for Sign-Off` is back with the owner to read and sign; `Decided` is signed off and awaiting application; `Actioned` is applied and awaiting his reading, so it is **green, not red** — the work is done but the decision is not, and red would hide the last thing it needs |
| **Topic** | a named project or focused subject; **unset is normal** | which decision log a `Decision` appears in. Not a level — Parent and Workstream say that |
| **Parent** | an issue | what owns it. On a `Decision`, the project or requirement that triggered it |

**Option colour says whose turn it is**, across every field that carries a
journey — `Stage`, `Phase`, `Decision State` and the board's `PR State`. Set by
the owner, 2026-09-09:

| colour | means |
| --- | --- |
| **blue** | Claude leads |
| **green** | Steve leads |
| **yellow** | on hold, or waiting |
| **red** | finished |

**Blue and green are not symmetrical, and that is the point.** Owner,
2026-09-09: *"Claude is looking over all the items and identifying things that
can be progressed, whereas I should be able to be more reactive."* So blue is
not merely *Claude's turn* — it is **Claude's to find**, swept for without being
asked. Green is the short list that has to be brought to the owner, and it is
short because everything else is somebody else's job to notice.

That is why `Triage` and `Ready for Project` are blue even though both need the
owner in the end: Claude leads them, arriving with the reading and the proposal.
An option is green only when the owner has to act *first*, not when he has to
agree.

**It is a fifth reading of the same fact**, beside the option name, and it is why
a board grouped by any of these can be scanned without reading a word: a column
of green is what is waiting on the owner. `Decision State` alternates blue and
green by design (D45), and `PR State` was built to match — `Awaiting review` is
the only green one, because it is the only state where Claude is not the one to
act.

**`Decision State` has no red, and that is correct.** A decision does not rest in
a finished state: `Actioned` still waits for the owner to read it and close the
issue, so the last option is green and the terminal state is *closed*. Found by
testing the convention on 2026-09-09 — four actioned decisions were painted
finished while genuinely waiting, which is the one thing the colours exist to
prevent.

**A new option needs a colour chosen, not defaulted.** Nothing enforces this, so
an option added without thought silently breaks the reading for every view that
groups on it.

**`patch`, `minor` and `major` were closed on 2026-09-07** and are no longer
values. They were a queue, and `Phase` `Q1`–`Q3` is the queue now — two schemes
answering one question. `minor` and `major`
had never held an issue; `patch` holds two closed ones, so all three were closed
rather than deleted and that history survives.

**Three distinctions are not fields, and are kept deliberately** — none of them
categorises a change, which is why no field could hold them:

| | | |
| --- | --- | --- |
| **gate** and **check** | a gate refuses and work stops; a check reports and a person decides | classifies *automation*. [3.6](3.6-change-lifecycle.md) §2.16 |
| **delivery** and **release** | a delivery is any update reaching its users; a release is a new application version in production | vocabulary the milestone rule depends on |
| an artefact's **route** | the same three values, per artefact | the source the `Route` field is derived from — see below |

**Retired, and named so they are recognised rather than reinstated**: `lane`, the
seven type *labels*, `needs-triage`, and the `Workstream` and `Index` issue types.

## How an artefact is named

The same convention wherever an artefact is listed — here, in a project issue's
*impacted artefacts*, or in a design note. Two lists can then be compared for
overlap by matching strings rather than by knowing both projects.

**The location is whatever names the thing precisely** — owner, 2026-09-02: *"a
repo path, a source module path, or 'OCI Console'."* Precise enough that two
people mean the same artefact, and no more.

| kind | canonical name | example |
| --- | --- | --- |
| a file in the repository | its path from the repository root | `docs/3.4-production-environment.md` |
| part of a file | the path, then the module or function | `crates/server-game/src/app.rs` — `settle_issue` |
| on a host | the host role, then the absolute path | `production:/etc/systemd/journald.conf.d/50-cap.conf` |
| a cloud resource | provider, type, the provider's own name | `OCI bucket tile-lite-elite-backups` |
| a GitHub object | `github:` then type and name | `github:label folded` |
| changed somewhere else | the place it is changed | `OCI Console` |

**The last row is the honest one.** Some artefacts have no path and no
identifier worth writing — a setting adjusted in a console, a value typed into a
web form. Naming the *place* is enough to find it again, and pretending to more
precision than exists is how an artefact list stops being trusted.

## The route an artefact takes

**Route is a property of the artefact, not of the change.** Owner, 2026-09-09:
*"the way we have Route it is really a property of the artefact, not the
delivery. A particular delivery will combine different artefacts and different
routes, and that will determine the specific process it will follow."* So the
artefact is where a route is true; the issue field is a summary of the artefacts
underneath it, and the process follows from the combination rather than from the
summary.

**A delivery takes the heaviest route among the artefacts it touches** — owner,
2026-09-02: *"artefacts should have a route, which feeds into a project
delivery."* The `Route` issue field records that result; this table is where it
comes from.

**Which is why the field cannot decide the process on its own.** `Route` says how
the change reaches its users. What shape it needs — a branch, a pull request, a
milestone, a row — depends on that *and* on whether the old version has to keep
working while the work is in progress, *and* on how many packages ship together.
`docs/3.3`'s four shapes read the field as one input of three, not as a key.

**The mixture is the normal case, not the exception.** #298 changed documents
(repository) and created a GitHub object by hand (other). #240 delivered the same
`Caddyfile` to rehearsal (other) and to production (production release), which is
why its two work packages carry different routes and the parent carries none.

**The ranking is not the table's order.** Heaviest first:

| | route | because |
| --- | --- | --- |
| 1 | **Production Release** | a release also changes the repository, and shipping is the dominant event |
| 2 | **Other** | owner, 2026-09-08: *"Other ranks above repository."* Something applied by hand is **not live until somebody applies it**, so a delivery that also changes a document did not go live at the merge |
| 3 | **Repository Change** | live on the push to `origin/main`, and nothing further is owed |

**Only the first pair was ever reasoned.** The rule read *heaviest*, with the
table taken top to bottom — which is right for a release against a repository
change and wrong for the pair below it, where it claimed a hand-applied change
went live at merge.

**The worked example is #298**, which added the `Decision` issue type: documents
in the repository, and a GitHub object created by hand. Owner, 2026-09-08: *"the
changes are configuration (route=other) and documents (route=repository). I have
set it to Other."*

| route | which artefacts | reaches its users |
| --- | --- | --- |
| **Production Release** | anything built into the image — `crates/**`, the word lists, `Caddyfile`, `Dockerfile`, `docker-compose.yml` — **and anything deployed to the production host**: files under `/opt/tile-lite-elite/`, systemd units, packages installed there | when `deploy.sh` deploys to production, which always takes a new semver |
| **Repository Change** | **anything else** in the repository — `docs/**`, `scripts/**`, `.github/**`, `.cargo/audit.toml`. A production release changes the repository too, so this row is the *otherwise* | when it is pushed to `origin/main` |
| **Other** | cloud resources, GitHub objects, and deploys to preview or rehearsal | when somebody applies it |

**`.cargo/` is split between the first two rows, and the file decides.** `.cargo/audit.toml` configures `cargo audit` and is read by nothing else, so it never reaches a build; `.cargo/config.toml` would set rustflags, the target directory or a registry, and would change the bytes. So the exception in `scripts/shipping-paths.sh` names the file and not the directory — a directory-wide exception would quietly let a build-affecting change onto `main` without a branch. Added 2026-09-10 when #374's commit was refused by the image rule, which was right to ask.

**The production host is on the first row, not the third** — D52, 2026-09-08.
Owner: *"any change to the production environment is a production release with a
new semver, and therefore a new build of the application. Even if the change does
not require a change in the application."* The release is what records that
production moved, and a production whose files changed under a version that did
not is a production nothing can describe.

**In practice it rides with a release rather than causing one.** Owner, same day:
*"my expectation is that changes to the production environment would go with
actual application changes. So the effect is to put the production tooling change
into an existing application release instead of doing it separately."* So a host
change takes a semver milestone and joins the release already being planned; it
does not justify cutting one of its own. The cost of the rule is that such a
change waits for the next release, which is the intended trade: production moves
in fewer, describable steps.

**The delivery's runbook combines the actions for its release**, in the order
they have to happen — the image and whatever lands on the host. That is the
runbook's job wherever a delivery has more than one kind of step, so it needs no
separate rule.

**"The production host" is the Oracle VM** — the Ubuntu instance we ssh into,
which runs the Docker daemon and whose kernel every container shares. Not the
hypervisor underneath it, which is Oracle's and which we cannot see, patch or
restart. Three layers are ours and each moves differently: the VM's own packages,
the Docker daemon on it, and the packages inside the image.

**A package we choose to install is ours; one the distribution updates is not.**
`pip install oci` on the host is a production release; an OS security update
applied by `unattended-upgrades` is the platform maintaining itself, and takes no
semver. The test is whether a project named it.

**Production cloud configuration stays `Other`.** The boundary is *deployed
artefacts*: a file, a unit or a package landing on the host is a release; an OCI
alarm, a policy or a dynamic group is applied by hand. Preview and rehearsal
deploys stay `Other` whatever they carry, because they are not production.

**Every artefact carries its route and a precise location** — owner,
2026-09-02. The route is one of the three; the location is the canonical name
above, which says exactly where the thing is.

**The kind of an artefact does not decide its route**, which is why both are
recorded. `docs/3.6-change-lifecycle.md` and `crates/rules-shared/src/wordlists/greylist.txt`
are both files in the repository; one is live when it is pushed and the other
when the next release ships.

**The rule in executable form is [`scripts/shipping-paths.sh`](../scripts/shipping-paths.sh)**,
sourced by `.githooks/pre-commit` and by `deploy.sh`. It is written as the
*exceptions* — the paths that do **not** ship — because the list of things that
do grows whenever a crate is added, and the list of things that do not is
stable. This document is the authority; that file is the copy a script can run,
and there is exactly one of it because it decides both whether a commit is
refused and whether a release is described correctly.

**Heaviest wins where a change touches several.** Production Release, then
Repository Change, then Other. A change that edits a document and a crate is a
release, because the document is live either way and the crate is not.

**A generator whose output is committed takes the route of the generator, not of
what it makes** — owner, 2026-09-05, reviewing PR #312: *"arguably this script
produces an asset used in the build, similar to the word list tooling. However
since we will obviously look at the icon before building the app it can be
classed as repository."*

`wordlist-tools` proposes `greylist.txt` and `scripts/mkfavicon.py` draws
`favicon.ico`. Both outputs ship; neither generator does, and the table above
already places them by path — owner, 2026-09-05: *"tools are implicitly
Repository."*

**What the table does not say is the test: *is there a human step between this
artefact and the image*, not *does its output ship*.** These two have one —
change the generator and nothing reaches a player until somebody runs it, reads
the result and commits it. A generator invoked **by the build** has no such step
and is Production Release despite living under `scripts/`, because changing it
changes what ships with nobody looking.

## The production host

Verified on the VM, 2026-08-21.

| artefact | route | what it is | why it is not in the repository |
| --- | --- | --- | --- |
| `production:~/tile-lite-elite/docker-compose.yml` | Production Release | the compose file the running stack uses | **copied there by `deploy.sh`** from the repository — the copy is a deployment artefact, and the source of truth is in git |
| `production:~/tile-lite-elite/snapshots/` | Other | pre-deploy database snapshots, newest five kept | data, created by `deploy.sh` |
| `artifacts/<sha>.tar.gz` | Other | the built images for one commit, with a `.sha256` beside it. Newest five kept | **a cache, not a record.** Git-ignored, created by `deploy.sh`, shared by rehearsal and production so both load the same bytes (#214). Losing one costs a rebuild of that commit |
| `production:/etc/systemd/journald.conf.d/50-cap.conf` | Other | `SystemMaxUse=50M`. Written 2026-07-30 | applied by hand. It is why journald is *not* on defaults, which #174 discovered the hard way |
| `production:` docker volumes `tile-lite-elite-data`, `-caddy-data`, `-caddy-config` | Other | the database, and Caddy's certificates and state | created by Docker, and the first is the only irreplaceable thing on the machine |
| `production:` iptables `INPUT` chain | Other | accepts established, ICMP, loopback and **22 only**; rejects the rest | applied by hand |

**Two notes worth keeping with the entries.**

Ports 80 and 443 do **not** appear in the `INPUT` chain. Docker publishes them
through its own `DOCKER` chain in the `nat` table, which bypasses `INPUT`
entirely — so reading `iptables -S INPUT` and concluding the site is unreachable
is a mistake waiting to be made twice.

The compose file on the host is a **copy**. Editing it directly changes what runs
until the next deploy overwrites it, silently, which is the worst kind of
configuration drift because it repairs itself just late enough to confuse
whoever is looking.

### Which level carries which field

Enforced by **pinning**, set from the field rather than the type: org settings →
Planning → Issue fields → the field → *Pin to types*. An unpinned field never
appears in the sidebar or the creation modal, which is why `Effort` sat empty on
53 issues — nobody was ever asked for it.

**Since 2026-09-08 there are three types, not four**: `Project Delivery` was
deleted, and a delivery is a sub-project — a `Project` with a parent. The last
column is that, and it differs from a parent only in what the parent owns for
it: requirements, design and the documents.

| | Requirement | Project (parent) | Project (work package) |
| --- | --- | --- | --- |
| **Workstream** | one of the ten in `docs/3.7`; unset is the triage queue | same | same |
| **Type of change** | `bug · functional · cosmetic · documentation · tooling` | same | same |
| **Route** | `Production Release · Repository Change · Other` — how the change reaches its users | same | same |
| **Effort** | `High · Medium · Low`; unset means triage could not say | same | — |
| **Stage** | `Triage · Scope, Options and Dependencies · On Hold · Ready for Project · Candidate Project 1–3`; unset is the inbox | — | — |
| **Phase** | — | `Scope · Q3 · Q2 · Q1 · Design and Test Approach · Development · User testing · Deployment · Post-deployment · Project Closedown`. `Q1`–`Q3` order what is next without inventing dates. `Post-deployment` means *awaiting its review* and is where `deploy.sh` leaves a project it ships; `Project Closedown` means the lessons-learnt is written and only the closing is left | — |
| **Priority** | — | `Urgent · High · Medium · Low` | — |
| **Milestone** | — | a semver if the delivery is a release, the previous semver plus a letter if not, `pre-approved` if it goes straight to `main`, or `no-release` before that is known. **Anything other than `pre-approved` means not pre-approved**, including none at all — absence is read as the safe answer | same |
| **Parent** | its workstream | its workstream | the index, or nothing |

**A field cannot be *restricted* to a type**, only pinned to one — every field
remains settable on any issue through *Add field*. The rule lives in the field's
description and in this table, not in the schema.

### What the tooling reads, and would break on

Every row is a **string matched literally**. Renaming any of them is a change
with a blast radius, not a tidy-up — [3.6](3.6-change-lifecycle.md) §2.2.

| what | read by | breaks how |
| --- | --- | --- |
| `Type of change` = `functional` | [`check-release-version.sh:33`](../scripts/check-release-version.sh), [`status.sh:243`](../scripts/status.sh) | **silently.** The release gate stops finding functional work, so every patch release passes. This happened on 2026-09-02: the option was renamed from `minor-function` and the gate matched the old string until it was repointed, passing a functional patch in the meantime |
| `Type of change` = `documentation`, `tooling` | [`status.sh:140`, `:320`](../scripts/status.sh) | quietly — merged work stops being reported as finished and looks blocked on a release |
| the field name `Type of change` | `check-release-version.sh`, `status.sh` (three queries) | loudly — the jq filter returns nothing and the column empties |
| issue type names `Requirement`, `Project`, `Workstream`, `Index` | [`actions.py`](../scripts/actions.py), and the board's `type:` view filters | the tree flattens; views empty |
| the `Phase` **field name** | [`actions.py`](../scripts/actions.py), [`deploy.sh`](../scripts/deploy.sh), [`verify.sh`](../scripts/verify.sh) | a project shows as *not started* whatever its phase; a shipped project is never advanced |
| the option value `Post-deployment`, **and its id** | `deploy.sh` sets it by option id after a release; `actions.py` and `verify.sh` match it by name | a release stops advancing what it ships, or the review reminder never fires |
| `IssueFieldChangedEvent` in an issue's timeline | `actions.py`, `verify.sh` — how long a project has been at a phase | the review reminder has no clock and says nothing |
| milestone lanes `patch`, `minor`, `major`, `no-release` | the board's release view; [`check-release-version.sh`](../scripts/check-release-version.sh) reads version milestones | a lane disappears from the release view |
| milestone titles that are versions | [`deploy.sh`](../scripts/deploy.sh), `check-release-version.sh` | a release closes nothing, or the gate cannot find its scope |
| the **parent link** | the board's `No Workstream Assigned` view; [`actions.py`](../scripts/actions.py) | the triage queue empties, and untriaged work becomes invisible |
| `Stage` and its four values | the board's backlog view | a requirement's journey stops being visible; nothing breaks loudly |
| label `folded` | search by hand, and the project form's instructions | a requirement absorbed into a project cannot be told from one closed as rejected |
| the field slug `type-of-change` | the board's **Needs triage** filter | the view renders **empty**, which reads as *nothing to triage* |

Workflows live in `.github/workflows/` and are repository artefacts, so they are
not listed here.

## What a script's exit status means

**Severity, and nothing else.** D46 (#327). A wait status carries eight bits, so
it cannot carry an identifier as well — `exit 40001` is observed as `65`, and
`exit 256` as **`0`**, which would report success for a fatal error.

| exit | means |
| --- | --- |
| `0` | it worked. Information and warnings are printed and still exit `0` — nothing failed |
| `1` | **fatal.** It went wrong and the run stopped. Nothing reached users |
| `2` | **could not judge.** Not a severity: the check could not run at all, for want of `gh`, `jq`, a network or an argument. `ci-status.sh` and `check-release-version.sh` set this so a missing tool cannot read as a pass |
| `3` | **non-fatal.** It went wrong and the run continued. `deploy.sh` returns this when production is live and a step *after* the swap failed |

**`3` exists because `1` was lying.** The 0.7.2 deploy shipped correctly and
exited `1` because its version bump was refused — saying *the deploy failed*
when production was live and healthy. Owner, 2026-09-05: *"If there is an error,
it should return non-zero. We would then look at what the error was. If it
returns zero we might not even look."* So the status stays non-zero and the
distinction moves into it, rather than into the output alone.

### A numeric code scheme was considered and rejected

A five-digit code — severity, script, error — was proposed for messages and
logs. **Rejected 2026-09-06**, and recorded here so it is not proposed again,
because the obvious future trigger would otherwise pull in the wrong mechanism
simply because it had been written down.

**Two things already do the job.** The server declares **forty-eight event
definitions** in [`4.7`](4.7-log-events.md), where the event *name* is the
stable handle a code would have been — readable, already governed, and checked
by `tests/log_schema.rs` and `check-log-hygiene.py`. And the nightly runs
refresh a **marker object only on a clean run**, with the alarm watching for it
going stale, so *"this failed again last night"* needs no identifier at all.

**Owner, 2026-09-06:** *"Scheduled and application driven jobs run on the
production VM server container can plug in to the existing logging framework and
error scheme… we should drop the idea of introducing a new scheme beyond
severity."*

**If script output ever needs aggregating**, the answer is to extend `4.7` —
structured lines with an event name, which `check-log-hygiene.py` can already
validate — rather than run a second, numeric identifier scheme beside the first.
There is a case for `deploy.sh` and its neighbours writing JSON events as well
as their present reporting; that is a separate question.

## What counts as an artefact

**Operating the processes is part of what the programme does, so the tools built
for that are artefacts, maintained like any other** (owner, 2026-09-03). There is
no separate category for tooling that never reaches a user: `deploy.sh` and the
hook that shows Claude the owner's comments are both things the programme owns,
and both are answerable to the register.

The question is not whether something runs in production. It is whether the
programme would have to rebuild it if it were lost.

**What is excluded, and why it is not an inconsistency:** test code, meaning
`scripts/tests/*.test.sh` and `crates/*/examples/`. A test exists to hold an
artefact to its behaviour, and is delivered with it rather than beside it. The
same line runs through `.githooks/pre-commit`, which excludes both from its
image rule and its registration rule.

This was settled after two failures of the older framing. `.claude/turn-check.sh`
was left out of the repository as *Claude's own bookkeeping*, and sat filtering
comments on a marker that nothing had written for weeks — invisible to the
register and to every test. And eight scripts, `verify.sh` among them, were
simply never added.

## When an entry appears

**When the delivery that creates it completes**, never in anticipation. A project
lists what it *intends* to touch in its own issue; this file records what
*exists*. Keeping those apart is what stops the register becoming a wish list
that nobody trusts.
