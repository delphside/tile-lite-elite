# Backups and restores

Where production's data is copied, and how it is checked, restored or wiped.
Every host step is the owner's to run ([CLAUDE.md](../CLAUDE.md)); host
commands name the host by its `ssh` alias, listed in Infrastructure's
[6.3.4](https://github.com/delphside/infrastructure/blob/main/docs/6.3.4-hosts.md#the-hosts).

| Kind | Where | When | Restored by |
| --- | --- | --- | --- |
| manual tarball | `~/tile-lite-elite/` on the VM | the owner takes one | [the manual restore](#taking-and-restoring-a-manual-backup) |
| [pre-deploy snapshot](#automatic-pre-deploy-snapshots) | `~/tile-lite-elite/snapshots/` on the VM | every `deploy.sh` run | `rollback.sh` |
| [nightly copy](#the-nightly-copy-that-leaves-the-vm) | the Oracle Cloud Infrastructure (OCI) bucket | 03:10 UTC | [Restoring the offsite backup](#restoring-the-offsite-backup) |

## Taking and restoring a manual backup

The owner takes a manual backup with the server stopped, because in SQLite's
write-ahead log (WAL) mode a copy taken while the server runs can miss the
WAL entry that completes the file:

```bash
ssh tile-lite-elite
cd ~/tile-lite-elite
docker compose stop server
docker run --rm -v tile-lite-elite-data:/data -v "$PWD":/backup debian \
  tar czf /backup/tile-lite-elite-data-$(date +%Y%m%d).tgz -C /data .
docker compose up -d
```

The owner restores one with
[Replacing production's database](#replacing-productions-database), loading
the tarball at step 4.

## Replacing production's database

The owner replaces the database on the VM in these steps:

1. Connect and stop the stack; the named volumes are untouched:

   ```bash
   ssh tile-lite-elite
   cd ~/tile-lite-elite
   docker compose down
   ```

2. Back up the volume, under a name that no manual backup of the same day
   shares:

   ```bash
   docker run --rm -v tile-lite-elite-data:/data -v "$PWD":/backup debian \
     tar czf /backup/tile-lite-elite-data-$(date +%Y%m%dT%H%M%S).tgz -C /data .
   ```

3. Clear the database files:

   ```bash
   docker run --rm -v tile-lite-elite-data:/data debian \
     sh -c 'rm -f /data/tile-lite-elite.sqlite3 /data/tile-lite-elite.sqlite3-wal /data/tile-lite-elite.sqlite3-shm'
   ```

4. Load what the case calls for:

   | Case | Loads |
   | --- | --- |
   | [manual restore](#taking-and-restoring-a-manual-backup) | the tarball's contents, extracted into the volume |
   | [Restoring production](#restoring-production) | the restored file, copied in as the database |
   | [Wiping production](#wiping-production) | nothing |

   The tarball, with its own name in place of `<tarball>`:

   ```bash
   docker run --rm -v tile-lite-elite-data:/data -v "$PWD":/backup:ro debian \
     tar xzf /backup/<tarball> -C /data
   ```

   The restored file:

   ```bash
   docker run --rm -v tile-lite-elite-data:/data -v "$PWD":/in:ro debian \
     cp /in/restored-<name>.sqlite3 /data/tile-lite-elite.sqlite3
   ```

5. Start the stack. With nothing loaded, the server recreates the database,
   migrations included:

   ```bash
   docker compose up -d
   ```

## Wiping production

The owner wipes production with
[Replacing production's database](#replacing-productions-database), loading
nothing at step 4. A schema change needs no wipe: migrations apply when
`deploy.sh` runs them before it starts the new version, and again on startup.

## Automatic pre-deploy snapshots

`deploy.sh`, on the VM:

1. loads the new images, after tagging the running ones `:previous`;
2. stops the server;
3. writes a tarball of the volume to `~/tile-lite-elite/snapshots/`;
4. applies the migrations on their own, and on a failure restores the snapshot;
5. starts the new version;
6. keeps the newest five snapshots
   ([4.4.1](4.4.1-configuration.md#environment-variables)).

Each snapshot is named for the version and commit being deployed, then the UTC
time:

```text
snapshots/pre-0.4.13-fb36f50-20260731T164500Z.tgz
```

`rollback.sh` restores a snapshot together with the `:previous` images
([4.3.6](4.3.6-when-a-release-goes-wrong.md#2-roll-back-across-a-migration)),
and the owner runs it.

## The nightly copy that leaves the VM

`tile-lite-elite-backup.timer` runs `backup-to-oci.sh` on the VM at 03:10 UTC,
with up to 5 minutes of delay. The script:

1. takes a consistent copy with `VACUUM INTO` while the server runs;
2. checks the copy with `PRAGMA integrity_check`;
3. gzips it and uploads `db-<UTC time>.sqlite3.gz` to the bucket;
4. uploads `marker-backup-ok`, after a successful upload only.

`tile-lite-elite-log-check.timer` runs the nightly log check at 03:40 UTC,
which uploads `marker-logcheck-ok` after a clean run.

**The VM can write backups and cannot read, list or delete them**, so neither
an attacker on the host nor a bug in the script can destroy them.

| Setting | Value |
| --- | --- |
| bucket | `tile-lite-elite-backups` |
| credential | a bucket-scoped *pre-authenticated request (PAR)*: object writes only, listing off. The VM reads it from `~/.tile-lite-elite-backup-par`, mode `0600`. |
| on the bucket | object versioning on, since a write PAR can overwrite an existing name |
| PAR expiry | **2028-08-23**. Nothing announces it. |

Deleting the PAR in the OCI console revokes it on the next attempt.

## Checking the backups

The owner checks the backups after each production deploy. Make a read PAR and
save it as in
[Restoring the offsite backup](#restoring-the-offsite-backup), then, from the
development machine:

1. List the objects:

   ```bash
   curl -sS "$(< ~/.tle-restore-par)" | jq -r '.objects[].name'
   ```

2. Read each marker, which holds a UTC time:

   ```bash
   curl -sS "$(< ~/.tle-restore-par)marker-backup-ok"
   ```

   Likewise `marker-logcheck-ok` and `marker-restore-ok`.
3. Compare the newest backup's age and each marker's with now:

   | Object | Healthy when under | If stale |
   | --- | --- | --- |
   | newest `db-<UTC time>.sqlite3.gz` | 26 hours | on the VM, `systemctl status tile-lite-elite-backup.service` |
   | `marker-backup-ok` | 26 hours | on the VM, `systemctl status tile-lite-elite-backup.service` |
   | `marker-logcheck-ok` | 36 hours | on the VM, `systemctl status tile-lite-elite-log-check.service` |
   | `marker-restore-ok` | 100 days | [drill a restore](#drilling-a-restore) |

4. Remove the credential, then delete the PAR in the console:

   ```bash
   shred -u ~/.tle-restore-par
   ```

## Renewing the write PAR

A renewal is a change outside the image, so it follows
[Changing production configuration](4.3.4-production-environment.md#changing-production-configuration).
The owner renews it before the expiry, and these steps are that
procedure's step 5, making the change on production:

1. Create a bucket PAR in the console with access *Permit object writes* and
   listing off. Its URL ends in `/o/`, because the script appends the object
   name.
2. Save the URL on the VM:

   ```bash
   ssh tile-lite-elite
   read -rs PAR && umask 077 && printf '%s\n' "$PAR" > ~/.tile-lite-elite-backup-par
   unset PAR
   ```

3. Test it on the VM:

   ```bash
   sudo systemctl start tile-lite-elite-backup.service
   journalctl -u tile-lite-elite-backup.service --since -10min -o cat
   ```

   It passes when the log shows both:
   - `uploaded db-<UTC time>` at the current time;
   - no `warning:` line, since the script exits 0 even when the marker upload
     fails.

4. Delete the old PAR in the console.
5. Update the expiry in the settings table of
   [The nightly copy that leaves the VM](#the-nightly-copy-that-leaves-the-vm).

## Restoring the offsite backup

The owner restores from the development machine, with a read PAR created in the
console for the occasion. No standing read credential exists, so **a restore
cannot begin without console access**, and whatever protects the Oracle account
protects the backups. The read PAR never goes on the production host: while it
is there, anyone on the host can read every backup.

1. In the console, open bucket `tile-lite-elite-backups` → *Pre-Authenticated
   Requests* → *Create*:
   - target: Bucket;
   - access: *Permit object reads*;
   - listing: on, because `restore-backup.sh` lists to find the newest object;
   - expiry: a day or two.
2. On the development machine, save the PAR:

   ```bash
   read -rs PAR && umask 077 && printf '%s\n' "$PAR" > ~/.tle-restore-par
   unset PAR
   ```

3. Check what is there. This downloads the newest backup, checks its integrity
   and player count, and writes `./restored-*.sqlite3`, loading nothing.
   `--object <name>` restores a named backup instead of the newest:

   ```bash
   ./scripts/operate/restore-backup.sh "$(< ~/.tle-restore-par)"
   ```

4. Optionally, load it into a local Docker volume, replacing its contents.
   `--into` names the volume; preview's is `tile-lite-elite-preview-data`
   (`docker-compose.preview.yml`). The script refuses while a container uses
   the volume, so stop the stack using it first. For production, use
   [Restoring production](#restoring-production).

   ```bash
   ./scripts/deliver/deploy-preview.sh down
   ./scripts/operate/restore-backup.sh "$(< ~/.tle-restore-par)" --into tile-lite-elite-preview-data
   ./scripts/deliver/deploy-preview.sh up
   ```

5. Remove the credential and the restored copy from this machine, which holds
   every player's data, then delete the PAR in the console:

   ```bash
   shred -u ~/.tle-restore-par restored-*.sqlite3
   ```

## Drilling a restore

**The owner drills a restore every 100 days**, to refresh `marker-restore-ok`,
in these steps:

1. Run steps 1 to 3 of
   [Restoring the offsite backup](#restoring-the-offsite-backup).
2. If `restore-backup.sh` exited 0, upload the marker from the production
   host, so the write PAR never leaves the host:

   ```bash
   ssh tile-lite-elite 'PAR="$(< ~/.tile-lite-elite-backup-par)"
     printf "%s\n" "$(date -u +%Y%m%dT%H%M%SZ)" > /tmp/m
     curl --fail -sS -T /tmp/m "${PAR}marker-restore-ok"; rm -f /tmp/m'
   ```

3. Run step 5 of [Restoring the offsite backup](#restoring-the-offsite-backup).

Do not use `restore-backup.sh --mark`: it puts the write PAR on the
development machine.

## Restoring production

The owner loads a restored database into production's volume from the
development machine.

1. Run steps 1 to 3 of
   [Restoring the offsite backup](#restoring-the-offsite-backup), which write
   `./restored-*.sqlite3`.
2. Copy the file to the VM:

   ```bash
   scp restored-<name>.sqlite3 tile-lite-elite:~/tile-lite-elite/
   ```

3. Follow [Replacing production's database](#replacing-productions-database)
   (its step 1 connects to the VM), loading the restored file at step 4, then
   delete the copy on the VM:

   ```bash
   rm ~/tile-lite-elite/restored-<name>.sqlite3
   ```

4. Check that production answers; it passes when `curl` exits 0:

   ```bash
   curl -fsS --max-time 10 https://tileliteelite.com/health
   ```

5. Run step 5 of [Restoring the offsite backup](#restoring-the-offsite-backup).
