# Tools

Every script and binary that acts on the application, one row each. Each row
says what the tool is for and links to the section that documents it, or to the
tool's own header where no section does. The programme's tools, and the rule
that tells the two kinds apart, are
[1.1](https://github.com/delphside/programme/blob/main/docs/1.1-programme-tooling.md#two-kinds-of-tooling).
What the tools touch (environment variables, volumes, ports) is
[4.4.1](4.4.1-configuration.md).

## The application's tooling

The scripts are in `scripts/`, in four folders that follow the workstreams that
own them. These folders are the technical profile's `scripts.groups`, which the
pre-commit hook reads. `scripts/tests/` holds this repository's tests.

| folder | holds | owned by |
| --- | --- | --- |
| `develop/` | building and running the application on a development machine, and the checks of its own code and documents that `check-docs.sh` runs | [Delivery Tooling](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.4-workstreams.md#delivery-tooling) |
| `deliver/` | preview, rehearsal and production together: deploying, rolling back, verifying, and the gates and libraries they share | [Delivery Tooling](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.4-workstreams.md#delivery-tooling) |
| `operate/` | the live system: backups, host checks, the log-hygiene job, and `systemd/`, the timers that run them | [Operations & Infrastructure](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.4-workstreams.md#operations--infrastructure) |
| `measure/` | benchmarks, the checks of the running server's limits, and the comment inventory | [Capacity Planning](https://github.com/delphside/programme/blob/main/applications/tile-lite-elite/3.1.4-workstreams.md#capacity-planning) |

Rules for a script here:

- A change takes a project and a branch, and is tried on preview or rehearsal
  first ([1.1](https://github.com/delphside/programme/blob/main/docs/1.1-programme-tooling.md#two-kinds-of-tooling)).
  The pre-commit hook warns, and does not refuse, when a commit to `main`
  touches one of these folders.
- A script finds the repository from its own path, so it gains a `..` for each
  folder it sits in (`scripts/<folder>/x.sh` is two below the root). A script
  that calls one in another folder says so (`../deliver/run-log.sh`).
- A new script is registered in the table of its folder. The pre-commit hook
  refuses a new script, git hook or `.claude/*.sh` whose file name appears in
  no register.

## Examples

**`crates/*/examples/` is not registered**, and that is deliberate. An example
demonstrates, measures or reproduces; nobody is expected to find it here and run
it. An example gets a row only where a document sends the reader to it, as it
does for the two benchmarks above.

What an example must never do is produce a file compiled into the binary:
`programme.toml` lists `examples/` as not reaching the image, so a generator of
a file the binary `include_str!`s is a crate (`crates/wordlist-tools`).
