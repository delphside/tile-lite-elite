## Terms in this page

| term | meaning |
| --- | --- |
| development machine | the machine that builds the benchmark and runs the reference; no other tenant, so steal is 0.00% |
| rehearsal, production | the same hardware, virtual machines whose CPU the hypervisor shares with other tenants |
| reference | the development machine's run or runs, which a comparison divides by |
| stall | time a move spent waiting because the hypervisor gave the physical CPU to another tenant; [`bench-compare.py`](#quoting-a-comparison) treats a timing over three times its position's fastest as one |
| genuine move | a move whose own cost is what the timing shows, with no stall in it |
| population | one of the two kinds of slow timing, the genuine move and the stall |

The machines, as each row's `cpu_model` and `cores` record them:

| machine | CPU | cores |
| --- | --- | --- |
| development machine | AMD Ryzen 5 7235HS | 8 threads |
| rehearsal, production | AMD EPYC 7551 | 2 |

## Benchmarking a performance change

Claude benchmarks a performance change or a new engine on rehearsal:

```bash
scripts/measure/bench-rehearsal.sh [games] [edition]
```

The defaults are 30 games and `official`. One binary serves the reference run
and the rehearsal run, so only the machine differs between them.

| step | actor | what happens |
| --- | --- | --- |
| 1 | Claude | runs `bench-rehearsal.sh` |
| 2 | the script | builds the benchmark once; the row's commit is `HEAD`, with `-dirty` when anything but the results CSV and `moves/` has changed |
| 3 | the script | runs it on the development machine as the reference, which appends a development-machine row to the results CSV |
| 4 | the script | copies the binary to rehearsal over ssh, runs it there and deletes it |
| 5 | the script | replaces the row's `unknown` commit (the host has no `git`), appends it to the results CSV and saves the per-move rows the binary printed |
| 6 | the script | prints rehearsal's previous row beside the new one, then compares with the reference, one run each |
| 7 | Claude | runs `bench-compare.py` over several runs a side for the figure to quote ([quoting a comparison](#quoting-a-comparison)) |

For step 7, run `bench-rehearsal.sh` once per run wanted: each call adds one
reference run and one rehearsal run, saved in `moves/` as described under
[the raw measurements](#the-raw-measurements). Then compare the two sets:

```bash
scripts/measure/bench-compare.py REF1.csv REF2.csv -- SUB1.csv SUB2.csv
```

| fact | value |
| --- | --- |
| minimum games | 30; `bench-rehearsal.sh` exits 1 for fewer |
| other exit 1 | the host prints no `row:` line |
| exit 0 | every completed run, whatever the figures: a check, not a gate, so a person decides |
| other non-zero exit | a failed build, scp or ssh (`set -e`) |
| run time on rehearsal | 2.7 to 4.4 s |
| run time on the development machine | 0.6 to 1.3 s |
| steal on the development machine | 0.00% in every row, so the figures need no cleaning |

### Production's run

The script reaches rehearsal only. Production's run is the owner's:

1. **Claude** builds the binary on the development machine:

   ```bash
   cargo build --release --example engine_timing_bench -p server-game
   ```

2. **owner** copies `target/release/examples/engine_timing_bench` to the
   production host and runs it:

   ```bash
   ./engine_timing_bench 30 official
   ```

3. **owner** hands back the output: the `row:` line, and the `MOVES` lines when
   the binary prints them (it does where the host has no build directory).
4. **Claude** appends the row to the results CSV with the commit filled in, and
   saves the `MOVES` lines as the run's per-move file.

## Reading an engine timing run

```bash
cargo run --release --example engine_timing_bench [games] [edition]
```

The benchmark plays engine-against-engine games (default 30, `official`)
through the same `maybe_run_engine_turn` the server uses. It appends one row to
`crates/server-game/examples/engine_timing_results.csv` and writes one file of
per-move rows ([raw measurements](#the-raw-measurements)). Thirty games give
1229 moves.

The run times each move twice and records what tells work from waiting:

| column or output | holds |
| --- | --- |
| `median_ms`, `p95_ms`, `p99_ms` | wall-clock time per move |
| `cpu_median_ms`, `cpu_p99_ms` | CPU time per move, from `CLOCK_PROCESS_CPUTIME_ID` |
| `slow_moves` | moves over 20 ms |
| `slow_cpu_starved` | slow moves that used under a fifth of their wall time as CPU |
| `steal_ms`, `steal_pct_of_capacity` | time the hypervisor took across the whole run, from `/proc/stat`, as a share of wall time times cores; per run, because the kernel records no owner for stolen time |
| the frequency chart | 100 buckets from zero to the slowest move, bars logarithmic, empty runs collapsed |

`host` is the hostname the binary reads; `cpu_model` and `cores` say what the
machine is.

### Rules for reading a run

1. **Compare CPU against wall first.** A `cpu_p99_ms` far below `p99_ms` shows
   the move waited. Equal CPU and wall show nothing on a virtual machine: the
   guest kernel credits a process with time the hypervisor took, so a stalled
   move can report CPU equal to wall.
2. **Compare median and p95 between runs.** A virtual machine's p99 sits inside
   its stalls, which are 23 to 29 of 1229 timings per run
   ([evidence](#evidence-that-the-tail-is-the-hypervisor)).
3. **Read `slow_moves` against the machine.** The 20 ms threshold separates
   genuine moves from stalls on the development machine only:

   | machine | slowest genuine move | stall population | `slow_moves` means |
   | --- | --- | --- | --- |
   | development machine | 16.4 ms | none seen | any count is a stall: one row in eight has a count, one move at 20.05 ms |
   | rehearsal | 35.9 ms | 45.6 ms and over, one at 28.2 ms | always non-zero (23 to 36 in five rows) because six positions cost over 20 ms; compare `slow_cpu_starved` (1 to 4) and the median |
   | production | as rehearsal | as rehearsal | as rehearsal (one row: 28, of which 9 starved) |

   The run prints a warning whenever `slow_moves` is above zero, naming the
   statistics that survive. On rehearsal and production read it with this table.
4. **Compare the same position, not two distributions.** The games are seeded,
   so `(game, turn)` is the same position on every machine and in every run.

## Quoting a comparison

`scripts/measure/bench-compare.py` pairs two machines' runs on `(game, turn)`.
Results below are the five-and-five runs of `moves/wide-5x5-c2281dc.csv`.

| form | median | p95 | p99 | use |
| --- | --- | --- | --- | --- |
| rehearsal against development machine, one run each, all moves | 1.56x | 2.46x | 11.37x | not quoted: the p99 is the hypervisor |
| one run each, moves over 5x the reference excluded | 1.53x | 1.78x | 1.75x | quick look; biased low |
| five runs each, per-move means | **1.58x** | **1.91x** | **2.10x** | the figure to quote |

The one-run form understates the per-move means:

| percentile | one run, moves excluded | per-move means | understated by |
| --- | --- | --- | --- |
| median | 1.53x | 1.58x | 3% |
| p95 | 1.78x | 1.91x | 7% |
| p99 | 1.75x | 2.10x | 17% |

The bias comes from the exclusion: a dearer move lasts longer, so it is likelier
to overlap a stall. On the first pair of runs the 28 moves excluded cost a
median 0.57 ms on the reference, against 0.25 ms for the median of all the
reference run's moves, and 7 of the 28 held a blank against a 5.4% base rate.

`scripts/tests/test_bench_compare.py` pins the ratio cut, the minimum baseline
and the `--wide` columns. The rules the script follows:

| rule | value | why |
| --- | --- | --- |
| exclusion is on the ratio | 5x the reference (`--cut` changes it) | a position slow on both machines is a slow position and stays in; one that took 55 ms on one side only was descheduled |
| cut sensitivity | on one pair of runs, 3x to 5x isolates the same 28 moves; 8x isolates 23 | the cut is not chosen to fit |
| unbiased form | several runs per side, reduced per position | no position is dropped |
| per-position reduction | the mean of the position's own timings, less any above three times its minimum; statistics are taken over the means | a stall is time added, never a property of the position |
| baseline | the position's minimum | the fastest observation is the best estimate of its cost; with two runs the median is their mean, which a stall drags up |
| self-comparison | a run against itself gives 1.000x at every percentile | the test suite requires it |
| `--wide FILE` | every run in one CSV, a row per position, with each position's minimum, stalls dropped and mean | refuses runs whose racks differ |

## The raw measurements

`crates/server-game/examples/moves/` holds the per-move files:

| fact | value |
| --- | --- |
| name | `<run>-<host>.csv`, `<run>` being the summary row's `timestamp_unix_seconds`, so the two join |
| committed | `wide-5x5-c2281dc.csv` only; `.gitignore` ignores files whose name starts with a digit |
| host without a writable build directory | the binary prints the rows prefixed `MOVES`, and the script saves them |
| runs started in the same second | share a `run`; one pair does in the committed file |
| `bench-compare.py` with runs sharing no positions | refuses |
| `bench-compare.py` with runs sharing some positions | warns |

| column | holds |
| --- | --- |
| `run` | the summary row's timestamp, in whole seconds |
| `game`, `turn` | the case marker: the same position on every machine and run |
| `seat`, `blanks`, `rack_tiles` | the rack the engine was given |
| `n_moves` | the candidates the engine iterates, counted outside the timed region with `enumerate_legal_moves` |
| `wall_ms`, `cpu_ms` | elapsed and CPU time for the move |

`blanks` drives the slowest positions: [the blank effect](#what-the-machine-difference-actually-is).

## Evidence that the tail is the hypervisor

Five development-machine and five rehearsal runs of one binary, on one day,
from `moves/wide-5x5-c2281dc.csv` unless the source is named.

| observation | figure | source |
| --- | --- | --- |
| steal, every EPYC row (rehearsal and production) | 28.7 to 31.5% of capacity; development machine 0.00% | `engine_timing_results.csv` |
| ordinary moves, rehearsal against the development machine's fastest time for the same position | median 1.8x | wide file |
| rehearsal timings over 20 ms, five runs | 142: 30 are the six genuine slow positions, 112 are on positions costing under 20 ms | wide file |
| of those 112, CPU credited as wall (at least 82%) | 80, median 83x the development machine's time for the position, 348x at worst | wide file |
| of those 112, starved | 32, under a fifth of wall time as CPU | wide file |
| rehearsal timings between 36 and 45 ms | none | wide file |
| slowest development-machine move in each run | 16.7 to 17.6 ms | wide file |

A timing is flagged as a stall when it exceeds three times its position's
fastest timing across the five rehearsal runs. Each run flags a different set:

| measure | figure |
| --- | --- |
| flagged per run | 23 to 29 |
| distinct positions flagged at least once | 123 |
| expected distinct if each run drew independently | 127 |
| flagged in all five runs | none |
| flagged once, twice, three times | 115, 6, 2 |

The stalls follow scheduling: they are an independent draw per run and a
different set each time.

## What the machine difference actually is

The factor between rehearsal and the development machine is not one number.
Both machines' timings per position here are the minimum of five runs, so the
stalls are out.

| development machine cost of the position | positions | rehearsal against development machine |
| --- | --- | --- |
| 0 to 0.15 ms | 221 | 1.33x |
| 0.15 to 0.25 ms | 515 | 1.64x |
| 0.25 to 0.5 ms | 328 | 1.85x |
| 0.5 to 1 ms | 99 | 2.06x |
| 1 to 3 ms | 47 | 2.15x |
| 3 to 10 ms | 13 | 2.15x |
| 10 to 16 ms | 6 | 2.13x |

The fastest single move is 0.093 ms on the development machine and 0.080 ms on
rehearsal. A clock difference would be flat at every size; the ratio rises from
1.33x in the smallest band to above 2x. [4.2.8](4.2.8-engine-performance.md)
gives the same shape from the search's fixed and per-candidate costs.

**A straight line fits it.** For one position, in milliseconds:

| symbol | meaning |
| --- | --- |
| `laptop_ms` | what the position costs on the development machine |
| `vm_ms` | what it costs on rehearsal |
| `ratio` | `vm_ms / laptop_ms`; over 1 means rehearsal is slower |

> **vm_ms = 2.210 × laptop_ms − 0.110**
>
> equivalently **ratio = 2.210 − 0.110 / laptop_ms**

- median relative error 3.3% over the 1229 positions;
- valid for `laptop_ms` from 0.09 to 16, the range measured;
- the fitted line crosses a ratio of 1.0 at 0.091 ms (`0.110 / 1.210`), below
  the cheapest position measured, so the line holds from 0.09 ms upward and the
  smallest band measures 1.33x;
- rehearsal pays 2.21x on the excess over that constant, so the ratio rises as
  the constant is outgrown.

**The algorithmic tail shows on the development machine.** A rack with a blank
costs a median 7.0x a rack without (the minimum of five runs); 66 of 1229 racks
(5.4%) hold one, and all six positions over 10 ms do. On rehearsal the stalls
hide it. [4.2.8](4.2.8-engine-performance.md) explains what a blank does to the
search.
