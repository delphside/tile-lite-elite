## Reading an engine timing run

`cargo run --release --example engine_timing_bench [games] [edition]` plays
engine-against-engine games (default 30, `official`) through the same
`maybe_run_engine_turn` the server uses. It appends one row to
`crates/server-game/examples/engine_timing_results.csv` and writes one file of
per-move rows ([raw measurements](#the-raw-measurements)). Thirty games give
1229 moves; the benchmark script refuses fewer.

Each move is timed twice, and the run records what the reader needs to tell
work from waiting:

| column or output | holds |
| --- | --- |
| `median_ms`, `p95_ms`, `p99_ms` | wall-clock time per move |
| `cpu_median_ms`, `cpu_p99_ms` | CPU time per move, from `CLOCK_PROCESS_CPUTIME_ID` |
| `slow_moves` | moves over 20 ms |
| `slow_cpu_starved` | slow moves that used under a fifth of their wall time as CPU |
| `steal_ms`, `steal_pct_of_capacity` | time the hypervisor took across the whole run, from `/proc/stat`, as a share of wall time times cores; per run, not per move, because the kernel does not record whose time it was |
| the frequency chart | 100 buckets from zero to the slowest move, bars logarithmic, empty runs collapsed |

`host` is the hostname and is never typed; `cpu_model` and `cores` say what the
machine is.

### Rules for reading a run

1. **Compare CPU against wall first.** A `cpu_p99_ms` far below `p99_ms` means
   the move waited. The converse does not hold on a virtual machine: the guest
   kernel credits a process with time the hypervisor took, so a stalled move
   can report CPU equal to wall.
2. **Compare median and p95 between runs; read nothing into a virtual
   machine's p99.** Stalls are few (28 of 1229 on rehearsal) and the p99 sits
   inside them.
3. **A non-zero `slow_moves` is the warning.** The 20 ms threshold separates
   the two populations: the slowest laptop move in eight rows is 14 to 20 ms,
   one row has a move over 20 ms, and every rehearsal row that records the
   column has 23 to 36 (1 to 9 of them starved). The run prints a warning
   naming the statistics that survive.
4. **Compare the same position, not two distributions.** The games are seeded,
   so `(game, turn)` is the same position on every machine and in every run.

### Evidence that the tail is the hypervisor

From `crates/server-game/examples/moves/wide-5x5-c2281dc.csv`: five laptop and
five rehearsal runs of one binary, on one day.

| observation | figure |
| --- | --- |
| steal on rehearsal-class hosts, every row | 28.7 to 31.5% of capacity (laptop 0.00%) |
| ordinary moves, rehearsal against the laptop's fastest time for the same position | median 1.8x |
| rehearsal moves over 20 ms, five runs | 142, of which 32 used under a fifth of their wall time as CPU |
| the other 110, which report CPU equal to wall | median 47x the laptop's time for the same position, 348x at worst |
| rehearsal timings between 36 and 45 ms | none; the second population starts at 46 ms |
| slowest laptop move in each of the five runs | 16.7 to 17.6 ms |

A move that costs 1.8x on rehearsal in general and 47x in a stall is not
showing a property of the search.

### The positions flagged are a different set each run

Flag a timing as a stall when it exceeds three times that position's fastest
timing across the five rehearsal runs. If the stalls were properties of
positions, every run would flag the same ones.

| measure | figure |
| --- | --- |
| flagged per run | 23 to 29 |
| distinct positions flagged at least once | 123 |
| expected distinct if each run drew independently | 127 |
| flagged in all five runs | none |
| flagged once, twice, three times | 115, 6, 2 |

The set behaves like an independent draw, which is what scheduling is.

## Quoting a comparison

`scripts/measure/bench-compare.py` pairs two machines' runs on `(game, turn)`.
Results below are the five-and-five runs of the file above.

| form | median | p95 | p99 | use |
| --- | --- | --- | --- | --- |
| rehearsal against laptop, one run each, all moves | 1.56x | 2.46x | 11.37x | never: the p99 is the hypervisor |
| one run each, moves over 5x the reference excluded | 1.53x | 1.78x | 1.75x | quick look only; biased low |
| five runs each, per-move means | **1.58x** | **1.91x** | **2.10x** | the figure to quote |

Rules the script follows; `scripts/tests/test_bench_compare.py` pins the ratio
cut, the minimum baseline and the `--wide` columns:

- **The exclusion is on the ratio, never on an absolute time.** A position slow
  on both machines is a slow position and stays in; an ordinary one that took
  55 ms on one side only was descheduled and comes out. The cut is 5x
  (`--cut` changes it); on one pair of runs any cut from 3x to 5x isolates the
  same 28 moves and 8x isolates 23.
- **Excluding whole moves biases the answer.** A dearer move lasts longer, so
  it is likelier to overlap a stall. The moves the single-run form drops cost a
  median 0.57 ms on the reference against 0.26 ms for all moves, and 7 of 28
  held a blank against a 5.4% base rate. It understates the factor by 3% at the
  median, 7% at the p95 and 17% at the p99.
- **The unbiased form is several runs per side, reduced per position.** Each
  position becomes the mean of its own timings, discarding any above three
  times its minimum; the statistics are taken over those means. No position is
  dropped.
- **The baseline is the minimum, not the median.** A stall only adds time, so
  the fastest observation is the best estimate of the position's cost. With two
  runs the median is their mean, which a stall drags up; the test suite compares
  a run with itself and requires 1.000x at every percentile.
- `--wide FILE` writes every run into one CSV, a row per position, with each
  position's minimum, stalls dropped and mean. It refuses runs whose racks
  differ.

## What the machine difference actually is

The factor between rehearsal and the laptop is not one number. Both machines'
timings per position are the minimum of five runs, so the hypervisor's stalls
are out. The laptop is an AMD Ryzen 5 7235HS (8 threads) and rehearsal an AMD
EPYC 7551 (2 cores), as each row's `cpu_model` and `cores` record.

| laptop cost of the position | positions | rehearsal against laptop |
| --- | --- | --- |
| 0 to 0.15 ms | 221 | 1.33x |
| 0.15 to 0.25 ms | 515 | 1.64x |
| 0.25 to 0.5 ms | 328 | 1.85x |
| 0.5 to 1 ms | 99 | 2.06x |
| 1 to 3 ms | 47 | 2.15x |
| 3 to 10 ms | 13 | 2.15x |

The fastest single move is 0.093 ms on the laptop and 0.080 ms on rehearsal.
A clock difference would be flat at every size; this is 1.0 at the smallest
and plateaus above 2x, the pattern of a memory-bound search, and the benchmark
does not measure cache misses. [4.2.8](4.2.8-engine-performance.md) gives the
same shape from the search's fixed and per-candidate costs.

**A straight line fits it.** For one position, in milliseconds:

| symbol | meaning |
| --- | --- |
| `laptop_ms` | what the position costs on the laptop |
| `vm_ms` | what it costs on rehearsal |
| `ratio` | `vm_ms / laptop_ms`; above 1 means rehearsal is slower |

> **vm_ms = 2.210 × laptop_ms − 0.110**
>
> equivalently **ratio = 2.210 − 0.110 / laptop_ms**

- median relative error 3.3% over the 1229 positions;
- valid for `laptop_ms` from 0.09 to 16, the range measured;
- the penalty is zero at 0.091 ms (`0.110 / 1.210`), the point where the
  machines meet, and rehearsal pays 2.21x on the excess above it, so the ratio
  rises as that constant is outgrown.

**The algorithmic tail is readable only on a machine nobody shares.** On the
laptop, a rack with a blank costs a median 7.0x a rack without (the minimum of
five runs); 66 of 1229 racks (5.4%) hold one, and all six positions over 10 ms
do. A blank multiplies the search by the letters it could stand for. On
rehearsal the stalls hide it.

## Benchmarking a performance change

A performance change or a new engine is benchmarked on rehearsal with
`scripts/measure/bench-rehearsal.sh [games] [edition]` (default 30 games,
`official`). Pairing a rehearsal run with a laptop run from a different commit
would mix a machine difference with a code change, so one binary serves both.

| step | actor | what happens |
| --- | --- | --- |
| 1 | Claude | builds the benchmark once; the row's commit is `HEAD`, with `-dirty` when anything but the results CSV and `moves/` has changed |
| 2 | Claude | runs it on the development machine as the reference |
| 3 | Claude | copies the binary to rehearsal over ssh, runs it there and deletes it |
| 4 | the script | replaces the row's `unknown` commit (the host has no `git`), appends it to the results CSV and saves the per-move rows the binary printed |
| 5 | the script | prints rehearsal's previous row beside the new one, then compares with the reference, one run each |
| 6 | Claude | runs `bench-compare.py` over several runs a side for the figure to quote ([quoting a comparison](#quoting-a-comparison)) |

- It is a check, not a gate: it exits 0 whatever the figures, so a person
  decides.
- It exits 1 for fewer than 30 games, and when the host prints no `row:` line.
- A run on rehearsal takes 2.6 to 4.4 s; on the laptop 0.6 to 1.3 s.
- **Production's run is the owner's.** He copies the binary built here, runs
  `engine_timing_bench 30 official` on the host and gives Claude the `row:`
  line, which Claude appends with the commit filled in.
- The development machine needs none of the cleaning: steal is 0.00% in every
  row, and the figures read as they stand.

## The raw measurements

`crates/server-game/examples/moves/` holds one file per run,
`<run>-<host>.csv`, where `<run>` is the summary row's
`timestamp_unix_seconds`, so the two join. Per-move files are untracked by
`.gitignore`; only `wide-5x5-c2281dc.csv` is committed. On a host without a
writable build directory the binary prints the rows prefixed `MOVES` instead,
and the script saves them.

| column | holds |
| --- | --- |
| `run` | the summary row's timestamp, in whole seconds |
| `game`, `turn` | the case marker: the same position on every machine and run |
| `seat`, `blanks`, `rack_tiles` | the rack the engine was given |
| `n_moves` | the candidates the engine iterates, counted outside the timed region with `enumerate_legal_moves` |
| `wall_ms`, `cpu_ms` | elapsed and CPU time for the move |

- `blanks` is the column that matters; see the blank effect above.
- Two runs started in the same second share a `run`; one pair does in the
  committed file.
- `bench-compare.py` refuses runs that share no positions and warns when only
  some are shared.
