## Terms in this page

| Term | Meaning |
| --- | --- |
| development machine | AMD Ryzen 5 7235HS, 8 logical CPUs (the `cores` column), no other tenant; builds the benchmark and runs the reference |
| rehearsal, production | the same hardware: AMD EPYC 7551 virtual machines of 2 logical CPUs, whose physical CPU the hypervisor shares with other tenants |
| run | one execution of the benchmark: one row in the results CSV and one per-move file |
| position | one `(game, turn)`: the games are seeded, so it is the same board and rack in every run on every machine |
| edition | the rule set and word list a game plays under; the names are `VariantRules::EDITION_NAMES` |
| moves directory | `crates/server-game/examples/moves/` in the tree the binary was built from; the path is compiled into the binary |
| reference | the development machine's run or runs, which a comparison divides by |
| subject | the run or runs on rehearsal or production, which a comparison divides |
| REF1, SUB1 and so on | in commands, the per-move files `<run>-<host>.csv` of the reference and subject runs ([the raw measurements](#the-raw-measurements)) |
| stall | time a move spent waiting because the hypervisor gave the physical CPU to another tenant |
| stall test, several runs a side | `bench-compare.py` flags a timing over 3x its position's fastest across the runs given |
| stall test, one run each | `bench-compare.py` flags a subject timing over 5x the reference's; `--cut` changes the 5x |
| genuine move | a move whose own cost is what the timing shows, with no stall in it |
| tail | the slowest moves of a run, which the p99 reads |

## Benchmarking a performance change

Claude benchmarks a performance change or a new engine on rehearsal:

```bash
scripts/measure/bench-rehearsal.sh [games] [edition]
```

The arguments are the benchmark's ([the defaults](#reading-an-engine-timing-run)).
One binary serves the reference run and the rehearsal run, so only the machine
differs between them: the script's own comparison gives the machine factor, not
the effect of a change. [Measuring a change](#measuring-a-change) gives the
effect.

| Step | Actor | What happens |
| --- | --- | --- |
| 1 | Claude | runs `bench-rehearsal.sh` |
| 2 | the script | builds the benchmark once; the row's commit is `HEAD`, with `-dirty` when anything but the results CSV and the moves directory has changed |
| 3 | the script | runs it on the development machine as the reference, which appends a development-machine row to the results CSV |
| 4 | the script | copies the binary to rehearsal over ssh, runs it there and deletes it |
| 5 | the script | replaces the row's `unknown` commit (the host has no `git`), appends it to the results CSV and saves the per-move rows the binary printed |
| 6 | the script | prints rehearsal's previous row beside the new one, then compares with the reference, one run each |
| 7 | Claude | repeats steps 1 to 6 until there are five runs a side, then compares the two sets for the figure to quote ([quoting a comparison](#quoting-a-comparison)) |

```bash
scripts/measure/bench-compare.py REF1.csv REF2.csv REF3.csv REF4.csv REF5.csv -- \
  SUB1.csv SUB2.csv SUB3.csv SUB4.csv SUB5.csv
```

The script prints the rehearsal run's per-move file and discards the reference
run's output, so it never names the reference file. After each run,
`ls -t crates/server-game/examples/moves/` lists the files newest first: the
first is the rehearsal run's, the second the reference run's, whose name holds
the development machine's hostname.

The script exits:

| Exit | When |
| --- | --- |
| 0 | every completed run, whatever the figures: a check, not a gate, so a person decides |
| 1 | fewer than 30 games asked for, or the host prints no `row:` line |
| other non-zero | a failed build, scp or ssh (`set -e`) |

### Measuring a change

Claude runs the script five times on the commit before the change and five
times on the commit after, checking each out in turn, with the same arguments
throughout. It compares the rehearsal files, before first:

```bash
scripts/measure/bench-compare.py \
  BEFORE1.csv BEFORE2.csv BEFORE3.csv BEFORE4.csv BEFORE5.csv -- \
  AFTER1.csv AFTER2.csv AFTER3.csv AFTER4.csv AFTER5.csv
```

The figure is the `ratio, per-move means` line at the median and p95: 1.00x is
no change and under 1.00x is faster. Both sides ran on rehearsal, so it holds
no machine factor, and the reference files are not used. The line
`paired on (game, turn)` counts the positions it used. The same engine, split
two runs against three, read 1.077x at the p95
([design notes](#design-notes-on-the-comparison)), so a difference of that size
is within the method's noise.

### Production's run

The script reaches rehearsal only. Production's run is the owner's:

1. **Claude** builds the binary and runs it on the development machine as the
   reference. The run prints its per-move file's name:

   ```bash
   cargo build --release --example engine_timing_bench -p server-game
   target/release/examples/engine_timing_bench 30 official
   ```

2. **owner** copies `target/release/examples/engine_timing_bench` to the
   production host and runs it as an unprivileged user. An unprivileged user
   cannot create the moves directory's compiled-in path on that host, so the
   binary prints the per-move rows as `MOVES` lines; a privileged user can
   create it, and the rows would go to a file on the host instead:

   ```bash
   ./engine_timing_bench 30 official
   ```

3. **owner** hands back the output (the `row:` line and the `MOVES` lines), then
   deletes the binary and any file it wrote.
4. **Claude** replaces the row's `unknown` commit with the one the binary was
   built from (`HEAD`, with `-dirty` when anything but the results CSV and the
   moves directory has changed) and appends the row to the results CSV. It
   saves the `MOVES` lines, prefix removed, as `<run>-<host>.csv` in the moves
   directory ([the raw measurements](#the-raw-measurements)).
5. **Claude** repeats steps 1 to 4 until there are five runs a side, then runs
   the `bench-compare.py` command above, with the reference runs' files as REF1
   to REF5 and the production runs' as SUB1 to SUB5.

## Reading an engine timing run

```bash
cargo run --release -p server-game --example engine_timing_bench [games] [edition]
```

The benchmark plays engine-against-engine games through the same
`maybe_run_engine_turn` the server uses:

- `games` defaults to 30; thirty games of `official` give 1229 moves;
- `edition` defaults to `official`;
- it appends one row to
  `crates/server-game/examples/engine_timing_results.csv`;
- it writes one file of per-move rows ([raw measurements](#the-raw-measurements)).

It takes two clocks for each move, wall and CPU, which tell work from waiting.
The row holds:

| Column or output | Holds |
| --- | --- |
| `host`, `cpu_model`, `cores` | the hostname the binary reads, what the machine is, and its logical CPUs |
| `median_ms`, `p95_ms`, `p99_ms` | wall-clock time per move |
| `cpu_median_ms`, `cpu_p99_ms` | CPU time per move, from `CLOCK_PROCESS_CPUTIME_ID` |
| `slow_moves` | moves over 20 ms |
| `slow_cpu_starved` | slow moves that used under a fifth of their wall time as CPU |
| `steal_ms`, `steal_pct_of_capacity` | time the hypervisor took across the whole run, from `/proc/stat`, as a share of wall time times cores; per run, because the kernel records no owner for stolen time |
| the frequency chart | 100 buckets from zero to the slowest move, bars logarithmic, empty runs collapsed |

### Rules for reading a run

1. **Compare median and p95 between runs.** A virtual machine's p99 sits inside
   its stalls, which are 23 to 29 of 1229 timings per run
   ([evidence](#evidence-that-the-tail-is-the-hypervisor)).
2. **Read `slow_moves` against the machine.** The 20 ms threshold separates
   genuine moves from stalls on the development machine only. The timings are
   from the five-and-five runs in `moves/wide-5x5-c2281dc.csv`; the counts are
   from the results CSV:

   | Machine | Genuine moves reach | Stalls seen | `slow_moves` means |
   | --- | --- | --- | --- |
   | development machine | 17.6 ms | none over 20 ms | a move over 20 ms, to inspect in the per-move file |
   | rehearsal | 35.9 ms | 21.7 and 28.2 ms, then 45.6 ms and over | always non-zero (23 to 36 in five rows) because six positions cost over 20 ms; compare `slow_cpu_starved` (1 to 4 in those rows) and the median |
   | production | not measured per move | not measured per move | as rehearsal (its one row: 28, of which 9 starved) |

   Of the development machine's rows in the results CSV, seven record
   `slow_moves`: six hold 0 and one holds 1, a move of 20.05 ms whose per-move
   file is not committed, so it cannot be classed as genuine or a stall. Rows
   from before `slow_moves` existed reach 21.88 ms (`official`) and 42.48 ms
   (`german`, which has more words).

   The run prints a warning whenever `slow_moves` is above zero, naming the
   statistics that survive. On rehearsal and production read it with the table.
   Then compare `cpu_p99_ms` with `p99_ms`:

   | `cpu_p99_ms` against `p99_ms` | Shows |
   | --- | --- |
   | far lower | the move waited |
   | equal | nothing on a virtual machine, because the guest kernel credits a process with time the hypervisor took |

3. **Compare position against position.** The games are seeded, so
   `(game, turn)` names one position in every run on every machine.

## Quoting a comparison

`scripts/measure/bench-compare.py` pairs two machines' runs on `(game, turn)`.
The results in this section are the five-and-five runs of
`moves/wide-5x5-c2281dc.csv`, built from commit c2281dc (app 0.7.1).

| Kind of comparison | Median | p95 | p99 | Use |
| --- | --- | --- | --- | --- |
| rehearsal against development machine, one run each, all moves | 1.56x | 2.46x | 11.37x | not quoted: the p99 is the hypervisor |
| one run each, moves over 5x the reference excluded | 1.53x | 1.78x | 1.75x | quick look; biased low |
| five runs each, per-move means | **1.58x** | **1.91x** | **2.10x** | the figure to quote |
| understated by the one-run kind | 3% | 7% | 17% | |

The bias comes from the exclusion: a dearer move lasts longer, so it is likelier
to overlap a stall. On the first pair of runs:

| Moves | Median time on the reference | Holding a blank |
| --- | --- | --- |
| the 28 excluded | 0.57 ms | 7 (25%) |
| all 1229 | 0.25 ms | 66 (5.4%) |

### Rules bench-compare.py follows

`scripts/tests/test_bench_compare.py` pins that the exclusion is on the ratio,
not on an absolute time (the 5x value itself is not pinned), the minimum
baseline and the `--wide` columns.

| Rule | Value | Why |
| --- | --- | --- |
| exclusion is on the ratio | 5x the reference | a position slow on both machines is a slow position and stays in; one slow on a single machine was descheduled |
| cut sensitivity | on one pair of runs, 3x to 5x isolates the same 28 moves; 8x isolates 23 | the result holds from 3x to 5x |
| unbiased kind | several runs per side, reduced per position | every position stays in |
| per-position reduction | the mean of the position's own timings, less the stalls; statistics are taken over the means | a stall adds time to a position without changing its cost |
| baseline | the position's minimum | the fastest observation is the best estimate of its cost; a stall only adds time ([design notes](#design-notes-on-the-comparison)) |
| self-comparison | the same positions with stalls at different places in each run, split two runs against three, give 1.000x at every percentile | the test suite requires it |
| `--wide FILE` | writes every run into one CSV, a row per position | the runs can be analysed side by side |

### The wide file

| `--wide` column | Holds |
| --- | --- |
| `game`, `turn`, `seat`, `blanks`, `rack_tiles` | the position, written once |
| `ref_wall_<run>`, `ref_cpu_<run>`, `sub_wall_<run>`, `sub_cpu_<run>` | each run's timings, named by its `run` |
| `ref_runs`, `ref_min_wall_ms`, `ref_stalls_dropped`, `ref_mean_wall_ms`, `ref_mean_cpu_ms`, and the same for `sub_` | per side: runs, the position's fastest wall time, timings discarded as stalls, and the means of what survived |
| `ratio_mean_wall` | subject mean over reference mean |

### Runs that disagree

What `bench-compare.py` does with runs that disagree:

| Case | Result |
| --- | --- |
| no position in common | refuses (exit 1) |
| the first reference and first subject run differ in positions | warns, with the count |
| a later run lacks positions | no warning: the comparison is cut to the positions every run has |
| `--wide` on runs whose racks differ | refuses (exit 1) |

## The raw measurements

The moves directory holds the per-move files:

| Fact | Value |
| --- | --- |
| name | `<run>-<host>.csv`, `<run>` being the summary row's `timestamp_unix_seconds`, so the two join; the host's other characters become `-` |
| committed | `wide-5x5-c2281dc.csv` only; `.gitignore` ignores files whose name starts with a digit |
| host that cannot create the moves directory | the binary prints the rows prefixed `MOVES`, and the script saves them |
| runs that finish in the same second | share a `run`, so on one host the later file overwrites the earlier; one pair does in the committed file |

| Column | Holds |
| --- | --- |
| `run` | the summary row's timestamp, in whole seconds |
| `game`, `turn` | the position: the same on every machine and run |
| `seat`, `blanks`, `rack_tiles` | the rack the engine was given |
| `n_moves` | the candidates the engine iterates, counted outside the timed region with `enumerate_legal_moves` |
| `wall_ms`, `cpu_ms` | elapsed and CPU time for the move |

## Evidence that the tail is the hypervisor

Five development-machine and five rehearsal runs of one binary, on one day. All
rows are from `moves/wide-5x5-c2281dc.csv` except the first, which is from
`engine_timing_results.csv`.

| Observation | Figure |
| --- | --- |
| steal, every EPYC row that records it (rehearsal and production) | 28.7 to 31.5% of capacity; development machine 0.00% |
| ordinary moves, rehearsal against the development machine's fastest time for the same position | median 1.8x |
| rehearsal timings over 20 ms, five runs | 142: 30 are the six genuine slow positions, 112 are on positions costing under 20 ms |
| of those 112, CPU credited as wall (at least 82%) | 80, median 83x the development machine's time for the position, 348x at worst |
| of those 112, starved (under a fifth of wall time as CPU) | 32 over the five runs, 4 to 8 a run |
| rehearsal timings between 36 and 45 ms | none |
| development machine's slowest move, per-run maximum | 16.7 to 17.6 ms |
| development machine's slowest move, minimum of five runs | 16.4 ms |

By the several-run [stall test](#terms-in-this-page), each run flags a different
set:

| Measure | Figure |
| --- | --- |
| flagged per run | 23 to 29 |
| distinct positions flagged at least once | 123 |
| expected distinct if each run drew independently | 127 |
| flagged in all five runs | none |
| flagged once, twice, three times | 115, 6, 2 |

The stalls follow scheduling: they are an independent draw per run.

## What the machine difference actually is

The factor between rehearsal and the development machine rises with the
position's cost. Both machines' timings per position here are the minimum of
the five runs in `moves/wide-5x5-c2281dc.csv`, so the stalls are out.

| Development machine cost of the position | Positions | Rehearsal against development machine |
| --- | --- | --- |
| 0 to 0.15 ms | 221 | 1.33x |
| 0.15 to 0.25 ms | 515 | 1.64x |
| 0.25 to 0.5 ms | 328 | 1.85x |
| 0.5 to 1 ms | 99 | 2.06x |
| 1 to 3 ms | 47 | 2.15x |
| 3 to 10 ms | 13 | 2.15x |
| 10 to 16 ms | 6 | 2.13x |

The fastest single move is 0.093 ms on the development machine and 0.080 ms on
rehearsal. A clock difference would be flat at every size; here the ratio rises
from 1.33x to above 2x. The cause is the search's fixed and per-candidate costs:
[4.2.8](4.2.8-engine-performance.md#what-a-move-costs-in-terms-of-the-search-itself).

**A straight line fits it.** For one position, in milliseconds (the names are
the equation's own, which 4.2.8 uses):

| Symbol | Meaning |
| --- | --- |
| `laptop_ms` | what the position costs on the development machine |
| `vm_ms` | what it costs on rehearsal |
| `ratio` | `vm_ms / laptop_ms`; over 1 means rehearsal is slower |

> **vm_ms = 2.210 × laptop_ms − 0.110**
>
> equivalently **ratio = 2.210 − 0.110 / laptop_ms**

- median relative error 3.3% over the 1229 positions;
- measured for `laptop_ms` from 0.09 to 16;
- the ratio is 1.0 at 0.091 ms (`0.110 / 1.210`), just under the cheapest
  position; the smallest band measures 1.33x.

Racks with a blank cost more, by the same minimum-of-five timings:

| Fact | Value |
| --- | --- |
| racks holding a blank | 66 of 1229 (5.4%) |
| cost against a rack without, median | 7.0x on the development machine, 9.1x on rehearsal |
| positions over 10 ms on the development machine | 6, all holding a blank |

Why a blank costs this is in
[4.2.8](4.2.8-engine-performance.md#what-a-move-costs-in-terms-of-the-search-itself).

## Design notes on the comparison

- The baseline is the minimum, not the median: with two runs the median is their
  mean, so a stall drags it up and escapes rejection. Comparing five runs of the
  same engine two against three gave 0.390x at the p95 on the median baseline,
  and 1.077x on the minimum, where 1.0 is correct.
