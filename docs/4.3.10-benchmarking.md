## Terms in this page

| Term | Meaning |
| --- | --- |
| development machine | AMD Ryzen 5 7235HS, 8 logical CPUs (the `cores` column), no other tenant; builds the benchmark |
| rehearsal, production | the same hardware: AMD EPYC 7551 virtual machines of 2 logical CPUs, whose physical CPU the hypervisor shares with other tenants |
| moves directory | `crates/server-game/examples/moves/` in the tree the binary was built from, its path compiled into the binary |
| results CSV | `crates/server-game/examples/engine_timing_results.csv`, tracked: one summary row per run |
| per-move file | `<run>-<host>.csv` in the moves directory: one row per move of a run ([the raw measurements](#the-raw-measurements)) |
| run | one execution of the benchmark: one row in the results CSV and one per-move file |
| position | one `(game, turn)`: the same board and rack in every run on every machine, because the games are seeded |
| edition | the rule set and word list a game plays under, named in `VariantRules::EDITION_NAMES` |
| reference | the runs a comparison divides by: the development machine's, or the before runs when measuring a change |
| subject | the runs it divides: rehearsal's or production's, or the after runs |
| machine factor | the subject's figure divided by the reference's for the same binary: how much slower rehearsal or production is than the development machine |
| REF1.csv, SUB1.csv, BEFORE1.csv, AFTER1.csv and so on | in commands, placeholders for the paths of per-move files in the moves directory: the reference, subject, before and after runs' ([the raw measurements](#the-raw-measurements)) |
| stall | time a move spent waiting because the hypervisor gave the physical CPU to another tenant |
| stall test, several runs a side | a timing over 3x its position's fastest across its own side's runs, which `bench-compare.py` flags |
| stall test, one run each | a subject timing over 5x the reference's (`--cut` sets another multiple), which `bench-compare.py` flags |
| genuine move | a move whose own cost is what the timing shows, with no stall in it |
| tail | the slowest moves of a run, which the p99 reads |

## Benchmarking a performance change

The script runs one binary on the development machine and on rehearsal:

```bash
scripts/measure/bench-rehearsal.sh [games] [edition]
```

The arguments are the benchmark's
([the defaults](#reading-an-engine-timing-run)). What to run depends on the
purpose:

| Purpose | What to run |
| --- | --- |
| a release's check ([4.3.3 §1.5.2](4.3.3-testing-ci-and-release.md#152-technical-tests-on-rehearsal)) | the script once, then read the two rows and its comparison, and keep the rows ([keeping the results rows](#keeping-the-results-rows)) |
| [the machine factor](#the-machine-factor) | the script five times and a comparison |
| the effect of a change | [Measuring a change](#measuring-a-change) |

### The machine factor

1. **Claude** runs `bench-rehearsal.sh` in `projectdev`
   ([4.3.2](4.3.2-development.md#two-worktrees)), on the commit to measure.
2. **The script** builds the benchmark once, so one binary serves both runs.
   The row's commit is `HEAD`'s short ID (`git rev-parse --short HEAD`), with
   `-dirty` when anything but the results CSV and the moves directory has
   changed.
3. **The script** runs it on the development machine as the reference. The
   binary appends a development-machine row to the results CSV and writes its
   per-move file, named with the development machine's hostname.
4. **The script** copies the binary to rehearsal over ssh, runs it there and
   deletes it.
5. **The script** replaces the row's `unknown` commit (the host has no `git`),
   appends the row to the results CSV and saves the per-move rows the binary
   printed.
6. **The script** prints rehearsal's previous row beside the new one, then
   compares with the reference, one run each. It discards the reference run's
   output, so it names only the rehearsal run's per-move file.
7. **Claude** lists the two files, newest first: the rehearsal run's, then the
   reference run's.

   ```bash
   ls -t crates/server-game/examples/moves/
   ```

8. **Claude** repeats steps 1 to 7 until there are five runs a side, keeps the
   10 rows ([keeping the results rows](#keeping-the-results-rows)) and compares
   the two sets for the figure to quote
   ([quoting a comparison](#quoting-a-comparison)):

   ```bash
   scripts/measure/bench-compare.py REF1.csv REF2.csv REF3.csv REF4.csv REF5.csv -- \
     SUB1.csv SUB2.csv SUB3.csv SUB4.csv SUB5.csv
   ```

### Exit status of bench-rehearsal.sh

| Exit | When |
| --- | --- |
| 0 | Every completed run, whatever the figures: Claude, who runs it, judges them. |
| 1 | fewer than 30 games asked for, or the host prints no `row:` line |
| other non-zero | a failed build, scp or ssh (`set -e`); an unknown edition, which panics the reference run (exit 101) |

### Keeping the results rows

Each run appends its rows to the results CSV, which the script leaves
uncommitted, and `git checkout` refuses when the two commits' CSVs differ.
**Whoever runs the benchmark** (Claude, or the owner for production's rows)
does this at every checkout, including the first:

1. stash the rows:

   ```bash
   git stash push -m bench-rows crates/server-game/examples/engine_timing_results.csv
   ```

2. check out the commit:

   ```bash
   git checkout <commit>
   ```

3. take the rows back, unless the push reported no local changes, when the pop
   would take another entry:

   ```bash
   git stash pop
   ```

4. if the pop reports a conflict, because the two CSVs differ in rows, keep
   the rows of both sides, delete the conflict markers, then run these; a
   clean pop needs nothing more

   ```bash
   git reset -q -- crates/server-game/examples/engine_timing_results.csv
   git stash drop
   ```

After the last run, check out the project branch by the same steps and commit
the CSV there.

### Measuring a change

Claude measures in `projectdev`, never the owner's `main` checkout, with the
same arguments throughout:

1. check out the commit before the change
   ([keeping the results rows](#keeping-the-results-rows)) and run the script
   five times
2. the same for the commit after the change
3. compare the rehearsal runs' files that step 7 of
   [the machine factor](#the-machine-factor) lists, before first:

   ```bash
   scripts/measure/bench-compare.py \
     BEFORE1.csv BEFORE2.csv BEFORE3.csv BEFORE4.csv BEFORE5.csv -- \
     AFTER1.csv AFTER2.csv AFTER3.csv AFTER4.csv AFTER5.csv
   ```

4. commit the rows on the project branch
   ([keeping the results rows](#keeping-the-results-rows))

Reading the comparison:

- the figure is the `ratio, per-move means` line at the median and p95: 1.00x is
  no change and under 1.00x is faster
- both sides ran on rehearsal, so it holds no machine factor
- `paired on (game, turn)` counts the positions it used
- the noise: five rehearsal runs of one engine, split two against three, read
  1.034x at the median and 1.077x at the p95
  ([design notes](#design-notes-on-the-comparison)), so a difference under 4%
  at the median and 8% at the p95 is noise

### Production's run

The script reaches rehearsal only. Production's run is the owner's:

1. **Claude** builds the binary in `projectdev`, on the commit to measure, and
   runs it on the development machine as the reference. The run appends a row to
   the results CSV there and prints its per-move file's name:

   ```bash
   cargo build --release --example engine_timing_bench -p server-game
   target/release/examples/engine_timing_bench 30 official
   ```

2. **The owner** copies `target/release/examples/engine_timing_bench` to the
   production host and runs it as an unprivileged user, so the per-move rows
   print as `MOVES` lines; the summary row prints as a `row:` line on every
   run:

   ```bash
   ./engine_timing_bench 30 official
   ```

3. **The owner** records the run in `projectdev`:
   1. copies the `row:` line, prefix removed
   2. replaces its `unknown` commit with the commit's short ID, as step 2 of
      [the machine factor](#the-machine-factor) says
   3. appends it to the results CSV, kept as
      [keeping the results rows](#keeping-the-results-rows) says
   4. saves the `MOVES` lines, prefix removed, as `<run>-<host>.csv` in that
      tree's moves directory ([the raw measurements](#the-raw-measurements))
4. **The owner** deletes the binary and any file it wrote on the host.
5. **Claude** checks that the CSV's last row carries the commit and names the
   production host, and that its per-move file is there.
6. **Claude** repeats steps 1 to 5 until there are five runs a side, then runs
   [the `bench-compare.py` command](#the-machine-factor), with
   the reference runs' files as REF1.csv to REF5.csv and the production runs'
   as SUB1.csv to SUB5.csv.

## Reading an engine timing run

```bash
cargo run --release -p server-game --example engine_timing_bench [games] [edition]
```

The benchmark plays engine-against-engine games through the same
`maybe_run_engine_turn` the server uses:

- `games` defaults to 30; 30 games of `official` give 1229 moves
- `edition` defaults to `official`
- it appends one row to the results CSV
- it writes one file of per-move rows
  ([raw measurements](#the-raw-measurements))

It takes two clocks for each move, wall and CPU, which tell work from waiting.
The row and the chart the run prints hold:

| Column or output | Holds |
| --- | --- |
| `host`, `cpu_model`, `cores` | the hostname the binary reads, what the machine is and its logical CPUs |
| `median_ms`, `p95_ms`, `p99_ms` | wall-clock time per move |
| `cpu_median_ms`, `cpu_p99_ms` | CPU time per move, from `CLOCK_PROCESS_CPUTIME_ID` |
| `slow_moves` | moves over 20 ms |
| `slow_cpu_starved` | slow moves that used under a fifth of their wall time as CPU |
| `steal_ms`, `steal_pct_of_capacity` | time the hypervisor took across the whole run, from `/proc/stat`, as a share of wall time times cores; per run, because the kernel records no owner for stolen time |
| the frequency chart | 100 buckets from zero to the slowest move, bars logarithmic, consecutive empty buckets collapsed |

### Rules for reading a run

1. **Compare median and p95 between runs.** A virtual machine's p99 sits inside
   its stalls, which are 23 to 29 of 1229 timings per run
   ([evidence](#evidence-that-the-tail-is-the-hypervisor)).
2. **Read `slow_moves` against the machine.** The 20 ms threshold separates
   genuine moves from stalls on the development machine only. For the `official`
   edition, with timings from the five-and-five runs in
   `moves/wide-5x5-c2281dc.csv` and counts from the results CSV:

   | Machine | Genuine moves reach | Stalls seen | `slow_moves` means |
   | --- | --- | --- | --- |
   | development machine | 17.6 ms | none over 20 ms in those runs | a move over 20 ms, to inspect in the per-move file |
   | rehearsal | 35.9 ms | from 28.2 ms | It is always non-zero (23 to 36 in six rows), because six positions cost over 20 ms; compare `slow_cpu_starved` (1 to 4 in those rows) and the median. |
   | production | not measured per move | not measured per move | as rehearsal (its one row that records `slow_moves`: 28, of which 9 starved) |

   The run prints a warning whenever `slow_moves` is above zero, naming the
   statistics that survive. On rehearsal and production, read it with this
   table, then compare `cpu_p99_ms` with `p99_ms`
   ([classing a slow timing](#classing-a-slow-timing)).
3. **Compare position against position**, with `bench-compare.py`
   ([quoting a comparison](#quoting-a-comparison)).

### Classing a slow timing

The rehearsal timings are from `moves/wide-5x5-c2281dc.csv`. A position is
*slow* when its fastest rehearsal run is over 20 ms, which six are. A rehearsal
timing is classed by the several-run [stall test](#terms-in-this-page).
Positions are written `(game, turn)`:

| Rehearsal timing over 20 ms | Read as | Seen |
| --- | --- | --- |
| over 3x its position's fastest | stall | from 28.2 ms at `(28, 2)`, whose fastest is 8.5 ms, then 45.6 ms and over |
| within 3x, on a slow position, over 20 ms above its fastest | stall, missed by the 3x test, so it stays in `bench-compare.py`'s per-position mean | nine, 67.5 to 93.3 ms (42 to 57 ms above the fastest), at `(0, 0)`, `(20, 3)`, `(21, 7)` and `(21, 9)` |
| any other within 3x | genuine | 21.7 ms at `(27, 0)` up to 35.9 ms at `(21, 9)`, including 22.2 to 31.5 ms non-fastest slow-position timings |

Development-machine timings over 20 ms in the results CSV, which have no
committed per-move file to class them:

- 20.05 ms (`official`)
- 21.88 ms (`official`; it predates `slow_moves`)
- 42.48 ms (`german`, a larger word list)

A run's `cpu_p99_ms` against its `p99_ms` shows:

| `cpu_p99_ms` against `p99_ms` | Shows |
| --- | --- |
| under a fifth | the move waited |
| within 15%, on the development machine (every row that records it) | the move's own work, with nothing waited |
| within 7%, on rehearsal and production (every row that records it) | nothing, because the guest kernel credits a process with time the hypervisor took |

## Quoting a comparison

`scripts/measure/bench-compare.py` pairs two machines' runs on `(game, turn)`.
The results in this section are the five-and-five runs of
`moves/wide-5x5-c2281dc.csv`, built from commit `c2281dc` (app 0.7.1).

| Kind of comparison | Median | p95 | p99 | Use |
| --- | --- | --- | --- | --- |
| rehearsal against development machine, one run each, all moves | 1.56x | 2.46x | 11.37x | Not quoted: the p99 is the hypervisor. |
| one run each, moves over 5x the reference excluded | 1.53x | 1.78x | 1.75x | quick look; biased low |
| five runs each, per-move means | **1.58x** | **1.91x** | **2.10x** | the figure to quote |
| understated by the one-run kind | 3% | 7% | 17% | |

The bias comes from the exclusion: a dearer move lasts longer, so it is likelier
to overlap a stall. On the first pair of runs:

| Moves | Median time on the reference | Holding a blank |
| --- | --- | --- |
| the 28 excluded | 0.57 ms | 7 (25%) |
| all 1229 | 0.25 ms | 66 (5.4%) |

### Rules bench-compare.py follows

| Rule | Value | Why | Pinned by test |
| --- | --- | --- | --- |
| exclusion is on the ratio | 5x the reference | A position slow on both machines is a costly position and stays in; one slow on a single machine was descheduled. | the ratio, yes; the 5x value, no |
| several runs a side | reduced per position | every position stays in | yes |
| per-position reduction | the mean of the position's own timings, less the stalls, with statistics taken over the means | A stall adds time to a position without changing its cost. | yes |
| baseline | the position's minimum | The fastest observation is the best estimate of its cost; a stall only adds time ([design notes](#design-notes-on-the-comparison)). | yes |
| self-comparison | 1.000x at every percentile on the test's synthetic data (the same positions with stalls at different places in each run, split two runs against three) | The same input must compare as itself. | yes |
| `--wide FILE` | writes every run into one CSV, a row per position | for analysing the runs side by side | the columns, yes |

On the first pair of runs, 3x, 4x and 5x each isolate the same 28 moves and 8x
isolates 23, so 5x is the widest cut that still isolates all 28.

### The wide file

| `--wide` column | Holds |
| --- | --- |
| `game`, `turn`, `seat`, `blanks`, `rack_tiles` | the position, written once |
| `ref_wall_<run>`, `ref_cpu_<run>`, `sub_wall_<run>`, `sub_cpu_<run>` | each run's timings, named by its `run` |
| `ref_runs`, `ref_min_wall_ms`, `ref_stalls_dropped`, `ref_mean_wall_ms`, `ref_mean_cpu_ms` and the same for `sub_` | per side: runs, the position's fastest wall time, timings discarded as stalls and the means of what survived |
| `ratio_mean_wall` | subject mean over reference mean |

### Runs that disagree

| Case | Result |
| --- | --- |
| no position in common | refuses (exit 1) |
| the first reference and first subject run differ in positions | warns, with the count |
| a later run lacks positions | no warning, and a comparison cut to the positions every run has |
| `--wide` on runs whose racks differ | refuses (exit 1) |

## The raw measurements

The moves directory holds the per-move files:

| Fact | Value |
| --- | --- |
| name | `<run>-<host>.csv`, `<run>` being the summary row's `timestamp_unix_seconds`, so the two join, with every character of the host but an ASCII letter or digit turned into `-` |
| committed | `wide-5x5-c2281dc.csv` only, as `.gitignore` ignores files whose name starts with a digit |
| host that cannot create the moves directory | The binary prints the rows prefixed `MOVES`, and the script saves them, or the owner for production. |
| runs that finish in the same second | They share a `run`, so on one host the later file overwrites the earlier; in the committed file two reference runs share `1788520313`, as two `ref_wall_1788520313` columns. |

Each per-move file's columns:

| Column | Holds |
| --- | --- |
| `run` | the summary row's timestamp, in whole seconds |
| `game`, `turn` | the position: the same on every machine and run |
| `seat`, `blanks`, `rack_tiles` | the seat to move, and the blanks and tiles in its rack |
| `n_moves` | the candidates the engine iterates, counted outside the timed region with `enumerate_legal_moves` |
| `wall_ms`, `cpu_ms` | elapsed and CPU time for the move |

## Evidence that the tail is the hypervisor

Five development-machine and five rehearsal runs of one binary, on one day. All
rows are from `moves/wide-5x5-c2281dc.csv` except the first, which is from
the results CSV.

| Observation | Figure |
| --- | --- |
| steal, every EPYC row that records it (rehearsal and production) | 28.7 to 31.5% of capacity; development machine 0.00% |
| ordinary moves, rehearsal against the development machine's fastest time for the same position | median 1.8x |
| rehearsal timings over 20 ms, five runs | 142: 30 on the six slow positions, 112 on the others |
| of those 112, CPU time at least 82% of wall time | 80, median 83x the development machine's time for the position, 348x at worst |
| of those 112, starved (under a fifth of wall time as CPU) | 32 over the five runs, 4 to 8 a run |
| rehearsal timings between 36 and 45 ms | none |
| development machine's slowest move, per-run maximum | 16.7 to 17.6 ms |
| development machine's slowest move, minimum of five runs | 16.4 ms |

By the several-run [stall test](#terms-in-this-page), each run flags a different
set:

| Measure | Figure |
| --- | --- |
| flagged per run | 23 to 29 |
| distinct positions flagged at least once | 123 |
| expected distinct if each run drew independently | 127 |
| flagged in all five runs | none |
| flagged once, twice, three times | 115, 6, 2 |

The stalls follow scheduling: they are an independent draw per run.

## The machine difference by position cost

The factor between rehearsal and the development machine rises with the
position's cost. Both machines' timings per position here are the minimum of
the five runs in `moves/wide-5x5-c2281dc.csv`, so the stalls are out.

| Development machine cost of the position | Positions | Rehearsal against development machine |
| --- | --- | --- |
| 0 to 0.15 ms | 221 | 1.33x |
| 0.15 to 0.25 ms | 515 | 1.64x |
| 0.25 to 0.5 ms | 328 | 1.85x |
| 0.5 to 1 ms | 99 | 2.06x |
| 1 to 3 ms | 47 | 2.15x |
| 3 to 10 ms | 13 | 2.15x |
| 10 to 16.4 ms | 6 | 2.13x |

The fastest single move is 0.093 ms on the development machine and 0.080 ms on
rehearsal. A clock difference would be flat at every size; here the ratio rises
from 1.33x to above 2x. The cause is the search's fixed and per-candidate costs:
[4.2.8](4.2.8-engine-performance.md#what-a-move-costs).

**A straight line fits it.** For one position, in milliseconds:

| Symbol | Meaning |
| --- | --- |
| `dev_ms` | what the position costs on the development machine |
| `reh_ms` | what it costs on rehearsal |
| `ratio` | `reh_ms / dev_ms`, over 1 where rehearsal is slower |

> **reh_ms = 2.210 × dev_ms − 0.110**
>
> equivalently **ratio = 2.210 − 0.110 / dev_ms**

- median relative error 3.3% over the 1229 positions
- measured for `dev_ms` from 0.09 to 16.4
- the ratio is 1.0 at 0.091 ms (`0.110 / 1.210`), just under the cheapest
  position; the smallest band measures 1.33x

Racks with a blank cost more, by the same minimum-of-five timings:

| Fact | Value |
| --- | --- |
| racks holding a blank | 66 of 1229 (5.4%) |
| cost against a rack without, median | 7.0x on the development machine, 9.1x on rehearsal |
| positions over 10 ms on the development machine | 6, all holding a blank |

Why a blank costs this is in
[4.2.8](4.2.8-engine-performance.md#how-the-fit-errs).

## Design notes on the comparison

**The baseline is the minimum, not the median.** With two runs the median is
their mean, so a stall drags it up and escapes rejection. Comparing five runs
of the same engine two against three gave 0.390x at the p95 on the median
baseline, and 1.077x on the minimum, where 1.0 is correct.
